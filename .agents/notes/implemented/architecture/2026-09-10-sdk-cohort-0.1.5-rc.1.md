# Agent Note: SDK cohort 0.1.5-rc.1

Status: implemented

## Problem

The family sat on the `0.1.5-alpha.2` cohort while the release line moved to `0.1.5-rc.1` (family-synchronized publish 2026-09-10 03:12 UTC; every consumed `dsh-*` package present, cordis / cosmokit / schemastery support pins unchanged), and the local host CLI had already moved to rc.1. Unlike the alpha.2 bump one day earlier, this is an in-line bump on the same `0.1.5` line with no expected vocabulary break; the upgrade must still move every cohort surface in one change and re-prove the external-aggregate mount, because the plugin SDK must never lead the host and the alpha.2-aligned `dsh-better-sidebar` build stays pinned.

## Decision

The whole repository moves to the `0.1.5-rc.1` cohort in lockstep on `sdk/rc1-cohort`, fast-forwarded onto `dev`:

- **Dependency ranges**: every `^0.1.5-alpha.2` range becomes `^0.1.5-rc.1`; the desktop runtime's exact host pin becomes `@deepseek-ai/dsh@0.1.5-rc.1`. Support pins stay as they were (`@deepseek-ai/cordis` `^4.0.2`, cosmokit `1.8.3`, schemastery `3.18.2`, plugin-include `1.0.7`, plugin-loader `1.0.3`).
- **Host floor, one contract, four surfaces**: `dsh.engines.dsh >=0.1.5-rc.1` in the 20 family packages plus `scripts/plugin-template`, the static `DSH >=0.1.5--rc.1` badge in `README.md`/`README.en.md`, the `npm install -g @deepseek-ai/dsh@0.1.5-rc.1` mount pins in `ci.yml`/`release.yml`, and the smoke-lane sentence in `docs/publish-prep.md`. Historical narratives that mention alpha.2 are left as history.
- **Release-age policy**: both `minimumReleaseAgeExclude` lists move to the exact rc.1 versions (rc.1 published today, so the exclusions are load-bearing). The desktop runtime's `overrides:` block (23 bare pins without the `@` prefix) must move with them: a first install that moved only the `@`-pinned exclude rows left the overrides at alpha.2 and produced a mixed-cohort desktop lockfile (430 alpha.2 rows) until the block was re-pinned and the lockfile regenerated. Both lockfiles resolve purely at rc.1 (2187 family rows each, `lockfileVersion 9.0` unchanged).
- **Upstream packaging defects persist at rc.1**: `dsh-client-store@0.1.5-rc.1` still runtime-imports `immer` (and the zustand surface), and `dsh-client-ui-primitives@0.1.5-rc.1` still imports `anser`, `clsx`, `katex`, `shiki`, `@shikijs/langs` and the mdast/micromark utility set, while both published manifests still declare no `dependencies` (verified in the rc.1 tarballs on 2026-09-10). The `packageExtensions` accommodation is retargeted from alpha.2 to rc.1 for exactly those two versions; no installed file is patched.
- **Shell module table**: the rc.1 `dsh-web-frontend` frozen table adds a `@deepseek-ai/dsh-client-ui-dockkit` row next to the existing seed. `shared/web-platform.ts` and its mirror contract (`shared/tests/web-platform.spec.ts`) take the row together; no repository client bundle imports the new module yet, so artifacts are unchanged.
- **Injection parity**: the rc.1 `dsh-web-app` composition roster (read from the installed host's `cordis.patch.yml`) still carries all 12 names of the `scripts/inject-contract.test.mjs` approved set — additive growth only; `dsh-client-ui-slots`/`dsh-client-store` remain the documented platform-table rows.
- **External aggregate**: `dsh-better-sidebar` rode `0.19.0-alpha.1` at migration time — its peers declare `^0.1.5-alpha.2`, which rc.1 satisfies on the same `[0,1,5]` tuple, and the mount smoke proved the pairing. The same-day [0.19.0 stable re-pin](2026-08-31-readd-better-sidebar-alpha2.md) then moved the aggregate to a release whose peers declare `^0.1.5-rc.1` directly. `@mlgbnb/dsh-archive-manager` stays excluded (no evidence its build stopped importing the removed `dsh-client-runtime` face).

## Alternatives considered

- **Drop the `packageExtensions` blocks at rc.1**: rejected — the upstream packaging defect was re-verified against the rc.1 tarballs, not assumed away with the version bump.
- **Bump `dsh-better-sidebar`**: rejected at migration time — no rc.1-aligned upstream release existed (latest was the pinned 0.19.0-alpha.1; the rc.1-aligned stable published later that day), and its declared peer range already accepted rc.1.
- **Leave the desktop `overrides:` pins at alpha.2**: rejected — the overrides exist precisely because the desktop payload must mirror one cohort exactly; a mixed lockfile there is the module-identity-split hazard the cohort discipline exists to prevent.

## Testing

`pnpm typecheck` (22 packages), `pnpm build`, `pnpm test`, `pnpm test:scripts`, `pnpm runtime-deps:check`, `pnpm aggregate:check`, `pnpm skin-center:check`, `pnpm community:check`, `pnpm docs:check`, `pnpm i18n:check` all pass at rc.1. `pnpm install --frozen-lockfile --ignore-scripts` proves both lockfiles resolve (root and desktop). The rc.1 shell's module table was read from the installed `dsh-web-frontend` dist bundle; the workspace inject union was checked against the installed host's composition roster. `scripts/e2e-mount.sh` mounts the freshly packed aggregate into a scratch profile under the real rc.1 CLI: host frame boots, better-sidebar mounts, excluded archive-manager is absent, headless render lane green. `test:scripts` initially exposed a pre-existing base defect — the f28e2f62 orca-link skin fix had not regenerated the committed `market/dist` — repaired in this change by regenerating the derived artifacts with the no-shell-dist mode (`tryon/` untouched), after the same failure was reproduced on the base commit.

## Consequences

The declared floor now names rc.1 everywhere, so plugin-manager install checks steer users to the host version that is actually current. The two `packageExtensions` blocks remain the standing debt until npm re-publishes client-store/client-ui-primitives with declared runtime imports. The desktop payload lesson is recorded for every future cohort bump: cohort moves must sweep both pin shapes, the `@version` exclude rows and the bare `overrides:` values, or the desktop tree silently runs a split cohort; `scripts/rollout-verify.test.mjs` additionally pins `desktop/runtime/host/package.json`'s exact `@deepseek-ai/dsh` seed to the scaffold floor cohort, so the GH Actions desktop packaging can no longer trail a bump.

Rollout executed 2026-09-10: the merged `dev` checkout reinstalled and rebuilt at rc.1 and the managed `web` profile (linked to this repository) was re-verified against the running rc.1 host on port 3080 with no service restart. Before/after captures are identical — the host frame, task-board, git-graph and pet mount, the orca-link skin renders, and the two pre-existing baseline findings (the repeated `remote.session` inject pageerror and the git-graph auto-isolation fallback warning) appear identically on both sides, so they are not cohort-move regressions. `DSH_WEB_PORT=3080 bash scripts/rollout-verify.sh --skip-profiles` passes end to end (host 0.1.5-rc.1 satisfies `>=0.1.5-rc.1`, root lockfile pure at rc.1, unauthenticated root answers 401); the unskipped run reports one FAIL on the `trading-web` profile — the nested `@dshtrading/indicators` cosmokit copy inside the DSH Trading desktop payload, which owns its own cohort (pre-existing, out of this repository's scope, and the same finding the checker's own guidance routes to dsh-trading's refresh script). A live LLM tool call was not exercised in the user's session; the module-identity crash class it guards against is structurally excluded by the cohort checker showing every `web`-profile family row is a host symlink.

Desktop seed closure, same day: the preinstalled profile payload had trailed npm since 2026-09-03 (seed 0.3.14 while the aggregate published through 0.3.19 — five releases, advanced only by hand). The seed moved to 0.3.19 with its release-age exclusion rows (model-capabilities and preset-center joined the aggregate at 0.3.19), and `desktop-release.yml` now seeds the profile payload from the tagged aggregate at packaging time in both jobs — a registry lookup resolves the seed to the tag version before staging, falling back to the committed seed with a warning when the npm publish lane is disabled — so an installer can no longer ship plugins older than its own release. The 0.3.19 plugin set is the 0.1.2-rc.1-era source (its declared floor `>=0.1.2-rc.1` is satisfied by the rc.1 host); the fully rc.1-aligned pairing arrives with the next family release built from this cohort.
