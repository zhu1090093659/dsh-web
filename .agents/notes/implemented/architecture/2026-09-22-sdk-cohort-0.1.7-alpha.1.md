# Agent Note: SDK cohort 0.1.7-alpha.1 on the permanent alpha branch

Status: implemented

## Problem

The official family published `0.1.7-alpha.1` on 2026-09-22 while the alpha branch stood on the `0.1.6-alpha.2` cohort it was created for (see [SDK cohort 0.1.6-alpha.2 on the permanent alpha branch](2026-09-17-sdk-cohort-0.1.6-alpha.2.md)). The machine's DSH install and its global CLI moved to the new cohort, so the alpha line had to follow: every family client plugin that injected `settingsScope` could no longer mount at all.

The release is a 1299-commit change record. Four of its changes reach this family:

- **The settings subsystem was rebuilt around the profile entry.** The client service `ctx.settingsScope` (`SettingsScope`, `SettingsScopeSnapshot`, `SettingsScopeSpec`, `SettingsScopeBinder.bind()`) became `ctx.configForms` (`ConfigForm`, `ConfigFormSnapshot`, `ConfigForms.get(entryId)`), and the namespace a form addresses is now the **profile entry id**, not a plugin-chosen name. The host `SettingsProvider` lost `register()` and `installSection()`; `SettingsForms` derives one form per active entry from that entry's own Cordis `Config`. `SettingsPathOp` answers became booleans, `$DSH_HOME/settings.yaml` is imported once and renamed `settings.yaml.imported`, and `settings.documentPath` now points at the profile patch.
- **The agent-preset domain became declarative.** `@deepseek-ai/dsh-agent-presets` is deleted along with its directory discovery (`$DSH_HOME/.agent-presets`, configured roots, one directory per preset). Presets are now ordinary Cordis rows: `@deepseek-ai/dsh-agent-preset` submits a `{ id, name, description, order, plugins }` definition to `@deepseek-ai/dsh-agent-preset-registry`, whose `ctx.agentPresets.register()` returns an unregister disposer owned by the declaring plugin. `read`, `copy` and `deletePreset` are gone; `AgentPresetRow.trust` and `AgentPresetRoster.authorable` are gone.
- **The session log moved to V4.** `tool/result` messages are `role: 'tool'` with `toolCallId` and `isError` at the message root, `ToolResultBlock` and the `'tool-result'` content block are gone, and `MessageSourceMap` dropped the `plugin` source.
- **The client design system and the session list were reshaped.** Icon components lost their size suffix (`IconCloseOutline16` → `IconCloseOutlineRegular`, `IconCloseOutline14` → `IconCloseOutlineMedium`), and `SessionListState` replaced `subagentsByParent` / `jobsBySession` with `projectionsBySession`.

The alpha environment had to keep running its own cohort: the `alpha` branch and its isolated home are the only place this cohort is adapted.

## Decision

The family moves to `0.1.7-alpha.1` on the same permanent alpha branch:

- **Cohort**: every consumed `@deepseek-ai/dsh-*` range, the plugin scaffold, the root README badges, the CI and release mount-smoke pins, the desktop runtime pin and its exclusion/override ledgers, and `docs/publish-prep.md` move to `0.1.7-alpha.1` together, and the declared host floor becomes `dsh.engines.dsh >=0.1.7-alpha.1`. The independent support pins move with the cohort's own vendor release: `@deepseek-ai/cordis` 4.0.2 → 4.0.3, `cosmokit` 1.8.3 → 1.8.4, `schemastery` 3.18.2 → 3.18.3, `cordis-plugin-include` 1.0.7 → 1.0.8, `cordis-plugin-loader` 1.0.3 → 1.0.4.
- **One new packaging-defect restoration**: `@deepseek-ai/dsh-client-ui-primitives@0.1.7-alpha.1` now also imports `@deepseek-ai/dsh-util-workspace-path` from its emitted `lib/index.js` while its published manifest declares no dependencies at all, so the workspace `packageExtensions` entry adds it beside the existing `diff` / `simple-icons` / micromark restorations.
- **`alpha` stays the only place the experimental cohort is adapted**; `dev` and the stable environment keep the accepted line.

## Settings: the family card binds to the entry's own config

The family keeps its own settings section and cards (the `dsh-web-settings` group) and re-points the binding instead of rebuilding the surface:

- `shared/client/settings/{settings-form.ts,PluginSettingsCard.tsx,plugin-card-seat.ts}` speak `ConfigForm` / `ConfigFormSnapshot`. A `false` answer from `set` / `unset` / `mutate` is a refusal or a skipped write and is reported as a failed save exactly like a rejection; a thrown transport failure still carries its reason.
- `packages/dsh-web-settings` keeps the `webUiSettings` service name and the `.bind({ namespace })` shape. It resolves a family namespace to the owning profile entry id by tracing the active profile rows through the package-identity alias table (`configEditor.entries()` matched on `options.name` or `options.config.plugin`), and then binds natively through `ctx.configForms.get(entryId)` — the path that also works for a remote browser. When no entry id can be resolved it falls back to the existing loopback HTTP bridge, whose host half now reads `settings.describe({ redactSecrets: true })` and writes `settings.mutate(entryId, ops, expectedRevision)`. The bridge `describe` response gained an optional per-namespace `entryId`; every existing field and route is unchanged. `ctx.settingsScope` survives only as a deprecated type-only alias.
- Every family host half drops its `settings.installSection(...)` / `settings.register(...)` block. The plugin's own `Config` is now the settings surface, so each one carries the fields and defaults that were registered before. Because a form only exists for an entry whose schema declares at least one **volatile** field (`SettingsForms.describe()` projects through `volatileForm()`, and `isVolatilePath` refuses every other write), those fields are marked `.volatile()` and read through their live references at call time. The old `setSource` / `onChange` hooks are replaced by a `loader/volatile-update` listener for the derived registrations that must follow an edit.
- The aggregate's `web-ui-pet` row loads the generic isolation shell, whose entry declares no pet `Config`; the Host therefore exposes no pet form even though the nested pet service is live. The pet settings card detects that missing form, reads the selected pet from `/api/pet/state`, and saves selection through `/api/pet/set-pet` with a state read-back. It shows only the pet selector in that mode. The pet's `petId` Config field is volatile but has no schema default: an absent profile choice leaves the persisted `pet.json` selection intact on restart. A standalone pet row with a served form keeps the profile-entry configuration path and all controls.
- `.volatile()` exists only in the DeepSeek fork, so every package that needs it moved `schemastery: ^3.18.0` to `@deepseek-ai/schemastery: ^3.18.3`.

One consequence is accepted rather than papered over: because the update from `settings.yaml` to `settings.yaml.imported` happens on the first 0.1.7 boot, `dsh-web-settings` reads `settings.yaml.imported` first and only treats `documentPath` as a settings document when its basename says so.

## A one-shot import for the orphaned family sections

The Host's own legacy import moves `$DSH_HOME/settings.yaml` into the profile configuration section by section, using each section's name as the entry id. Family row ids are `ui-pet` / `web-ui-pet`, `ui-liangshen` / `web-ui-liangshen`, `web-ui-usage`, … so a pre-cohort family section matched no entry, was logged as rejected and stayed orphaned in the renamed file: every family setting would silently revert to its schema default.

`dsh-web-settings` therefore imports those sections itself, once, after the composition settles:

- **Resolution, two rules in order.** A section whose name the family alias table knows resolves to the served entry that family namespace belongs to; otherwise a section whose name equals a top-level `Config` field declared by exactly one served entry resolves to that field. Two or more declaring entries, or none, leaves the section alone and logs it.
- **Path.** Both rules place the value by the same decision: inside the field when the resolved entry declares a field of the section's name (the Skin Center declares `skin-background`, `skin-custom-theme` and `skin-wallpaper` as top-level fields of one entry), at the entry root otherwise (the ordinary family case).
- **Merge.** Only paths the entry's own user layer does not already carry are written, so an existing value is never overwritten and a re-run is a no-op. Writes go through the official `settings.update(entryId, patch, revision)` path with the descriptor's revision.
- **One-shot.** Each section that lands is recorded in `$DSH_HOME/dsh-web-settings-legacy-import.json` (`{ version, sections: { <section>: { entryId, path, fields, importedAt } } }`) as soon as its write succeeds, so a partial failure never records what did not land and a value the user later clears is not resurrected on the next boot. An unreadable or unknown-version marker makes the import a no-op rather than a re-import.
- The import never rejects into plugin activation, logs its outcome per section, and does nothing when the Host serves no settings surface or no config editor.

Sections of the official settings surface and of non-family plugins are left in the renamed document by design; they are not this group's to migrate.

## Presets: declare is enable

The inert library survives; the two-directory model does not.

- `$DSH_HOME/agent-presets/<id>/` stays the market install target and keeps its provenance and integrity checks. `$DSH_HOME/.agent-presets` and every directory move are gone, because nothing scans either directory any more.
- `dsh-preset-center`'s host half declares each installed preset to the registry at runtime — `ctx.agentPresets.register({ id, name, description, order, plugins })`, with the returned disposer held in the plugin's own `ctx.effect`. Install declares; disable undeclares and keeps the bytes; uninstall undeclares and deletes the directory. The composition review that used to gate the enable step now gates the install step, so the consent boundary is unchanged in kind and earlier in the flow.
- `dsh-liangshen` stops syncing `presets/liangshen/` into `~/.dsh/.agent-presets` and declares its own preset from its host half, reading the rows out of its shipped `agent.cordis.yml`. The `presentation` and guard switches are applied to the parsed rows in memory and the preset is re-declared, so no file is rewritten and no restart is needed. Relative `.mjs` rows are absolutized because the registry mounts a declaration under its own loader base.
- Both packages read compositions with a package-local, fail-closed YAML reader instead of adding a YAML dependency: it accepts exactly the subset a preset ships and raises on anchors, aliases, flow collections and anything else it does not understand. It preserves `!!js` expressions in the encoding the harness uses. Both also rewrite a relative row `name` (`./x.mjs`) into an absolute file URL against the preset's own directory, because the registry mounts a declaration under the *declaring* plugin's base URL and a preset's shipped files would otherwise resolve inside that package.

## Session V4 and client drift

- `dsh-pet` reads the tool-result error flag from the V4 message root (`message.isError`) instead of the removed content block, which had been silently evaluating to `false` and rendering failed turns as successes.
- Icon imports follow the design system's rename (`…16` → `…Regular`, `…14` → `…Medium`); every call site passes an explicit size, so nothing rendered differently.
- `dsh-session-id`'s fixtures follow `SessionListState` to `projectionsBySession`.

## What the cohort did not change

- **Slot keys**: the cohort removes exactly one key, `conversation.session.header.leading`, and adds 17. The family neither registers nor reads any of them, so no slot work was needed. Two owner-prop extensions (`conversation.session.header` gained `hideChrome`, `rightbar.session` gained `active` / `retainTab`) affect occupants only.
- **Injected module roster**: the 13 browser faces pinned by `scripts/inject-contract.test.mjs` all still exist at 0.1.7; the cohort adds seven faces that no family row uses.
- **Frozen module table**: `PLATFORM_MODULES` in the host's `packages/client/web/src/platform.ts` is byte-identical between the two tags.
- **The `readBytes` unification** lands in `@deepseek-ai/dsh-api-workspace-files`, which the family does not declare; `ctx.fs.readBytes` and the `Workspace` interface are unchanged.
- **Boot diagnostics**: the four startup-failure message shapes `dsh-doctor` parses textually are byte-identical, so its attribution still matches.

## Alternatives considered

Retiring `dsh-web-settings` and letting every family plugin be edited through the native auto-generated pages was rejected for this change: it is a product-level change to the family's settings surface, not a compatibility repair, and it would remove the family section that users navigate by. Re-pointing the existing cards keeps the user-visible surface and confines the migration to the binding layer, with the native pages still reachable through the official plugin inventory.

Making the preset enable/disable split survive by writing and removing preset rows in the profile patch through the config editor was rejected: it recreates an inert middle state that the upstream model deliberately removed, needs a new host seam, and buys nothing the install-time consent gate does not already provide. Declaring on install makes "installed" and "live" the same fact, which is what the registry's ownership model now expresses.

Parsing preset compositions with a general YAML parser was rejected because a preset row list carries `!!js` expressions, which a stock parser refuses or mangles, and because the market's preset bytes are third-party content: a fail-closed subset reader that names what it refuses is safer than a permissive parser whose acceptance can diverge from the Loader's. The cost — legitimate YAML a preset might use (anchors, flow mappings) is refused rather than accepted — is recorded as a limitation.

Calling `settings.configure({ auto: false })` on every family plugin that ships a custom card was rejected for this change: the call is a second activation-time seam per package and a mis-wired one fails the whole row. The question turns out to be moot in this cohort — `autoGenerate` reaches the client wire but no shipped `dsh-client-ui-*` package reads it, so the flag decides nothing the user sees today. The call is worth revisiting when a client consumes it.

## Consequences

`dev` and the stable environment stay on the accepted cohort. Three cohort surfaces stay coupled and must move together: the repository workspace, the desktop runtime workspace, and the isolated alpha home. Each family settings card now depends on the profile rows exposing an entry id this family can map back to a namespace; a family plugin installed under a row spelling absent from the alias table is served by the bridge transport only. A settings write now lands in the profile patch, not in `$DSH_HOME/settings.yaml`, and a non-volatile write remounts the row while a volatile one applies live. The running DSH service must be restarted before any of this reaches the GUI, because the bundles and the composition changed.

On an aggregate row without a Host pet form, pet selection is persisted in `pet.json` by the pet service. Display and master-switch controls are withheld on that page because the generic shell cannot save their profile configuration; the standalone pet row still serves them.

## Testing

In the alpha working tree: `pnpm typecheck`, `pnpm build`, `pnpm test`, `pnpm test:scripts`, `pnpm test:desktop`, `pnpm test:standards`, `pnpm docs:check`, `pnpm i18n:check`, `pnpm emoji:check`, `pnpm aggregate:check`, `pnpm market:check`, `pnpm skin-center:check`, `pnpm libs:check`, `pnpm runtime-deps:check`, `pnpm sync-shared:check` and `pnpm community:check` pass. The migrated behaviours are pinned by tests: the shared form's refusal path and the bridge's entry-id resolution in `dsh-web-settings`, its two-rule legacy import with the held-field, unserved, ambiguous, one-shot and refused-write cases, the declarative preset lifecycle, the composition reader and its relative-row resolution in `dsh-preset-center` and `dsh-liangshen`, the live volatile re-read in every host half that gained one, and the V4 tool-result failure path in `dsh-pet`.

`scripts/e2e-mount-rewrite`, `scripts/e2e-mount-rewrite.test.mjs`, `scripts/publish-legacy-aggregate.mjs` and `scripts/e2e-mount.sh` pass GNU tar `--force-local` on the Windows/MSYS lane, because GNU tar reads the `C:\...` output path those helpers hand it as a remote host spec. The flag is added only where the platform is Windows, so the Linux lane is unchanged.

The mount smoke is **not** verified on a Windows workstation: it reaches the profile composition step and then fails inside the `dsh` CLI, which on this machine is a symlink into a DSH source checkout whose committed `lib/` predates the cohort's own multi-file `dsh.bundle.patch` support (`loadProfileDirectory` joins the declared patch directly, so the official `dsh-web-app` array crashes profile boot, where the tagged source calls `bundlePatchPaths` and skips a failing bundle instead). That is a host-side build staleness outside this repository; the lane passes once the DSH checkout is rebuilt, which repository rules reserve to the operator.
