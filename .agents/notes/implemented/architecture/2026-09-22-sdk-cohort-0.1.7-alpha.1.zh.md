# Agent Note: SDK cohort 0.1.7-alpha.1 on the permanent alpha branch

Status: implemented

## Problem

官方家族在 2026-09-22 发布了 `0.1.7-alpha.1`，而 alpha 分支仍停在它当初为之创建的 `0.1.6-alpha.2` cohort（见 [SDK cohort 0.1.6-alpha.2 on the permanent alpha branch](2026-09-17-sdk-cohort-0.1.6-alpha.2.md)）。本机 DSH 与全局 CLI 已切到新 cohort，alpha 线必须跟上：所有 inject 了 `settingsScope` 的家族客户端插件都无法挂载。

这是一份 1299 个提交的变更记录，其中四处变化触达本家族：

- **设置子系统围绕 profile entry 重建。** 客户端服务 `ctx.settingsScope`（`SettingsScope`、`SettingsScopeSnapshot`、`SettingsScopeSpec`、`SettingsScopeBinder.bind()`）变为 `ctx.configForms`（`ConfigForm`、`ConfigFormSnapshot`、`ConfigForms.get(entryId)`），而表单寻址的 namespace 现在是 **profile entry id**，不再是插件自选的名称。宿主 `SettingsProvider` 失去 `register()` 与 `installSection()`；`SettingsForms` 按每个活跃 entry 自身的 Cordis `Config` 派生一张表单。`SettingsPathOp` 的答案变为布尔值，`$DSH_HOME/settings.yaml` 只导入一次并重命名为 `settings.yaml.imported`，`settings.documentPath` 现在指向 profile patch。
- **agent-preset 域改为声明式。** `@deepseek-ai/dsh-agent-presets` 连同它的目录发现（`$DSH_HOME/.agent-presets`、已配置根目录、一个 preset 一个目录）一起被删除。preset 现在是普通 Cordis 行：`@deepseek-ai/dsh-agent-preset` 向 `@deepseek-ai/dsh-agent-preset-registry` 提交 `{ id, name, description, order, plugins }`，其 `ctx.agentPresets.register()` 返回由声明方持有的注销闭包。`read`、`copy`、`deletePreset` 消失；`AgentPresetRow.trust` 与 `AgentPresetRoster.authorable` 消失。
- **会话日志升级到 V4。** `tool/result` 消息现在是 `role: 'tool'`，`toolCallId` 与 `isError` 位于消息根；`ToolResultBlock` 与 `'tool-result'` 内容块消失；`MessageSourceMap` 去掉 `plugin` 来源。
- **客户端设计系统与会话列表被重塑。** 图标组件去掉尺寸后缀（`IconCloseOutline16` → `IconCloseOutlineRegular`，`IconCloseOutline14` → `IconCloseOutlineMedium`），`SessionListState` 用 `projectionsBySession` 取代 `subagentsByParent` / `jobsBySession`。

alpha 环境必须继续运行自己的 cohort：`alpha` 分支及其隔离 home 是适配该 cohort 的唯一场所。

## Decision

家族在同一永久 alpha 分支上迁移到 `0.1.7-alpha.1`：

- **Cohort**：所有被消费的 `@deepseek-ai/dsh-*` range、插件脚手架、根 README badge、CI 与 release 挂载冒烟 pin、desktop runtime pin 及其 exclusion/override 台账、`docs/publish-prep.md` 一起移到 `0.1.7-alpha.1`，声明的最低宿主版本变为 `dsh.engines.dsh >=0.1.7-alpha.1`。独立支持 pin 随 cohort 自身的 vendor 发布推进：`@deepseek-ai/cordis` 4.0.2 → 4.0.3、`cosmokit` 1.8.3 → 1.8.4、`schemastery` 3.18.2 → 3.18.3、`cordis-plugin-include` 1.0.7 → 1.0.8、`cordis-plugin-loader` 1.0.3 → 1.0.4。
- **新增一处打包缺陷还原**：`@deepseek-ai/dsh-client-ui-primitives@0.1.7-alpha.1` 的 `lib/index.js` 现在还 import `@deepseek-ai/dsh-util-workspace-path`，而它发布的 manifest 完全不声明依赖，因此 workspace 的 `packageExtensions` 条目在既有 `diff` / `simple-icons` / micromark 还原之外补上它。
- **`alpha` 仍是适配实验 cohort 的唯一场所**；`dev` 与稳定环境保持已接受的那条线。

## Settings: the family card binds to the entry's own config

家族保留自己的设置分区与卡片（`dsh-web-settings` 组），只重接绑定层，不重建界面：

- `shared/client/settings/{settings-form.ts,PluginSettingsCard.tsx,plugin-card-seat.ts}` 改用 `ConfigForm` / `ConfigFormSnapshot`。`set` / `unset` / `mutate` 返回 `false` 表示宿主拒绝或跳过写入，与拒绝一样上报为保存失败；抛出的传输失败仍携带其原因。
- `packages/dsh-web-settings` 保留 `webUiSettings` 服务名与 `.bind({ namespace })` 形状。它通过包身份别名表追踪活跃 profile 行（`configEditor.entries()` 按 `options.name` 或 `options.config.plugin` 匹配）把家族 namespace 解析为所属 profile entry id，然后经 `ctx.configForms.get(entryId)` 原生绑定——这条路径对远程浏览器同样有效。解析不到 entry id 时回落到既有的 loopback HTTP 桥，其宿主半边改为读 `settings.describe({ redactSecrets: true })`、写 `settings.mutate(entryId, ops, expectedRevision)`。桥的 `describe` 响应新增可选的按 namespace 的 `entryId`；所有既有字段与路由不变。`ctx.settingsScope` 仅作为已废弃的纯类型别名保留。
- 每个家族宿主半边都删除了 `settings.installSection(...)` / `settings.register(...)` 块。插件自身的 `Config` 现在就是设置面，因此各自携带先前注册的字段与默认值。由于只有声明了至少一个 **volatile** 字段的 entry 才会生成表单（`SettingsForms.describe()` 经 `volatileForm()` 投影，`isVolatilePath` 拒绝其余所有写入），这些字段标记为 `.volatile()` 并在调用点通过实时引用读取。旧的 `setSource` / `onChange` 钩子由 `loader/volatile-update` 监听替代，用于必须跟随编辑的派生注册。
- 聚合包的 `web-ui-pet` 行加载通用隔离壳，其 entry 不声明宠物 `Config`；因此即使内部宠物服务正在运行，宿主也不暴露宠物表单。宠物设置卡识别表单缺失，从 `/api/pet/state` 读取当前选择，经 `/api/pet/set-pet` 保存并回读确认；此模式只展示宠物选择。宠物的 `petId` Config 字段仍是 volatile，但没有 schema 默认值：profile 未显式指定宠物时，重启会沿用 `pet.json` 持久化的选择。独立宠物行若提供表单，则仍通过 profile entry 配置保存并展示全部控件。
- `.volatile()` 只存在于 DeepSeek fork，因此所有需要它的包把 `schemastery: ^3.18.0` 换成 `@deepseek-ai/schemastery: ^3.18.3`。

一处后果被如实接受而非掩盖：因为 `settings.yaml` → `settings.yaml.imported` 的升级发生在首个 0.1.7 启动，`dsh-web-settings` 优先读 `settings.yaml.imported`，且只在 basename 表明它是设置文档时才把 `documentPath` 当作设置文档。

## 为成为孤儿的家族分节做一次性导入

宿主自身的旧版导入把 `$DSH_HOME/settings.yaml` 逐分节搬进 profile 配置，并用「分节名」当 entry id。家族的行 id 是 `ui-pet` / `web-ui-pet`、`ui-liangshen` / `web-ui-liangshen`、`web-ui-usage` 等，因此旧版留下的家族分节匹配不到任何 entry，被记为 rejected 并滞留在改名后的文件里：每一项家族设置都会静默回落到 schema 默认值。

因此 `dsh-web-settings` 自己在组合稳定后做一次导入：

- **解析，两条规则按序。** 分节名能被家族别名表识别时，解析到该家族 namespace 所属的已服务 entry；否则若分节名恰好等于**唯一**一个已服务 entry 声明的顶层 `Config` 字段名，则解析到那个字段。有两个以上 entry 声明、或无人声明，则不动该分节并记日志。
- **路径。** 两条规则用同一个判定决定落点：解析到的 entry 声明了与分节同名的字段时写进该字段（皮肤中心把 `skin-background`、`skin-custom-theme`、`skin-wallpaper` 声明为同一个 entry 的三个顶层字段），否则写在 entry 根（普通家族插件的情形）。
- **合并。** 只写该 entry 自身 user 层还没有的路径，因此既有取值永不被覆盖、重复运行是空操作。写入走官方 `settings.update(entryId, patch, revision)`，revision 取自对应 descriptor。
- **一次性。** 每个成功落地的分节立刻记进 `$DSH_HOME/dsh-web-settings-legacy-import.json`（`{ version, sections: { <分节>: { entryId, path, fields, importedAt } } }`），因此部分失败不会记下没写成的分节，用户之后清空的取值也不会在下次启动被复活。标记文件不可读或版本未知时导入转为空操作，而不是重新导入。
- 导入永不把异常抛进插件激活，逐分节记录结果，并在宿主没有设置面或没有 config editor 时空转。

官方设置面与非家族插件的分节按设计留在改名后的文档里，不归这个包迁移。

## Presets: declare is enable

惰性库保留，双目录模型不保留。

- `$DSH_HOME/agent-presets/<id>/` 仍是市场安装目标，并保留其来源与完整性校验。`$DSH_HOME/.agent-presets` 与所有目录搬迁都被删除，因为两个目录都不再被扫描。
- `dsh-preset-center` 的宿主半边在运行时把每个已安装 preset 声明给注册表——`ctx.agentPresets.register({ id, name, description, order, plugins })`，返回的注销闭包由插件自己的 `ctx.effect` 持有。安装即声明；禁用即撤销声明并保留文件；卸载即撤销声明并删除目录。原先把关启用步骤的组合审阅现在把关安装步骤，同意边界在性质上不变、在流程上提前。
- `dsh-liangshen` 不再把 `presets/liangshen/` 同步到 `~/.dsh/.agent-presets`，改由宿主半边声明自己的 preset，并从随包发布的 `agent.cordis.yml` 读取行。`presentation` 与 guard 开关作用于内存中解析出的行并重新声明 preset，因此不改写文件、不需要重启。相对 `.mjs` 行会转为绝对路径，因为注册表在自身的 loader base 下挂载声明。
- 两个包都用包内 fail-closed 的 YAML 读取器解析组合，而不是新增 YAML 依赖：它只接受 preset 会用到的那部分语法，遇到锚点、别名、flow 集合及任何不认识的结构即报错，并以 harness 使用的编码保留 `!!js` 表达式。两者都会把相对的 `name`（`./x.mjs`）改写成相对 preset 自身目录的绝对 file URL——注册表在**声明方**插件 的 base URL 下挂载声明，否则 preset 随包发布的文件会被解析到那个包内部。

## Session V4 and client drift

- `dsh-pet` 改为从 V4 消息根读取工具结果失败标记（`message.isError`），此前它读的已删除内容块会静默求值为 `false`，把失败回合渲染成成功。
- 图标 import 跟随设计系统改名（`…16` → `…Regular`，`…14` → `…Medium`）；每个调用点都显式传入尺寸，因此渲染结果不变。
- `dsh-session-id` 的 fixture 跟随 `SessionListState` 改为 `projectionsBySession`。

## What the cohort did not change

- **Slot 键**：本 cohort 只删除一个键 `conversation.session.header.leading`，新增 17 个。家族既不注册也不读取其中任何一个，因此无需槽位改动。两处 owner props 扩展（`conversation.session.header` 增加 `hideChrome`，`rightbar.session` 增加 `active` / `retainTab`）只影响占位方。
- **inject 模块名单**：`scripts/inject-contract.test.mjs` 固定的 13 个浏览器面在 0.1.7 全部仍在；本 cohort 新增的 7 个面没有家族行使用。
- **冻结模块表**：宿主 `packages/client/web/src/platform.ts` 的 `PLATFORM_MODULES` 在两个 tag 之间字节一致。
- **`readBytes` 统一**落在 `@deepseek-ai/dsh-api-workspace-files`，家族未声明该包；`ctx.fs.readBytes` 与 `Workspace` 接口未变。
- **启动诊断**：`dsh-doctor` 以文本解析的四类启动失败文案字节一致，归因仍然匹配。

## Alternatives considered

弃用 `dsh-web-settings`、让每个家族插件都改由原生自动生成页面编辑，本轮被否决：那是对家族设置面的产品级改动而非兼容性修复，并且会移除用户赖以导航的家族分区。重接既有卡片保住了用户可见面，并把迁移限制在绑定层，原生页面仍可通过官方插件清单到达。

为了让「启用/禁用」二分存活，改由 preset-center 通过 config editor 往 profile patch 增删 preset 行，被否决：那重建了上游刻意移除的惰性中间态，需要一个新的宿主接缝，而且并未带来安装时同意门之外的任何东西。安装即声明让「已安装」与「已生效」成为同一事实，这正是注册表所有权模型所表达的内容。

用通用 YAML 解析器解析 preset 组合被否决：preset 行清单带有 `!!js` 表达式，常规解析器会拒绝或误读；而且市场里的 preset 字节是第三方内容，一个会明确指出自己拒绝什么的 fail-closed 子集读取器，比一个接受面可能与 Loader 分歧的宽松解析器更安全。代价——preset 可能合法使用的 YAML 特性（锚点、flow 映射）会被拒绝而非接受——作为限制记录在案。

对每个自带卡片的家族插件调用 `settings.configure({ auto: false })`，本轮被否决：该调用是每个包第二个激活期接缝，接错会让整行加载失败。而在本 cohort 这个问题其实不存在——`autoGenerate` 会传到客户端线路上，但已发布的 `dsh-client-ui-*` 没有任何一个读它，因此该标记今天不决定任何用户可见的东西。等有客户端开始消费它时再回来处理。

## Consequences

`dev` 与稳定环境保持已接受的 cohort。三个 cohort 面继续耦合、必须一起移动：仓库 workspace、desktop runtime workspace、隔离的 alpha home。每个家族设置卡片现在依赖 profile 行暴露一个本家族能映射回 namespace 的 entry id；装在别名表中没有的行使拼写下的家族插件只能由桥传输服务。设置写入现在落到 profile patch 而非 `$DSH_HOME/settings.yaml`，非 volatile 写入会重挂载该行，volatile 写入实时生效。运行中的 DSH 服务必须重启，这些改动才会到达 GUI，因为 bundle 与组合都已改变。

聚合行没有宿主宠物表单时，宠物选择由宠物服务持久化到 `pet.json`。该页面不展示显示布局和总开关控件，因为通用隔离壳无法保存这些 profile 配置；独立宠物行仍提供这些控件。

## Testing

在 alpha 工作树中：`pnpm typecheck`、`pnpm build`、`pnpm test`、`pnpm test:scripts`、`pnpm test:desktop`、`pnpm test:standards`、`pnpm docs:check`、`pnpm i18n:check`、`pnpm emoji:check`、`pnpm aggregate:check`、`pnpm market:check`、`pnpm skin-center:check`、`pnpm libs:check`、`pnpm runtime-deps:check`、`pnpm sync-shared:check`、`pnpm community:check` 全部通过。被迁移的行为由测试固定：`dsh-web-settings` 中共享表单的拒绝路径与桥的 entry id 解析、它的双规则旧版导入（含已持有字段、未服务 entry、歧义、一次性、写入被拒等情形）、`dsh-preset-center` 与 `dsh-liangshen` 的声明式 preset 生命周期、组合读取器及其相对行解析、每个因此新增的宿主半边的 volatile 实时重读，以及 `dsh-pet` 的 V4 工具结果失败路径。

`scripts/e2e-mount-rewrite`、`scripts/e2e-mount-rewrite.test.mjs`、`scripts/publish-legacy-aggregate.mjs` 与 `scripts/e2e-mount.sh` 在 Windows/MSYS 平台给 GNU tar 传 `--force-local`：GNU tar 会把这些辅助脚本交给它的 `C:\...` 输出路径读成远端主机名。该参数只在 Windows 平台添加，Linux 车道不变。

挂载冒烟在 Windows 工作站上**未验证通过**：它走到 profile 组合步骤后失败在 `dsh` CLI 内部——本机的 `dsh` 是指向某个 DSH 源码检出目录的符号链接，而该目录里已提交的 `lib/` 早于本 cohort 自身的多文件 `dsh.bundle.patch` 支持（`loadProfileDirectory` 直接 join 声明的 patch，于是官方 `dsh-web-app` 的数组会让 profile 启动崩溃；tag 源码在此处调用 `bundlePatchPaths` 并跳过失败的 bundle）。这是本仓库之外的宿主侧构建陈旧问题，重建该 DSH 检出后该车道即可通过，而仓库规则把重建保留给操作者。
