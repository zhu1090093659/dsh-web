# Agent Note: Remote bridge protocol v1 is a transport-decoupled native-client surface

Status: implemented

Sibling surface decision: [remote control reuses the official UI](2026-08-29-remote-control-reuses-official-ui.md) owns the browser path — the paired-device cookie and the gated `/remote` channel. This note owns the second surface: a protocol-shaped, cookie-free path for native clients.

## Problem

`dsh-remote-web-ui` publishes a phone surface by pairing a browser: the device gets a cookie, and every call rides the `/remote` channel, which re-issues it with the process's own browser credential. That is the right shape for a browser — it inherits the official UI, the mobile adaptation layer and the settings bridge for free. It is the wrong shape for a native client that has no browser, no cookie jar, and no Web GUI bundle: an iOS app would have to emulate a browser session, and it would still inherit a web page's failure modes.

Two constraints shape what "native client" can mean here. The harness has no official HTTP API for this: driving `/api` directly from a remote origin is governed by whatever the harness fence happens to trust, and a plugin that builds a product on it inherits the SDK cohort's endpoint names and the harness's own authentication as a version-coupled dependency. And the browser credential itself cannot be replayed across the relay: it is authority-bound to the exact `host:port` a browser visited and has no loopback exemption, so a proxied re-issue to `127.0.0.1` is refused — the very defect `dsh-remote-web-ui` had to work around by redeeming its own launch token.

So a native client needs a transport the harness does not have, and its own access control. What was missing was a decision about what that surface is, how it authenticates, and how it relates to the browser one.

## Decision

- **The bridge is its own package, and protocol v1 is its own contract.** `@linxin666/dsh-remote-bridge` is one plugin row with two halves (`packages/dsh-remote-bridge`): the host half publishes one exact WebSocket upgrade route at `/ios/v1` and one exact HTTP route at `/remote-bridge/pair/token`, and the browser half the same row declares (`dsh.client` -> `exports["./client"]`) adds one sidebar-foot pairing panel. The protocol is a JSON envelope — `{"t":"req","id","m","p"}`, `{"t":"res","id","ok","r"|"e"}`, `{"t":"ev","seq","m","p"}`, `{"t":"ping"|"pong","ts"}` — over one text frame per message; nothing in the method layer mentions HTTP, cookies or a browser session, so the same envelope can ride a loopback socket, a LAN bind or a relayed origin unchanged.
- **The bridge consumes the harness in-process.** Session work goes through `ctx.typertGateway` (`invoke` for unary calls, `stream` for `session/follow`), with the gateway's `error.code` vocabulary as the only failure discriminator and the family's bounded retry for the service-activation window. Permission requests are answered in-process by listening on `ctx.on('approval/request')` — never through `$events`/`$events/result` — and an approval nobody answers normalizes to `unavailable`, which the harness treats as a rejection, so a silent phone is never consent.

- **An approval is announced once per claim and replayed to a connection that declares the approval capability.** `approval.request` reaches every paired connection the moment a tool asks, and that first broadcast stays outside any capability on purpose: a name that gated it would take approvals away from every client written before the name existed, which is the opposite of what a capability is for here. What a client opts into is the second delivery. A connection that declares `approvals.v1` is handed every still-unsettled approval after its `hello` — `BridgeHub.replayApprovals`, wired beside `replayQuestions` in `attach` so every construction path gets it and no other path replays — under the same pairing check, the same capability check and the same `emit` route as the question channel, with one payload builder shared by the first broadcast and the replay so the card a phone was shown and the card handed to it again cannot drift. A released approval cannot come back: `ApprovalRegistry.#settle` is the single path out of the pending map, and an answer, the bridge's own two-minute timeout, the agent's cancellation and the withdrawal that follows the last phone all delete the entry before it settles. The replay emits a frame and touches neither the claim nor its timer, so re-handing a question never lengthens the deadline it was opened with. The name is deliberately absent from `SERVED_CAPABILITIES` and raises no minor: advertising a capability is, by this repository's convention, a minor addition, and this channel changes nothing a client can observe in the handshake — no field, no answer, no method — so the declaration is the whole switch and the name reaches a client through this package's documentation.
- **Every gateway call speaks for one in-process owner peer, exercised only behind the bridge's own pairing gate.** Since SDK 0.2.1 `InvokeRemoteRequest.peer` is mandatory and the authorization layer reads only `peer.principal`; the bridge mints a single owner peer (`{kind:'owner'}`, `interactions:'none'`) at mount in `core/owner-peer.ts`, bound to the plugin fiber with an idempotent `dispose()`, and attaches it to every `invoke` and `stream`. That full-control claim is safe for the same reason the pre-0.2.1 implicit privilege was: the only paths to it pass the bridge's pairing check — dispatch answers `unpaired` before any gateway call exists, and the three unpaired methods never invoke the gateway — and no field of a client frame is ever read into the peer, so a client cannot name a principal. `interactions:'none'` keeps forwarded Host events untouched: approvals reach devices through the bridge's own `approval/request` claim and the protocol's own events, not a Typert forwarded-event subscription.
- **The bridge mints its own bootstrap token.** The loopback-only `GET /remote-bridge/pair/token` hands the operator a one-time 32-byte secret valid for 30 s; `pair.begin` spends it and issues a nonce; `pair.finish` verifies a raw 64-byte ES256 signature over that nonce against the offered P-256 SPKI and stores a roster entry — public key, SHA-256 fingerprint, timestamps — in `$DSH_HOME/remote-bridge/devices.json` (0700/0600, temp file plus atomic rename). The device token itself is 32 random bytes and only its SHA-256 hash is kept. `dsh-remote-web-ui` is not touched: its pairing service still mints browser cookies for the browser path, and the two rosters are separate files with separate revocation.
- **The browser half renders that token and never spends it.** The panel registers into the official `sidebar.footer.action` seat — the list slot ui-sidebar declares, which `dsh-remote-web-ui`'s phone trigger occupies, and whose other former occupant, the `dsh-update` updater, has been removed — reads the same loopback-gated route over a same-origin request, and renders the secret in the official headless `Modal`: one card holding a `qrcode.react` symbol, one fixed-height status line (the 30 s countdown beside its bar, or the expiry sentence in the same box), one address line, the single-use note and one action row of official `Button`s. The address line names the kind of address the symbol carries rather than the address itself: a located public origin reads "The QR code carries the public address: the iPhone connects to this computer as soon as it scans", because the code burns 30 seconds after it appears while a durable public hostname rendered as text outlives every screenshot it appears in, and the symbol already carries the address the phone needs. A LAN literal is not that fact, and the line names it — "The QR code points at the LAN address {origin}: the iPhone must be on the same network" — when the host calls the origin a LAN address or when the literal itself answers only inside the network this page is already on. With neither, the line says outright that no public address was found and that the connection address must be set in the app before scanning. The QR payload is the bare token when the host cannot name an origin and the host's own `{token,url}` answer when it can; a URL the host did not vouch for would let the phone's own parser rewrite its origin onto this machine's loopback address, which is the one address a phone cannot reach. The encoded string is mirrored once, as `data-dsh-qr-value` on the symbol's part, and never printed as text: copy and mint-again hand over exactly that string, and past the deadline copy is disabled while mint-again stays the one way back to a scannable symbol. `403`, an unexpected status and a network failure each render as their own named state, never as a silent panel. Closing reverses the opening — the card stays mounted through its exit and plays the dialog's own enter keyframe backwards, read off the mounted dialog because the bundler scopes that name, and the reduced-motion path keeps the lifecycle as one short opacity fade — and geometry is held across states, so a countdown, an expiry and a copy confirmation move nothing around them. The panel cannot mint a device token, spend one, list the roster or revoke a device, and it adds no wire surface.
- **One authorization rule, checked before dispatch.** A connection whose device token is absent, unknown or revoked may call exactly three methods (`hello`, `pair.begin`, `pair.finish`); everything else answers `unpaired`. The device token rides the upgrade as `Authorization: Bearer` and, for clients that cannot set handshake headers, as `?token=`; the comparison hashes both sides and compares equal-length digests.
- **The connection's event `seq` is not a resume cursor.** A connection's event `seq` starts at 1 and numbers what that connection received; the snapshot's `lastSeq` is the harness cursor — a different counter from `seq`, which the protocol never compares — and it is the only watermark a reconnect can be resumed from: a client that sees a gap or reconnects calls `session.snapshot`, naming that watermark as `sinceSeq` once it declared `session.snapshot.since.v1` and taking the full baseline otherwise. `session.snapshot` opens the harness `session/follow` stream and keeps it as the connection's subscription, so deltas arrive without polling.
- **One frame is 10 MiB, and a client may ask for a baseline it can actually render.** The cap is one constant (`MAX_FRAME_BYTES` = 10 MiB) that the receive judgment, the snapshot fit, the `frame-too-large` message and the outbound-event drop all read, so the number is never written twice; it was raised from 256 KiB because a phone's baseline is a whole session's history in one frame. Raising the cap alone would only turn "refused" into "opens very slowly", because the bulk of a baseline is durable records the client does not render — `system/message` and `request/header` runs inside one turn, 150 KB and up each. So `hello`'s `cap` array is now read, and a client that declares `session.snapshot.trim.v1` is sent a baseline trimmed inside each turn to the four entry types it renders (`user/message`, `assistant/message`, `tool/call`, `tool/result`); a turn whose entries are all bookkeeping stays a turn with an empty `entries` array, and every turn-level field, the turn list and `lastSeq` keep the projection's own values. A capability is an announcement, not a negotiation: an unknown name, an unreadable `cap` and an absent key are all ignored, and a client that declares nothing — every client written before this capability existed — receives byte for byte the baseline protocol v1 always served. The trim runs before the frame budget does: entries are trimmed first, then whole oldest turns are dropped, and only then does `snapshot-too-large` answer.
- **A delegated child is addressed through its durable parent, and history is paged by entry.** `session/follow` and `session/page` take a `SessionAddress`, and the harness refuses a child asked as an ordinary session with `session/agent-busy` — "subagent Sessions require their durable parent address". That refusal is why 457 of one phone's 828 roster rows answered `snapshot-unavailable` for sessions holding complete logs: the bridge sent `{kind:'session'}` for every id and flattened the harness's own diagnostic into a generic failure that reads like a transient one. The bridge now retries that one session with `{kind:'subagent', parentSessionId, childSessionId, mode:'unknown'}`, learning the parent from the roster — the only endpoint that carries lineage — at most once per connection, and every other failure crosses to the client with the harness's own code instead of being swallowed. `mode` is always `unknown`: the harness checks a claimed mode against the child's descriptor and accepts `unknown` for every child, and the bridge cannot read a child's mode before the call. The same fix makes `session.history` work for those sessions: it pages the opening baseline backwards BY ENTRY from a durable `seq` watermark, defaults to 512 KiB per page, lets a turn's entries split across pages while that turn keeps its own fields, gives an entry larger than the whole budget a page of its own instead of a refusal, and is a pure read that never opens, drops or re-addresses the subscription.
- **A second capability bounds the opening screen itself.** Paging `session.history` backwards left the first screen unfragmented: opening a live session still delivered its whole 3.3 MB opening window in one frame, so "a big session opens like a small one" was not yet true. `session.snapshot.page.v1` makes `session.snapshot` answer with the newest page instead, cut by the very same entry-level slice history uses and measured against `maxBytes` (default 512 KiB), so the first screen and every later page come from one code path and cannot disagree. The gate is what keeps that from being a regression: a client that does not declare it receives the whole window byte for byte, and a client that does gets `hasMore` plus a cursor that is simply its own oldest entry's `seq` — the same value `session.history` takes as `before`, so no field restates it. `snapshot-too-large` no longer answers a connection that declared it, because an entry too large for the budget is a page of its own rather than a refusal. Measured on a relayed iPhone client on 2026-10-19, that rule is also the answer to a suspected defect: two replies of 2209876 and 2218877 bytes, 3.54 s each, from a client that declared the capability. The budget is measured on the whole encoded answer — `JSON.stringify` of the very `res` frame the client receives — and never per turn, so what it bounds is the page and not an entry: `pageTurns` ends a page at an entry and never inside one, and its verification loop returns a one-entry page without measuring it at all, so an entry past the budget IS the page and the answer is exactly as large as that entry. 2.2 MB is therefore not a page budget that failed to apply but one newest entry of 2.2 MB — a file read, a long answer, an image result — with the same window of ordinary entries answering 513794 bytes against the same 512 KiB. Trimming or splitting such an entry would hand the client content the session does not say, and refusing it would take the session away from the capability that exists to open big sessions, so the bound is stated rather than narrowed: a page is inside `maxBytes` unless the newest entry alone is past it, and that sentence is pinned on both sides by `tests/snapshot-page.spec.ts` — a 2200221-byte one-entry page and a 513794-byte control. The one thing it leaves standing is the frame cap: an entry past 10 MiB still crosses as a page rather than a refusal, which is this same decision applied literally.
- **A message says where it came from, and a spawned child is a delta of its own.** Protocol v1 carried content but not origin: every durable `user/message` became the same `user-message` delta whether a human typed it, a child session relayed it, or the harness injected runtime context, and nothing on the wire announced that an agent had started a child at all. `hello` answers `minor:2` for this channel and advertises `capabilities` — the four this bridge served when it landed: `session.snapshot.trim.v1`, `session.snapshot.page.v1`, `questions.v1`, `subagent.thread.v1` (thirteen at `minor:11` today; see the last decisions). A capability a mounted plugin adds is absent from that list, because the bridge is not its author and the plugin's own documentation stays the place a client learns it. A `user-message` delta and a snapshot `user/message` entry now carry an optional `actor` derived mechanically from the durable `source` record: `user` and `user-approval` are `human`, `agent-message` and `subagent-settled` are `agent` with the sender's session id, and every other source kind is `system` with the host's own string verbatim — a message is never dropped for carrying an origin this contract has not classified, and an event whose source carries no readable kind carries no `actor` rather than a guessed one. `actor` is not gated by a capability: it is an additive key that a client which never reads it ignores. The `subagent` delta is gated by `subagent.thread.v1`, carries `{childId, label?, mode?, callId?}` from the durable `subagent/catalog` event, and ties itself to the call that spawned the child in two tiers — first the spawn's own `tool/result`, which names the child in one of the two shapes this harness writes (an activation handle `{"kind":"activation","subagentId":…}`, alone or nested in a `run_code` answer, or the plain `started subagent …` notice it prints), so both a step that issued several calls and one call that started a team are decided by the payload that says which child it is about; then, only when no result names the child, the pre-existing rule that this turn and step issued exactly one `tool/call`. A step with two calls, or a call already tied to another child, leaves the anchor omitted instead of guessed, because a wrong `callId` hangs a phone's thread on the wrong card. A `subagent/catalog` entry is also one of the entry types a trimmed baseline now keeps, carrying the spawning call in `data.callId`, and one `SpawnCallIndex` answers both halves — a subscription as it watches and a baseline after reading the session's records — so the baseline half this channel had left open is closed without a new method, topic, frame shape or minor.
- **Following a delegated child is authorized, and the authorization is what decides who may be read.** Reading a child's own log is the one place where relaxing an address decision could become a session-read channel, so the rule is stated in terms of sessions this connection may already read: an ordinary session the roster names, and any session the connection has already opened, are followable; a delegated child is followable only while the `parentSessionId` on its roster row resolves into that set, and a child row never authorizes itself — otherwise one refused read would teach the connection to follow it on the retry. A child whose parent no roster row resolves answers `session-not-followable` before any follow stream is opened, while an id the roster does not know at all keeps the old path where the harness answers for it. That decision needs lineage before the first attempt, so the roster is read then: a child whose parent it names is addressed as a delegated session straight away, and the harness's `session/agent-busy` refusal still drives the single retry when the read resolved no parent.
- **The relay is unchanged.** The bridge rides whatever origin the instance already publishes: `market/worker/src/relay.js` looks the tunnel target up, rewrites only the `Host` header and returns the origin's response verbatim, and a WebSocket upgrade crosses the same single hop because the Workers runtime upgrades a `fetch` that carries an `Upgrade` request with a null body. The loopback gate, not the relay, is what keeps the token endpoint out of reach from the public origin.- **The roster carries the host's own session metadata, and titles are read in-process.** `session.list` republishes the summary fields a phone groups and labels by — `cwd`, `parentSessionId`, `origin` — plus `blank`, and adds `archived` from the workspace registry's single archive set; each optional key is present only when this process can actually answer it, so a bridge that cannot read the archive set omits the key instead of answering `false`. `session.titles` answers a batch of up to 100 ids out of `ctx.sessionTitle.get` over the live sessions `ctx.sessions` holds — never one follow stream per session, which is what the roster's empty title used to cost them — and caches each resolved title for 10 s. The cache is time-bounded rather than event-invalidated because a title change is a `session/title` *log* event with no cordis event behind it: an invalidation hook would mean a listener on every live session, while a TTL bounds staleness (a rename can take 10 s to show) and each batch call refreshes. Both services are reached as optional structural faces through `ctx.get` rather than `inject`: requiring them would let the title or workspace plugin's absence take the whole bridge down, so an unmounted service answers `""` for one id or omits one key instead.
- **Background jobs are published read-only, in the host's own two scopes, and only to a client that asked.** `hello` now answers `minor:3` and advertises `jobs.v1`; behind it `jobs.list` answers `{sessionId?, scope, jobs}` and `jobs.changed` carries the identical box. The bridge reads `ctx.jobs` — the `JobRegistry` that the `job` Remote namespace is itself a projection of — so there is no second store, no polling loop and no status vocabulary of its own: each row is `{id, kind, status, label, ownerSessionId?, startedAt, finishedAt?}`, projected field by field from the host's `JobView`, and the host's `output` (ring offsets, spill paths), `progress`, `detail` and `outputLimitBytes` never reach the wire. A job list is owner-fenced in the host (`JobRegistry.list(caller?: SessionId)`): naming a session returns that session's own jobs plus every unowned one, naming none returns only the unowned ones, and there is no global list to publish — so the method takes an optional `sessionId`, echoes it as `scope:'session'`, and answers `scope:'unowned'` with no session key otherwise. The bridge does not fold the two into a fake global view: that would be either N fenced reads aggregated together or a second source of truth, and the honest thing to say is what the host says — jobs are session-owned, the unowned scope is not "everything", and a client that wants both calls twice. Change detection is the registry's own event stream, filtered to lifecycle commits: an `output` append moves no row and is dropped at that layer, so the channel can never degrade into one frame per byte of job output. A burst is folded by a 100 ms window — the default the job controller itself uses for `observeFlushMs` — and a whole-set re-read that projects identically to the last frame a connection received publishes nothing. Watching is what `jobs.list` earns: a connection that declares `jobs.v1` but never lists a scope receives no job frame and costs the registry no read, which is what keeps N open sessions from becoming N sets streaming at a phone that asked for none. The watch ends with its connection, and the registry subscription ends with the last watcher.
- **A client that already holds a set is sent the difference, and the bridge computes it.** `hello` now answers `minor:4` and advertises `delta.v1`; behind it `session.list` and `board.snapshot` take an optional opaque `since` token and answer one of two shapes — `{mode:"reset", token, …}` with the whole body as it always was, or `{mode:"delta", token, …changed, removed}` with only what moved. The bridge is the only place this can be computed: it already holds, per connection, exactly what it last sent, while the host keeps answering its complete set on every call — so the saving is bytes on the wire between the bridge and the phone, never a change to a host API. A row counts as changed when its **serialised body** differs from the last one this connection sent, not when a timestamp moved: the host's `updatedAt` is not a change signal for `agentRunning`, `blank`, `archived` or a task's `column`. `removed` is always sent for an id this connection was given and the host no longer names, because a delta that silently drops a row is worse than a reset. Each connection retains at most its last full set — 5000 roster rows, 2000 board tasks — and answers `reset` past that cap with an empty token, since one phone must never pin an unbounded copy of the host's state; it also answers `reset` when more than 60% of the rows changed, because past that share the delta carries most of the body already and the two extra keys only make it bigger. A token this connection did not itself issue — another connection's, an earlier boot's, an older answer's, or garbage — answers `reset`: a wrong base is a wrong answer, and only the exact set the window last sent may be diffed against. A client that never declared `delta.v1` is answered today's body plus the ignorable `mode` and `token` keys with no copy retained for it, so every client written before this channel is byte for byte where it was. The window is a field of the connection object (`core/delta.ts`) and dies with it; the board plugin borrows the same mechanism through the extension seam (`declares` and a per-connection `deltas` seat) instead of keeping a second copy of a rule whose numbers the protocol pins once. `board.snapshot`'s reset keeps the host snapshot verbatim under `snapshot` — what every pre-existing client reads — and publishes `revision` and `tasks` beside it, so a delta-capable client parses one shape across both modes and an older one parses the shape it always did.
- **An archived session is not on the roster at all.** `hello` answers `minor:11` today, having answered `minor:5` from this decision until the agent and deep-history channels each raised it to 6, the frame-form, compact-roster and snapshot-`since` channels raised it to 10, and the fork channel raised it to 11, and advertises `session.list.omit-archived.v1` — the one capability here that negotiates nothing, because the saving belongs to the bridge rather than to a client's version: the phone hid every archived row on arrival, so a 935-row reference roster paid 346 rows and 76,608 of its 212,426 bytes (36%) for rows no client ever rendered. The archive set was already read once per listing to fill the row's `archived` flag; that same read now skips an archived session before its row is built, so no field of it is read and nothing of it crosses. What does not change: the key stays in the schema and a surviving row carries `archived: false`, an archive set this process cannot read still drops nothing and still omits the key, and lineage still comes from each row's own `parentSessionId`, so a live child of an archived parent is still listed with that parent id. The roster is also the set the delta window diffs, so the two transitions need no special case: a session archived between two listings arrives in `removed` and a restored one arrives in `changed`, exactly as a row that stopped or started existing does. The one thing this narrows is the follow gate — the roster is what authorizes a session, so a child of an archived parent now answers `session-not-followable` until the parent is restored; on the reference host that narrowing had no instance (0 live children of archived parents at the time of the change), which is why the rule was accepted instead of bought back by authorizing an id the roster no longer names.
- **An Agent is a preset instantiated as a session, so the bridge forwards the roster and the creation.** `hello` answers `minor:6` for this channel and advertises `agents.v1`; behind it `presets.list` answers whatever `agentPresets/list` publishes and `session.create` hands the host's own `SessionCreateRequest` to `session/create`, both forwarded rather than interpreted. The product direction is that one Agent is one session instantiated from a preset — the way the local `liangshen` preset is — which until now the phone could only reach by running a task-board card. The bridge is not the author of either vocabulary: a preset row is whatever the registry publishes, plugin list included, and a creation request is whatever the host validates, so a field renamed, defaulted or dropped here would diverge from the host the moment the host grew one. Nothing is required, defaulted or dropped on the way through, a request the host rejects crosses with the host's own code and text (a shape the gateway will not take answers `gateway/arguments-invalid`), and a failure carrying no code stays this bridge's `internal`. Both methods sit behind the one capability, so a client written before them is refused `unknown-method` for each and no request is made on its behalf: the roster is read when a phone asks for it and never at handshake time, so a connection that declared the channel and browses nothing costs the host no read.
- **Durable history pagination is its own method, and the minor is now 7.** `session.history` slices the follow opening window, which is as wide as the harness was asked to open it — 200 messages — so a client can page that window's own entries and not one entry older; measured on a client, it listed five turns while the host held eight, and dropping the two baseline capabilities made the older pages reachable but left `session.snapshot` timing out, so the session never opened at all. `session.history.deep` answers that gap and is the one method here that reads the session store instead of the follow stream: the request is `{sessionId, before?, maxBytes?}`, the answer is `{turns, nextBefore?, hasMore}` with `turns` byte-identically shaped to `session.history`'s — each turn keeps its own `seq`, `time`, `endSeq`, `endTime` and `reason`, each entry its own `seq`, `time`, `type` and `data` passed through from the durable record — and `before` is the same exclusive durable watermark, so a client may reuse a cursor taken from either method. Every page is read from the host's own `session/page`, and because that endpoint demands a `throughSeq` that is a `seq` the log actually holds (its `-1` sentinel answers an empty page, not the whole log) each page costs two host calls: `session/projections`'s `asOfSeq` becomes that `throughSeq`, and the read then walks back with `beforeSeq`. Nothing of the follow subscription is involved: no stream is opened, no window bounds the answer, no state is kept on the connection and no page is cached, so the same `before` answers the same page and a call cannot change what the session is. The entries are the store's own records and are not trimmed by `session.snapshot.trim.v1`, because the client that asked for a page of history asked for history. The byte budget is the one `session.history` already enforces — 512 KiB by default, cut BY ENTRY from the store's span through the same `pageTurns` and the same real-frame `measure` — so an entry larger than the whole budget is a page of its own rather than a refusal, and a store read that ended short of the session's oldest entry still reports `hasMore`, because the store's own answer is folded into the page's. `session.snapshot` and `session.history` are byte for byte what they were, and both baseline capabilities stay declared. Unlike the channels gated above — the subagent thread, the job channel and the roster narrowing — this capability gates nothing: `session.deep-history.v1` only announces that the method exists, and every paired connection may call it, because a pure read of the store costs no other client anything. `hello` now answers `minor:7`: the agent channel raised 5 to 6, durable history raised 5 to 6 on its own branch, and one protocol carrying both is one minor above either.
- **Large answers cross as raw DEFLATE, and the minor is now 8.** Measured on the real relay on 2026-10-19 (`make probe-relay`, five samples, medians): one round trip costs about 410 ms and throughput is about 240 KB/s, so a 154470-byte `session.list` took 1074.6 ms and a 506089-byte `session.snapshot` took 2438.6 ms while the same payloads over loopback took 101 ms and 4.5 ms — bytes, not round trips, were the cost. permessage-deflate cannot be used here for two independent reasons: `URLSessionWebSocketTask` exposes no API for `Sec-WebSocket-Extensions`, so a native client cannot even offer it, and the frame reader refuses RSV bits and the 101 response advertises no extensions. So the compression is carried by the protocol itself: a connection that declares `frame.deflate.v1` may be answered in **binary** frames whose payload is `deflateRaw` of the JSON text that would otherwise have been a text frame (RFC 1951, no zlib header, no adler32 trailer, level 6), always server to client, never the other way. Three bounds are deliberately part of the contract rather than tuning knobs: frames below 1024 bytes stay text so a handshake answer never pays deflate overhead; a frame that does not shrink is always written as text, so the capability can never make a frame larger; and the 10 MiB ceiling keeps being measured on the decompressed text before parsing, so every budget in this package still speaks the uncompressed size. A connection that declares nothing sees exactly the old path, byte for byte — `BridgeTransport.frameDeflate` is reported once after `hello` records the capability, and `send()` only ever chooses between two encodings of the same envelope. Accepted sockets also get `setNoDelay(true)`, since a 410 ms path makes Nagle's extra delay visible on small frames. On the same origin and the same tunnel, with only this package swapped: the roster fell from 154470 to 21521 bytes and from 1074.6 to 611.9 ms, and the three sampled baselines fell from 2438.6/2442.3/2462.7 ms to 775.5/790.4/797.4 ms at 19.5–20.6% of their bytes, with the decompressed text byte-identical to what the text path produced. `hello` now answers `minor:8`, and `frame.deflate.v1` is appended to `SERVED_CAPABILITIES` without moving any earlier slot.
- **A peer that stops answering a ping is closed at its own deadline.** `IDLE_PING_MS` still probes a connection that has been silent for 20 s, and that ping now arms `LIVENESS_TIMEOUT_MS` = 10 s: any inbound frame cancels it — a pong that answers no ping stays a no-op — and a peer that sends nothing at all for the whole deadline is torn down through the same `dispose()` path every other close uses, with close code 4000 (`CLOSE_LIVENESS_TIMEOUT`) and one log line naming the deadline. The deadline only ever exists because a ping went out, so a client that is merely quiet is never closed for being quiet; 10 s is also more than an order of magnitude above the ~410 ms one-way cost measured over the relay on 2026-10-19.
- **The roster has a compact, pageable form, and the minor is now 9.** The roster is the most repeated large reply on the link — every reconnect pays for it again — and on the real relay on 2026-10-19 a 663-row `session.list` cost 154470 bytes uncompressed and 21521 after `frame.deflate.v1`, so its bytes are worth cutting before compression rather than only after it. `session.list.compact.v1` is the name behind that cut, and it takes both halves to appear: the capability AND at least one compact parameter in the request. `cwd` is a boolean deciding whether the absolute directory crosses, `maxRows` cuts the roster into pages of that many rows, and `after` names the last row the previous page carried, so a page is continued rather than re-requested. Compact rows are ordered most recent first with the id as the tiebreak, which is what makes `after` a cursor instead of a position; `nextAfter` is present exactly while rows remain, and a cursor naming no row of the current roster answers a first page again, exactly as a delta token this window never issued answers a reset. `updatedAt` crosses only when this connection has not already sent this client that exact value for that id, so a repeated listing carries none of them, and `compact:true` states the row schema so an absent `updatedAt` can never be read as a value the host never had. Nothing else about the row changes: `title`, `agentRunning`, `blank`, `archived`, `parentSessionId` and `origin` are today's, under today's names, so a page is the same roster cut short rather than a second schema. Compatibility is two-sided and tested: a client that did not declare the capability is answered today's body for a request carrying every compact parameter (those keys are simply not part of its protocol), and a client that declared the name but names no parameter is answered today's body byte for byte, because the parameters are the switch and the capability is only permission to use them. No second measurement path was added: the page is bounded by rows rather than bytes, its size cap is the one the roster delta window already retains (`ROSTER_DELTA_MAX_ROWS`), and the roster shrinks by leaving members out rather than by measuring a frame. A compact page and a `since` token are two different answers to two different questions, and a request naming both is refused `invalid-args`, so no client can believe it holds an increment it was never sent. Measured on a synthesized 663-row roster (ids, working directories, millisecond timestamps and lineage; titles empty, which both sides pay for equally, so the saving is a lower bound): 100470 bytes as today, 70143 for the first compact listing, 52905 for the same listing repeated once the client holds the timestamps, and 8024 for one screenful of 100 rows.
- **A snapshot can answer a reconnect with only what was missed, and the minor is now 10.** Measured on a real iPhone: one reconnect re-paid the whole session baseline — one `session.snapshot` — at 0.86-1.06 s, five times in one run, so those seconds were the same bytes every time rather than five different ones. `session.snapshot.since.v1` is the name behind that cut, and it takes both halves to appear: the capability AND a `sinceSeq` in the request. `session.list` already answers a delta against a set the bridge itself kept, but a snapshot has no such token to keep — the one durable anchor a client holds is the `lastSeq` a previous snapshot reported — so the parameter is a durable event seq rather than this connection's envelope seq, and the bridge decides from the follow window it is holding rather than from a memory of another connection. Continuity is proved and never assumed: only when the current window's oldest entry sits at or below `sinceSeq + 1`, or the window is empty, is the increment served; every other case answers the ordinary baseline with `mode:"full"` and `reset:true` instead of a delta with an invisible hole in it. The proof reads the untrimmed window, so a client that declared `session.snapshot.trim.v1` can be answered a reset where a delta would have been correct — a reset is correct either way and the reverse is not. An increment that would not fit one 10 MiB frame takes that same reset path rather than a refusal, because the client's recovery from a hole is the flag. Rejected: buffering deltas per connection (the bridge holds no state for a disconnected client, and the first reconnect after a restart would pay twice), a `hasMore` on the increment (a delta that does not fit is not a page, and paging already has an owner), and letting the capability alone switch the reply (a client would lose the whole window between adopting the name and tracking `lastSeq`).
- **A fork is the host's cut, so the bridge forwards the fork point and nothing else.** `hello` answers `minor:11` for this channel and advertises `session.fork.v1`; behind it `session.fork` sends `{sessionId, atSeq?}` as the single `request` argument of the host's `session/fork` and answers the host's own `SessionForkValue`. The fork point belongs to the host's vocabulary, not this bridge's: `atSeq` is an inclusive source-event seq, an omitted one means the newest finished turn, and a cut the host opens itself is closed by a synthetic finishing event it writes — so an `atSeq` a client never sent stays off the wire instead of being invented here, which would move the cut silently. What the bridge does own is the shape check the host would otherwise spend a call on: a `sessionId` that is not a non-empty string and an `atSeq` that is not a positive integer are refused `invalid-args` before any gateway call, whereas everything else — a host that will not fork, a session it will not fork, an open cut — crosses as the host's own `code` and `msg`, an uncoded failure as this bridge's `internal`. The method exists only behind the capability, so a client written before it is refused `unknown-method` and no fork is asked on its behalf. The number it takes is 11: this channel and the snapshot-`since` channel were both cut from 9, `since` landed on `dev` first and took 10, and the later landing steps over the earlier one — the minor counts additions to this protocol rather than the order branches were written in, so no frozen name or existing capability moves.
- **`hello` also advertises the capabilities the mounted extensions require, and the list is computed on every greeting.** The answer is `SERVED_CAPABILITIES` followed by the distinct non-blank capabilities the extension registry's tables gate on (`RemoteBridgeRegistry.capabilities()`, ascending), a name both halves know listed once. A bridge with no extension mounted answers byte for byte the list it always did — this protocol's names keep their order at the front — while a plugin that mounts after the bridge was built is visible to the next connection, because nothing here is frozen at construction; a withdrawn table takes its capability with it unless another registered method still requires it. Advertising an extension's name moves no `MINOR`: that number counts additions to this protocol, and a plugin's capability is the plugin's own. A capability deliberately absent from `SERVED_CAPABILITIES` for gating no method (such as `approvals.v1`) stays absent until some registered table requires it. This closed a real gap rather than a theoretical one: the board plugin had registered `board.v1` and its methods, `hello` answered the static list alone, and a phone reading the handshake concluded the host serves no Tasks. Adding the name to `SERVED_CAPABILITIES` was the alternative, and it was refused for the reason that constant carries no vocabulary it is not the author of.

- **A page's `hasMore` counts entries, and it answers only about the projection it was cut from — so the opening window's own cut is not folded in.** A real iPhone showed the field answering `false` where a page of 95 rows was expected to end a session of one oversized turn at `seq` 510, and the client hid its "load earlier" entry. Checked against the code and a case rather than assumed: `pageTurns` slices `flat`, the flattened `{turn, entry}` pairs, so `start > 0` already means "an older ENTRY was left out" and never "a whole turn was left out" — one 20-entry turn against the 512 KiB default answers 12 entries with `hasMore:true`, and `tests/snapshot-page.spec.ts` pins it. The cut that can still answer `false` is the other one: `session/follow` opens the harness window at `maxMessages: 200`, the harness reports its own `hasMore` on that opening frame, and `#baselineAnswer` does not fold it in. Per §9.5 that is the intended answer rather than a defect: the field promises "older content inside what this answer was cut from", a page carrying every entry of a window that is itself the newest segment has nothing older to serve, and a `true` with no page behind it is the one shape that loops — `session.history`, sliced from the same window, answers `{turns:[], hasMore:false}` below that window's oldest entry. Durable history below the window is `session.history.deep`'s question, because it reads the store and folds the store's own `hasMore`; a client that wants a "load earlier" entry beyond the window asks there instead of reading this field as "the session ends here". Rejected: folding the window's flag into the page (it would promise a page the bridge cannot serve and hand back a cursor it cannot honour), and the turn-level reading of `start > 0` that the device report started from (the index walks entries, not turns).

- **A baseline read is answered by a stream that has not moved since its opening frame.** The opening window is a moment, not a state: a connection keeps one `session/follow` stream per session and answered `session.snapshot` and `session.history` from the window that stream opened with, so a session that ran another turn on that very stream was answered the window of the moment the stream was opened — one iPhone read `turns:[] lastSeq:3` on a connection that had since received `seq=467`, and `turns:1 lastSeq:21` on a fresh connection. A subscription now records whether any frame followed its opening one (`Subscription.advanced`, set by the drain as the frame arrives). A read of a subscription that never moved awaits and reuses it exactly as before, so a session that stayed silent still costs one stream however often it is read; a read of one that has moved aborts that drain, forgets the subscription and opens a fresh stream, answering with the cursor that stream's own opening frame carries. Only a stream that has moved is retired, so every `session.snapshot` and `session.history` answer comes from a window no older than its subscription's own movement.

## Alternatives considered

- **Re-open a follow stream on every baseline read, or refresh the window a subscription already holds.** Rejected both ways: the first makes a silent session pay one stream per read, which is the reuse this connection exists to keep; the second is not something the harness offers, because a `session/follow` window is fixed when the stream opens and an open stream cannot be re-opened from its first frame.

- **Replay the browser credential over the relay.** Rejected on the shipped evidence in the sibling note: the harness browser-auth cookie is authority-bound to the `host:port` a browser visited and has no loopback exemption, so a proxied re-issue to `127.0.0.1` is refused; `dsh-remote-web-ui` only forwards a call because it redeems its own launch token once and holds a live paired-device cookie. A native client has neither, so this path would have required the bridge to mint and hold a browser session — a credential store for a session the user never opened.
- **Add a token-minting method to `dsh-remote-web-ui`.** Rejected: it would couple the two packages' lifecycles and make one surface's authentication depend on the other's configuration and roster format. The bridge's whole point is that a native client does not need the browser plugin to be installed, and the sibling note's own boundary is that the browser channel re-issues calls with the process credential — a seam that must not become a general-purpose issuer.
- **Build on the official `/api` HTTP surface.** Rejected: it exposes the harness's own authentication and the SDK cohort's endpoint names as the bridge's compatibility contract. The sibling note records that nothing in the runtime emits the `api/gate` seam on this cohort, so a direct `/api` call from a remote origin is governed by the harness fence plus whatever cookie the browser already redeemed — a trust posture the bridge cannot state, let alone enforce.
- **Reuse the browser channel's WebSocket (`/remote/api/remote.mux`) as the transport.** Rejected: that socket is the official client's multiplexed Typert connection, and proxying it would put a second protocol inside a channel whose gate is defined in terms of a paired browser. The bridge speaks its own envelope to a client that speaks only that envelope.
- **Put the pairing panel in `dsh-remote-web-ui`.** Rejected: that package's panel mints the browser path's own pairing link, whose credential is a paired-device cookie — a different secret, with a different lifetime and a different roster behind it. Rendering this package's one-time token there would have forced the two rosters and the two revocation flows to agree, which is precisely the coupling the package boundary above exists to avoid; a second occupant of the same footer seat keeps the two surfaces side by side with no shared state. Shipping the panel inside this package also keeps the native path usable with `dsh-remote-web-ui` absent, which is the property the bridge was created for.
- **Buffer deltas so a reconnect resumes incrementally.** Rejected: it would make the bridge a durable log with its own retention and delivery guarantees, for a client population that recovers from a full baseline in one call. The snapshot path already exists and is the honest recovery mechanism, and the incremental snapshot that shipped keeps that rejection intact: it reads the window it would have opened anyway and remembers nothing between connections.
- **Read the persisted log ourselves, the way `dsh-session-log-export` does.** Rejected after the address fix removed the need for it: parsing `session.v4.jsonl.zstd` would make the bridge own a compression format and an on-disk layout that belong to the harness, would hand the client a second source of truth that disagrees with the live stream about an in-flight turn, and would buy nothing the durable address does not already give — the delegated address returns the child's whole log through the same follow stream the root sessions use.
- **A `subagent.events` method, or a `subagent.*` topic, carrying the child's own process events.** Rejected: the parent stream is already a durable log the bridge follows, so a child's arrival is one event in a stream the phone is subscribed to — a second method would add a subscription to open, page, close and authorize, a second cursor to advance, and a second place where "is this child still running" is answered. The wire addition is one delta kind; the interior of the child is read through the very follow stream that already exists.
- **Mirror the child's increments into the parent's stream.** Rejected: it would make the parent's log the authority for another session's content, put two sessions' turn and step counters in one delta stream — a client could no longer tell which session a `turn-end` belonged to — and multiply one session's frame budget by the number of children, which neither the relay hop nor the client's single subscription was sized for. An expanded thread subscribes to the child and gets the same frames any session gives; collapsed, it costs nothing.
- **Follow any session id a paired client names.** Rejected: pairing authorizes a caller for this host, not for an arbitrary id a frame names, and a child id whose parent nothing resolves is exactly the read channel the gate exists to prevent. The relaxed case is narrow on purpose — one level below a session the caller is already authorized for — and it grows only along the path the caller actually walked.
- **Serve `session.history` from the harness's own `session/page`.** Considered and rejected in favour of paging the opening baseline. `session/page` counts `maxMessages`, not bytes, so a 512 KiB page budget would still have to be enforced by the bridge; it needs a `throughSeq` that only a follow opening frame supplies; and a page's records may begin mid-turn, so rebuilding the turn shell from them would have to fabricate or omit the turn's own `seq`, `endSeq` and `reason`. The opening baseline is the only source that already carries those fields, which is what keeps a page and a snapshot from ever disagreeing. The deep-history decision above is not a reversal of this one: it serves a NEW method from `session/page` — the byte budget stays the bridge's, the `throughSeq` comes from the projection watermark instead of a follow opening frame, and a store page's turn shells are rebuilt by the same shared projection — while `session.history` itself still pages the opening baseline.
- **Publish the `job/list` Remote stream instead of reading the registry.** Rejected: `JobListRequest.sessionId` is required, so that endpoint serves one session's fenced set and cannot serve the unowned scope at all — there is no session to name for it. Reading `ctx.jobs` serves both scopes from one seam and from the same authority the controller projects; the alternative was either two seams with two subscription models, or a synthetic session id whose "unowned" meaning the host does not document.
- **Report one global "N background tasks" count across sessions.** Rejected: the host has no such view — both of its reads are owner-fenced — so the count would have to be assembled by the bridge from N fenced reads, and a number nobody authoritative computed is exactly the second source of truth this channel exists to avoid. A phone shows the count for the scope it asked about, and asks twice if it wants both.

- **Let the host compute the difference.** Rejected: the host has no per-connection notion at all — it answers the roster and the board to whoever asks — so making it the differ would mean giving the bridge's connection bookkeeping to a service that does not have it, and teaching two host APIs a wire shape they currently know nothing about. The bridge is the only layer that already holds what it last sent.
- **Diff on the client, which already holds the previous body.** Rejected on arithmetic: the client would have to download the whole body to diff it, which is exactly the cost that is being removed. It also cannot work for `removed` without keeping the previous full set on the phone, which is the memory the delta is meant to save.
- **Keep the board's delta windows in the board plugin, keyed by connection id.** Rejected after trying it in design: releasing a dropped connection's state would need a second registry with its own expiry in the plugin, and the two packages would each own a copy of the token and cap rules that §15 pins once. The seam hands the plugin `declares` and the connection's own `deltas` seat instead, so the mechanism and its lifetime are the bridge's and the board's vocabulary stays the board's.
- **Answer a delta whenever the client sends any token it was given, even an older one.** Rejected: only the last set is retained, so an older token names a base that no longer exists — the answer would have to be a diff against the wrong set or a full copy of every set ever sent. Resetting is the honest answer, and it is also the recovery path.
- **Gate the omission behind `session.list.omit-archived.v1`, so a client that declares nothing keeps the full roster.** Rejected: a capability is announced rather than negotiated, and an archived row costs its bytes whoever asked for it — the older client filters the same rows away after paying for them, so the gate would preserve the cost and only preserve access to rows no UI renders. Advertising the fact instead lets a client drop its own filter without making the wire depend on its version.
- **Keep skipping the row but authorize the skipped id, so a child of an archived parent stays followable.** Rejected: the roster is the authorization source for a session, so re-admitting a session it no longer names would make the follow gate answer for ids nothing publishes, and an archived session would stay readable through a path the roster no longer shows. The child keeps its lineage either way, and a phone that needs the parent restores it.
- **Shorten `updatedAt` instead of omitting it.** Rejected: rounding a millisecond timestamp to seconds is the only form that fits in fewer characters, and it loses a value the client holds and renders, while the omission already removes the whole field for every row that did not move — on a reconnect, every row. A second encoding (an offset from a base carried once) was rejected too: it would add a member to every answer and a rule to every client to save about six bytes per changed row, on the reply whose cost was elsewhere.
- **Bound a compact page by bytes through `pageTurns`.** Rejected: `pageTurns` slices turns and entries, and the roster's page is a row count the client asks for so it can fill one screen; a byte cut over rows would need a second measurement path for a body `pageTurns` never sees, which is exactly what this change is not allowed to add, for a reply that is already the smaller one.
- **Let a compact page carry a `since` token as well.** Rejected: the two answers have two different bases — an increment against the set this connection last sent, a page against a cursor — and honouring both in one answer would need two tokens and two notions of "the client's base". A request naming both is refused `invalid-args` instead, so a client never believes it holds an increment it was not sent.

## Consequences

- **A baseline read on a stream that has moved costs a reopen, and what was in flight between the two streams is not replayed.** The deltas a phone already received are not withdrawn, and the fresh window covers every durable record, but a process-local assistant-stream chunk in flight while the old drain was aborted is not re-sent; the answer that triggered the reopen is a whole window of the session, which is what a client asking for a baseline is about to render.

- Two remote surfaces now exist with two independent access controls: the browser path (paired cookie, `/remote` channel, `dsh-remote-web-ui`'s roster) and the native path (device token, `/ios/v1`, the bridge's roster). Revoking one does not revoke the other, which is the intended separation — and the reason each package's README states its own security model.
- The package ships a browser half beside its host half, and the direction is one-way: the client half may read the pairing route and render it, and may not mint, spend, list or revoke anything. Its single wire call is a same-origin `GET` of a route the browser pairing path never serves.
- The bridge now owns UI copy as well as a wire format: the panel registers a `remote-bridge` locale namespace and occupies a seat in the Web GUI's sidebar foot, so its trigger joins the family's footer rows and its text follows the repository's zh/en dictionary discipline.
- The method set of protocol v1 is frozen at nine client methods plus the approval reply — `session.titles` and `session.history` join the roster, snapshot, prompt and interrupt methods — and the wire layout of every DSH endpoint the bridge may call lives in one table (`src/core/wire.ts`), including three endpoints no method exposes yet. A new method that names an argument key wrongly fails at the gateway with `arguments-invalid` rather than silently mis-invoking. The subagent thread keeps that count: it adds one delta kind and one optional object, never a method.
- **The child gate is narrower than the address fix it grew out of.** A delegated child whose `parentSessionId` no roster row resolved used to be served, because the follow stream only needed the parent id the child's own row carried; it now answers `session-not-followable` and opens no stream. A client renders that as an explanation rather than as a retryable failure, and the cost is deliberate: lineage comes from the host's roster and never from a frame, the roster is read once per connection before the first attempt, and the readable set grows one level at a time along the path the caller actually walked.
- The bridge owns a durable format of its own: `$DSH_HOME/remote-bridge/devices.json`. Its shape is a compatibility surface from the day it ships, and a corrupt file is quarantined rather than silently emptied, so a roster that fails to parse can never be mistaken for a roster with no devices.
- A client that loses its device token pairs again with a fresh bootstrap token — the routine recovery path, not an exception path. Nothing about the flow requires hand-editing the roster.
- The token endpoint is reachable only from the machine itself, and the same link is written to the Host log while the code itself is rendered in the pairing panel; the phone's side of that line is only the kind of address — `pair a device with <ws link>` followed by `(phone: lan)` when the host calls the origin a LAN address or the literal itself answers only inside the network this page is already on, `(phone: public)` in every other case, and no suffix when the host found no address at all — because this pairing line is the one an operator pastes elsewhere, and neither the public hostname nor the LAN literal belongs in it. The log line and the code on screen are live secrets for their 30-second lifetime, which the README states where an operator will read it.
- The job channel adds one method, one topic and one capability, and touches no existing frame: `jobs.list` is the seventeenth entry in the frozen method set, old clients never call it and receive no `jobs.changed` (they are never subscribed), and a new client on an older host sees no `jobs.v1` in `capabilities` and must render that as "unknown", never as "zero jobs". Two write-shaped things stay deliberately out of scope: `job.kill` needs an approval story of its own, and `job/follow`'s output stream would add a byte cursor, a lossy flag and ring retention to a surface that only needs a count.
- The agent channel adds two methods and one capability and touches no existing frame or topic. It is the first place where the bridge forwards a host request it cannot state the shape of: a client that sends `session.create` a body the host rejects learns the host's reason, and one that omits a field the host requires learns it from the host rather than from the bridge's own copy of the schema — the price is that a client cannot validate a creation request locally, which is deliberate, because the host's schema moves with the host. A new client on an older host sees no `agents.v1` in `capabilities` and must render presets and creation as unavailable rather than as empty.
- The compact roster is the second body whose bytes are cut for a client that asks, and the first that can be cut without a delta window: a phone that declares `session.list.compact.v1`, asks for 100 rows and pages with `after` pays 8024 bytes instead of 100470 for the same roster, and a client that declares nothing — or declares the name and asks for nothing — receives protocol v1's own bytes unchanged. `hello` answers `minor:9` for it, and a new client on an older host sees no such name in `capabilities` and must render the roster as unpaged rather than as an error.
- The roster is the one protocol v1 body that shrank for every client rather than only for those that declare a capability; every other answer a client that declares nothing receives is unchanged. Measured against the running host before the restart: 935 rows, 346 of them archived, 76,608 of 212,426 roster bytes (36%), and 0 live children of archived parents — so the follow-gate narrowing above is a rule with no instance on that host today, and the byte saving is paid back on every single listing.
