# Agent Note: 远程桥协议 v1 是与传输解耦的原生客户端面

Status: implemented

同级面的决策：[远程控制复用官方界面](2026-08-29-remote-control-reuses-official-ui.md) 拥有浏览器路径——配对设备 cookie 与受门禁的 `/remote` 通道。本 note 拥有第二条面：为原生客户端准备的、协议形状且不带 cookie 的路径。

## Problem

`dsh-remote-web-ui` 靠配对浏览器发布手机面：设备拿到 cookie，之后每次调用都走 `/remote` 通道，而该通道用进程自身的浏览器凭据重新签发。对浏览器而言这是正确的形状——它白拿了官方 UI、移动适配层与设置桥。对没有浏览器、没有 cookie 罐、也没有 Web GUI 包体的原生客户端而言，这是错误的形状：iOS App 得先模拟一个浏览器会话，而且照样继承网页的失效模式。

两条约束决定了这里「原生客户端」只能是什么样。其一，宿主没有为此准备的官方 HTTP API：从远程 origin 直接打 `/api`，受制于宿主围栏恰好信任什么，而把产品建在其上的插件会把 SDK cohort 的端点名与宿主自身的鉴权变成自己的版本耦合依赖。其二，浏览器凭据本身无法跨中继回放：它与浏览器访问过的确切 `host:port` 绑定，且没有 loopback 豁免，因此代理重发到 `127.0.0.1` 会被拒——正是 `dsh-remote-web-ui` 不得不自行兑换 launch token 才绕开的那个缺陷。

所以原生客户端需要一种宿主本来没有的传输，以及自己的访问控制。缺的是一个决策：这条面是什么、如何鉴权、与浏览器那条面是什么关系。

## Decision

- **桥是独立包，协议 v1 是独立契约。** `@linxin666/dsh-remote-bridge` 是同一插件行承载的两个半区（`packages/dsh-remote-bridge`）：宿主半区发布一条精确的 WebSocket upgrade 路由 `/ios/v1` 与一条精确的 HTTP 路由 `/remote-bridge/pair/token`，而同一行声明的浏览器半区（`dsh.client` -> `exports["./client"]`）再加一个侧栏底部的配对面板。协议是一套 JSON 信封——`{"t":"req","id","m","p"}`、`{"t":"res","id","ok","r"|"e"}`、`{"t":"ev","seq","m","p"}`、`{"t":"ping"|"pong","ts"}`——一条消息一个文本帧；方法层不出现 HTTP、cookie 或浏览器会话，因此同一套信封可以原样跑在 loopback socket、局域网绑定或被中继的 origin 上。
- **桥在进程内消费宿主。** 会话工作走 `ctx.typertGateway`（一元调用用 `invoke`，`session/follow` 用 `stream`），只以 gateway 的 `error.code` 作为失败判别，并对服务激活窗口使用家族既有的有界重试。权限请求在同一进程内监听 `ctx.on('approval/request')` 作答——绝不走 `$events`/`$events/result`——而无人应答的审批会被归一为 `unavailable`，宿主按拒绝处理，因此沉默的手机永远不等于同意。

- **一次审批在认领时广播一次，并重放给声明了审批能力的新连接。** 工具发起请求的那一刻，`approval.request` 会送达每一条已配对连接，而这次首播刻意不放在任何能力名之后：一个门控首播的名字会夺走所有在该名字存在之前写下的客户端的审批通道，而这正是能力在本通道里不该做的事。客户端可选的是第二次送达。连接在 `hello` 里声明 `approvals.v1` 后，桥会立刻把仍未结算的审批重新发给它——即 `BridgeHub.replayApprovals`，与 `replayQuestions` 一起接在 `attach` 里，因此所有构造路径都覆盖、别处一概不重放——配对检查、能力声明检查与 `emit` 路径都与提问通道同构，且首播与重放共用一个载荷构造函数，手机原先看到的卡片与再次收到的卡片不会漂移。已释放的审批不可能复活：`ApprovalRegistry.#settle` 是离开待办表的唯一路径，作答、桥自身的两分钟超时、agent 的取消、以及最后一台手机离开后的撤回，都会在结算之前把该条目删掉。重放只发一帧，既不动认领也不动它的计时器，因此重新递一次问题绝不会延长它开认领时的那一刻截止时间。这个名字刻意不在 `SERVED_CAPABILITIES` 里、也不伴随 minor 升级：按本仓约定，公告一个能力属于 minor 追加，而本通道不改变客户端在握手里能观察到的任何东西——没有字段、没有答案、没有方法——因此声明本身就是整个开关，名字经由本包的文档传达给客户端。
- **每次网关调用都以同一个进程内 owner peer 发言，且只在桥自己的配对门禁之后被用到。** 自 SDK 0.2.1 起 `InvokeRemoteRequest.peer` 必填，而鉴权层只读 `peer.principal`；桥在挂载时于 `core/owner-peer.ts` 铸造单个 owner peer（`{kind:'owner'}`、`interactions:'none'`），绑定插件 fiber、`dispose()` 幂等，并挂到每一次 `invoke` 与 `stream` 上。这个完全控制声明安全的原因与 0.2.1 之前那种隐式特权相同：通向它的路径都要过桥的配对检查——分发在任何网关调用存在之前即以 `unpaired` 作答，而那三个未配对方法从不调用网关——且客户端帧的任何字段都不会被读进 peer，因此客户端无法自报 principal。`interactions:'none'` 保证不碰宿主转发事件：审批经桥自己的 `approval/request` 认领与协议自有事件抵达设备，而不是经 Typert 转发事件订阅。
- **桥自签 bootstrap token。** 仅 loopback 可达的 `GET /remote-bridge/pair/token` 把一枚 32 字节、30 秒有效的一次性密钥交给操作者；`pair.begin` 花掉它并签发 nonce；`pair.finish` 用所给 P-256 SPKI 验证对该 nonce 的原始 64 字节 ES256 签名，然后在 `$DSH_HOME/remote-bridge/devices.json` 落一条名册条目——公钥、SHA-256 指纹、时间戳（目录 0700、文件 0600、临时文件加原子 rename）。设备令牌本身是 32 随机字节，只保留其 SHA-256 哈希。`dsh-remote-web-ui` 不被改动：它的配对服务继续为浏览器路径签发 cookie，两份名册是两个文件，吊销互不相干。
- **浏览器半区渲染那枚 token，且从不消耗它。** 面板注册进官方 `sidebar.footer.action` 座位——ui-sidebar 声明的那个列表槽位，`dsh-remote-web-ui` 的手机触发器占用它，而 `dsh-update` 的更新器只在安装了 `@linxin666/dsh-update` 的 profile 里占用它——用同源请求读同一条仅 loopback 门禁的路由，并把密钥渲染在官方无头 `Modal` 里：一张卡片装着 `qrcode.react` 二维码、一条固定高度的状态行（30 秒倒计时配进度条，或同一个盒子里那句过期说明）、一条地址说明、那条一次性说明，以及一行动作（都是官方 `Button`）。二维码里装的，在宿主说不出来源时装裸 token，说得出来时装宿主自己那份 `{token,url}` 应答；宿主没背书过的 URL 会让手机端自己的解析器把 origin 改写成这台机器的 loopback 地址，而那恰恰是手机唯一够不到的地址。编码串只在二维码部件的 `data-dsh-qr-value` 里留一份镜像，绝不以文字渲染：复制与重新取码经手的都是这同一个字符串，而过期之后复制被禁用，重新取码是回到可扫状态的唯一路径。`403`、意外状态与网络失败各自渲染成有名字的状态，绝不呈现为一块沉默的面板。关是开的反向——卡片保持挂载直到出场结束，把弹窗自己那段进场 keyframe 反着播完，名字在关闭时从挂载着的弹窗上读出来，因为打包器会给它加作用域；reduced-motion 下这条生命周期换成一段短淡出——并且几何在各状态间钉死，倒计时、过期与复制确认都不挪动身边的元素。面板不能签发设备令牌、不能消耗配对码、不能列名册、不能吊销设备，也不新增任何 wire 面。
- **一条授权规则，在分发之前检查。** 设备令牌缺失、未知或已吊销的连接只能调三个方法（`hello`、`pair.begin`、`pair.finish`），其余一律回 `unpaired`。设备令牌随 upgrade 以 `Authorization: Bearer` 携带，也给无法设置握手 header 的客户端留了 `?token=`；比对先对两侧取哈希，再比等长摘要。
- **连接的 event `seq` 不是续传游标。** 连接的 event `seq` 自 1 起，给的是该连接收到的东西编号；快照的 `lastSeq` 是宿主游标——与 `seq` 是两个计数器，协议从不比较二者——也是重连唯一能续传的水位：发现跳号或重连的客户端调 `session.snapshot`，声明了 `session.snapshot.since.v1` 时把该水位作为 `sinceSeq` 带上，否则拿完整基线。`session.snapshot` 打开宿主 `session/follow` 流并保持它作为本连接的订阅，因此增量无需轮询即到达。
- **一帧 10 MiB，且客户端可以要求一份它真能渲染的基线。** 上限是一个常量（`MAX_FRAME_BYTES` = 10 MiB），接收判定、快照拟合、`frame-too-large` 文案与出站事件丢弃都读它，因此这个数字不会被写第二遍；它从 256 KiB 提高，是因为手机的基线就是一整个会话历史压在一帧里。但只提上限，等于把「被拒绝」换成「打开得极慢」：基线里的大头是客户端根本不渲染的持久记录——单个回合内部的 `system/message` 与 `request/header` 段落，动辄 150 KB 以上。于是 `hello` 的 `cap` 数组现在会被读取，声明 `session.snapshot.trim.v1` 的客户端拿到的基线在每个回合内部被裁到它能渲染的四种 entry（`user/message`、`assistant/message`、`tool/call`、`tool/result`）；一个回合的 entry 若全是记账记录，该回合仍保留为 `entries` 为空的回合；每个回合级字段、回合列表与 `lastSeq` 都保持投影自己的取值。能力是公告而非协商：未知名字、读不懂的 `cap` 与缺失的键都被忽略，什么都不声明的客户端——该能力出现之前写下的所有客户端——逐字节拿到协议 v1 一直以来提供的基线。裁剪先于帧预算：先裁 entry，再丢最旧的整回合，之后才轮到 `snapshot-too-large` 作答。
- **被委派的子会话通过持久父地址寻址，历史按 entry 分页。** `session/follow` 与 `session/page` 收的是 `SessionAddress`，而把一个子会话当作普通会话来问，宿主会拒绝：`session/agent-busy`——"subagent Sessions require their durable parent address"。正是这条拒绝，让某台手机 828 行名册里的 457 行、对那些明明握着完整日志的会话回 `snapshot-unavailable`：桥对每个 id 都发 `{kind:'session'}`，并把宿主自己的诊断抹成一句读起来像临时故障的泛泛失败。现在桥只对这一个会话改用 `{kind:'subagent', parentSessionId, childSessionId, mode:'unknown'}` 重试，父 id 取自名册——唯一携带谱系的端点——且每个连接至多读一次；其余任何失败都带着宿主自己的错误码穿过，不再被吞掉。`mode` 恒为 `unknown`：宿主会把声明出来的 mode 与子会话描述符比对，而对任何子会话都接受 `unknown`，且桥在调用前读不到子会话的 mode。同一处修复让 `session.history` 对这些会话也生效：它从持久 `seq` 水位按 **entry** 往回分页，默认每页 512 KiB，允许一个回合的 entry 跨页而该回合保留自己的字段，让比整页预算还大的单条 entry 独占一页而不是被拒，并且是绝不打开、丢弃或改指订阅的纯读。
- **第二个能力给首屏本身加上预算。** 把 `session.history` 往回分页，并没有切分首屏：打开一个活跃会话仍然一次交付整个 3.3 MB 开帧窗口，所以「大会话像小会话一样秒开」当时并不成立。`session.snapshot.page.v1` 让 `session.snapshot` 改回最新一页，用的是 history 那同一套按 entry 的切片，并按 `maxBytes`（默认 512 KiB）衡量，因此首屏与其后每一页都出自同一条代码路径，不可能互相矛盾。能力门控正是让它不构成回归的原因：不声明的客户端逐字节拿到整个窗口；声明的客户端额外拿到 `hasMore`，以及一个恰好等于它自己最旧那条 entry 的 `seq` 的游标——正是 `session.history` 的 `before` 所取的值，所以不再有字段重述它。`snapshot-too-large` 不会再回给声明了该能力的连接，因为比预算还大的 entry 会独占一页而不是被拒绝。2026-10-19 在一台经中继的 iPhone 客户端上实测：声明了该能力的连接收到 2209876 与 2218877 字节的两条应答，各耗时 3.54 秒——这条规则同时也是那个疑似缺陷的答案。预算按整个编码后的应答计量（`measure` 回调里对客户端实际收到的那个 `res` 帧做 `JSON.stringify`），从不按回合计量，因此它约束的是页而不是 entry：`pageTurns` 只在 entry 处结束一页、绝不从 entry 内部切断，而它的校验循环对「只有一条 entry 的页」根本不测量就直接返回，所以一条超过预算的 entry 就是那一页，应答也恰好和它一样大。2.2 MB 因此不是没有生效的分页预算，而是最新那条 entry 本身有 2.2 MB——一次文件读取、一段很长的回答、一个图片结果——而在同样的 512 KiB 之下，一窗普通 entry 的应答是 513794 字节。裁剪或切开这样一条 entry，交给客户端的内容就不再是会话自己说的；拒绝它，又把「让大会话开得出来」的那份能力从这个会话上拿走；所以这里把这个界写清楚而不是收窄它：除最新那条 entry 自己就超过 `maxBytes` 的情况之外，一页都在预算之内。这句话的两半都由 `tests/snapshot-page.spec.ts` 钉住——2200221 字节的单 entry 页，以及 513794 字节的对照。唯一被留下的是帧上限：超过 10 MiB 的单条 entry 仍会作为一页过线而不是被拒绝，这是把上面那条决定照字面执行的结果。
- **一条消息会说明它从哪来，而一个被派生出来的子会话是它自己的 delta。** 协议 v1 一直携带内容却不携带来源：无论人打的、子会话转述的、还是宿主注入的运行时上下文，每条持久 `user/message` 都变成同一个 `user-message` delta，而"某个 agent 起了一个子会话"这件事在线路上完全没有公告。本通道落地时 `hello` 回 `minor:2` 并公告 `capabilities`——本桥当时服务的四个：`session.snapshot.trim.v1`、`session.snapshot.page.v1`、`questions.v1`、`subagent.thread.v1`（今天是十三个、`minor:11`，见最后几条）。插件注册的能力不在其中：桥不是它的作者，客户端照旧从插件自己的文档得知它。`user-message` delta 与快照里的 `user/message` entry 现在带一个可选的 `actor`，机械地取自持久 `source` 记录：`user` 与 `user-approval` 是 `human`；`agent-message` 与 `subagent-settled` 是 `agent`，并带上发送方的会话 id；其余任何来源种类都是 `system`，原文照抄——一条消息不会因为携带了本契约没分类过的来源就被丢弃，而 source 里读不出种类的错误事件干脆不带 `actor`，而不是猜一个。`actor` 不受能力门控：它是可选键，从不读它的客户端直接忽略。`subagent` delta 由 `subagent.thread.v1` 门控，从持久 `subagent/catalog` 事件取 `{childId, label?, mode?, callId?}`，并且把锚点接到派生它的那次调用上按两级来：先看 spawn 自己的 `tool/result`——它用本宿主会写的两种形状点名 child（激活句柄 `{"kind":"activation","subagentId":…}`，单独返回或嵌在 `run_code` 的答案里；或它打印的 `started subagent …` 通知）——因此无论那一步发过多条调用、还是一次调用起了一整队，都由载荷说的是哪个 child 来定；只有在没有任何结果点名该 child 时，才退回原有判据：这个 turn 与 step 只发过一条 `tool/call`。一步发过两条、或同一条调用已经挂过另一个 child 时，锚点一律省略而不是猜——`callId` 猜错会把手机上的线程挂到错的卡片上。`subagent/catalog` 现在也是裁剪基线保留的 entry 类型之一，并在 `data.callId` 里带上派生它的那次调用；同一个 `SpawnCallIndex` 同时回答两半——实时订阅边看边答，基线读完整个会话再答——因此这条通道当初留待下一轮的基线半区就此闭合，没有新增方法、主题、帧形状或 minor。
- **跟随一个被委派的子会话需要授权，而授权本身决定谁可被读取。** 读子会话自己的日志，正是"放宽一条地址裁定"可能变成"任意会话读取通道"的那一处，因此规则用"本连接已经可以读哪些会话"来表述：名册列出的普通会话、以及本连接已经打开过的任何会话都可跟随；被委派的子会话只有它名册行上的 `parentSessionId` 解析进这个集合时才可跟随，而子会话自己那一行永远不构成自我授权——否则一次被拒的读取就会教会这个连接在下一次重试里读它。父会话解析不出来的子会话在任何 follow 流打开之前就回 `session-not-followable`；而名册完全不认识的 id 维持旧路径，由宿主自己对它作答。这条裁定要求在做第一次尝试之前就知道谱系，所以名册在那时读：被名册指明父的子会话直接用委派地址寻址，而那次读取没能解析出父时，仍由宿主的 `session/agent-busy` 拒绝驱动唯一一次重试。
- **中继无需改动。** 桥搭在实例本来就发布的那个 origin 上：`market/worker/src/relay.js` 查出隧道目标、只重写 `Host` header、原样返回 origin 的响应，而 WebSocket upgrade 走同一跳，因为 Workers 运行时会把携带 `Upgrade` 请求且 body 为空的 `fetch` 升级为 WebSocket。把 token 端点挡在公网 origin 之外的是 loopback 门禁，不是中继。- **名册带上宿主自己的会话元数据，标题在本进程内读。** `session.list` 除重发手机用来分组与命名的摘要字段——`cwd`、`parentSessionId`、`origin`——以及 `blank` 之外，还从 workspace registry 的唯一归档集补上 `archived`；每个可选键只在本次进程确实能回答时才出现，因此读不到归档集的桥省略该键，而不是回 `false`。`session.titles` 用 `ctx.sessionTitle.get` 读 `ctx.sessions` 活跃持有的会话，回答一批最多 100 个 id——绝不为每个会话各开一条 follow 流（名册里空标题的老代价正来自此）——并把每个已解析的标题缓存 10 秒。缓存按时间失效而不是按事件失效：标题变更是 `session/title` 这条*日志*事件，背后没有 cordis 事件；做失效钩子等于给每个活跃会话挂一个监听器，而 TTL 把陈旧度限住（重命名最多 10 秒后才可见），且每次批量调用本身就是一次刷新。两个服务都通过 `ctx.get` 以可选的结构化 face 访问，而不进 `inject`：把它们列为必需会让标题或工作区插件缺位时整个桥一起倒下；服务未挂载时，一个 id 回 `""`，一个键被省略。
- **后台任务只读发布，用宿主自己的两个 scope，且只发给问过它的客户端。** `hello` 现在回 `minor:3` 并公告 `jobs.v1`；其背后 `jobs.list` 回 `{sessionId?, scope, jobs}`，`jobs.changed` 载荷是**同一个盒子**。桥读的是 `ctx.jobs`——`job` Remote 命名空间本身就是它的一个投影——因此没有第二份存储、没有轮询、也没有自己的状态词表：每一行是 `{id, kind, status, label, ownerSessionId?, startedAt, finishedAt?}`，逐字段取自宿主的 `JobView`，而宿主的 `output`（环偏移与 spill 路径）、`progress`、`detail`、`outputLimitBytes` 一律不上线。任务表在宿主侧按 owner 设防（`JobRegistry.list(caller?: SessionId)`）：点一个会话，得到该会话自己的任务加所有无主任务；不点会话，只得到无主任务；宿主没有全局表可发。于是本方法收可选的 `sessionId`，有则以 `scope:'session'` 回显它，无则回 `scope:'unowned'` 且不带会话键。桥**不**把两者折成一个假全局视图：那要么是把 N 个设防读聚合起来，要么是第二份事实源；诚实的话就是宿主自己的话——任务归会话所有，`unowned` 不是「全部」，两个都想要的客户端调两次。变更检测用宿主 registry 自己的事件流，只取生命周期提交：`output` 追加不动任何一行，在这一层就被丢弃，所以这条通道永远不会退化成「每个输出字节一帧」。一波提交由 100 ms 窗口折叠——正是 job controller 自己给 `observeFlushMs` 用的默认值——窗口到期后整集重读，若投影与该连接上一次收到的帧完全相同就不发。订阅是 `jobs.list` 换来的：声明了 `jobs.v1` 却一次都没列过 scope 的连接收不到任何任务帧，也不让 registry 多一次读——这正是「N 个打开着的会话变成 N 份集合往一个什么都没问的手机上推」的拦阻所在。订阅随连接结束，而 registry 上的事件订阅随最后一个订阅者结束。
- **已握着一份集合的客户端只收差值，而差值由桥算。** `hello` 现在回 `minor:4` 并公告 `delta.v1`；它背后 `session.list` 与 `board.snapshot` 接受一个可选的不透明 `since` 令牌，回两种形状之一——`{mode:"reset", token, …}` 带与从前逐字相同的整份身体，或 `{mode:"delta", token, …changed, removed}` 只带动了的部分。这件事只能在桥里算：桥本来就按连接持着它上一次发出的那一份，而宿主每次照旧回答完整集合——所以省下的是桥与手机之间的字节，从来不是宿主 API 的变化。一行算"变了"的判据是**整行的序列化结果**与上一次不同，而不是某个时间戳动了：宿主的 `updatedAt` 不是 `agentRunning`、`blank`、`archived` 或任务 `column` 的变更信号。`removed` 一定会发：一个本连接被发过、这次宿主不再列出的 id 进 `removed`，因为静默丢掉一行比一次 reset 更糟。每条连接最多保留它最后一份完整集合——名册 5000 行、看板 2000 个任务——越过上限即回 `reset` 且令牌为空，一部手机绝不能钉住宿主状态的无界副本；`changed` 超过全部行数的 60% 时也回 `reset`，因为过了这个比例增量本身就带着身体的大部分，多出来的两个键只是让它更大。不是本连接自己发出的令牌——别的连接的、上一次启动的、更早一次应答的、或任何垃圾串——一律回 `reset`：基底错了答案就是错的，只有这个窗口最后发出的那一份才允许被当作差值基底。从未声明 `delta.v1` 的客户端收到的是今天的身体加上可忽略的 `mode` 与 `token` 两个键，且不为它保留任何副本，因此这条通道之前写的每个客户端逐字节停在原地。窗口是连接对象上的一个字段（`core/delta.ts`），随连接一起消失；看板插件通过扩展缝（`declares` 与按连接的 `deltas` 座位）借用同一套机制，而不是把一份被协议钉死一次的规则抄第二份。`board.snapshot` 的 reset 把宿主快照逐字保留在 `snapshot` 下——那是所有既有客户端读的东西——并在旁边发布 `revision` 与 `tasks`，于是支持增量的客户端在两种形状下解析同一套字段，而老客户端解析它一直解析的那套。
- **已归档的会话根本不在名册上。** `hello` 今天回 `minor:11`（自这条决定起回 `minor:5`，agent 与深历史两条通道各自把它提到 `minor:6`，帧形态、紧凑名册与快照增量三条把它推到 `minor:10`，fork 通道再推到 `minor:11`），并公告 `session.list.omit-archived.v1`——这是这里唯一不协商任何东西的能力，因为省下的字节属于桥而不属于某个客户端的版本：手机一收到就把每一行已归档会话藏起来，因此一份 935 行的参照名册为 346 行、212,426 字节中的 76,608 字节（36%）付了钱，而这些行从来没有客户端渲染过。归档集本来就在每次列出时读一次、用于填该行的 `archived` 标记；现在同一次读取在构造该行之前跳过已归档会话，因此它的任何字段都不会被读，也没有任何东西穿到线路上。不变的部分：该键仍留在 schema 里，存活行携带 `archived: false`；本进程读不到归档集时仍然一行都不丢、仍然省略该键；谱系仍然来自每行自己的 `parentSessionId`，因此已归档父会话的活跃子会话仍带着那个父 id 被列出。名册同时也是 delta 窗口做差分的那一集，所以这两种迁移都不需要特例：两次列出之间被归档的会话出现在 `removed` 里，被恢复的出现在 `changed` 里，与一行停止存在或开始存在的走法完全相同。唯一被收窄的是跟随闸门——授权一个会话的是名册，因此已归档父会话的子会话现在回 `session-not-followable`，直到父被恢复；在那台参照宿主上这次收窄没有任何实例（改动当时已归档父会话的活跃子会话为 0），所以选择接受这条规则，而不是靠授权一个名册不再点名的 id 把它买回来。
- **一个 Agent 就是被实例化成会话的一个预设，所以桥转发预设名册与创建请求。** `hello` 回 `minor:6`（本通道把 5 提到 6） 并公告 `agents.v1`；它背后 `presets.list` 回 `agentPresets/list` 发布的东西，`session.create` 把宿主自己的 `SessionCreateRequest` 交给 `session/create`，两者都是转发而不是解释。产品方向是一个 Agent 等于一个由预设实例化出来的会话——就像本机的 `liangshen` 预设那样——而在这之前手机只能靠跑一张任务看板卡片才走到那里。桥不是这两套词表的作者：预设行是注册表发布的东西（连它的插件清单一起），创建请求是宿主校验的东西，所以在这里被改名、被补默认值或被丢掉的字段，会在宿主长出该字段的那一刻与宿主分家。整条路上不要求任何字段、不补默认值、不丢弃任何键；宿主拒绝的请求带着宿主自己的错误码与原文穿出去（网关不接受的身体回 `gateway/arguments-invalid`），没有错误码的失败仍是本桥的 `internal`。两个方法同属一个能力，因此在这之前写下的客户端对两者都收 `unknown-method`，也不会因为它发任何请求：预设名册是手机问了才读、握手时从不预读，所以声明了这条通道却什么都不看的连接不花宿主任何一次读取。
- **持久历史分页自成一个方法，minor 也随之到 7。** `session.history` 切的是 follow 开帧窗口，而窗口有多宽取决于向宿主开了多大——200 条消息——因此客户端只能翻这个窗口自己的 entry，再旧一条都翻不到；在某个客户端上实测：它列出五轮，而宿主记着八轮，去掉两个基线能力之后更旧的页能翻到了，但 `session.snapshot` 会超时、会话根本开不出来。`session.history.deep` 补的正是这个缺口，也是这里唯一读会话存储、而不读 follow 流的方法：请求是 `{sessionId, before?, maxBytes?}`，响应是 `{turns, nextBefore?, hasMore}`，其 `turns` 与 `session.history` 的逐字同形——每个回合保留自己的 `seq`、`time`、`endSeq`、`endTime` 与 `reason`，每条 entry 的 `seq`、`time`、`type`、`data` 都从持久记录原样透传——而 `before` 是同一个持久排他水位，因此客户端可以复用来自任一方法的游标。每一页都取自宿主自己的 `session/page`；由于该端点要求 `throughSeq` 必须是日志里真实存在的 `seq`（它的 `-1` 哨兵回的是空页，不是整份日志），每一页是两次宿主调用：先取 `session/projections` 的 `asOfSeq` 当 `throughSeq`，再用 `beforeSeq` 往回读。整个过程与 follow 订阅无关：不打开任何流、没有任何窗口约束答案、连接上不保留状态、也不缓存页面，所以同一个 `before` 必得同一页，且一次调用不会改变会话本身。返回的 entry 是存储自己的记录，不按 `session.snapshot.trim.v1` 裁剪，因为要一页历史的客户端要的就是历史。帧预算就是 `session.history` 已经在用的那一套——默认 512 KiB，用同一套 `pageTurns` 与同一份真实帧 `measure`，把存储返回的那一段**按 entry** 切开——因此比整页预算还大的单条 entry 独占一页而不是被拒绝，而存储这次只读到一半时，页尾也仍会报 `hasMore`，因为存储自己的答案被折进了这一页。`session.snapshot` 与 `session.history` 逐字节未变，两个基线能力继续声明。与上面那些开了通道的能力——子代理线程、后台作业、名册收窄——不同，这个能力不设门控：`session.deep-history.v1` 只公告方法存在，所有已配对连接都能调用，因为对存储的纯读不向任何其他客户端收费。`hello` 现在回 `minor:7`：agent 通道把 5 提到 6，持久历史在它自己的分支上同样从 5 提到 6，而同时承载两者的这一份协议比任一者高一位。
- **大应答以裸 DEFLATE 过线，minor 现在是 8。** 2026-10-19 在真实中继上实测（`make probe-relay`，五个样本取中位数）：一个往返约 410 ms、吞吐约 240 KB/s，于是一个 154470 字节的 `session.list` 要 1074.6 ms、一个 506089 字节的 `session.snapshot` 要 2438.6 ms，而同一条载荷走 loopback 只要 101 ms 与 4.5 ms——成本在字节，不在往返次数。permessage-deflate 在这里有两条互相独立的不可用理由：`URLSessionWebSocketTask` 没有设置 `Sec-WebSocket-Extensions` 的 API，原生客户端连提议都发不出；帧读取器又直接拒绝 RSV 位，101 响应也从不宣告扩展。所以压缩由协议自己承载：声明了 `frame.deflate.v1` 的连接可以被应答为 **binary** 帧，载荷是那条本会走 text 帧的 JSON 文本的 `deflateRaw`（RFC 1951，无 zlib 头、无 adler32 尾，等级 6），方向固定为服务端到客户端。三条边界属于契约而不是可调参数：小于 1024 字节的帧一律仍走 text，让握手应答不必付 deflate 的开销；压缩后不缩短的帧一律写回 text，因此这个能力绝不会让任何一帧变大；10 MiB 上限继续按**解压后**的文本在解析前判定，所以本包所有预算说的仍是未压缩尺寸。什么都没声明的连接看到的就是旧路径，逐字节一致——`BridgeTransport.frameDeflate` 只在 `hello` 记下能力后上报一次，`send()` 永远只是在同一信封的两种编码之间选择。接受的 socket 另外设置 `setNoDelay(true)`：410 ms 的路径会让 Nagle 的额外延迟在小帧上显形。同一 origin、同一条隧道，只换这个包：名册由 154470 降到 21521 字节、由 1074.6 降到 611.9 ms，三场抽样基线由 2438.6/2442.3/2462.7 ms 降到 775.5/790.4/797.4 ms，线上字节为其 19.5–20.6%，而解压后的文本与 text 路径产出的逐字节相同。`hello` 现在答 `minor:8`，`frame.deflate.v1` 追加在 `SERVED_CAPABILITIES` 末尾，既有槽位一格未动。
- **不再应答 ping 的对端按它自己的截止时间被关闭。** `IDLE_PING_MS` 仍会在连接静默 20 秒后探活，而这次 ping 现在会武装 `LIVENESS_TIMEOUT_MS` = 10 秒：任何入站帧都会取消它——没有对应 ping 的 pong 仍是空操作——整整一个截止时间内什么帧都没发的对端，会走其他所有关闭同样走的 `dispose()` 路径被拆除，关闭码 4000（`CLOSE_LIVENESS_TIMEOUT`），并留下一条点名该截止时间的日志。这个截止时间只因 ping 发出而存在，所以只是安静但会应答的客户端永远不会因为安静被关闭；10 秒也比 2026-10-19 在 relay 上测得的约 410 毫秒单向时延高出一个数量级以上。
- **名册有了紧凑且可分页的形态，minor 随之到 9。** 名册是线路上重复最多的大应答——每次重连都要再付一次——而 2026-10-19 在真实中继上，一份 663 行的 `session.list` 未压缩是 154470 字节、经 `frame.deflate.v1` 后是 21521 字节，所以它的字节值得在压缩之前先切，而不是只在压缩之后。`session.list.compact.v1` 就是这次切分的名字，而它需要两半同时出现：能力，以及请求里至少一个紧凑参数。`cwd` 是布尔值，决定绝对目录是否过线；`maxRows` 把名册切成每页这么多行；`after` 点名上一页最后一行，因此是续页而不是重取。紧凑行按最近优先排序、id 作平手判据，这正是 `after` 成为游标而不是位置的原因；`nextAfter` 只在后面还有行时出现，而指不到当前名册任何一行的游标会再回一次第一页——就像本窗口从未签发过的 delta 令牌回 reset 一样。`updatedAt` 只在本连接尚未把该 id 的这个确切值发给该客户端时过线，因此重复列出时一个都不带；`compact:true` 声明了行的 schema，于是缺失的 `updatedAt` 永远不会被读成宿主从来没有的值。行的其它部分一概不变：`title`、`agentRunning`、`blank`、`archived`、`parentSessionId` 与 `origin` 都是今天的那几个、今天的那几个名字，所以一页是同一份名册被截短，而不是第二套 schema。兼容是双向的、也有测试：未声明该能力的客户端带着全部紧凑参数请求，得到的仍是今天的身体（这些键根本不在它的协议里）；声明了名字却一个参数都不带的客户端，逐字节得到今天的身体——参数是开关，能力只是允许使用开关。没有新增第二条测量路径：页按行数而不按字节约束，它的上限用的是名册 delta 窗口本来就保留的那个（`ROSTER_DELTA_MAX_ROWS`），而名册靠省掉成员来变小，而不是去测量一个帧。紧凑页与 `since` 令牌是两个不同问题各自的答案，同时出现时以 `invalid-args` 拒绝，因此不会有客户端以为自己握着一份从未发给它的增量。在一份合成的 663 行名册上实测（id、工作目录、毫秒时间戳与谱系；标题为空，两侧同等付费，所以省下的是下界）：今天 100470 字节，第一次紧凑列出 70143 字节，客户端已握有时间戳后重复同一列出 52905 字节，一屏 100 行 8024 字节。
- **快照可以只回答重连错过的部分，minor 因此到 10。** 真机 iPhone 上测到：一次重连会把整份会话基线（一次 `session.snapshot`）重新付一遍，代价 0.86-1.06 s，一次运行里发生了五次，说明那几秒每次都是同一批字节，而不是五批不同的字节。`session.snapshot.since.v1` 是这次裁剪的名字，而它要两半同时成立才出现：能力，以及请求里的 `sinceSeq`。`session.list` 已经能对桥自己保存的集合做差，但快照没有可保存的 token——客户端唯一持有的持久锚点，是上一份快照报出的 `lastSeq`——所以这个参数是持久事件 seq，而不是本连接的信封序号，桥据自己当前握着的 follow 窗口判断，而不是凭对另一条连接的记忆。连续性是证明出来的，绝不假设：只有当前窗口最旧那条 entry 的 seq 小于等于 `sinceSeq + 1`、或窗口为空时，才给增量；其余情况回普通基线，另加 `mode:"full"` 与 `reset:true`，而不是给一份带着看不见的洞的 delta。证明读的是未裁剪的窗口，因此声明了 `session.snapshot.trim.v1` 的客户端，有时会拿到一份本可用增量代替的 reset——reset 在两种情况下都正确，反过来则不然。装不进一帧 10 MiB 的增量走同一条 reset 路径而不是拒绝，因为客户端从洞里恢复靠的就是这个标志。被否决的方案：按连接缓存 delta（桥不为断开的客户端持有状态，进程重启后第一次重连要付两遍）；在增量上加 `hasMore`（装不下的 delta 不是一页，分页已经有主）；以及让能力单独决定应答（客户端在刚接受这个名字、还没维护 `lastSeq` 的那段时间会丢掉整个窗口）。
- **fork 的切点属于宿主，因此桥只转发切点、别的都不解释。** `hello` 回 `minor:11`（本通道把 10 提到 11）并公告 `session.fork.v1`；它背后 `session.fork` 把 `{sessionId, atSeq?}` 作为宿主 `session/fork` 唯一的 `request` 参数送出，再把宿主自己的 `SessionForkValue` 原样回给客户端。切点是宿主的词表，不是本桥的：`atSeq` 是包含式的源事件 seq，省略即最新一个已完成轮，而宿主自己打开的切点由它写下的合成收尾事件收口——因此客户端从没给过的 `atSeq` 就不出现在线路上，而不是在这里被补一个、悄悄挪动切点。桥真正承担的是那道本该由宿主花一次调用才会给出的形状校验：不是非空字符串的 `sessionId` 与不是正整数的 `atSeq` 在任何网关调用之前就以 `invalid-args` 被拒；其余的一切——宿主不肯 fork、某个会话它不肯 fork、一个敞开的切点——都带着宿主自己的 `code` 与 `msg` 穿出，没有错误码的失败以本桥的 `internal` 穿出。方法只在能力名之后存在：在它之前写下的客户端收 `unknown-method`，也不会因为它向宿主发出任何请求。它取的号是 11：本通道与快照增量通道都从 9 切出，增量先落在 `dev` 上取走 10，后落地者顺提——minor 数的是这份协议追加了几次，而不是分支写下的先后，因此没有任何冻结名字或既有能力被挪动。
- **`hello` 也公告已挂载扩展所要求的能力，且这份清单每次握手现算。** 答案取 `SERVED_CAPABILITIES`，其后跟上扩展注册表里各表所门控的去重、非空能力名（`RemoteBridgeRegistry.capabilities()`，升序），两边都知道的名字只出现一次。没挂任何扩展的桥回的仍是它一直回的那份清单，逐字节相同——本协议的名字保持原有顺序在最前——而桥建好之后才挂载的插件对下一条连接已经可见，因为这里没有任何东西在构造时被冻结；撤下的表会把它的能力名一起带走，除非还有别的方法要求它。公告某个扩展的名字不动 `MINOR`：那个数字数的是这份协议的追加，而插件的能力是插件自己的。为「不门控任何方法」而刻意不在 `SERVED_CAPABILITIES` 里的能力（例如 `approvals.v1`）仍然不在其中，直到某张注册表要求它。这补的是一个真实的缺口而非纸面上的：看板插件早已注册 `board.v1` 与其方法，`hello` 却只回静态清单，于是读握手的手机会判定这台宿主不提供 Tasks。另一种做法是把这个名字写进 `SERVED_CAPABILITIES`，否决的理由是那个常量不携带任何它并非作者的业务词表。

- **一页的 `hasMore` 数的是 entry，而且只回答它被切自的那份投影——所以开帧窗口自己那一刀不折进来。** 真机 iPhone 上这个字段回了 `false`，而那次预期是一个 `seq` 已到 510 的单超大回合会话在 95 行之后该说「还有更早」，客户端于是把「加载更早」的入口藏了起来。对着代码与一个用例核实过，而不是照着报告假设：`pageTurns` 切的是 `flat`，也就是摊平后的 `{turn, entry}` 对，所以 `start > 0` 的含义本来就是「漏掉了一条更早的 entry」，从不是「漏掉了整个回合」——20 条 entry 的单回合对着 512 KiB 默认预算回 12 条 entry 并带 `hasMore:true`，`tests/snapshot-page.spec.ts` 把它钉住。仍可能回 `false` 的是另外那一刀：`session/follow` 按 `maxMessages: 200` 打开宿主窗口，宿主在开帧上给出自己的 `hasMore`，而 `#baselineAnswer` 并没有把它折进来。按 §9.5，这是既定应答而不是缺陷：这个字段承诺的是「这份应答被切自的那段里还有更旧的内容」，而当一页已经装下「本身就是最新一段」的窗口的每条 entry 时，它没有更旧的东西可给；给出 `true` 而身后没有一页，正是唯一会成环的形状——从同一窗口切片的 `session.history` 在那窗口最旧那条 entry 之下回的是 `{turns:[], hasMore:false}`。窗口之下的持久历史属于 `session.history.deep` 的问题域，因为它读的是存储、并把存储自己的 `hasMore` 折进去；想拿到窗口之外的「加载更早」入口的客户端应该去那里问，而不是把这个字段读成「会话到此为止」。被否决的方案：把窗口标志折进这一页（等于承诺一页桥给不出、并递回一个兑现不了的游标）；以及把 `start > 0` 读成回合级（真机报告最初的判断，但这个索引走的是 entry）。

- **基线读取由一条自首帧以来没有再前进的流来回答。** 开流窗口是一个时刻而不是状态：连接为每个会话保存一条 `session/follow` 流，并一直用这条流开流时的窗口回答 `session.snapshot` 与 `session.history`，于是在这条流上又跑了一轮的会话，拿到的是开流那一刻的窗口——真机上同一条连接在收到 `seq=467` 之后仍答 `turns:[] lastSeq:3`，换一条新连接则答 `turns:1 lastSeq:21`。订阅现在记录首帧之后是否还有帧到达（`Subscription.advanced`，由 drain 在拿到帧时置位）：没有前进的订阅照旧被等待并复用，静默会话因此仍然只开一条流，读多少次都不多开；已经前进的订阅先中止它的 drain、从连接上摘除，再开一条新流，用它自己首帧的 cursor 作答。只有已经前进的流会被作废，所以每个 `session.snapshot` 与 `session.history` 的答案都来自一个不比其订阅自身推移更旧的窗口。

## Testing

增量快照在连接层有覆盖（`tests/snapshot-since.spec.ts`，7 个用例）：什么都没声明的客户端带着 `sinceSeq` 请求时拿到今天的字节，且不新增任何增量字段；声明了能力但不带水位的客户端同样拿到今天的字节；水位落在窗口内时，应答是水位之上的 entry，形状就是基线自己的回合形状，带 `mode:"since"` 与 `reset:false`；窗口已经滚过该水位时，应答是整份基线另加 `mode:"full"` 与 `reset:true`，字节恰好是今天的字节加上这两个字段；窗口里一条 entry 都没有时，应答是空增量；越过一帧的增量回落到同一条 reset 路径，而不是拒绝。体积问题钉在一个合成的、仿真的 24 回合会话上：192 条持久 entry，其中 96 条会被渲染；整份基线 569876 字节，替换它的重连增量 23835 字节，即重连只为最后一个回合付费，而不是全部。

存活截止时间在连接层用假时钟覆盖：什么都没答的对端在 ping 之后一个 `LIVENESS_TIMEOUT_MS` 以 `CLOSE_LIVENESS_TIMEOUT` 关闭，并留下一条点名它的日志；每轮都应答的对端连续三个周期保持连接，且每次应答后都过完一整个截止时间；与 pong 无关的入站帧与 pong 一样满足截止时间。

基线的时效性由 `tests/session.spec.ts` 覆盖：在连接自己那条流上又跑了一轮的会话，由第二条流带着最新窗口与它自己的 cursor 作答；而保持静默的会话仍然由它开的那一条流作答。

## Alternatives considered

- **每次读基线都重开一条 follow 流，或就地刷新订阅已持有的窗口。** 两条都被否决：前者让静默会话为每次读取付一条流，而那正是这条连接要守住的复用；后者不是 harness 提供的能力，`session/follow` 的窗口在开流时确定，已经开着的流无法从首帧重开。

- **跨中继回放浏览器凭据。** 依同级 note 已落地的证据否决：宿主浏览器鉴权 cookie 与浏览器访问过的 `host:port` 绑定且没有 loopback 豁免，代理重发到 `127.0.0.1` 会被拒；`dsh-remote-web-ui` 之所以能转发调用，是因为它自行兑换过一次 launch token 并持有活着的配对设备 cookie。原生客户端两者皆无，因此这条路会迫使桥自造并持有浏览器会话——为一段用户从未打开的会话建一个凭据库。
- **给 `dsh-remote-web-ui` 加一个签发方法。** 否决：那会把两个包的生命周期绑在一起，让一条面的鉴权依赖另一条的配置与名册格式。桥的全部意义在于原生客户端不需要安装浏览器插件；同级 note 自己的边界是浏览器通道用进程凭据重发调用——那道缝不能变成通用签发器。
- **建立在官方 `/api` HTTP 面之上。** 否决：它把宿主自身的鉴权与 SDK cohort 的端点名变成桥的兼容性契约。同级 note 记录到本 cohort 上运行时并不发出 `api/gate` 缝，因此从远程 origin 直接打 `/api` 只受宿主围栏加上浏览器已兑换的那份 cookie governing——一种桥既说不清也管不住的信任姿态。
- **复用浏览器通道的 WebSocket（`/remote/api/remote.mux`）当传输。** 否决：那条 socket 是官方客户端多路复用的 Typert 连接，代理它等于把第二套协议塞进一条门禁按「已配对浏览器」定义的通道里。桥用自己那套信封，对只懂这套信封的客户端讲话。
- **把配对面板放进 `dsh-remote-web-ui`。** 否决：那个包的面板签发的是浏览器路径自己的配对链接，其凭据是配对设备 cookie——另一种密钥，生命期不同，背后的名册也不同。把本包的一次性 token 渲染到那里，会迫使两份名册与两条吊销流程保持一致，而上面划出的包边界存在的意义正是避免这种耦合；让同一侧栏座位多一个占用者，两条面就能并排放着而互不共享状态。把面板留在本包内，也让原生路径在 `dsh-remote-web-ui` 缺席时依然可用，而那正是当初造出这个桥要保住的性质。
- **缓存 delta 让重连可以增量续传。** 否决：那会把桥变成一份自带保留策略与投递保证的持久日志，而它服务的客户端群体一次完整基线调用就能恢复。snapshot 路径本就存在，也是诚实的恢复机制；已经落地的增量快照没有推翻这条否决——它读的就是本来也会打开的那个窗口，连接之间什么都不记。
- **像 `dsh-session-log-export` 那样自己读持久化日志。** 在地址修复之后否决，因为地址修复已经消除了这个需要：解析 `session.v4.jsonl.zstd` 会让桥去拥有一套本属于宿主的压缩格式与磁盘布局，会让客户端拿到与实时流对进行中回合不一致的第二份事实源，而且换不到持久地址给不了的东西——委派地址就是通过普通会话所用的那条 follow 流，把子会话的整份日志取回来。
- **新增一个 `subagent.events` 方法，或一个 `subagent.*` 主题，承载子会话自己的过程事件。** 否决：父流本来就是桥在跟随的持久日志，子会话的出现只是手机已订阅的那条流里的一条事件——再加一个方法意味着多一条要打开、分页、关闭、授权的订阅，多一个要推进的游标，还有第二处回答"这个子会话还在跑吗"。线路上只加一种 delta；子会话的内部通过本来就存在的那条 follow 流读取。
- **把子会话的增量镜像进父流。** 否决：那会让父会话的日志成为另一个会话内容的权威，把两个会话的 turn 与 step 计数器塞进同一条 delta 流（客户端再也分不清一条 `turn-end` 属于哪个会话），并让一个会话的帧预算乘以子会话个数——无论中继那一跳还是客户端的单条订阅都不是按这个规模设计的。展开的线程订阅子会话，拿到的是任何会话都给的那套帧；收起时零成本。
- **对一个已配对客户端点名的任何会话 id 都放行跟随。** 否决：配对授权的是"你能用这台宿主"，不是"帧里写哪个 id 就读哪个"，而父会话无人解析的子会话 id，恰恰就是这道闸门要挡住的读取通道。放宽的那一格是有意做窄的——只在调用方已被授权的会话下面一层——并且只沿着调用方真正走过的路径生长。
- **用宿主自己的 `session/page` 来实现 `session.history`。** 考虑过，最终否决，改为对开帧基线分页。`session/page` 数的是 `maxMessages` 而不是字节，512 KiB 的分页预算仍然要由桥来执行；它需要的 `throughSeq` 只有 follow 开帧才提供；而它返回的记录可能从一个回合中间开始，靠它们重建回合外壳，就只能编造或省略该回合自己的 `seq`、`endSeq` 与 `reason`。开帧基线是唯一已经带着这些字段的来源，这也正是一页与一次快照永远不会互相矛盾的原因。 上面那条深历史决定并不是对这一条的推翻：它用 `session/page` 服务的是**新**方法——字节预算仍归桥、`throughSeq` 来自投影水位而不是 follow 开帧、存储返回的页由同一份共享投影重建回合外壳——而 `session.history` 本身仍旧对开帧基线分页。
- **改为发布 `job/list` 那条 Remote 流，而不是读 registry。** 否决：`JobListRequest.sessionId` 必填，那条端点只服务「一个会话的设防集合」，完全服务不了 unowned scope——那里没有会话可点。读 `ctx.jobs` 用一道缝、同一个权威就服务了两个 scope；另一条路要么是两条缝配两套订阅模型，要么是塞一个合成会话 id，而「它等价于无主」这件事宿主并没有写进契约。
- **跨会话报一个全局「N 个后台任务」。** 否决：宿主没有这个视图——它两个读都是按 owner 设防的——这个数字只能由桥从 N 个设防读拼出来，而一个没人权威计算过的数字，正是这条通道存在要避免的第二份事实源。手机显示它问过的那个 scope 的计数，要两个就调两次。

- **让宿主算差值。** 否决：宿主根本没有「按连接」这个概念——名册与看板是对任何来问的人作答——让它当差分者，等于把桥的连接账本交给一个并不持有它的服务，还要教两个宿主 API 一套它们现在完全不知道的线路形状。桥是唯一已经握着「上一次发了什么」的那一层。
- **在客户端做差，反正它握着上一份身体。** 按算术否决：客户端要把整份身体下载下来才能做差，而那恰好就是要省掉的开销。而且没有在手机上保留上一份完整集合就做不出 `removed`，那笔内存正是增量想省的。
- **把看板的增量窗口放在看板插件里、按连接 id 索引。** 设计阶段试过后否决：释放一条断开连接的状态需要在插件里再来一套带过期的注册表，而且两个包会各自持有一份 §15 只钉一次的令牌与容量规则。扩展缝改为交给插件 `declares` 与连接自己的 `deltas` 座位，于是机制与其生命周期归桥，看板的词表仍归看板。
- **只要客户端发来任何它被发过的令牌就回增量，哪怕更早的也接受。** 否决：只保留最后一份，更早的令牌指向一个已经不存在的基底，答案只能是对着错的集合做差、或把发过的每一份都留着。回 reset 是诚实的答案，同时也是恢复路径。
- **把省略放在 `session.list.omit-archived.v1` 后面，让什么都不声明的客户端继续收到完整名册。** 否决：能力是公告而非协商，已归档行的字节无论谁问都要付——较老的客户端先付钱再把这些行过滤掉，所以这道闸门只保留成本，只保住「看得到没有 UI 渲染的行」这件事。反过来公告这个事实，客户端就能自己去掉过滤器，而线路不必依赖客户端的版本。
- **继续跳过该行，但把被跳过的 id 加进授权，让已归档父会话的子会话仍可跟随。** 否决：授权一个会话的是名册，把一个名册不再点名的会话重新放进来，会让跟随闸门为没有任何端点发布的 id 作答，而已归档会话会沿着名册不再展示的路径继续可读。子会话在两种做法下都保住谱系，需要父的客户端把父恢复即可。
- **把 `updatedAt` 缩短，而不是省略。** 否决：把毫秒时间戳取整到秒是唯一能用更少字符表达的形式，而那是把客户端握着并渲染的值丢掉；省略已经在每一行没动过的记录上把整个字段去掉了——重连时就是每一行。第二种编码（相对某个基准的偏移）同样否决：它要给每条应答加一个成员、给每个客户端加一条规则，只为在变动的行上省下约 6 个字节，而这份应答的开销根本不在这里。
- **让紧凑页借 `pageTurns` 按字节约束。** 否决：`pageTurns` 切的是回合与 entry，而名册的页是客户端为了填满一屏而要求的行数；对行做字节切分需要第二条测量路径去量一份 `pageTurns` 永远看不到的身体，而这恰恰是本次变更不允许新增的东西，何况这份应答本来就是更小的那一份。
- **让紧凑页同时也带 `since` 令牌。** 否决：两种答复有两个不同的基准——增量是相对本连接上一次发出的那一集，页是相对一个游标——一条应答里同时满足两者，就要两个令牌和两套「客户端的基准」。同时出现的请求以 `invalid-args` 拒绝，于是客户端永远不会以为自己握着一份未发给它的增量。

## Consequences

- **在已经前进的流上读基线要付一次重开，且两条流之间在途的内容不会补发。** 手机已经收到的 delta 不会被撤回，新窗口也覆盖每一条持久记录，但旧 drain 被中止时正在途中的进程内 assistant-stream 分片不会被补发；触发重开的那次回答是整个会话窗口，而这正是读基线的客户端接下来要渲染的东西。

- 现在有两条远程面、两套互不依赖的访问控制：浏览器路径（配对 cookie、`/remote` 通道、`dsh-remote-web-ui` 的名册）与原生路径（设备令牌、`/ios/v1`、桥自己的名册）。吊销其一不吊销其二，这正是有意的分离——也是两个包的 README 各自陈述自己安全模型的原因。
- 本包现在在宿主半区旁边多了一个浏览器半区，方向是单向的：浏览器半区可以读配对路由并渲染它，不能签发、消耗、列出或吊销任何东西。它唯一的 wire 调用，是对一条浏览器配对路径从不提供的路由发起同源 `GET`。
- 桥现在除了 wire 格式还拥有 UI 文案：面板注册了 `remote-bridge` locale 命名空间，并占用 Web GUI 侧栏底部的一个座位，因此它的触发器加入家族的底部行，文案遵循仓库的 zh/en 字典纪律。
- 协议 v1 的方法集冻结为九个客户端方法加一个审批回复：`session.titles` 与 `session.history` 加入了名册、快照、发言与中断这几条方法；桥可能调用的每个 DSH 端点的 wire 布局集中在一张表里（`src/core/wire.ts`），其中还包含三个尚无方法暴露的端点。新方法若把某个参数名写错，会在 gateway 处以 `arguments-invalid` 失败，而不是静默调错形状。子代理线程保持这个数目：它加了一种 delta 与一个可选对象，没有加方法。
- **子会话这道闸门比它生长于其上的地址修复更窄。** 父会话没有任何名册行可解析的被委派子会话，过去是能读的——follow 流只需要子会话自己那一行上的父 id；现在它回 `session-not-followable` 且不打开任何流。客户端把它渲染成解释而不是可重试的失败，而这个代价是有意的：谱系只来自宿主名册，绝不来自帧；名册在每个连接第一次尝试之前读一次；可读集合只沿调用方真正走过的路径、一层一层地生长。
- 桥自己拥有一份持久格式：`$DSH_HOME/remote-bridge/devices.json`。它的形状从上线那天起就是兼容性面；损坏的文件被隔离待查而不是被静默清零，因此「解析失败的名册」永远不会被误当成「没有设备的名册」。
- 丢掉设备令牌的客户端用一枚新的 bootstrap token 重新配对——这是常规恢复路径而非异常路径。整个流程里没有任何一步需要手工改名册。
- token 端点只能从本机触达，同一条链接会写进宿主日志，而配对码本身渲染在配对面板里；那行日志与屏幕上那串码在其 30 秒生命期内都是活着的密钥，README 把它们写在操作者会读到的地方。
- 任务通道只加一个方法、一个主题、一个能力名，不碰任何既有帧：`jobs.list` 是冻结方法集里的第十七项，老客户端从不调它、也收不到 `jobs.changed`（它们根本不会被订阅），而新客户端在老 host 上看到 `capabilities` 里没有 `jobs.v1`，必须把这件事渲染成「不知道」，绝不能渲染成「零个后台任务」。两件写成路径的事有意留在界外：`job.kill` 需要自己的审批故事，`job/follow` 的输出流会给一条只需要计数的面加上字节游标、`lossy` 标记与环形保留。
- agent 通道加两个方法、一个能力名，不碰任何既有帧或主题。它是桥第一次转发一个它说不出形状的宿主请求：发送 `session.create` 的客户端若身体被宿主拒绝，学到的是宿主自己的理由；漏了宿主必需字段，也是从宿主而不是从桥自己的 schema 副本学到——代价是客户端无法在本地校验创建请求，这是有意的，因为宿主的 schema 会跟着宿主走。新客户端在旧宿主上看到 `capabilities` 里没有 `agents.v1`，必须把预设与创建渲染成不可用，而不是渲染成空。
- 紧凑名册是第二个为「开口要的客户端」切字节的身体，也是第一个不需要 delta 窗口就能切的：声明了 `session.list.compact.v1`、要 100 行并用 `after` 续页的手机，为同一份名册付 8024 字节而不是 100470 字节；而什么都没声明、或声明了名字却什么都没要的客户端，收到的仍是协议 v1 自己的字节，不变。为此 `hello` 回 `minor:9`，新客户端在旧宿主上会在 `capabilities` 里看不到这个名字，必须把名册渲染成「不可分页」而不是报错。
- 对每个客户端都变短的协议 v1 响应体只有名册本身，而不只是对那些声明了能力的客户端；什么都不声明的客户端收到的其余答案都没有变化。在重启前对运行中的宿主实测：935 行，其中 346 行已归档，名册 212,426 字节中的 76,608 字节（36%），已归档父会话的活跃子会话为 0——所以上面的跟随闸门收窄在那台宿主上今天没有任何实例，而省下的字节在每一次列出时都会兑现。
