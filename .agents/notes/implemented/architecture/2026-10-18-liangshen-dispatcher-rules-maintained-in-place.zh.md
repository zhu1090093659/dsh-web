# Agent Note: 梁神调度规则在本仓维护，并就地更正

Status: implemented

在[调度者身份](2026-10-10-liangshen-dispatcher-identity.md)之上扩展，取代该笔记「只追加」的编辑规则；与[行为探测](../testing/2026-10-18-liangshen-behaviour-probes.zh.md)配对，规则改动此后由它来度量。

## Problem

调度块最初是一份第三方预设 persona 前缀的逐字副本，保住它诚实的那条规则叫「只追加、绝不折进原文」：本地新增进 `DISPATCHER_RULES_APPENDIX`，参考文本保持与抽取时逐字节一致。那条规则保护的是出处，却在这个块唯一要干的活上失效。

更正不是新增。当参考文本里有一句已经为假，附录条目就让模型对同一个决策握着两条规则，而面对两种解读的会话会取更严的那种，并且从不核对哪一种才是本意。这个块还冻结在 0.24.6，而上游谱系在动：到 2026-10-18，一个真实部署组装出的参考文本已经多了每轮积压扫描、把上限写成上限而不是区间、带单位与累计规则的限额段、歧义限额的逃逸指令，以及「评审中发现的缺陷要么回流要么上交」。冻结副本一条都没有，而仓里没有任何东西能发现这一点，因为唯一的同步机制是维护者手工重读一个 npm 包。

其中两句不只是过时，而是错到了会改变行为：

- R2 断言挂载了 `list_subagent_models` 与暴露 provider/model/reasoning_effort「总是同时出现或消失，所以单信号足够」。工具行与它的参数是静态挂载的，它们存在并不能说明本会话是否记录了 allowlist。真实状态有三种：已列、未列（什么都不拦）、未挂载。
- R8 又把那个读法当成了兜底理由：「allowlist 为空且用户未开启」成了停止委派的许可。在未列状态下这恰好相反——委派可用且什么都不拦——于是规则从一条没人验证过的前提里长出了一条自设限制，并静默降级为单干。

## Decision

这个块是本仓维护的 fork。更正就地应用；新增仍进附录。

- `DISPATCHER_RULES` 于 2026-10-18 从来源包发布的谱系（一个真实 DSH 部署组装出的调度者规则集）重新抽取，于 2026-11-02 按该包的 0.55.0 再次同步，又于 2026-11-03 按 0.56.0 及该包尚未发布的 Agent Teams 改动同步一次，再于 2026-11-13 按 0.72.0 同步一次。现在承载 R0、R-G、R1 到 R9、R-W 与二十三条反模式。
- 2026-11-02 的再同步并入两处上游改动：R9（计划模式管线，做了适配——计划模式是用户的开关：用户开了就在模式内规划，没开就照常规划后执行，调度者从不向用户索要这个模式；本部署没有 `enter_plan_mode` 行，上游那句强制提示也没有搬过来），以及随调度执行守卫一起发布的那组规则——常设子代理契约、报告协议、主控专用工具清单、按影响而非按工作量停手、精简增量任务书、不罚 hand_back、界面 Before/After 证据门、删除测试，与反模式 21 至 25。这组规则的另一半执行面见[调度执行守卫](2026-11-02-liangshen-dispatch-execution-guard.zh.md)。
- 2026-11-03 这一趟并入此后第二处上游改动，也是更大的一处：上游 0.56.0（`138de7a`）把 R1 从「责任清单」改成按「耦合度 × 并行收益」三选一的执行拓扑（Lead-Core / Hybrid / Fan-out），把主控身份改名为 Lead & Dispatch Agent，把 R8 改为相对 R1 现在授权的「计划内直执」来定义，补上 Lead-Core / Hybrid 主干上「先修后交付」的义务，并注明 Harness 0.2.2 起 `[State: Unlisted]` 会话的显式路由仍可能受父路由限制。同一个包随后又按现行的内置 Agent Teams 运行期重写了 R0.5——现行运行期只是在原生子代理工具之上多加一块共享任务板，因此判据只认 `spawn_teammate`，而任务板始终是 R5 任务书之下的记账面，不是第二个调度者。
- 有两条上游内容刻意不带，`provenance.omissions` 连同理由记录在案：`[Dispatch Ledger]` 指向 `dispatch_ledger` 工具，上游 R9 驱动 `enter_plan_mode` / `leave_plan_mode`；本预设两者都没挂。照搬它们等于把每个调度者送去一个只会答「unknown tool」的工具，比一句过时的规则更糟——它在调用处就失败，而不是在规则处。
- 2026-11-13 这一趟按 0.72.0（`64cf068`，先读 0.71.0 的 `f1121c8` 与 `75aeea2`）同步，其中最大的一处是**删除**：上游在 `c182e68` 里整段删掉 R0.5 兼容性闸门，因为 harness 0.2.1-rc.2 已把旧代 Agent Teams 运行期整体移除，判据从此只可能答「缺席」，而这个部署跑的是更新的 harness，闸门在这里同样恒为死重。与代次无关的任务板契约没有跟着消失，抽成常驻的 `[Agent Teams Board]` 段保留。这一趟同时并入 R0 的 L2-Clear / L2-Governed 分档与 `[Execution Economy]`（每步最多两次无实质进展就换招）、G4 的外部先例检索（GitHub 文档与仓库、官方文档、论文、规范）、R6 改名 Lead Acceptance，以及把界面 Before/After 证据门收窄到只针对回归风险的既有视觉改动。删除既不是更正也不是省略，单列在 `provenance.removals`：它在这里跑过，上游把它删了，而没有任何东西替代它。
- 上游在同一次提交（`a1e31bf`）里把自己的 persona 前缀改写成更短的形式：每条规则一句判定，论证性文字删掉。本块采纳的是这种**行文**，不是上游的原文：两个半区各自的分工不变（G7 至 G16 挂在那套分段结构上），而这次压缩过后，本记录里的每一条更正与新增都还在。长度是实打实的成本——这个块随每个请求发出——所以留下来的是判定，不是论证。
- 同一趟把块从 35,447 字符压到约 24,600 字符，约等于每一步 2,700 tokens 的常驻成本；2026-11-13 的同步再压到约 22,200 字符。比上游多出来的部分，正好是上游不承载的东西：本地附录与 R2 的 fork 更正。
- `DISPATCHER_RULES_PROVENANCE` 记录来源包、承继版本、重抽日期、段的清单，每一条就地更正的「被取代的句子 / 替换文本 / 为什么」，以及——自这次再同步起——每一条新增规则与它来自的上游提交，外加每一条刻意的省略与本部署没挂的那个工具。更正、新增、省略与删除分开记：更正替换的是一个错的读法，新增补的是一个缺失，省略两者都不是——它在别处正确，在这里会错，而删除是一条曾经在这里运行、上游把它连同它所描述的处境一并删掉的规则。这条记录就是新鲜度契约：此后任何一次重抽若丢掉某条更正，`tests/minimal-prompt.test.ts` 会红。
- `tools/check-dispatcher-rules.mjs` 是漂移检查。来源包已安装时它逐句比对两份文本并报告差异；未安装时明说并正常退出，因为「不存在」不是漂移的证据。
- 更正是出处记录里点名的五条：R2 的三态、R8 被撤回的理由、R6/R7 记录化的重派次数与每轮扫描、R0/R5 的上限即上限与 [Limits] 单位规则，以及后来补上的一条 R2 fork 更正。原来那句 fork 规则既把该工具禁到「只用于评审」，又声称守卫会拒绝被继承的路由；按原样两句话都不成立。让子 agent 跑在父代理自己那条路由上，是最省的同路由子代理（不欠 route: 行，前缀与 KV 缓存都保住）；而内置断言会跳过被继承的路由——它在调用未指名路由时就提前返回。执行是分层的，所以块里现在明说哪一层管什么：宿主侧守卫可以接管 inherit 型工具，直接拒绝这样的 fork，而且那种拒绝不是子调用靠参数能补救的；无论如何 [State: Listed] 下这次允许清单核对都是模型自己的活。同一条更正还点明了这套设计依赖的邻接事实：一个没挂载路由字段的委派工具就处于 inherit 模式，向它索要显式参数是任何调用都无法满足的拒绝。
- 附录有两条同属此原则：G13 改为引用 R0 当前的措辞（`at most 2 key questions`）而不是已被取代的区间；G16 是新增的——登记的事实是登记那一刻的读数，主体已变的事实必须先重读、落定后撤销，过期锚点比没有锚点更糟，而本预设投射的事实登记簿正是这样一种锚点。违规项 C 覆盖「拿它做规划」。

## Alternatives considered

- 继续只追加，在附录里加一条「本条目取代 R2」。否决：这是同一个双解读问题换了个更好看的标签，而模型没有可靠办法把一条靠后的附录条目排在它与之矛盾的编号规则之前。
- 只重抽、不记出处。否决：更正恰恰是未来的维护者最容易重新推错的部分，没有记录的重抽会静默把它们退回去。
- 保持逐字并把握来源包当构建输入。暂否决：那是一个没有可写 checkout 的 npm 包，把构建钉在它上面会让预设无法离线构建。漂移脚本给出同样的信号而不引入这种耦合。

## Consequences

- 调度会话跑的提示词是当前规则集，而不是一份带年代戳的副本；错误规则在它被读到的地方被改掉。
- 这个块现在是本地文本：上游改动只能经一次有意的重抽抵达，而出处记录与标题清单测试都让这件事看得见。
- 提示词于 2026-10-18 重抽时多出约 4 KB，2026-11-02 再同步又多了约 6 KB，随后被压缩回约 24.6 KB：内容留下，论证性文字没有。长度是这个模式每个请求都要付的成本，所以这个块现在按它的判定内容来写，而不是按它的论证来写。
- 一次重抽现在是两处编辑（常量与出处记录），不再是粘贴一次。

## Testing

- `packages/dsh-liangshen/tests/minimal-prompt.test.ts` 固定块的最后一条反模式、十三个 section 标题的顺序、附录的总述行、出处记录（含两条省略，此后谁把它们抄进来都会红）、2026-11-03 这批标记（Lead & Dispatch 身份、三套拓扑、只认 `spawn_teammate` 的 R0.5、`dispatch_ledger` 的不在场），以及每条更正的两个方向：新句子在、被取代的句子不在。fork 更正由它自己的测试固定：最省同路由那句与欠着的那次允许清单核对必须在，被取代的禁令和它承诺的硬拒绝必须不在。
- `packages/dsh-liangshen/tests/preset-composition.test.ts` 把 persona 的收敛边界钉在「它禁止的那次重复」上，而不是轮数。
- `node tools/check-dispatcher-rules.mjs` 报告与已安装来源包之间的漂移状态。
