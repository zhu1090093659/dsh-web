# Agent Note: Agent squads ship as their own sub-plugin

Status: implemented

## Problem

The family had one place to describe "an agent I start again and again": a task-board card. A card already carries the launch targets such an agent needs — agent preset, permission, model, reasoning effort — and the board's runner already creates the session, pins those targets and records the execution. Reusing the card as the definition was the cheap option: no new package, no new ledger, one surface.

It does not hold. A card is a unit of work with a status lifecycle: it moves across columns, it can be scheduled by cron, it opens a subtask tree, and it settles through an acceptance gate. A member definition has none of those states — it is a reusable launch target whose whole lifecycle is create, edit, delete — so the definition would ride a record whose fields describe executions, and every later ledger migration would keep carrying fields no definition reads. One run would also get two owners: the board's runner writes the execution, a members list would have to write which member the session belongs to, and the second record would disagree with the first across every restart boundary.

The second question arrives with the first member session: where does the member brief go — the first user message, or the session's system prompt?

## Decision

`packages/dsh-agents` is a standalone family sub-plugin. It owns its ledger under `$DSH_HOME/dsh-agents`, seven routes under `/dsh-agents/api`, its own launch order in `src/host/service.ts`, and one sidebar row plus one center page registered through `slots.inject`; its browser half is its own loader entry. The definition/run seam is `src/host/run-gateway.ts`, so the launcher can be replaced without touching the ledger, the routes or the UI. The package ships its own display metadata — `icon.svg` and `locale/{en,ru,zh}.json` carrying `meta.title` and `meta.description` — because the family row mounts the real package name, and the host reader resolves both through that package's exports ([package README](../../../../packages/dsh-agents/README.md)).

The member brief is a system-prompt section, not the first user message. The evidence is in [the member-brief judgement](../../../../packages/dsh-agents/docs/member-prompt.md): the assemble context exposes only the `Agent`, whose identity is the session id, so the brief is resolved per session at assemble time from the members ledger; the section's `text` is a function the prompt assembler calls on every turn, so an edited brief changes the next turn instead of the launch; and an empty section is dropped at render time, which is what keeps a non-member session byte-identical. The same identity survives M2: a teammate is an `Agent` too, so `agent.id` still resolves the brief.

A first user message cannot do any of that. It is frozen into the transcript when the session is created, so a corrected brief would need a new session; it is re-sent on every turn as the user's own instruction, where it can be edited, quoted or mistaken for a command; and it cannot be conditional, so the launch would have to decide whether the user wrote it. That same file states the one place the section loses — a preset that marks its own persona section `complete` is restored as the only section — and records the fallback for that case, per-member materialized presets.

Family membership follows [the family row note](2026-10-19-remote-bridge-in-family-aggregate.md): `packages/dsh-web-all/aggregate.yml` lists `../dsh-agents` in `patchFrom` and in `deps`, so the generator emits insert row `web-ui-agents` with `name: '@linxin666/dsh-agents'` and writes the `workspace:*` dependency. `familyIds` pins the row id from the child's package-prefixed `dsh-agents` to the family's short `web-ui-agents` from the first release, the same trade `dsh-win-bash` records. No tombstone subpath and no `shellNotes` entry exist for this family: a row mounting the real package name has no `web-all/<family>` import left for an older profile to resolve, and the aggregate's `shell-metadata` tree therefore owns the compat subpaths only. The entry is on the running app's critical path rather than a publication step: the desktop profile's bundle row names the repository root package `dsh-web`, whose `dsh.bundle.patch` is this aggregate's `cordis.patch.yml`.

## Alternatives considered

- **Reuse `@deepseek-ai/dsh-experimental-agent-team-profile` unchanged.** Rejected for M1: it is a profile bundle that prescribes one team shape and its own role text, so the family's squads would be an alias over fixed roles; it models neither a member brief nor per-member pinned preset, permission and model, which is the whole content of a member definition here. Its experimental name also buys no stability contract, and M2 needs its source, not its frozen shape.
- **Keep runs on task-board cards.** Rejected: the run would be settled by the board's runner and appear as a card in the board's columns, while the members list would keep the second opinion described under Problem. Scheduling, verification and subtask semantics of a card are inherited by anything that runs through it, and a member launch must not inherit them.
- **Inject the brief as the first user message.** Rejected on the four properties listed under Decision: it cannot change after launch, it is indistinguishable from a user instruction, it cannot be empty-only-for-non-members, and it would make the run gateway fabricate a user turn the user never typed.
- **Materialize one preset per member up front.** Rejected as the default and kept as the documented fallback: a preset per member turns saving a definition into a disk write plus a preset-registry refresh, and deleting a member into asset cleanup, which is too much machinery for the one case it fixes — a preset whose persona section is `complete`.

## Consequences

- The board and the agents plugin keep separate ledgers and separate id spaces. A member session is not a board card, and a board card is not a squad member; neither surface lists the other.
- The aggregate's `lib/` does not inline this plugin's browser half, so changing `packages/dsh-agents/src/client` needs only that package's rebuild, and the aggregate's own bundle stays the compat layer.
- A deployment without the optional agent-preset registry, workspace registry, command dispatcher or live-agent roster still mounts the row; a launch that needs the missing face fails closed with a named code instead of silently degrading. The row's `enabled` switch gates the ledger, the routes and the prompt section together.
- The official agent-team runtime is forked into `src/team/` and `src/tools/` at a pinned baseline ([fork provenance](../../../../packages/dsh-agents/docs/fork-provenance.md)), so a squad runs as a team: one Lead session plus one teammate per member, behind the same `run-gateway.ts` seam, and the member brief section follows teammates without a second injection path. The Team tools install only into sessions this Host started as a squad run, and no native `tool-subagent*` row is ever disabled; both are deliberate deltas a later change must not undo ([runtime deltas](../../../../packages/dsh-agents/docs/runtime-deltas.md)). A second, unrelated tool set covers the definitions themselves: ten model-facing tools (`squads_list`, `squads_read`, `squads_create`, `squads_update`, `squads_delete`, `squad_member_add`, `squad_member_update`, `squad_member_remove`, `squads_run_member`, `squads_run_squad`) register globally with `enabled` in every session and reach the same `AgentsHostService` in process, so an ordinary conversation reads, edits and runs squads without a page open ([definition tools](../feature/2026-10-21-agents-definition-tools.md)). The official bundle is a catalog profile any deployment can enable, and its rows (`agent-team`, `tool-agent-team`, `ui-agent-team`) share no id with this family's `web-ui-agents` row; no profile-scoped assumption carries the aggregate, because a deployment that already serves `agentTeams` keeps that service while the fork — its Team tools included — stays unmounted as a whole ([runtime deltas](../../../../packages/dsh-agents/docs/runtime-deltas.md)), so mounting this row over it does not fail on a duplicate registration.
- `GET /dsh-agents/api/state` carries the agent-preset ids this deployment serves (`presets`), which is what the squad page offers as a Lead preset. The list is one registry read through the same face every preset pin resolves through, it leaves out presets the registry reports unusable, and a deployment whose registry is absent or failing answers without the field instead of with an empty list.
- The session entry points resolve their two optional faces live. The GUI's workspace opener (`uiWorkspace`) and the shared session catalog (`sessions`) belong to other official plugins, so the browser half bridges both with `ctx.inject` plus its `inner.effect` cleanup into one per-instance snapshot (`packages/dsh-agents/src/client/session-faces.ts`) instead of probing `ctx.get` while the row applies, and the page subscribes to that snapshot so a face that appears re-renders it. A provider that mounts after this row enables the actions, a provider that unloads withdraws them, and a deployment that serves neither keeps the actions visible but disabled with a stated reason instead of hiding them - hiding made a load-order accident read as "this member never ran". Neither service enters the row's own `inject` list, because the page must mount on a deployment that serves neither; the two official client packages are declared only as `dsh.client.inject` load-order hints and as devDependencies for the type-only declarations of those services.
- Known limit, shipped as is: a preset whose persona section is `complete` drops the brief for its sessions; the fallback above is the recorded way out.

## Testing

`packages/dsh-agents/tests/member-prompt.spec.ts` pins the injection decision — identity extraction with its field-rename fallback, the latest run per session, no injection after a definition is deleted, an empty section for non-member sessions, and one ledger read per assembly. `packages/dsh-agents/tests/squad.spec.ts` pins the `team:squad` roster text, the squad run record landing before the first message is queued, the Lead-preset refusal, and a squad that pins no workspace running anyway — its Lead session opens and `createSession` is called with no `workspaceId`. The two workspace refusals are pinned one level down: `packages/dsh-agents/tests/service.spec.ts` and `packages/dsh-agents/tests/agent-tools.spec.ts` carry both `workspace-unavailable` and `workspace-unknown`, and `packages/dsh-agents/tests/routes.spec.ts` carries the route-level 409. `packages/dsh-agents/tests/team-runtime.spec.ts` pins the forked runtime's invariants: the `agentTeam` projection at `stateVersion` 4 registered exactly once per mount, the install gate (no Team tool in a plain root session, the full set in a squad-run session), the pin order preset then start then permission and model then checkpoint, and a source scan proving no row, config or source in this package disables the native subagent tools. `packages/dsh-agents/tests/routes.spec.ts` pins the served state body, including the preset list and its absence when the registry is missing. `node scripts/aggregate.mjs --check` pins the emitted row, the `workspace:*` dependency and the absence of a `shell-metadata` directory for this family. `packages/dsh-agents/tests/client-session-faces.spec.tsx` pins the live resolution on a real cordis tree - both faces absent when the row applies, served after the providing fibers mount, withdrawn again when they unload - and the panel's own enable, open and disable over that snapshot. `packages/dsh-agents/tests/apply-inject.spec.ts` pins the mount under an inject-enforcing context: the ledger routes with none of the five runtime faces, the forked runtime once with all five, and an already-served `agentTeams` that keeps the service while neither the fork nor its tools subscribe to anything.
