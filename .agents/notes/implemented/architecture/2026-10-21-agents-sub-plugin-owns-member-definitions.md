# Agent Note: Agent squads ship as their own sub-plugin

Status: implemented

## Problem

The family had one place to describe "an agent I start again and again": a task-board card. A card already carries the launch targets such an agent needs — agent preset, permission, model, reasoning effort — and the board's runner already creates the session, pins those targets and records the execution. Reusing the card as the definition was the cheap option: no new package, no new ledger, one surface.

It does not hold. A card is a unit of work with a status lifecycle: it moves across columns, it can be scheduled by cron, it opens a subtask tree, and its run settles onto the ledger. A member definition has none of those states — it is a reusable launch target whose whole lifecycle is create, edit, delete — so the definition would ride a record whose fields describe executions, and every later ledger migration would keep carrying fields no definition reads. One run would also get two owners: the board's runner writes the execution, a members list would have to write which member the session belongs to, and the second record would disagree with the first across every restart boundary.

The second question arrives with the first member session: where does the member brief go — the first user message, or the session's system prompt?

## Decision

`packages/dsh-agents` is a standalone family sub-plugin. It owns its ledger under `$DSH_HOME/dsh-agents`, eight routes under `/dsh-agents/api`, its own launch order in `src/host/service.ts`, and one sidebar row plus one center page registered through `slots.inject`; its browser half is its own loader entry. The definition/run seam is `src/host/run-gateway.ts`, so the launcher can be replaced without touching the ledger, the routes or the UI. The package ships its own display metadata — `icon.svg` and `locale/{en,ru,zh}.json` carrying `meta.title` and `meta.description` — because the family row mounts the real package name, and the host reader resolves both through that package's exports ([package README](../../../../packages/dsh-agents/README.md)).

The member brief is a system-prompt section, not the first user message. The evidence is in [the member-brief judgement](../../../../packages/dsh-agents/docs/member-prompt.md): the assemble context exposes only the `Agent`, whose identity is the session id, so the brief is resolved per session at assemble time from the members ledger; the section's `text` is a function the prompt assembler calls on every turn, so an edited brief changes the next turn instead of the launch; and an empty section is dropped at render time, which is what keeps a non-member session byte-identical. The section serves the member runs this package launches; a teammate is an ordinary subagent the Lead starts, so it has no run record and this section never resolves it — its brief travels in the Lead's spawn prompt instead.

A first user message cannot do any of that. It is frozen into the transcript when the session is created, so a corrected brief would need a new session; it is re-sent on every turn as the user's own instruction, where it can be edited, quoted or mistaken for a command; and it cannot be conditional, so the launch would have to decide whether the user wrote it. That same file states the one place the section loses — a preset that marks its own persona section `complete` is restored as the only section — and records the fallback for that case, per-member materialized presets.

The collaboration runtime is the deployment's, not this package's: the base bundle mounts `agent-team` and `tool-agent-team`, which serve `agentTeams`, the `team_task_*` board, the `team:policy` section and the `agentTeam` projection, so this package owns no team service, no team tool and no projection. What it adds on top is the whole-squad orchestration: the roster context that tells the Lead who its members are, and the Team-mode switch that makes the native board reachable. A teammate is an ordinary subagent, so its permission is the parent session's permission captured at delegation — the native subagent tool takes no permission parameter — which makes a member's permission a requirement stated to the Lead and a pin only for the member run this package creates itself.

Family membership follows [the family row note](2026-10-19-remote-bridge-in-family-aggregate.md): `packages/dsh-web-all/aggregate.yml` lists `../dsh-agents` in `patchFrom` and in `deps`, so the generator emits insert row `web-ui-agents` with `name: '@linxin666/dsh-agents'` and writes the `workspace:*` dependency. `familyIds` pins the row id from the child's package-prefixed `dsh-agents` to the family's short `web-ui-agents` from the first release, the same trade `dsh-win-bash` records. No tombstone subpath and no `shellNotes` entry exist for this family: a row mounting the real package name has no `web-all/<family>` import left for an older profile to resolve, and the aggregate's `shell-metadata` tree therefore owns the compat subpaths only. The entry is on the running app's critical path rather than a publication step: the desktop profile's bundle row names the repository root package `dsh-web`, whose `dsh.bundle.patch` is this aggregate's `cordis.patch.yml`.

## Alternatives considered

- **Reuse `@deepseek-ai/dsh-experimental-agent-team-profile` unchanged.** Rejected for M1: it is a profile bundle that prescribes one team shape and its own role text, so the family's squads would be an alias over fixed roles; it models neither a member brief nor per-member pinned preset, permission and model, which is the whole content of a member definition here. Its experimental name also buys no stability contract, and M2 needs its source, not its frozen shape.
- **Keep runs on task-board cards.** Rejected: the run would be settled by the board's runner and appear as a card in the board's columns, while the members list would keep the second opinion described under Problem. Scheduling, verification and subtask semantics of a card are inherited by anything that runs through it, and a member launch must not inherit them.
- **Inject the brief as the first user message.** Rejected on the four properties listed under Decision: it cannot change after launch, it is indistinguishable from a user instruction, it cannot be empty-only-for-non-members, and it would make the run gateway fabricate a user turn the user never typed.
- **Materialize one preset per member up front.** Rejected as the default and kept as the documented fallback: a preset per member turns saving a definition into a disk write plus a preset-registry refresh, and deleting a member into asset cleanup, which is too much machinery for the one case it fixes — a preset whose persona section is `complete`.

## Consequences

- The board and the agents plugin keep separate ledgers and separate id spaces. A member session is not a board card, and a board card is not a squad member; neither surface lists the other.
- The aggregate's `lib/` does not inline this plugin's browser half, so changing `packages/dsh-agents/src/client` needs only that package's rebuild, and the aggregate's own bundle stays the compat layer.
- A deployment without the optional agent-preset registry, workspace registry, command dispatcher or live-agent roster still mounts the row; a launch that needs the missing face fails closed with a named code instead of silently degrading. The row's `enabled` switch gates the ledger, the routes, the model-facing tools, the member-brief section, the squad context and the Team-mode switch together.
- The collaboration runtime is the Host's own: `@deepseek-ai/dsh-base` mounts `agent-team` and `tool-agent-team`, which supply the `agentTeams` service, the `team_task_*` board, the `team:policy` section and the `agentTeam` projection (`stateVersion` 7, wire shape `{ enabled, tasks, failure? }`). The 2,991 forked lines and their coexistence gate existed only because this package also wanted to own that service name; with the runtime shipped by the deployment there is no second registration to arbitrate, no gate to keep, no upstream baseline to replay and no unmount decision to make, so the fork and the gate are both gone. What remains here is what the runtime does not do: the ledger, the panel, member runs and the orchestration below.
- A squad Lead's Team mode is switched on by this package, because the native service starts a new root with Team mode off (`defaultEnabled` false) unless a deployment changes that default, and a Lead without it opens with neither the task board nor the team policy. The switch fires when the run record is durable and before the Lead's first message is queued: the Host announces `agent/created` inside session creation, so the record does not exist yet at announce time and a check there can never see the run. The `agent/created` listener stays as the fallback for a Lead announced later. Both paths reach nothing else: a teammate is not a root, and a session the user opened is not recorded as a Lead. A deployment that serves no `agentTeams` service keeps everything else and reports the one capability it lost.
- The roster and the goal reach the Lead as the `team:squad` system-prompt context this package registers at order 125, between the subagent delegation context and the harness source. A context survives a member preset that registers a `complete` section, and the position is held here because the Host's central table names no Team context. Each row carries the member's name, preset, permission (stated as inherited), model and complete brief, followed by the spawn contract — `description` becomes the teammate label, `agent_preset` the preset, `provider`/`model`/`reasoning_effort` the model pin, and the prompt opens with the brief — and by the board contract (`team_task_*`, `blockedBy`, `send_message`, `wait_agent`).
- A member's permission is a declaration for a squad run and a pin only for a member run. The Lead calls the native subagent tool itself, and that tool takes no permission parameter: the child's permission is captured from the parent session at delegation. This package is not in that path, so it has no moment of its own at which to apply a pin, and the roster states the inheritance instead; the member run this package creates itself still applies the pinned permission through the command dispatcher before the first message.
- The live team view reads the Host's `subagentCatalog` projection (`stateVersion` 6) from the shared client session store: the Lead's direct children as `{ id, createdAt, mode, label?, name? }`. The `agentTeam` projection cannot be that source at `stateVersion` 7 — it carries the saved Team mode and the task board only, and its wire shape has no member row. The Lead row is rendered from the squad's own `leadPreset`, a member row joins on the label the roster tells the Lead to set, and a row's status is the Host's `running` flag when the store reports one and the child's mode otherwise. An empty catalog is the Lead before it starts anyone, a deployment with no session catalog is unavailable, and neither polls.
- The proposal route `GET /dsh-agents/api/squad/team` and the browser's polling fallback are gone with the forked runtime they fed: `subagentCatalog` is published by the Host, so there is no host-side proposal to serve and no second live-team source to drift from it. `DSH_AGENTS_ROUTE_PATHS` stays at the eight routes the contract freezes, and `/squad/team` is not one of them.
- A second, unrelated tool set covers the definitions themselves: ten model-facing tools (`squads_list`, `squads_read`, `squads_create`, `squads_update`, `squads_delete`, `squad_member_add`, `squad_member_update`, `squad_member_remove`, `squads_run_member`, `squads_run_squad`) register globally with `enabled` in every session and reach the same `AgentsHostService` in process, so an ordinary conversation reads, edits and runs squads without a page open ([definition tools](../feature/2026-10-21-agents-definition-tools.md)).
- `GET /dsh-agents/api/state` carries the agent-preset ids this deployment serves (`presets`), which is what the squad page offers as a Lead preset. The list is one registry read through the same face every preset pin resolves through, it leaves out presets the registry reports unusable, and a deployment whose registry is absent or failing answers without the field instead of with an empty list.
- The session entry points resolve their two optional faces live. The GUI's workspace opener (`uiWorkspace`) and the shared session catalog (`sessions`) belong to other official plugins, so the browser half bridges both with `ctx.inject` plus its `inner.effect` cleanup into one per-instance snapshot (`packages/dsh-agents/src/client/session-faces.ts`) instead of probing `ctx.get` while the row applies, and the page subscribes to that snapshot so a face that appears re-renders it. A provider that mounts after this row enables the actions, a provider that unloads withdraws them, and a deployment that serves neither keeps the actions visible but disabled with a stated reason instead of hiding them - hiding made a load-order accident read as "this member never ran". Neither service enters the row's own `inject` list, because the page must mount on a deployment that serves neither; the two official client packages are declared only as `dsh.client.inject` load-order hints and as devDependencies for the type-only declarations of those services.
- Known limit, shipped as is: a preset whose persona section is `complete` drops the brief for its sessions; the fallback above is the recorded way out.

## Testing

`packages/dsh-agents/tests/member-prompt.spec.ts` pins the injection decision — identity extraction with its field-rename fallback, the latest run per session, no injection after a definition is deleted, an empty section for non-member sessions, and one ledger read per assembly. `packages/dsh-agents/tests/squad.spec.ts` pins the `team:squad` roster text, the squad run record landing before the first message is queued, the Lead-preset refusal, and a squad that pins no workspace running anyway — its Lead session opens and `createSession` is called with no `workspaceId`. The two workspace refusals are pinned one level down: `packages/dsh-agents/tests/service.spec.ts` and `packages/dsh-agents/tests/agent-tools.spec.ts` carry both `workspace-unavailable` and `workspace-unknown`, and `packages/dsh-agents/tests/routes.spec.ts` carries the route-level 409. `packages/dsh-agents/tests/apply-inject.spec.ts` pins the Team-mode switch on a real cordis tree — `setEnabled(lead, true)` once for a recorded Lead, never for an ordinary session or a teammate, and a row that registers no session projection at all — beside the mount under an inject-enforcing context with none of the five runtime faces and with all of them. `packages/dsh-agents/tests/client-squad-team.spec.tsx` pins the catalog read: a teammate appears without a page reload, an empty catalog reads as the Lead before it starts anyone, a deployment with no session catalog says so once, and a member run keeps its own card. The route list is pinned at eight entries with no `/squad/team` in `packages/dsh-agents/tests/protocol.spec.ts` and `packages/dsh-agents/tests/squad.spec.ts`. `packages/dsh-agents/tests/routes.spec.ts` pins the served state body, including the preset list and its absence when the registry is missing. `node scripts/aggregate.mjs --check` pins the emitted row, the `workspace:*` dependency and the absence of a `shell-metadata` directory for this family. `packages/dsh-agents/tests/client-session-faces.spec.tsx` pins the live resolution on a real cordis tree - both faces absent when the row applies, served after the providing fibers mount, withdrawn again when they unload - and the panel's own enable, open and disable over that snapshot. `packages/dsh-agents/tests/apply-inject.spec.ts` also pins a workspace registry that activates after the row applied reaching both the picker and a pinned run.
