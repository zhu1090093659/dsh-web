# Agent Note: 梁神自带子路由守卫

Status: implemented

扩展[子 agent 模型选择开关](../bug-fix/2026-10-07-liangshen-preset-child-model-selection.zh.md)与[调度规则](2026-10-18-liangshen-dispatcher-rules-maintained-in-place.zh.md)：前者让预设开启子 agent 模型选择，后者把路由纪律写进提示词；本记录拥有这两者都给不了的那层执行；它在委派期的边界与[调度执行守卫](2026-11-02-liangshen-dispatch-execution-guard.zh.md)配对，后者管住同一份组成里的决定口。

## Problem

harness 把会话的已授权子路由记录成一条持久的 `subagent/model-selection-policy` 事件，但它自带的委派工具只拒绝**显式**指定且不在清单内的路由：调用没有点名 `provider`/`model` 时，路由断言在真正比对之前就返回了。而 `subagent_fork` 这类只继承的工具根本没法点名。于是一个允许清单只授权某一族模型的会话，仍会在三种形态下静默地把子代理派到父路由上：

- 不带参数的 `subagent` 调用，回退到配置的子默认值或父路由；
- `subagent_fork` 调用，按设计继承父路由；
- 没有挂载路由字段的委派工具——为旧 SDK cohort 写的组合恰好就是这么挂的——它连被索要参数都做不到。

设置服务拒绝记录空清单，所以真实存在的是「没有策略」与「非空清单」两态；空清单在持久日志里仍可表示，而它什么都不授权。

## Decision

预设多挂一行 `subagent-routes`（`presets/liangshen/subagent-routes.mjs`），在组合作用域里注册 `ctx.tools.guard`：

- **显式模式**（`subagent`）：带策略的会话必须点名一组完整的、已授权的 `provider`/`model`。缺一半、完全没点名、点名了清单外的路由，各有自己的可修正理由，并列出可用路由。
- **继承模式**（`subagent_fork`、`spawn_teammate`）：点名路由一律按越权重路由拒绝，因为那正是该工具存在的意义所在；否则校验继承路由——取调用方最新的请求头，首次请求前回退到创建选项——是否在清单内。拒绝理由会说明子代理无法改路由，并指向能改路由的工具。
- **模式跟着实际挂载的工具走**：守卫问注册表该工具此刻声明了哪些字段，因为配置里的模式只是预设的意图，参数才是运行时事实。没声明路由字段的工具按它将继承的路由执行，绝不被索要一个任何调用都满足不了的参数对。
- **读不到就放行**：缺策略事件、缺会话注册表、注册表答不出工具字段，都留给 harness 自己处理；只有能从持久日志证明的拒绝才会发生。
- 向上找祖先策略只跨越委派缝自己创建的父子链接（`origin: subagent`），无关的父会话不能把它的清单强加给它并不拥有的委派。
- 该行默认开启，可在自身 config 里用 `enabled: false` 关闭，也可覆盖显式/继承工具名。

## Alternatives considered

- 依赖部署侧的宿主守卫插件。否决：梁神是调度模式的复刻，必须自带这项能力；只装了这个预设的部署否则会继续保留守卫本就要堵住的静默继承。
- 只管只继承的工具。否决：不带参数调 `subagent` 与 fork 一样绕开清单，而且更常见。
- 对所有委派工具无条件索要显式参数对。否决：没挂路由字段的工具接受不了，这种拒绝无法被任何调用满足——正是同一周那次预设修复所修的组合缺陷。
- 把缺失的策略事件当成空清单。否决：「缺失」不是「什么都不授权」，而是「本会话没有记录策略」，那样会在每个未配置的部署上制造拒绝。
- 整体复制宿主插件的实现。否决：它带着设置采样、作用域选项、teammate 策略与前缀模型容忍，这些不属于本预设；紧凑移植给预设想真正拥有的行为留一个家。

## Consequences

- 记录了允许清单的梁神会话，再也无法通过上述三种形态把子代理派到清单之外。
- 读不到的事实绝不阻塞委派，所以没有守卫缝的宿主保持 harness 自身行为，预设照常加载。
- 空清单表示什么都不授权，比宿主插件「空即视为未列」的读法更严；设置服务让该状态无法从界面产生，差异只出现在手改日志里。
- 提示词里的 fork 指引在两种部署下都为真：内置断言会跳过继承路由，而这一层不会。
