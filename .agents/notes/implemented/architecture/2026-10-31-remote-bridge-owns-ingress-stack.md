# Agent Note: The remote bridge owns the ingress stack and retires remote-web-ui from aggregate

Status: implemented

## Problem

Remote access for the dsh-web family originally shipped across two separate packages: `packages/dsh-remote-web-ui` (browser Web GUI mirroring via pairing cookie gates, `/api/pair` endpoints, `/remote` proxy routes, and mobile portrait CSS/DOM adaptations) and `packages/dsh-remote-bridge` (protocol v1 WebSocket at `/ios/v1` for native clients). However, the underlying ingress infrastructure — relay identity registration (`relay-registry`), lease claim/release control (`relay-control`), dual quick/named tunnel connectors (`relay-connector`), Durable Object bridge connector (`relay-bridge-connector`), cloudflared tunnel lifecycle (`tunnel`, `tunnel-plan`, `tunnel-orphan`), tunnel ingress port sync (`ingress-sync`), and LAN edge forwarding (`lan`, `lan-bind`, `lan-forward`, `firewall`, `host-bind-capability`) — resided inside `dsh-remote-web-ui`.

This split introduced structural problems:
1. Native clients and the remote bridge depended on network infrastructure owned by the browser-mirroring package, preventing the bridge from functioning as a self-contained remote access stack.
2. The browser-mirroring approach in `dsh-remote-web-ui` incurred heavy security risks (full-control bearer cookies on secondary devices) and maintenance burdens (DOM selectors in `mobile-adapt.ts` drifted with upstream DSH releases), whereas protocol v1 offers typed, hardware-keyed (P-256) RPC/subscription streaming.
3. Completely removing `dsh-remote-web-ui` from the repository at once would break existing user profiles whose `cordis.patch.yml` still references `@linxin666/dsh-web-all/remote-web-ui`, while immediately renaming persisted identity directories on disk would orphan paired devices.

## Decision

The ingress stack is migrated directly into `packages/dsh-remote-bridge`, and `dsh-remote-web-ui` is retired from the family aggregate:

- **Ingress stack relocation**: `relay-registry`, `relay-control`, `relay-connector`, `relay-bridge-connector`, `tunnel`, `tunnel-plan`, `tunnel-orphan`, `ingress-sync`, `lan`, `lan-bind`, `lan-bind-plan`, `lan-forward`, `firewall`, and `host-bind-capability` now live in `packages/dsh-remote-bridge/src/host/`. The bridge manages public and local connectivity in-process.
- **Inbound surface restricted to `/ios/v1` via loopback ingress gate**: A dedicated ingress gate (`src/host/ingress-gate.ts`) binds strictly to `127.0.0.1`. It forwards exclusively WebSocket upgrades targeting `/ios/v1` to the host protocol port (rewriting `Host` to loopback authority); all other HTTP requests and upgrades are answered with `404 {"error":"not-found"}` and closed without dialing upstream. Cloudflare quick and named tunnels target the dynamic loopback port bound by `ingress-gate` (never the harness `webServer` port), and the LAN forwarder targets the same gate port. The Durable Object multiplexer in `relay-bridge-connector.ts` applies the same `/ios/v1` whitelist. The entire exposed surface across all ingress vectors is strictly `/ios/v1`.
- **Browser pairing and mobile web adaptation retired**: The pairing cookie gate, `/api/pair` endpoints, `/remote` proxy channel, and mobile portrait CSS/DOM touch adaptations from `dsh-remote-web-ui` are not migrated into `dsh-remote-bridge`. The bridge's Web GUI panel is display-only for native mobile app pairing codes.
- **Graceful aggregate retirement via tombstone and `retiredPlugins`**: `packages/dsh-remote-web-ui` is removed from `packages/dsh-web-all/aggregate.yml` `deps` and `patchFrom`, so the bundle no longer mounts a `web-ui-remote-web-ui` row. To prevent boot crashes (`ERR_PACKAGE_PATH_NOT_EXPORTED` breaking transactional loader activation) on profiles still referencing `@linxin666/dsh-web-all/remote-web-ui`, the aggregate exports a `tombstone` pointing to its fault-isolation shell, and `remote-web-ui` is registered in `retiredPlugins`. The shell reads this registry and mounts the row as a silent no-op. The package directory is kept for standalone installation during deprecation and scheduled for deletion in the next release.
- **Historical spelling retention for identity paths**: Relay identity files remain under `$DSH_HOME/remote-web-ui-registry/<profile>.json` and connector state under `remote-web-ui-relay-bridge.json`. Retaining these paths preserves operational continuity across plugin migration, preventing token invalidation and broken bookmarks on previously paired devices.
- **Configuration and address resolution**: Settings default to `relay: true`, `autoTunnel: false`, and `lanBind: undefined` (off), configured through profile YAML without a settings UI. The quick tunnel announcer registers the gate URL to the relay Worker when running; when remounting with `relay=false` and an on-disk identity exists, it unregisters the previous registration row and releases its lease once via `pair.release()` (`relay=false` never mints a new identity and has zero side effects if no identity file exists; unmounting neither releases nor unregisters, preserving bookmarked origins for server-side GC); state file `remote-web-ui-relay-bridge.json` persistence is verified behaviorally (defaulting to `$DSH_HOME`, not via source text assertions). Public addresses are decided by `livePublicOriginOf` (bridge/named leases prioritize stable subdomains; quick leases fall back to tunnel running URLs during registration), then fall back to `DSH_REMOTE_PUBLIC_BASE_URL`, and LAN fallback provides an address only when the LAN forwarder is actually listening with its bound address and port (never guessing the first IP in candidate lists, returning no address when stopped; completely eliminating on-disk registry rows as an address fallback).

## Alternatives considered

- **Keep the ingress stack in `dsh-remote-web-ui` and declare it as a dependency of `dsh-remote-bridge`.** Rejected: this would permanently couple the bridge to a deprecated package, prevent removing `dsh-remote-web-ui` from dependencies, and contradict the single-responsibility principle of the aggregate.
- **Port browser cookie gating and mobile touch adaptation into `dsh-remote-bridge`.** Rejected: browser Web GUI mirroring is explicitly sunset in favor of native protocol v1 clients. Porting cookie-based full-control credentials would expand the bridge's attack surface, and porting `mobile-adapt.ts` would preserve brittle DOM-selector maintenance.
- **Point tunnels directly at the webServer port instead of using `ingress-gate`.** Rejected: pointing external tunnels directly at the webServer would expose every harness endpoint, plugin HTTP route, and internal control plane. The loopback-only `ingress-gate` guarantees fail-closed isolation where non-whitelisted paths never reach the upstream server.
- **Immediately delete the `./remote-web-ui` subpath export from `packages/dsh-web-all/package.json`.** Rejected: the DSH loader audits entry activation transactionally; a missing subpath causes an unhandled import error, rolling back the bundle and crashing the entire `dsh web` host during boot. Tombstones and `retiredPlugins` provide zero-downtime backward compatibility.
- **Rename `$DSH_HOME/remote-web-ui-registry/` to `$DSH_HOME/remote-bridge-registry/`.** Rejected: changing the storage path would discard previously minted relay IDs and secrets, immediately breaking bookmarked URLs and requiring users to manually re-pair every existing mobile device.
- **Use the stable subdomain from the on-disk identity file as an address fallback.** Rejected: an identity file only proves that an ID was once minted, not that the Worker row currently points to this machine or is reachable. When quick registration has not yet succeeded, lease claiming fails, or relay is turned off, reading the file would put an unreachable offline subdomain into the pairing QR, and because it took precedence over LAN, local network fallbacks would never be reached. This fallback was completely removed, also eliminating the last data dependency on the legacy plugin's data directory. Also rejected guessing the first IP from candidate LAN interfaces as a fallback: a guessed address may have no active listener behind it, so fallbacks are strictly gated on the LAN forwarder actually listening.

## Consequences

- `@linxin666/dsh-remote-bridge` is completely self-contained for WAN and LAN ingress with zero dependency on `dsh-remote-web-ui`.
- All public ingress channels (quick tunnel, named tunnel, relay bridge) and LAN forwarding expose exclusively `/ios/v1`; plain HTTP routes and arbitrary WebSocket paths are blocked at the ingress gate before dialing upstream.
- Existing profiles with legacy `remote-web-ui` rows mount silently without errors, while new bundle installations no longer install or load the deprecated package.
- Operators using standalone `@linxin666/dsh-remote-web-ui` can continue running it during the deprecation period, but the package is retired from the aggregate and slated for deletion.
- Documentation across the repository reflects the new ownership, pointing to `@linxin666/dsh-remote-bridge` for remote access and clarifying that the legacy browser-pairing surface is discontinued.
- Completely severed the last runtime dependency on legacy plugin data files: pairing addresses are derived exclusively from live state (realtime), environment variables, and LAN literals, without reading disk registry rows.
- **Known risk and rationale for acceptance**: if the deprecated `dsh-remote-web-ui` is installed in the same profile with relay enabled, mounting the new bridge with `relay=false` withdraws the registration row and releases the lease of the shared identity file, terminating the legacy plugin's relay; if both plugins enable relay concurrently, they contend over the same Durable Object connection or overwrite quick tunnel registrations. This risk is accepted because: the legacy plugin is officially deprecated and retired from the aggregate, and documentation explicitly forbids enabling relay concurrently on both; the alternative of segregating identity paths per plugin would mint divergent subdomains during the transition, forcing users to re-pair every mobile device upon migration, which introduces far more complexity than value.
