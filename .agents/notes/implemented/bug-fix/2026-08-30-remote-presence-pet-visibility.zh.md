# Agent Note: 远程在场通过宠物自身的可见性开关隐藏/恢复宠物

Status: implemented

## Problem

手机镜像仍显示宠物：对 `[data-dsh-plugin="pet"]` 的 CSS 抑制依赖精灵位于该根之内，即便修复了 portal，以根为键的 CSS 路径仍是间接手段——用户的要求很明确：远程连接时调用宠物自带的隐藏功能，远程结束时调用显示功能。宠物是主机全局的（无会话维度），所以手机镜像期间页面还把宠物的悬浮气泡画在对话上；而手机应用通过隧道启动需要几十秒，启动页上唯一有内容的就是宠物——看起来像应用坏了。

## Decision

**远程插件现在从在场状态驱动宠物自己的可见性开关。** 新增主机侧链路（`src/remote-presence-pet.ts`）订阅配对快照流：

- 第一个配对设备变为 `online`（阶段 `connected`）时，读取宠物当前显示状态，仅当当前可见时调用 `PetService.setVisible(false)`——与宠物隐藏按钮同一个 RPC。
- 最后一个设备离线超过宽限期（默认 120 秒；在场清扫约 25 秒后把设备翻转为离线，短暂后台的手机不应让宠物闪烁）后调用 `setVisible(true)`——但仅当本链路执行过隐藏。
- 用户手动隐藏被尊重：连接时已 `false` 则不记录、不恢复。宽限期内重连取消待定恢复；第二个设备上线不重复隐藏。

宠物服务在每个转换时经 `ctx.get('pet')` 以结构切片解析（无包间边），任何失败都降级为无操作：远程控制功能从不依赖宠物已安装。CSS 抑制与精灵 portal 修复保留（它们保证表面语义单根），但不再是用户依赖的机制。

## Alternatives considered

- **继续打磨 CSS 抑制。** 被用户否决：可见的失效形态（手机上的宠物与其气泡、看起来空白的启动页只剩宠物）说明 CSS 隐藏太容易被破坏且动作太迟——它无法在启动窗口隐藏宠物（宠物在应用 UI 之前就已挂载）。
- **用宠物的 `enabled` 设置而非 `visible`。** 否决：`enabled` 是插件总开关（停止轮询与整个表面）；`visible` 才是用户所指的"隐藏宠物"，并保留召唤路径。

## Consequences

- 连接会全局隐藏主机宠物（桌面与手机共用一个宠物）；最后一个镜像结束（宽限期过去）后宠物恢复。
- 手机启动窗口内宠物也不出现：设备在门控 mux 打开时即被触碰，早于应用 UI。
- 宠物插件缺席时链路无效；配对流程不变。

## Testing

- 单元（`tests/remote-presence-pet.spec.ts`，5 例）：首台在线隐藏 + 最后离线后恢复、宽限期内重连取消、尊重手动隐藏、无宠物无操作、第二台设备不重复隐藏。
- 实测（QA :3191）：手机连接前宠物显示为 `visible: true`；仿真手机扫码后变为 `visible: false`；关闭手机侧（离线翻转 + 宽限）后恢复 `visible: true`。宠物包：463 测试 / 39 文件全绿；远程包：288 测试 / 26 文件全绿。
