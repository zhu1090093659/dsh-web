# Agent Note：遥测汇总滚存缓存与索引化读路径

状态：已实施

## 问题

tv.dsh-market.com（私有遥测仪表盘）每次访问都返回「502 — Summary upstream
returned 503」。仪表盘 worker 只渲染市场 worker `GET /api/telemetry/summary`
的结果，即市场 worker 的汇总聚合在 D1 上持续失败。

在生产库实测定位根因：`telemetry_events` 没有任何二级索引，九条汇总聚合
每条都全表扫描宽表——遥测上线仅九天（2026-08-24）就已有约 202 万行 / 828 MB，
且每天新增 13-29 万行。心跳侧语句单条耗时 17.7-24.7 秒，九条语句组成的
`env.DB.batch` 事务因此超出 D1 限制，处理器的 catch 把每次失败都归一成约定的
503 `storage-unavailable`。按每天约 7% 的增速，任何一次性修复都会在数周内
再次被撑爆；badge cron 的全表扫描 `COUNT(DISTINCT visitor)` 也在同一轨迹上
（17 秒且每 30 分钟爬升一次）。

## 决策

两层修复——迁移 `0006_telemetry_summary_cache.sql` 加 worker 改动，
2026-09-01 已应用于生产：

- 覆盖索引 `idx_telemetry_kind_day (kind, day, visitor, subject, version,
  channel)`：所有汇总聚合变为索引内扫描（日序列 17.7 秒 -> 0.88 秒）。独立的
  `idx_telemetry_day` 把 30 分钟一次的保留期 DELETE 变成范围探测。
- 汇总滚存缓存 `telemetry_summary_cache`，按精确查询窗口（天数 + 两个分页
  窗口）一行，TTL 30 分钟：新鲜行直接返回（约 0.05 秒）；过期行触发一次实时
  重算并回种；实时聚合失败时无论多旧都回退上一份缓存，与 badge 的陈旧兜底
  同一模式。
- 九条聚合改为四个 D1 batch——一个轻量 chunk（日序列、热门路径、当日活跃、
  渠道）加每个心跳分组扫描各一个单语句 batch——因为即使有索引，整个 batch
  事务仍会超出 D1 限制（43.8 秒的冷调用失败），而最重的单语句约 14 秒。对生产
  数据冷算约 34 秒；只有 cron 和偶发的 TTL 过期需要支付。
- cron 预热（`refreshSummaryCache`）每个 tick 刷新 tv 首屏键（30 天、10 行页）
  加一个范围按钮窗口的轮转槽位（7/30/90/365 天、默认分页）：定时调用在大约
  两分钟处会被终止，每 tick 五个约 40 秒的窗口会死在半路，所以每个 tick 只承载
  约 80 秒的工作。用户点击的翻页偏移按需预热；30 天内窗口 TTL 30 分钟，
  90/365 天窗口容忍 12 小时陈旧。
- 全量 badge 计数迁移到 `telemetry_visitors (kind, visitor)`：心跳写入路径在
  与事件行同一个 D1 batch 里 upsert 加盐访客哈希，迁移回填了存量访客，cron
  现在只对约 17 万行的主键范围做计数（0.02 秒），不再全表扫描。

## 已考虑的替代方案

- 仅加覆盖索引：实测不足——不拆分的 batch 仍超出 D1 限制，且日增速会在数周内
  再次击穿。
- 按（访客 × 条目）事实表让窗口 UV 查询降到 O(subject 行数)：这是终极形态，
  但需要重设计写入路径与回填；等滚存缓存出现真实痛点再做。
- 砍掉 90/365 天窗口：没有必要；随保留期增长，陈旧兜底会让它们优雅降级。

## 后果

- 仪表盘与 API 消费方读到最多 30 分钟陈旧的聚合（badge 已是同样取舍）；/data
  翻页器点击任意偏移的首击在每个 TTL 窗口内可能等待约 34 秒。
- 90/365 天窗口随 400 天保留期增长；当其单语句扫描最终超出 D1 限制时，这些
  窗口会冻结在最近一次成功滚存而不是报错。下一步结构演进是按条目的事实表。
- 迁移与 worker 部署之间的几分钟里，`telemetry_visitors` 缺了一批访客；补跑
  一次回填 INSERT 已闭合缺口，任何残余也会在一天内被每次心跳的 upsert 自愈。
