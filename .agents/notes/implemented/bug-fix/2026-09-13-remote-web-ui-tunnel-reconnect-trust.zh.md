# Agent Note: 配对栅栏在隧道重连期间保留公网主机

Status: implemented

## Problem

issue #1547：打开自动公网隧道后，所有公网请求都返回 403 `{"ok":false,"code":"forbidden"}`，而面板仍显示二维码与其中的地址。隧道离开 `running` 时，相位监听器立刻清空了 `service.publicBaseUrl`，而配对栅栏的受信任主机表恰恰只由这个字段拼成，于是二维码上印着的那个主机不再受信任。连专门为「配对前可调用」而存在的 `GET /api/pair/status` 也一并被拒，面板没有任何说明。

报告者的机制判断是对的。诊断还发现它不完整：命名隧道的主机名由配置固定，已注册中继的子域名也是稳定的，而旧代码在每次重启时都会无理由地丢掉中继基址。

## Decision

`src/public-base.ts` 用一个小的 `PublicBaseKeeper` 统一持有受信任的公网基址。它把 `relayUrl ?? tunnelUrl` 发布给 `service.setPublicBaseUrl`，并按隧道模式处理相位：

- **命名隧道**主机名固定，重连不改变任何东西；
- **中继**注册是稳定的，不再随隧道重启被撤销；只有中继报告 `off` 或整体卸载时才清除；
- **快速隧道**确实会换新主机名，因此上一个主机在有限宽限期（`PUBLIC_BASE_GRACE_MS`，60 秒）内继续受信任，只有到期仍未带着新地址回来才丢弃。Cloudflare 边缘可能仍在投递手机已经建立的连接，而移动网络频繁重连，瞬间丢弃会把手机的这次重试变成静默 403。

`running` 阶段上报的新地址会取消待执行的丢弃；`reset`/`dispose` 在卸载或模式不再持有基址时清空 keeper。

## Alternatives considered

把栅栏放宽到接受 `tunnelStatus.url`：否决。那等于信任一个插件已经宣告死亡的地址，而且受信任列表会出现两个可能互相矛盾的真相来源。

按 issue 的第二条建议在隧道未运行时让面板隐藏二维码：不作为主修方案。它对已经发出请求的手机没有帮助，而重连通常几秒内完成，隐藏地址反而让用户看不到自己正在看的那个地址。面板本来就在二维码旁显示隧道状态，所以请求不再失败之后，状态并不静默。

立刻丢弃主机但返回更明确的错误码：否决。手机无法根据错误码采取行动，而报告者自己的实验表明窗口期内该地址仍然可路由。

## Consequences

栅栏现在会比发布它的隧道多信任一个地址最多 60 秒。在快速隧道模式下这是一次真实且有界的放宽：若某个 Cloudflare 快速主机名被释放并立刻被他人注册，在这段窗口内会通过主机检查——不过配对仍需一次性令牌或既有的设备 Cookie。命名与中继主机没有这种风险；对它们而言这次改动是消除缺陷，而不是增加窗口。`tests/public-base.spec.ts` 钉住了四种行为（命名保留、中继保留、快速宽限后丢弃、新地址取消丢弃）。
