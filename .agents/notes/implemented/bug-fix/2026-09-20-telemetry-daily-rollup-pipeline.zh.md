# Agent Note: 按日滚存让看板窗口始终可算

Status: implemented

## Problem

2026-09-20 tv.dsh-market.com 又只显示冻结序列：7 天视图停在 2026-09-13，30 天视图停在 2026-09-16，而 `telemetry_events` 每一天都在（2026-09-13：123,160 条心跳行 / 21,609 个访客；2026-09-20 当时部分：96,026 / 16,938）。7 天视图渲染的载荷计算于 2026-09-13T06:07Z，即该 UTC 日才过六小时——所以最后一个点显示 7,186 个实例，而当天真实值达到 21,609。

根因正是 [2026-09-16 的决策记录](2026-09-16-telemetry-aux-degradation-and-rollup-freshness.zh.md) 已经记下的终局：每个看板窗口都在事件表上跑 `COUNT(DISTINCT visitor)`，而表已到 4,958,102 行 / 2.9 GB。2026-09-20 21:30 CST 的 cron 日志显示：30 天预热的 `D1_ERROR: out of memory: SQLITE_NOMEM`、渠道分组以 `D1 DB is overloaded` 降级、365 天槽同样被杀；30 天与 365 天的按条目扫描在 D1 API 层直接失败（`internal error 7500`），7 天槽四天里只成功写入一次。只降级辅助扫描救不了看板自身序列所需的核心扫描。

## Decision

所有心跳与页面访问窗口聚合改为读 cron 触发器维护的按 UTC 日滚存表；心跳读路径不再触碰 `telemetry_events`。

- `market/worker/migrations/0008_telemetry_daily_rollup.sql` 新增 `telemetry_rollup_days`（完成游标）、`telemetry_rollup_daily`（每日每 kind 的事件数与去重访客数）、`telemetry_rollup_items`（每日、kind、条目）与 `telemetry_rollup_dims`（每日、kind、条目、维度值）。
- `rollupDayStatements(day)` 是一天重建的唯一出处——三条 delete、五条 `INSERT OR REPLACE ... SELECT` 聚合、最后写完成标记——入参校验为 UTC 日桶，整体作为一个 D1 batch 执行：一天要么完整滚存，要么整体重试，部分完成的那天绝不写标记。
- `refreshDailyRollups` 在每次 cron tick 的汇总预热之前运行：今天与昨天总是重写（昨天的写入可延续到午夜，且重建幂等），随后在 60 秒预算内按由新到旧回填游标仍欠的日期，让看板的短窗口先恢复；被杀的 tick 下次从游标续跑。
- `assertRollupCoverage` 拒绝聚合仍有未滚存日期的窗口，于是 `handleTelemetrySummary` 继续返回上一份完整缓存，而不是发布短序列——只显示一天的序列读起来和丢数据一模一样。
- 日序列、当日活跃数与条目总数按日精确；期间活跃、渠道与版本分布是各日去重计数之和（按日去重求和）。窗口级 `COUNT(DISTINCT visitor)` 需要同时把窗口内每天的访客集合放进记忆体，因此不再保留。看板列名改为「期间活跃」，面板说明写明这是求和。

聚合成本从「天数 × 事件数」降为「天数 × 目录规模」（看板窗口数千行，保留期边界约 8 万行）。

## Testing

- `scripts/market-worker.test.mjs` 通过假 D1 驱动滚存路径：cron 用例钉住遍历顺序（今天、昨天、最欠的新日期）、标记是 batch 最后一条、`idx_telemetry_kind_day` 提示、两个预热窗口与成批的滚存清理；失败的单日被记录而不是中断整次 tick；覆盖门用两个用例钉住——返回上一份缓存，以及无缓存时 503——两者都断言没有任何聚合执行。
- 滚存 SQL 用真实 SQLite 引擎（`node:sqlite`）跑两天夹具：日序列、条目行、渠道/版本行、窗口求和、条目总数与当日查询都与直接聚合一致，重复重建后每一行不变，夹具也复现了文档化的语义差（同一天活跃的实例在区间列里计两次）。

## Alternatives considered

- 加 `(kind, subject, visitor, day)` 覆盖索引并把条目扫描改写成按索引序的 `GROUP BY subject, visitor`：保留窗口级 DISTINCT 语义，但复杂度仍是 O(窗口行数)——正是 2026-09-14 压垮 30 天窗口、2026-09-20 压垮核心扫描的增长。属缓解而非根治。
- 写入路径预聚合 (day, kind, subject, visitor)：在生产表上实测，单日 `COUNT(DISTINCT subject || '|' || visitor)` 为 102,748 而总行数 102,759——事件 id 已按访客 + 条目 + 版本 + 渠道去重，这个粒度的所谓事实表还是那 490 万行。
- 记录真实每日活跃（把日期放进事件 id，每个活跃实例每天一行）能让所有窗口有界，但重复上报从未落库：历史无法回填，日序列会从约 2 万直接跳到真实日活而没有过渡。指标变更不该夹在故障修复里。
- 延长缓存 TTL 或提高预热频率：失败的是聚合本身，TTL 越长只是冻结越久。只滚存条目表、日序列继续扫事件表，等于把看板头条曲线留在失败路径上。
- 用离线回填工具替代 cron 遍历：游标表让定时遍历可续跑、能自愈，且不必维护第二份会漂移的 SQL。

## Consequences

- 恢复是渐进的：今天与欠下的日期每 30 分钟滚存一批，7 天与 30 天窗口在最初几次 tick 内回来，90/365 天窗口等回填走到。窗口日期未齐之前，继续返回上一份缓存而不是短序列。
- 期间活跃变成求和：某实例在 7 天窗口内每天都活跃则计七次，旧的窗口级 DISTINCT 只计一次。生产实测：站点级 7 天 138,489 → 165,481（+19.5%），30 天 500,716 → 691,196（+38%）；日序列、当日活跃数与条目总数不变。
- `telemetry_rollup_items` 每天约增 200 行、`telemetry_rollup_dims` 约 750 行；四张滚存表与事件表用同一个 400 天保留期裁剪，保留策略变动时必须一起改。
- 回填滞后会表现为「陈旧但完整」的看板：新鲜度横幅本来就报告滚存年龄，而任何窗口都不会悄悄发布短序列。
