# Agent Note: teammate names collide for CJK-titled members

Status: implemented

## Problem

运行一次成员标题为纯中文的团队模式级联（`teamRun: true`）时，成员无法完成派生。生物词典项目卡片把六个阶段容器作为六个 teammate 运行，第六个在 251 ms 内被拒绝：

```
teammate provisioning failed: teammate name "subtask-e048c604" was already used in this Team
```

Host 只在 run group 内每个成员都终态后才结算父任务，因此被拒绝的派生让整条级联保持打开：五个子任务的 execution 一直是 `endedAt: null`，父任务等待一个永远无法完成的组，卡片数小时停留在「进行中」列。

根因在名字生成。`teammateName` 用 `[^a-z0-9]+` 清洗标题，清洗后为空时回退到常量 `subtask`，再追加 run group token。纯中文标题清洗后为空串，于是同一次执行里**每个**中文标题成员都产生同一个名字。token 用于区分同一棵树的多次执行，这正是它被加入的原因；但没有任何东西区分同一次执行内的两个成员。该缺陷随中文标题数量放大，而不是只影响恰好撞车的一对：真实数据把六个阶段容器压成五个不同名字，并把某个阶段容器的八个子任务压成六个——其中**三个**都渲染成 `subtask-8dd00e0e`。

## Decision

`teammateName(title, token, memberId)` 现在追加第三个区分量：成员 task id 的 FNV-1a（32 位）摘要，渲染为八位小写十六进制。run group token 仍区分多次执行；成员摘要区分同一次执行内的成员。摘要取自成员身份而非标题，因此标题完全相同的两个成员也能区分，且标题在运行中被编辑时名字保持稳定。

摘要使用内联纯函数而不是 `node:crypto`：`core/subtask.ts` 同时被编译进 client 程序与 host，不能导入 Node 内置模块。名字只需要稳定、分布良好的区分量，不需要密码学强度。

三个调用点都传入 task id：派生调用、Lead 提示词的成员列表，以及提示词自身的回退分支。Lead 提示词与派生必须得出同一个名字，因此它们用相同参数调用同一函数。

## Testing

`host-service.spec.ts` 通过 `TaskBoardHostService` 驱动一次真实的团队执行，使用两个纯中文标题的子任务，断言产生两次派生且两个名字互不相同、均满足服务契约。相对旧实现它会以 `expected 1 to be 2` 失败——两次派生只有一个不同名字——这正是生产故障的端到端复现。`subtask-run.spec.ts` 直接覆盖名字生成：同一成员与同一次执行总是得出同一个名字，标题相同的两个成员保持不同，且每个名字都是 lower-kebab-case、不超过 64 字符、且不为 `lead`，与服务端 `TEAM_INVALID_MEMBER_NAME` 规则一致。

## Alternatives considered

- **追加序号或计数器。** 要求调用方知道每个成员的位置，且只在成员列表不变时才正确；Lead 提示词与派生必须对顺序达成一致，任何编辑后重新推导都可能把一个成员的名字给到另一个成员。
- **改为对标题取摘要。** 能修好中文场景，但无法区分标题相同的两个成员，且标题一被编辑名字就会变化，而 Team 内的名字是不可变的。
- **让回退前缀按成员唯一，例如 `subtask-<id>`。** 对中文标题有效，但会一并改变 ASCII 路径，使每个名字长度不受约束，且对两个清洗后相同的不同标题没有任何保证。
- **把中文标题转写或截断为 ASCII。** 转写是为一个只需唯一的名字引入大依赖做猜测；截断不保证唯一性。
- **让派生失败后用后缀重试。** 拒绝本身就是要消除的故障；重试循环让派生耗时取决于碰撞情况，并把首次尝试记为错误。

## Consequences

- 面向中文标题成员的团队执行可以为每个成员完成派生。对线上生物词典卡片重新推导，六个阶段子任务得出六个不同名字，后续内容与平台发展的八个子任务得出八个，均满足服务契约。
- 名字变长九个字符，因此 32 字符标题 slug 加上 token 再加上摘要仍在上限 64 字符之内；过长的 ASCII 标题仍由 slug 截断兜底。
- 名字不跨该变更保持稳定：已持有旧名字的 Team 不能用新实现重新进入。团队执行总是新建 Lead 会话这条既有规则已保证这一点，旧实现下的残留 teammate 不会与新名字冲突。
- 此前的事故——容器卡在「进行中」列——正是该缺陷造成的记账问题。通过修复账本结算它只消除了症状；本次变更消除了原因。
