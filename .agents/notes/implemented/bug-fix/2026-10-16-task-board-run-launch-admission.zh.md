# Agent Note: run 启动准入给子树的会话突发定界

Status: implemented

## Problem

一次看板动作可以在同一个 tick 里要求 DSH 创建整棵子树的会话。用真实入口对着计数网关实测：一棵 40 子任务的树发出 41 次 `session/create`，同刻并发峰值 41，而且没有任何东西给它定界——本仓没有，运行时也没有：官方子代理包只声明递归深度而没有扇出宽度，宿主 settings schema 里根本没有 subagents 键。本仓实测出的纪律把重型实施子代理限制在 3 个（[多代理资源纪律](../../../../docs/multi-agent-resources.md)），而这条纪律没有任何东西强制。两条派发路径都是这样发火的——普通级联每个成员一个会话，团队执行则把每个成员一次性交给 Lead。

## Decision

一个**服务级**准入队列给两条派发路径上「创建会话的那一半」把关，宽度经一个实时回调读取，因此设置改动对下一次准入即生效。

队列取服务级而不是每个 run group 一个，因为它约束的压力是机器范围的——宿主进程的内存与它驱动的 swap——而两个标签页开出的两个 run group 共用同一个宿主，所以每组一个上限只会把突发乘以标签页数，而不是给它定界。准入在 run group 之间轮转、组内 FIFO，这既让一个组的第一个条目始终是它的根（承载 run shape 与 teammate 名字空间的那次运行），也让一棵大子树无法饿死它之后才开的运行。

一个槽位一直持有到该 launch 的 promise 结算，所以「在飞」的含义是「仍在创建并 prompt 它的会话」；槽位在 launch 启动之前**同步**占用，因此单次 pump 不会超额准入。`runLaunchWidth`（1..16，默认 3，volatile）的唯一事实源在 `src/core/launch-width.ts`，与 `src/core/poll-cadence.ts` 拥有轮询节奏的方式一致。

队列出现之后，有两处细节开始承重。其一，run group 在它第一次准入时**冻结一次**宿主模型目录，并把同一个值交给之后每一个成员（[任务验收本身已于后续移除](../simplification/2026-11-11-remove-task-board-goal-run-and-acceptance.zh.md)）：在会话被 prompt 之前冻结可避免排队中途目录变化只作用于后启动的成员。读取失败不缓存，下一个成员照常重读，与逐执行读取时的行为一致。其二，排队等槽位的时间正是 execution 可能被结算掉的时间——人工 settle，或团队执行按 Lead 的判定收口——因此一个 execution 已经关闭的 launch 会被丢弃，而不是建出一个没人观察的会话。

## Alternatives considered

**每个 run group 一个宽度。** 否决：它约束错了资源。隐患是宿主的内存，而它被每个标签页、每个组共享，因此 N 个组仍会一次产生 N × 宽度 个会话。

**推迟账本准入，让成员分批进入运行列。** 否决：它会破坏 run group 的原子开启以及依赖它的父子结算规则，改动面远大于它所消除的突发。

**全局单一 FIFO 而不轮转。** 否决：一棵大子树会把它之后开启的每一次运行都队头阻塞。

**在 runner 自己的 launch 里加信号量。** 否决：团队执行的成员根本不经过它——它们经 Agent Teams 服务派生——因此两条路径都必须在派发点被覆盖。

**子树超过宽度就拒绝整次运行。** 按请求方的裁决否决：它违背「一个 run group 开启它整棵子树」这一写下来的承诺，会把一张卡片变成部分执行。队列让每个成员最终都会启动，只改变它们何时启动。

## Consequences

子树成员数超过宽度的卡片现在让成员分批启动，因此一个成员可能在它的会话存在之前就已停在运行列里。这是唯一可观察的差异：组仍然开启它整棵子树，单个成员的失败仍然只结算该成员，父任务仍在自己的回合与全部直接子任务都结算后才结算。宿主停止时，仍在等待的成员被结算为 `cancelled`——与下次启动的中断恢复对「从未到达会话的执行」记下的判定相同——而从未到达会话的调度出现次数按会话前条款退款，因此宿主从未真正开始的运行无法花掉运行预算。

## Testing

一个计数网关盖在真实入口上钉住这条界：同一棵 40 子任务的树，原本产生 41 次并发创建，现在峰值等于配置宽度，而 40 个成员仍然全部启动。断言写的是「等于宽度」，而不是「小于未分批的计数」，所以一个仅仅削弱了突发的队列会失败。绕过队列会让新断言中的九条变红，且该绕过已逐字节复原。其余用例覆盖大型组与小型组之间的轮转公平性、成员等待期间宽度被实时调高、排队中被结算的成员此后绝不再启动、单个成员创建失败不会拖住其他成员，以及宿主在成员仍在排队时停止。`pnpm --filter @linxin666/dsh-client-ui-task-board typecheck`、`test`（1119 过 / 1 跳过）、`build` 与 `pnpm i18n:check` 均通过。
