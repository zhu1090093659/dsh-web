# Agent Note: An official plugin update is one official call, and a batch is our sequence over it

Status: implemented

## Problem

On the packaged Desktop client, the update block's batch action could not move any of the third-party plugins it offered. Three shipped facts produced that:

- An application-owned profile has exactly one writer: the official in-process plugin manager the host mounts. The CLI refuses `--profile desktop` outright.
- That manager's only install primitive (0.2.1-rc.2) refuses a package the profile already carries whenever the host mounts `hmr`, which is every profile host, so an in-place update was not expressible as an install at all.
- The shipped workaround ran the replacement as two calls of ours: `removeBundle`, then `installBundle` with our own rollback, our own layer-index restoration and our own single retry of a `bundle-in-use` removal refusal. It worked, but it was this gateway re-deriving a lifecycle the official manager owns, and every refusal it could not clear (the second `bundle-in-use`, i.e. the row is genuinely still loaded in this process) ended the whole run — the browser drove one update job per plugin and stopped at the first failure, which is what the reported `操作失败: 官方插件管理器更新失败: 已安装版本无法移除（bundle-in-use）` reads as.

Since `@deepseek-ai/dsh-plugin-manager` 0.2.2-rc.1 the manager exposes `updateBundle(name, version, { requestId })`: it checks the target on the registry (it must exist, declare a bundle and accept the running DSH version), removes the installed version while the host mounts `hmr`, installs the target with the selection it found, and reinstalls the version it removed when that installation fails or is cancelled. It answers `PluginUpdateResult` — `{ from, to, step: 'check' | 'remove' | 'install', result: ChangeResult, restore?: ChangeResult }` — so the phase that ended the run and that phase's own verdict are both readable. The package's `dsh.engines.dsh` floor is already `>=0.2.2-rc.1`.

## Decision

`CliGateway.runNativeUpdate` makes one official call and reads its verdict, and the batch is this host's order over that same primitive rather than a second writer:

- **One official call replaces the assembled sequence.** `updateBundle` is handed the installed name, the exact version the route resolved and the job id as its `requestId`; `installBundle` and `removeBundle` are no longer called for an update at all, and the `already-installed` branch, the hand-written rollback and the restore-spec bookkeeping are gone with them. `nativeUpdateFailure()` reads the verdict of the phase that ended the run and names that phase (`检查新版本时被拒` / `移除已安装版本时被拒` / `安装新版本时失败`), `nativeUpdateRestartRequired()` reads `application: 'restart-required'`, and `nativeUpdateRestoreNote()` states whether the version the manager removed is back on disk or the person has to reinstall by hand.
- **Two guards stay ours, because the official call does not cover them.** First, the layer index: the official removal drops the name from `dsh.profile.bundles` and the reinstall appends it, and that array is the layer order the loader applies patches in, so a run of updates would drift every row's inheritance; `restoreBundleIndex()` puts the bundle back where it sat. Second, the `bundle-in-use` retry: the official guard deselects the bundle, reloads the profile and only then judges whether the bundle's rows still hold a running fiber, so `applyNativeUpdate()` answers that refusal with exactly one more call against the state the reload left on disk. A second refusal is final: the selection is restored through `setBundleEnabled`, and the report says the plugin is still loaded and to restart DSH before running this update again.
- **A batch is one job, applied in order, that does not stop at a refusal.** `CliGateway.updateAll(entries)` records one row per requested plugin under `GatewayJob.results` (`phase`, `targetVersion`, `landed`, `error`, `restartRequired`) and `current` naming the row in flight; each row runs the same per-plugin path the single update route runs (the official call on an application-owned profile, the CLI everywhere else), and a legacy migration is a row kind of its own. The batch job settles `done` once the last row is answered — the rows carry the failures, because every writer below is atomic per plugin and one stuck plugin must not throw away the ones behind it. A row that landed and needs a restart is a landed row carrying that fact, never an error.
- **`POST /api/plugin-manager/updates` resolves each id before anything runs.** `planUpdate()` is the single route's own resolution extracted, so both entry points refuse the same rows for the same reasons (not installed, not a direct registry plugin, unresolvable latest, already at it, a DSH minimum this host does not satisfy). A refusal becomes that row's `error` in the job instead of failing the request, duplicates are resolved once, and the batch is capped at `MAX_BATCH_UPDATES` (50).
- **The browser makes one call.** The toolbar's `updateAll(ids)` posts the ids once and polls the one job, reporting the row in flight through the same `updatingAll` copy as before; settled rows leave the list, refused rows stay listed with the host's reason rendered in the row, and only a failure of the request itself reaches the alert line. The official installer channel has no batch endpoint, so there the face keeps looping its own single update — the only writer that channel accepts.
- **No fallback to the old sequence.** A manager without `updateBundle` is reported as such (`官方插件管理器没有提供 updateBundle（需要 DSH >= 0.2.2-rc.1）`); the engines floor is the premise, and a second verdict reader kept alive for an unreachable runtime is debt, not safety.

## Alternatives considered

- **Keep the hand-written two-phase as a fallback for a manager without `updateBundle`.** Rejected: `package.json` requires DSH `>=0.2.2-rc.1` in both `dsh.engines.dsh` and the host peer, so the fallback is unreachable; keeping it means two rollback implementations and two ways to read the same verdict.
- **Keep the browser driving one update job per plugin.** Rejected: one request and one job per row, per-row HTTP work in a component, and the stop-on-first-failure policy living in the browser rather than beside the writer that produces the failures.
- **Stop the batch at the first refusal.** Rejected: every writer below is atomic per plugin — the official manager rolls its own failed replacement back — so a refusal leaves a working plugin and no reason to abandon the rows behind it. This was the reported failure's whole shape.
- **Report the refusal and stop (the previous workaround's behaviour).** Rejected earlier and still rejected: the update block exists to move plugins forward, and on the desktop runtime stopping left it permanently decorative whenever one plugin could not be unloaded in-process.
- **Disable the update action when the host mounts `hmr`.** Rejected: that is every profile host, so it disables the feature everywhere to describe one missing upstream primitive.
- **Write the new dependency and run the launcher's bundled pnpm from the host half.** Rejected: a second writer of the same profile — the two would race the lock, the bundle patch application and the reload the official manager performs around a change, and the repository's rule is that a profile has exactly one writer.
- **Confirm with the person before the plugin is briefly uninstalled.** Rejected: the update is already a confirmed, user-initiated action with a visible job, and the manager's own restore leaves a working plugin when the replacement cannot land, so an extra prompt buys risk information the job's own report already carries.

## Consequences

- A desktop update runs as one official call that internally unloads and reinstalls the bundle; a client that keeps polling the one job simply sees a normal in-flight update.
- Failure reporting is wider and more precise than before: the phase that refused is named, the manager's own reason rides along (the pnpm diagnostic, the packages an `incompatible-version` refusal names, a cancellation), and a failed replacement says whether the old version is back or the reinstall must be manual.
- An update that lands but cannot be loaded in the current process reads as exactly that: `job.restartRequired` carries the bundle and both client surfaces say so. The fact never rides `job.error`, because an error row would fail the run and the version really did land.
- A batch update no longer leaves the profile with a different bundle order than the one it started with, so rows keep inheriting from the same layers across a run of updates.
- One refusal in a batch costs one row instead of the whole run, and the panel keeps that row listed with its reason, so "update all" now answers "which of mine are still behind, and why".
- Updates on every non-desktop runtime are unchanged: the CLI path never sees the official primitive, and the CLI's own guards (duplicate-mount stripping, insert-row and boot preflight) stay where they were.

## Testing

`packages/dsh-plugin-manager/tests/gateway-jobs.spec.ts` pins the update path against a scripted manager whose `installBundle` and `removeBundle` throw on purpose, so a test that reaches for the old two-phase sequence fails instead of passing quietly: one call per update with the job id as `requestId`, a thrown call, a folded refusal naming its phase, a green run that moved nothing, the restore clause in both shapes, `restart-required` as a landed fact, the single `bundle-in-use` retry, the persisted refusal with its restart remedy and selection restored, a non-`bundle-in-use` refusal after exactly one call, the layer index the bundle keeps, the cancellation and the incompatible-version copy.

The batch has its own coverage there and in `tests/update-route.spec.ts`: rows applied in order with per-row `landed`/`error`, a run that continues past a failing row, a refused row seeded before the run, a migration as a batch row, a batch with every row refused still settling `done`, the native path on an application-owned profile, and the route's 400/500 cases, de-duplication and per-row refusals. `tests/plugin-list-toolbar.spec.tsx` pins the single call, the per-row failure line, the partial-run copy, the restart-required row still counting as applied, and the whole-request failure. `tests/protocol.spec.ts` pins the tolerant read of the batch rows.

The reproducing rig for the refusal behind this path lives in the DSH checkout, not here: `packages/boot/plugin-manager/tests/manager.spec.ts` boots a real profile Include, a real Loader and the real `hmr` service, which is the only place the official guard can be observed end to end.
