# Agent Note: Task-board event stream stall recovery and pending execution verification

Status: implemented

## Problem

The browser mirror of the task board relies on Server-Sent Events (`/api/task-board/events`) to learn that the Host state has moved. However, an SSE push channel cannot be verified from the browser side: an HTTP stream can stop delivering bytes without either endpoint explicitly closing it (for example, a half-open TCP socket or an intermediary reverse proxy that stops reading or forwarding). In that state, the browser's `EventSource` receives no frames and fires no `onerror` event. The stream remains open and completely silent.

When this silence occurs while an execution is running, the mirror continues rendering the card as "running" indefinitely, even though the Host runner has already recorded the session id, run the task, and settled the execution in `$DSH_HOME/task-board/ledger-v2.json`. The user panel is stuck displaying stale in-flight state.

Furthermore, on the Host side, the event stream handler previously ignored write failures (which Node.js reports solely through the `res.write` callback) and registered no `error` listener on the HTTP response. A dead connection therefore stayed active on the Host, continuing to tick heartbeats into nowhere without terminating the response or releasing subscriptions.

## Decision

Commit `fc590adcc` addresses the stalled stream and unverifiable push delivery through four coordinated mechanisms across the host and client layers, while rules-level contracts are codified in `packages/dsh-task-board/AGENTS.md` under "浏览器镜像与推送":

1. **Host stream teardown on failure (`packages/dsh-task-board/src/host-routes.ts`)**: `/api/task-board/events` wraps every `res.write` call with a completion callback and registers an `error` listener on `res`. Because Node reports broken pipes or write failures only through the callback (its return value indicates backpressure rather than error), any write callback error or response `error` event immediately clears the heartbeat timer, unregisters the ledger subscription, and destroys the HTTP response (`res.destroy()`). This forces the TCP connection closed so that the browser's `EventSource` observes a broken connection and triggers `onerror`.
2. **Resynchronization on connection open (`packages/dsh-task-board/src/client/host-api.ts`)**: `HttpTaskBoardHostTransport.subscribe` hooks `events.onopen` so that every connection establishment or reconnection triggers a state re-read. While the stream emits a connect frame upon opening, a frame whose revision matches the already-mirrored revision would be applied without re-fetching; explicit re-reading on `onopen` turns every reconnect into an authoritative resynchronization point rather than waiting for a subsequent Host revision advance.
3. **Bounded verification for in-flight executions (`packages/dsh-task-board/src/client/pending-verify.ts`)**: Because an SSE pushed frame is inherently unverifiable from the browser side (a silent stream emits neither data nor errors), the mirror must verify the only state that is known with certainty to be transient: open, unsettled executions. While `controller.getSnapshot().tasks.some(hasOpenExecution)` is true, `startPendingVerification` polls the Host snapshot every 15 seconds (`PENDING_VERIFICATION_MS = 15_000`), matching the stream error reconnect cadence. The loop disarms itself immediately as soon as the last in-flight execution settles. An idle board with no work in flight performs zero state reads, strictly preserving the "idle board does not poll" rule. In addition, when the document is hidden (`document.visibilityState !== 'visible'`), reads are deferred until the page becomes visible again.
4. **No in-flight request deduplication in `controller.ts` `refreshRemote` (Decision 2026-10-31)**: `TaskBoardController.refreshRemote()` intentionally does not implement in-flight request collapsing or deduplication for concurrent snapshot fetches. Snapshot application (`acceptRemote`) is already idempotent via monotonic revision comparisons (`snapshot.revision < this.hostState.revision` is safely ignored). In contrast, coarse request deduplication (such as reusing a pending in-flight promise) risks resolving a newer trigger (such as a visibility change or reconnect following a Host update) with a stale snapshot whose request began before that update occurred. The trade-off is that bursts of reconnects or simultaneous triggers may issue concurrent duplicate `GET /api/task-board/state` requests; this overhead is explicitly accepted to guarantee snapshot freshness and correctness.

## Alternatives considered

- **Treat SSE heartbeat comment frames as data frames in the browser**: Rejected. Heartbeats on `/api/task-board/events` are sent as SSE comments (`: ping\n\n`) every 15 seconds to prevent intermediate proxies from dropping idle TCP connections. Under the W3C Server-Sent Events standard, browsers do not deliver comment lines to `EventSource` listeners (they are invisible to the panel application). They serve solely as transport-level keepalives and cannot be consumed as application-level health checks.
- **Unconditional polling on an idle board**: Rejected. Adding a periodic background polling loop regardless of board state would violate the fundamental package rule that an idle board does not poll (established in issue #1821 and `.agents/notes/implemented/bug-fix/2026-10-06-task-board-idle-roster-poll.md`). Furthermore, polling amplifies full ledger reads (loading and serializing the entire task snapshot and scheduler state), wasting Host CPU and disk I/O when no executions are running.
- **Rely solely on `EventSource.onerror` for failure detection**: Rejected. When a TCP socket is half-open or a reverse proxy stalls, no packets are received or rejected. The browser operating system and browser networking stack do not synthesize an error, so `onerror` never fires while the connection hangs in silence.
- **In-flight request deduplication in `controller.refreshRemote`**: Rejected. Coarse deduplication of concurrent `GET /api/task-board/state` calls introduces subtle race conditions where a refresh triggered by a later event (such as `visibilitychange` or `onopen`) attaches to an earlier in-flight request that fetched pre-update state, returning an outdated snapshot. Monotonic revision comparison already makes duplicate responses safe and idempotent.

## Consequences

- Stalled or broken SSE connections on the Host are proactively torn down when writes fail or response errors occur, freeing Node.js timers and ledger subscriptions.
- The browser mirror never remains stuck on "running" when an execution settles during an SSE outage; pending verification guarantees recovery within 15 seconds.
- An idle board with no running tasks performs no verification reads, consuming zero additional HTTP requests.
- Reconnecting streams always resynchronize the full Host snapshot on `onopen`.
- Monotonic revision check in `controller.ts` ensures stale snapshot responses never revert newer client state, while allowing overlapping requests during reconnection bursts.
