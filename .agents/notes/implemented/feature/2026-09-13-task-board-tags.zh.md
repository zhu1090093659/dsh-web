# Agent Note: 看板与经济执行提示中的任务标签

Status: implemented

## Problem

任务看板此前只能用生命周期状态（待规划／待办／进行中／已完成／已失败）给任务分类，因此同时跑十几条跨业务线常驻任务的用户无法表达「这条任务属于哪条业务线」。issue #1521 记录了缺口带来的代价：报告人不得不维护一份横跨任务模型、协议、runner 与客户端渲染的本地 13 文件补丁，而升级时补丁失效产生了最糟的失败形态——旧文件覆盖新版、协议不匹配，看板能渲染却读不到任务。

## Decision

任务行带可选的 `tags: { name, promptPrefix? }[]`。name 是徽章、搜索词与筛选键；可选的 `promptPrefix` 是每次执行前注入到执行 Prompt 之前的一行。字段缺失、前缀缺失、无标签任务，三者都是空操作。

### 模型与上限

- `TASK_TAG_LIMIT` 为 8、`TAG_NAME_MAX_LENGTH` 为 32、`TAG_PROMPT_MAX_LENGTH` 为 200，全部在 `src/core/tasks.ts` 强制。
- `normalizeTags` 负责修复（去空白、丢空名与重复、封顶数量与长度、把空白前缀收敛为「仅展示」）；`isTaskTagList` 负责严格校验。修复用于账本，严格用于线上报文。
- 徽章色调来自 `tagTone(name)`——把名字哈希进固定的六色调色板。每个标签不存任何东西，同一标签也不可能一张卡片一个颜色。

### 线上报文与账本

- `create` 只接受非空且完全合法的 `tags` 列表；`update` 接受合法列表或显式 `null`（表示清空）。空数组不作为清空手段，因为它与客户端 bug 无法区分。
- `parseLedger` 逐条修复该字段，绝不丢任务行（与 schedule、freeze 既有的修复策略一致），因此手改过的账本只会退化标签，不会丢任务。
- 不 bump schema：字段是可选且纯新增，旧版本写出的 v3 文档原样加载，旧版本读到新文档则忽略该字段。

### 执行 Prompt

- `promptText` 在交接前言与任务正文之前插入 `标签提示` 段，逐行列出带前缀标签的 `- [name] prefix`。没有任何带前缀标签的任务，产出的字符串与加入该功能前完全一致。
- 该段位于续接卡片来源声明包裹之外：卡片指令仍留在自己的来源声明之内。
- 前缀与卡片正文共用同一个分隔符转义 helper，因此提示行无法伪造「来源声明」标记。

### 看板界面

- 卡片徽章、顶栏多选标签筛选（候选项来自全账本在用的标签，含已归档任务）、同时匹配标签名的搜索，以及新建/编辑表单里的标签编辑器（标签名输入提供看板上已有的标签，并沿用已有标签的执行提示）。
- 多选为「与」语义：增加一个标签只会收窄结果集。
- 新增语义部件 `tag-filter`、`tag-chip`、`tag-badge`，已在同一次改动中记录进 [semantic-attrs-v1.md](../../../packages/skins/skin-center/contracts/semantic-attrs-v1.md)。

## Alternatives considered

**在任务看板设置卡上做标签目录（名称 → 执行前缀）。** 这正是报告人为颜色勾勒的设计，对「只定义一次业务线」也很顺。否决原因是它把功能的一半放进了第二个存储：Host runner 必须在执行时异步读设置，才能回答账本已经能回答的问题；而卡片显示的标签可能与某次运行注入的前缀不一致。把标签留在任务上保持单一权威来源，也让 `promptText` 继续是任务记录的纯函数。「只定义一次」的体验由编辑器承接：输入已在使用的名字时会沿用它的提示。

**把前缀编码进标签名（例如 `work|产物归档到 02-work/`）。** 否决：这会让用户读到的徽章变成序列化的线上格式，而且名字里合法包含分隔符时无处安放。

**每个标签存一个颜色。** 否决：颜色是表现层，却要像数据一样校验与迁移，而且同一标签的两张卡片可能各说各话。哈希进固定调色板不可能和自己不一致。

**把账本 schema bump 到 v4。** 否决：纯新增的可选字段不需要迁移，bump 只会为每个既有账本强加一次原地重写和一次失败模式，换不来任何兼容性收益。

**把标签当作首次执行后冻结的内容字段。** 否决：内容字段冻结是因为它们是「实际跑了什么」的凭证；标签是塑造**下一次**运行的分类——业务线会变，已经跑过的任务必须还能重新打标签。

**按标签分组的看板视图（需求里的「可选」那半）。** 延后，未实现。筛选已经能回答「只看某条业务线」；再加一套看板布局会让渲染路径与响应式 CSS 翻倍，而这套视图目前还没人需要。它随时可以作为同一模型之上的增量加入。

## Consequences

- 无标签任务在每一层都不受影响：相同的 Prompt 字节、相同的线上补丁形状、相同的账本文档。
- 标签在首次执行后仍可编辑，因此不受内容冻结门管辖；编辑只影响后续运行。
- 筛选候选项来自账本而非某份声明，所以某个标签一旦不再被任何任务使用就会从筛选里消失——这是有意为之，也是不存在清理入口的原因。
- Prompt 从此多了一段客户端断言的前言。它受门禁、做了分隔符转义、并位于来源声明包裹之外，但用户写下的执行提示仍能影响该任务的每一次运行——这正是该功能的用意。
- 必需的验证：`tests/tags.spec.ts` 覆盖修复、严格门禁、无标签字节一致、注入顺序、分隔符转义与「与」语义筛选；`pnpm --filter @linxin666/dsh-client-ui-task-board test` 与 `pnpm i18n:check` 是包级门禁。

共享弹窗字段的既有决定见 [task-modal-shared-form](../simplification/2026-08-26-task-modal-shared-form.zh.md)，本次改动扩展了它。
