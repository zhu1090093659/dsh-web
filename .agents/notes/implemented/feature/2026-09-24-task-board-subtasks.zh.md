# Agent Note: 任务看板子任务与父卡派发

Status: implemented

## Problem

看板把每个任务都建模为一张独立卡片。天然可分解的工作——涉及三个模块的迁移、带后续修复的评审、一次发布清扫——只能录成几张互不相关的任务，它们之间的关系只存在于用户脑中。需求是让这层关系成为一等公民：任务可以带子任务，执行它要对整组有个交代。同一条需求也点明了要避免的失败模式：没有任何上限的级联会在每次运行时成倍开启会话，因此默认深度只允许一层子任务，最多可配置到三层。

## Decision

任务行带一个可选的 `parentId`，Host 是这条链接的唯一写入方。部署设置 `maxSubtaskDepth`（1..3，默认 1）限定树深：取 1 时一个任务只能有一层子任务，子任务不能再有自己的子任务；取 2 或 3 则允许更深。`src/core/subtask.ts` 独占父子准入判定、一次运行要接手的派发集合、强制预设、继承解析与历史 run group 的折叠，账本、用例与浏览器交互面都只读这一个模块。

### 父子准入

- 创建时可带 `parentId`；`set-parent` 动作把在看板上的现有任务挂为子任务，或以 `null` 解除关联。两者走同一组判定：父任务必须存在且在看板上、任务不能挂到自己或自己的后代之下、结果深度（父任务深度 + 1 + 被移动任务自身的子树高度）不得超过上限。拒绝就是 Host 错误，绝不静默修补。
- 删除仍有子任务的任务会被拒绝，由用户显式解除关联或删除子任务；归档父任务会一并归档整棵子树，且任一成员存在未结算执行时整体拒绝；恢复任务会同时恢复它的祖先与子树，因此看板上的子任务不会指向已归档的父任务。存在未结算执行的任务也不能被改挂父任务或解除关联：它的链接可能仍是某个运行中 run group 的父指针，移动它会让那个父任务卡住。
- 加载或导入会修复悬空链接（父任务缺失、成环，或父任务已归档而子任务还在看板上），只丢弃链接，绝不丢弃任务行；已经存下的、深于当前上限的链会被保留，因为上限只管新链接，而后代遍历本身已按上限收敛。

### 单卡运行与父卡派发

- `run` 与 `rerun` 只开一条 execution——被请求的那张卡——并在一个恒为单成员的 `runGroupId` 下开启。任何后代都不会被开 execution，子卡也不会因为父卡执行而进入运行列。直接执行某张子卡是同一个操作：无论它是否带父卡、自己是否带子任务，它都是这次运行的 root，它下面的东西也不展开。
- 树里还有活的卡按「自治派发者」执行。「还有活」指存在不在「完成」列、且未归档的后代；`src/core/subtask.ts` 的 `hasOutstandingDescendants` 是强制预设与 Prompt 派发段共同的唯一判定。这时执行在启动时强制改用 `LIANGSHEN_PRESET_ID`（`liangshen`，由 `packages/dsh-liangshen` 提供），按次覆盖、绝不写进卡片的 `mode`，并跳过 session 复用、新开会话。部署没有注册 `liangshen` 预设时 fail closed，卡片上写明缺少该预设；运行 legacy Agent Teams 那一代的部署同样 fail closed，判据是 `LEGACY_AGENT_TEAMS_TOOL` 这一个指纹——该部署上调度预设无法编排（它会停下来等人回复，而无人值守运行永远等不到），因此启动在任何 session 存在之前就被拒绝，卡片携带 `LEGACY_AGENT_TEAMS_REASON`，不会一直停在运行列（issue #2031）。部署的工具注册表读不到时探测回答 false，因此不提供注册表的部署强制行为与从前完全一致。没有未完成后代的卡执行形态与平常一致。
- 派发段按标题、任务 id 与状态列出每张未完成子卡，说明 Host 不为它们开会话，并要求这个会话用 `task_board_get` 逐张读卡、用 `subagent` 按依赖顺序派发（互不依赖的可以并发）、完工前用 `task_board_manage({action:'record-external-outcome'})` 把结论写回。
- 始终没到的结论由 Host 补：父卡自身执行一旦落到决定性判定，未完成集合里仍未回填的后代全部继承该判定，记为一条 external 记录，`initiatedBy` 带 `parent-run:` 前缀，原因写明本卡未单独开会话执行、结论继承自父卡运行。回填幂等——同一 run group 已有 execution、存在未结算执行、或已有更晚终态记录的卡都不动；`cancelled` 的父判定什么都没判，因此什么都不写。
- cron 走同一条路径：到期的卡只开自己的运行，拦住它的仍是单卡门禁（正在运行、权限未确认、额度上限）。
- 这个形态之前的 run group 仍然会被折叠：成员在自己回合结算，存下来的组父卡在自身结果已记录且组内不再有未结算子项时终结（失败优先，其次取消），启动恢复与每次名册轮询都会折叠每个已可裁决的运行。折叠幂等，旧运行不会把看板挂住。

### Agent Team 执行（已退役）

- 当初引入它是为了让一次执行覆盖整棵树：级联给每个成员各开一个会话，五个任务的子树就是一个动作扇出五个顶层会话。一个任务级团队开关改为把子树压平成一个 Team——Host 只启动根，由 Lead 经 `ctx.agentTeams.spawnTeammate` 为其余每个成员派生 teammate，成员由 Lead 的判定统辖，不报结果的 teammate 也无法把这条链永久留在运行列。
- 退役的原因是 teammate 同样一次性全派生，和 Host 自己的启动器没有区别：Lead 无法等一个 teammate 出结果再派下一个，因此有串行依赖的子任务仍按派生当时的顺序跑。它把会话数量减少了，却没有让顺序变对，还给看板的语义多压一层——卡片级开关、团队 provider 配置、依赖可选服务的 fail closed 路径，以及一个在没有 Agent Teams 的部署上什么都不做的详情页勾选框。取代它的是父卡自治派发：只有父卡自己的会话能在决定下一步跑什么之前看到每张子卡的结果，顺序因此归 agent 而不是调度器。
- 整个面都移除了：协议的 create/patch 团队字段、快照里的团队可用性标志、agent 工具的团队运行参数、团队 provider 配置、Host 侧 `spawnTeammate` 调度面。`TaskRecord.teamRun` 只为让旧版本写下的账本还能读——不迁移、不写新值、也绝不改变一张卡怎么执行。
- 账本里已有的 team run group 仍会结算：记录了自身结果的 Lead 会收口 Team 里还挂着的一切，开机折叠按处理任何历史多成员组同样的方式终结该组。这条路径是刻意保留的，旧运行不能把看板挂住。

### 执行目标继承

[思考强度决策](2026-10-11-task-board-reasoning-effort.md) 拥有与模型绑定的档位继承规则。

- 子任务自己的工作区、agent 预设、权限与模型优先；任何一项未设置，就在启动时逐级向上解析到最近的祖先，直至根任务。创建时表单以父任务的工作区、预设与模型预填，权限选择停留在「继承」，卡片只存下用户真正给过的值。
- 继承来的权限取自祖先的有效绑定（含其交接包钉住的权限），并带上该祖先的确认戳，因此已确认高权限卡片的子任务可以直接运行；子任务自己钉住或经交接包携带权限时，仍按自己的确认门判定。确认门判定的是被运行那张卡解析出的绑定：子卡自己未确认的钉住是它自己执行时的门，不再拦住父卡，因为父卡根本不为它开会话。
- 权限只解析、绝不复制：子任务不存继承来的绑定与确认戳，因此解除关联后只是一张普通卡片，而不是一张已确认的高权限卡片。创建时若复制绑定，就不得不连人工确认一起复制，那么一个已确认的父任务就能批量产出可脱离的已确认高权限卡片——创建路径因此不再做这次复制。

### 看板交互面

- 任务详情块展示父任务链接、带状态的直接子任务列表、以父任务执行目标为起点的「添加子任务」表单、关联现有根任务的入口，以及解除关联动作；到达深度上限后，添加控件让位于上限说明，解除关联与关联候选列表都会避开正在运行的任务。「添加子任务」表单的权限选择停留在「继承父任务」，这正是 Host 连同父任务确认戳一起继承该绑定的前提。
- 卡片带子任务徽标（父任务显示计数、子任务显示标记、历史多成员 run group 的父卡还没结算完时显示等待文案），看板顶栏提供隐藏子任务筛选，设置卡把深度上限做成 1/2/3 三选一。深度字段与设置卡其他字段一样是 schema-volatile——Host 的设置写入路径以 volatile 为准入门槛——已提交的修改经 `loader/volatile-update` 到达运行中的行，重新读取引用并通过 `setMaxSubtaskDepth` 应用到在线账本，无需重挂载。浏览器侧的 Host 镜像现在会把部署常量（会话默认权限与子任务深度）带过 SSE 心跳帧，此前镜像会把它们丢掉。

## Alternatives considered

**由 Host 侧级联、每个成员各开一个会话。** 先落地、后否决：整组同时启动，成员之间有串行依赖时，实际顺序取决于准入排到谁，父任务也无法把一个成员的结果喂给下一个。现在父任务自己的会话负责派发，顺序判断就落在能看到结果的那一端。

**只建立父子链接、不做级联。** 已否决：需求明确指出执行一张卡要对它的整组有个交代，一条无人响应的链接只是标签而不是关系。

**在账本里把 run group 做成一等实体，单独一节并配套迁移。** 已否决：execution 上的 group id 加上由 `parentId` 推导子任务，已经回答了监视器要问的全部问题；新增一节只会加深 v3 文档与恢复路径，却没有任何收益。

**深度固定为一层。** 已否决，改为可配置上限：需求允许更深的树，而把取值钳制在 1..3 可以避免错误配置抬高护栏。

**删除父任务时级联删除子树。** 已否决，改为显式拒绝：删除父任务是破坏性操作，应由用户决定子任务的去向，而不是由 Host 猜测。

**把账本 schema 升到 v4。** 已否决：父子字段是可选的增量字段，升版只会让旧版本读到新文档时把它隔离，却没有兼容性收益。

**在看板上单做层级视图或树视图。** 暂缓，未实现：徽标、详情块与隐藏子任务筛选已经回答了首日问题，而第二种看板布局会让渲染与响应式路径翻倍。

## Consequences

- 执行一个任务只开一个会话，就是这张卡自己的。带未完成子任务的卡还会为它派发的每个子 agent 花额度；看板本身不再多开任何会话。
- 父卡片的判定就是它自己回合的判定。从未单独开过会话的子任务以一条写明来历的 external 记录继承该判定，因此读者既知道父卡判了什么，也不会误以为子卡跑过。
- 已在「完成」列的子任务不在派发集合里，因此把子任务逐个跑完再执行父任务只花一个会话，而不是整棵树重来一遍；定时到点同样如此，需要再跑的子任务移回 `todo`（或单独执行它）即可。判定不向上流动：父任务在自己回合结算，从未回报的子任务继承父任务的判定，而不是反过来塑造它。
- 子任务保有自己的执行历史、标签与计划；解除关联或改挂父任务只改变链接。自身计划处于启用状态的子任务结算后回到 `todo`，因此它仍在下一次父任务的派发集合里。
- 父子字段是 v3 账本内的可选增量字段：加入该功能前的文档可原样加载，旧版本读到新文档会忽略 `parentId`。
- 必需验证：`tests/subtasks.spec.ts` 覆盖准入、继承、子树生命周期与派发集合，`tests/subtask-run.spec.ts` 覆盖单卡运行（手动、重跑与定时）、只看被运行那张卡的权限门、Prompt 的派发段、未被动过的子任务继承到的结论、历史团队运行组的折叠与重启恢复，`tests/subtask-view.spec.tsx` 覆盖详情块及其执行提示、关联入口与看板筛选，`tests/run-launch-width.spec.ts` 与 `tests/launch-admission.spec.ts` 覆盖多张卡之间的启动准入，包内 `typecheck`、`test`、`build` 与 `pnpm i18n:check` 为门禁。
