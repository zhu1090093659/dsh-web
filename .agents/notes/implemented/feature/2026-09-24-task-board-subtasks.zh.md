# Agent Note: 任务看板子任务与级联执行

Status: implemented

## Problem

看板把每个任务都建模为一张独立卡片。天然可分解的工作——涉及三个模块的迁移、带后续修复的评审、一次发布清扫——只能录成几张互不相关的任务，它们之间的关系只存在于用户脑中。需求是让这层关系成为一等公民：任务可以带子任务，执行它会执行整组。同一条需求也点明了要避免的失败模式：没有任何上限的级联会在每次运行时成倍开启会话，因此默认深度只允许一层子任务，最多可配置到三层。

## Decision

任务行带一个可选的 `parentId`，Host 是这条链接的唯一写入方。部署设置 `maxSubtaskDepth`（1..3，默认 1）限定树深：取 1 时一个任务只能有一层子任务，子任务不能再有自己的子任务；取 2 或 3 则允许更深。`src/core/subtask.ts` 独占父子准入判定、级联形态、继承解析与延迟结算折叠，账本、用例与浏览器交互面都只读这一个模块。

### 父子准入

- 创建时可带 `parentId`；`set-parent` 动作把在看板上的现有任务挂为子任务，或以 `null` 解除关联。两者走同一组判定：父任务必须存在且在看板上、任务不能挂到自己或自己的后代之下、结果深度（父任务深度 + 1 + 被移动任务自身的子树高度）不得超过上限。拒绝就是 Host 错误，绝不静默修补。
- 删除仍有子任务的任务会被拒绝，由用户显式解除关联或删除子任务；归档父任务会一并归档整棵子树，且任一成员存在未结算执行时整体拒绝；恢复任务会同时恢复它的祖先与子树，因此看板上的子任务不会指向已归档的父任务。存在未结算执行的任务也不能被改挂父任务或解除关联：它的链接可能仍是某个运行中 run group 的父指针，移动它会让那个父任务卡住。
- 加载或导入会修复悬空链接（父任务缺失、成环，或父任务已归档而子任务还在看板上），只丢弃链接，绝不丢弃任务行；已经存下的、深于当前上限的链会被保留，因为上限只管新链接，而级联遍历本身已按上限收敛。

### 级联执行

- `run` 与 `rerun` 为每个参与者——被请求的任务及其在上限内的看板后代——在同一 `runGroupId` 下各开一条 execution，由 Host 服务分别启动。已经存在未结算 execution 的参与者被跳过，不进入 run group。
- 父任务先把自身会话结果记在 execution 上（`ownResult` 与 `ownError`）并保持打开：卡片会一直留在「进行中」列，直到它自己的回合与该组内每个直接子任务都结算。最终判定把自身与子任务的结果折叠起来，失败优先，其次取消，最后成功，并保留第一条失败文本。
- Host 监视器会跳过已记录自身结果的 execution，因为已无内容可查。子任务结算时沿父子链向上，逐个结算已就绪的父任务，重启恢复对没有记录 session 的参与者先取消、再走同一条向上路径。run group id、自身结果与最终结算都会持久化，因此重启后仍能结算延迟中的父任务。
- cron 走同一条路径：到期任务会开启整棵树，若树中存在未确认的高权限绑定，则整棵树作为一个整体被拒绝，计划滚动到下一触发点，原因记入 scheduler error。

### Agent Team 执行（opt-in）

- 任务级 `teamRun` 开关把一次级联从「每个参与者一个会话」切换为「一个 Lead 会话 + 每个参与者一个 teammate」。Host 只启动根任务，随后借助可选的 Agent Teams 服务——用 `ctx.agents.get(sessionId)` 取到 live Lead，调 `ctx.agentTeams.spawnTeammate(leadAgent, { name, description, prompt, context, provider, signal })`——为其余每个成员派生 teammate，并把 teammate 的会话 id 挂到该成员的 execution 上。结算路径不变：既有会话监视器检查挂上的会话，父任务仍折叠自己的直接子任务。
- 子树在这个模式下被压平成同一个 Team，因为只有 Lead 能派生；teammate 名字取「成员标题 slug + run group token + 成员 task id 摘要」。两个区分量各解决一类冲突：token 区分同一棵树的多次执行，成员摘要区分**同一次执行**内的不同成员。摘要必不可少，因为纯中文标题 slug 后为空串，同一次执行里每个这样的成员都会共用同一个通用前缀，第二个派生会被 `TEAM_MEMBER_NAME_TAKEN` 拒绝；标题完全相同的两个成员也由它区分。名字保持 lower-kebab-case 且不超过服务的 64 字符上限。团队执行总是新建 Lead 会话（同一 Team 内名字不可变，复用旧会话会冲突），provider 来自配置项 `teamProvider`（默认 `spawn`）。
- 该模式 fail closed 而不降级：未提供 `agentTeams` 服务的部署会对手动团队执行明确拒绝（计划执行则记录原因）；成员**自己**的绑定高于会话默认值时也会被拒绝，因为 teammate 运行在 Lead 会话内、无法承载该钉住值。继承来的绑定属于 Lead，按 Lead 自己的确认门判定。
- 两种模式都会在启动的提示词里说明本次运行的形态：级联列出它会开启的各个独立会话，团队模式说明本会话是 Lead，并按名字列出每个 teammate 与团队工具。

### 执行目标继承

- 子任务自己的工作区、agent 预设、权限与模型优先；任何一项未设置，就在启动时逐级向上解析到最近的祖先，直至根任务。创建时表单以父任务的工作区、预设与模型预填，权限选择停留在「继承」，卡片只存下用户真正给过的值。
- 继承来的权限取自祖先的有效绑定（含其交接包钉住的权限），并带上该祖先的确认戳，因此已确认高权限卡片的子任务可以直接运行；子任务自己钉住或经交接包携带权限时，仍按自己的确认门判定。确认门判定的是解析后的绑定，所以树中任何一处未确认的绑定都会让整次运行在任何会话启动前被拒绝。
- 权限只解析、绝不复制：子任务不存继承来的绑定与确认戳，因此解除关联后只是一张普通卡片，而不是一张已确认的高权限卡片。创建时若复制绑定，就不得不连人工确认一起复制，那么一个已确认的父任务就能批量产出可脱离的已确认高权限卡片——创建路径因此不再做这次复制。

### 看板交互面

- 任务详情块展示父任务链接、带状态的直接子任务列表、以父任务执行目标为起点的「添加子任务」表单、关联现有根任务的入口，以及解除关联动作；到达深度上限后，添加控件让位于上限说明，解除关联与关联候选列表都会避开正在运行的任务。「添加子任务」表单的权限选择停留在「继承父任务」，这正是 Host 连同父任务确认戳一起继承该绑定的前提。
- 卡片带子任务徽标（父任务显示计数、子任务显示标记、级联父任务延迟结算时显示等待文案），看板顶栏提供隐藏子任务筛选，设置卡把深度上限做成 1/2/3 三选一。深度字段与设置卡其他字段一样是 schema-volatile——Host 的设置写入路径以 volatile 为准入门槛——已提交的修改经 `loader/volatile-update` 到达运行中的行，重新读取引用并通过 `setMaxSubtaskDepth` 应用到在线账本，无需重挂载。浏览器侧的 Host 镜像现在会把部署常量（会话默认权限与子任务深度）带过 SSE 心跳帧，此前镜像会把它们丢掉。

## Alternatives considered

**串行级联：父任务跑完再跑子任务。** 已否决：父任务自身的回合可能很长，子任务也很少逐字节依赖它的结果，而卡住的父任务会拖住整组；最终选择并发开启整组，这也是提出需求时选定的语义。

**只建立父子链接、不做级联。** 已否决：需求明确指出执行任务就要执行整组，一条无人响应的链接只是标签而不是关系。

**在账本里把 run group 做成一等实体，单独一节并配套迁移。** 已否决：execution 上的 group id 加上由 `parentId` 推导子任务，已经回答了监视器要问的全部问题；新增一节只会加深 v3 文档与恢复路径，却没有任何收益。

**深度固定为一层。** 已否决，改为可配置上限：需求允许更深的树，而把取值钳制在 1..3 可以避免错误配置抬高护栏。

**删除父任务时级联删除子树。** 已否决，改为显式拒绝：删除父任务是破坏性操作，应由用户决定子任务的去向，而不是由 Host 猜测。

**把账本 schema 升到 v4。** 已否决：父子字段是可选的增量字段，升版只会让旧版本读到新文档时把它隔离，却没有兼容性收益。

**在看板上单做层级视图或树视图。** 暂缓，未实现：徽标、详情块与隐藏子任务筛选已经回答了首日问题，而第二种看板布局会让渲染与响应式路径翻倍。

## Consequences

- 执行一个任务可能同时开启多个会话：在默认深度下就是每个直接子任务一个会话，每个都像普通 DSH 会话一样消耗 API 额度。
- 父卡片是一个聚合体：它会一直处于运行中直到整组结算，其状态就是整组的判定，因此一个已完成的父任务可能掩盖某个失败子任务的细节，直到用户打开这棵树。
- 子任务保有自己的执行历史、标签与计划；解除关联或改挂父任务只改变链接。
- 父子字段是 v3 账本内的可选增量字段：加入该功能前的文档可原样加载，旧版本读到新文档会忽略 `parentId`。
- 必需验证：`tests/subtasks.spec.ts` 覆盖准入、继承与折叠规则，`tests/subtask-run.spec.ts` 覆盖级联分组、延迟结算、cron 拒绝与重启恢复，`tests/subtask-view.spec.tsx` 覆盖详情块、关联入口与看板筛选，包内 `typecheck`、`test`、`build` 与 `pnpm i18n:check` 为门禁。
