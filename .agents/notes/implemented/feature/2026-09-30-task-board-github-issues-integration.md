# Agent Note: GitHub Issues as Task Board work items with controlled write-back

Status: implemented

The bounded inbound close/reopen extension is owned by [GitHub remote close cycles](2026-10-31-task-board-github-remote-close.md), which partially supersedes this note's earlier local-column-only choice while leaving discovery, labels, credentials and PR lifecycle here.

## Problem

External development teams track epics and deliverables on GitHub Issues, but executing them with local DSH agents previously required manual copy-pasting of prompt text and status reconciliation across browser tabs. Direct bidirectional synchronization between GitHub and an autonomous agent creates substantial security and stability risks: untrusted external issue text could attempt prompt injection or escalate session permissions, API rate limits or network outages could halt ongoing local agent work, and uncontrolled label synchronization could overwrite user labels or trigger unintended issue closures.

## Decision

Implement Host-side GitHub Issue synchronization for the DSH Task Board as an additive external provider extension (`packages/dsh-task-board-github`), carried inside the board's opaque per-task `TaskRecord.integrations` container under the extension's own `github` key:

- **Inbound discovery**: Issues are discovered through two channels and either one selects them: they carry a configured inclusion label (default `dsh`), or they are assigned to the repository's configured login (`@me` resolves to the account the host authenticated as). A selected issue is materialized as a local Task Board card, or reconciled with the existing card of the same immutable identity `{ owner, repository, issueNumber }`; an issue that loses both channels deactivates its card.
- **Authoritative local state machine**: The existing 5-column kanban state machine remains authoritative. The `running` column remains Host-local. GitHub state labels (`dsh:state:*`) are an external projection rather than a secondary state machine.
- **Controlled write-back**: Write-back operations strictly add or remove DSH-owned state and phase labels (`dsh:state:*`, `dsh:phase:pr`). Unrelated user labels (such as `bug`, `security`, `priority:high`, and the inclusion label itself) are never modified or deleted.
- **Execution immutability**: Remote issue title and body refresh the card's prompt and description only before the first execution opens. Once an execution attempt has started, remote updates are stored as updated provider metadata (`remoteTitle`, `remoteBody`), leaving the historical execution prompt unchanged.
- **Templated execution prompt**: the card's prompt is not the issue body. `src/core/prompt.ts` composes it as a pure function of the issue snapshot and the repository configuration: a header naming the issue (reference, link, repository labels with DSH-managed labels and the inclusion label left out), a fixed workflow section (read the repository's agent instructions, work on `issue-<number>` against `baseBranch`, run the required checks, report through `task_board_github_get` + `task_board_github_comment`, never close the issue before its pull request merges, end with a comment instead of inventing changes when nothing is needed), and the issue body verbatim, last, inside an `ISSUE 原文 开始` / `ISSUE 原文 结束` wrap that names the text untrusted. Every delimiter the prompt relies on — this wrap's and the board's own `来源声明` pair — is defused inside issue and model text, so neither can close the wrap early or counterfeit a board declaration. The template is written in Chinese like the board runner's own preambles and carries a file-level `i18n-allow:` marker; it is agent-facing text, not UI copy.
- **Hand edits survive synchronization**: the provider stores `promptHash`, the fingerprint of the prompt it last generated, and regenerates on a sync only while the card's prompt still matches it. A prompt somebody edited carries no fingerprint and is kept by every later sync. A card synchronized before the template existed has no fingerprint; it counts as untouched exactly when its prompt still equals the raw body (or title) the old projection copied, so those cards adopt the template on their next sync and edited ones keep their text.
- **Optional AI analysis, as one section**: the task-detail seat dispatches `analyze` (and `clear-analysis`, `move-backlog`) through the board's generic extension-action channel. The host asks the optional `llm` service — resolved per call, never injected, through `prepareCall` with the public `stream` as fallback — for a JSON object of four fields: goal, steps, acceptance criteria, `needsCodeChange`. The issue reaches the model as delimited data whose closing tag is defused, the reply is extracted defensively and re-bounded by the same normalizer a stored payload passes through, and a failure is typed (`no-model`, `model-error`, `parse-failed`, `timeout`). The route is the request's model, else the repository's `analysisModel`, else the card's pinned model, else the host default read from `session/modelCatalog` through the optional gateway. The call runs in the background because it outlives the board's 15 s action channel: validation is synchronous (not linked, frozen, hand-edited without `overwrite`, already in flight, no analyzer), progress and outcome are written to the card payload (`analysisPendingSince`, then `analysis` or `analysisError`), and a pending marker found at provider start is cleared because the request behind it died with the previous host. The stored analysis carries `sourceHash`, the fingerprint of the issue title and body it was written from; the template renders it under an "unreviewed model output, the original wins" banner only while that fingerprint matches, so an edited issue drops its stale analysis from the prompt without a model call. A result that arrives after the card started executing is kept for the record and leaves the prompt alone (the board's content gate refuses the patch).
- **Deactivation without loss**: Removing the inclusion label marks the local task deactivated, hiding it from the active board while retaining all execution history. Re-adding the label restores the card via the same identity.
- **Host-side credentials & outbound HTTPS**: All GitHub API calls occur on the Host via outbound HTTPS (`api.github.com`). Tokens are resolved from Host environment variables or profile patches and never exposed to the browser or the agent.
- **PR lifecycle & safe closure**: Auto PR creation (default off) or manual creation (`task_board_github_create_pr`) verifies the remote branch exists, creates the PR, records PR metadata, and applies `dsh:phase:pr`. Merging the PR marks the PR merged, clears `dsh:phase:pr`, sets `dsh:state:done`, and conditionally closes the issue if configured. PR closed without merge never closes the issue.
- **Agent-initiated write-back**: `task_board_github_comment` posts one Markdown comment on the issue (non-empty body, at most 16000 characters, an over-long body refused rather than truncated). `task_board_github_close_issue` closes the issue, and is gated on exactly one condition: the card's linked pull request is MERGED. The remote PR state is read at close time rather than trusting the cached flag, so a PR merged since the last sync is not reported as unmerged. This is the same judgement automatic close-on-merge applies, so the two paths cannot disagree about whether the work landed — which is what the rejection below was protecting.
- **Repository to workspace inference**: a card the sync materializes is pinned to a local workspace whose directory name matches the repository (case-insensitive; `.`, `_` and `-` are one separator; POSIX and Windows paths both understood). The rule lives in `src/core/workspace-match.ts` as a pure function, is resolved through the OPTIONAL `workspaceRegistry` service by structural probe rather than `inject` (a deployment serving none must still mount this extension), and is read at each materialization rather than once at start. Every miss — a lookalike name, a substring, two checkouts of the same project, an absent registry — pins nothing, which is the board's pre-existing inheritance behavior, so this rule can never move a card somewhere new. To carry the pin, the board's provider contract gained an optional `workspaceId` on `TaskBoardTaskDraft` (additive; absent leaves the board's own inheritance rules in charge).
- **Fault isolation**: GitHub network or API errors record `lastSyncError` on the task metadata and never disrupt or fail ongoing local executions.
- **Bounded, self-healing, and visible background sync**: every GitHub request is bounded at `DEFAULT_REQUEST_TIMEOUT_MS` (30s) with a real AbortSignal plus a racing ceiling, and raises `GitHubTimeoutError` so "GitHub said no" stays distinguishable from "GitHub never answered". The pass re-entry guard is a TIMESTAMP (`inFlight: { since }`), not a boolean: a pass still running one poll interval later is taken over rather than waited on. A pass records `lastSyncAt` only when it reached a repository cleanly, keeps the errors it collected, counts consecutive unproductive passes, and publishes all of it as `health` on the provider summary, through `GET /api/task-board-github/status`, and as a Background sync line in the settings card; three poll intervals without a clean pass reads as stale. Background failures are logged to the host instead of discarded.
- **The credential is resolved per PASS, not at activation**: the harness credential store is an async host service that may not be serving when this row activates, and a token read that races it yields nothing. The provider then mounted unauthenticated, and because the mount key was computed from that same absent token and re-resolution only happened on a `credentials/reference-updated` event that a pre-existing credential never fires, it stayed that way for the life of the host — reproducing on every restart. `GitHubSyncService` now takes a `credential()` seam, calls it at the start of every pass, and pushes the result onto the client with `setToken()`; the activation-time read survives only as the fallback for a mount with no seam, and an absent token is no longer part of the mount key. A pass that finds no credential reports ONE reason naming the reference it looked up, not one identical line per repository.
- **The listing is one page**: `listIssues` requests `state=all&per_page=100` and never paginates, so in a repository with more than 100 issues only the newest 100 take part in the inclusion decision, and an older one is seen only when the per-card single-issue read still finds it included. This is recorded as a known limitation in the README rather than silently relied on.
- **Proxy as configuration, not only environment**: two volatile keys — `proxyMode` (`auto` by default, or `custom` / `direct`) and `proxyUrl` (read only by `custom`) — drive the transport, are editable in the settings card's "Network proxy" block through the same loopback-only setup routes, and are part of the provider's mount key so an edit reaches the next request instead of waiting for a restart. `auto` is the default because it is the mode that is right without being configured. Detection is a cached, non-throwing probe: `execFileSync('reg', ['query', ...])` on Windows and `scutil --proxy` on macOS, parsed by functions that take the stdout as a string so the parse is testable without spawning anything, memoized for 30 seconds because the probe is synchronous and sits on the request path, and read as "no system proxy" on every failure. The parsed forms are the platform's, not a private invention: a per-protocol `ProxyServer` list is read https-first, and both parsers report a SOCKS-only configuration as `socks5://` so the resolver can name what it cannot speak. `GET /api/task-board-github/status` and `GET .../proxy` report `{ mode, url, effective, source }` — the resolved URL and where it came from, never a credential — and `PUT .../proxy` writes both fields in one revision-guarded batch.
- **Agent tools & UI**: The extension contributes nine scoped agent tools through the board's `registerTool` capability, so they follow the board's master switch AND the extension's own `enabled` switch: the seven synchronization and write-back tools (`task_board_github_list`, `task_board_github_get`, `task_board_github_refresh`, `task_board_github_create_pr`, `task_board_github_link_pr`, `task_board_github_comment`, `task_board_github_close_issue`) plus two configuration tools — `task_board_github_setup` (credential status, store, clear, and a live connection test) and `task_board_github_repositories` (list, add, remove, update). Its browser half renders under the same gate: a `data-dsh-part="github-integration"` section in the Task Detail view and a compact `#<issueNumber>` card decoration, registered into the two child seats the board declares (`task-board.detail.section`, `task-board.card.decoration`). The integration block (`data-dsh-part="github-settings"`) renders in the extension's own settings card beside the switches that govern it and reaches the host through this extension's own loopback-only setup routes, not through a board seat: the same routes a person configures with are what a model configures with through the two configuration tools.

The board-facing contract that makes this integration an extension instead of an inlined feature — the `taskBoard` provider service, the three child seats, the capability faces, the opaque `TaskRecord.integrations` container and the three-state switch — is owned by [the task board external provider extension contract](../architecture/2026-09-30-task-board-extension-contract.md). That contract partially supersedes this note: the GitHub endpoint decisions stay this note's, while the dependency direction and the storage coupling recorded here are replaced there.

## Architecture and Host-Side Security

All GitHub API communication is centralized in `GitHubApiClient` and `GitHubSyncService` in the extension package's host half (`packages/dsh-task-board-github/src/host/`). The extension imports no task-board module: it restates the provider contract in its own `src/core/contract.ts` and resolves the board's `taskBoard` service at runtime. Credentials are resolved on the host in a fixed order — the harness credential store (`ctx.credentials`, the store the Models page writes API keys into), then the environment variable named by `tokenEnv`, then `GH_TOKEN` — and a token is written only through `src/host/credentials.ts`: the settings card and `task_board_github_setup` post it once to this extension's loopback-only setup routes, the host stores it, and no reply, snapshot or tool result carries its value. It never enters a client-visible store, the settings namespace, a websocket/SSE boundary or an agent payload. The provider owns its own immutable-identity index, built from the board's cards when it starts and pruned as the board reports deletions; every task read and write goes through the capability face (`tasks.*`, `integration.*`), and published read-only state rides the board snapshot's `extensions` map, so the board stays the single authority over content, columns and events. The extension row owns the configuration (`tokenEnv`, `repositories`) and the two switches (`enabled`, `announceToAgent`); every key is volatile, which is what lets the settings card, the two configuration tools and the profile patch all write it through `ctx.settings.mutate` and reach the running provider without a row reload. Untrusted issue content is isolated into string metadata fields (`remoteTitle`, `remoteBody`, `remoteLabels`) and never injected into permissions, workspace identity, handover bundles, or promptPrefixes; it reaches the execution prompt only inside the templated provenance wrap described above.

The outbound transport belongs to `GitHubApiClient`: `src/host/proxy.ts` resolves the proxy one destination actually uses from the plugin configuration (`proxyMode` / `proxyUrl`) rather than from the environment alone, honours `NO_PROXY` (a named host covers its subdomains, an entry may pin a `:port`) for every source, and tunnels `https` with a `CONNECT` request over `node:http` / `node:https` / `node:tls`, because the package ships no HTTP-stack dependency of its own. The three modes are the whole of it: `direct` never proxies, `custom` dials the configured URL (a missing scheme is filled in with `http://`, and an empty value is not a decision, so it falls back to `auto`), and `auto` reads the conventional variables and then the operating system's own proxy — the Windows registry through `reg query`, `scutil --proxy` on macOS, nothing on any other platform. A proxy scheme this transport cannot speak is refused with a reason on the resolution result instead of being thrown: the request then goes direct, and `socks` is the case that exists in practice. `GitHubApiClient` is built from that resolution (`proxyClientOptions`), never left to re-read the environment, so `direct` wins over an inherited `HTTPS_PROXY` and a detected system proxy is used where no variable names one. A transport failure is retried once with a fresh connection for an idempotent method (`GET`, `HEAD`, `PUT`, `PATCH`, `DELETE`) and then rethrown as `GitHubTransportError`, which carries the endpoint and the transport cause, so a card's `lastSyncError` names what broke instead of undici's bare `fetch failed`. A `POST` gets one attempt: a transport failure does not prove the request never arrived, and repeating a comment or pull-request creation would write the same thing twice. A timeout and an API refusal are never repeated either — the first already spent the whole 30-second ceiling, and the second came from GitHub, which answered the question. A stored credential reaches the mounted client through `reloadCredential()`, which also drops the login cached for an `@me` rule; without it the client kept the token it read on the previous pass, so a write attempted right after an operator replaced the token authenticated with the superseded one until the next poll or a restart.

Background polling operates on its own configurable timer (`HostTimerFace`) independent of the 5-second session roster poll, preventing API rate limit starvation and decoupling external network latency from local heartbeat loops.

The setup routes are addressed origin-absolute: `GITHUB_SETUP_API_PREFIX` is `/api/task-board-github`, because the Host webserver keys a route by the raw request pathname, which always begins at the origin root. A registered key without that leading slash can never match a request, and the settings card then reported "the Host refused the request (404)" for a deployment that was in fact mounted. The browser half calls the same route document-relative (`GITHUB_SETUP_API_PREFIX.slice(1)`), so a GUI served under a sub-path still resolves it against its own entry directory, and `tests/setup-routes.spec.ts` asserts that both halves name one path.

The extension's configuration surface is the board's own settings card, not a card of its own: it registers into the `task-board.settings.section` seat the board declares and renders, so a provider is configured where the board it configures is configured. Two rules keep that reachable. The section is NOT gated by the extension's own master switch — it is where that switch lives, and a section gated by the switch could never turn it back on; a disabled extension replaces its credential/repository form with an explanation instead. And the registration follows the seat's DECLARATION lifecycle (`slots.inject`) rather than registering once: the board's card re-declares the seat whenever it moves between plugin-card seats (the family group loading after boot is the normal case), and re-declaring releases every entry registered in the seat — a one-shot registration is silently dropped, and the section then never renders while nothing reports an error.

## Alternatives considered

Direct two-way mirror between GitHub Issue state and Task Board columns was considered, where changing an issue state on GitHub would immediately drive local card movement and vice-versa. This was rejected because local task execution in DSH represents concrete agent runtime sessions: an external label change must not arbitrarily trigger or abort active local processes, and external GitHub status cannot represent transient local execution states like session launching or teammate spawning.

Storing GitHub labels as native `TaskTag` objects on the card was considered. This was rejected because `TaskTag` has an 8-tag limit and optionally prepends instructions to agent execution prompts (`promptPrefix`). Treating untrusted remote labels as prompt prefixes would allow remote label additions on GitHub to alter agent execution instructions, and large label sets would violate the 8-tag capacity gate.

Client-side GitHub API access using user-provided personal access tokens in the browser was considered. This was rejected because exposing GitHub tokens to browser memory and client bundles creates credential leakage risks and would prevent background synchronization and scheduled task execution when the browser tab is closed.

Closing the GitHub Issue immediately when local task execution succeeds was considered. The rejection stands: successful code generation or local test passing does not mean the work is reviewed or deployed, and the industry standard path is linking the issue to a Pull Request ("Fixes #123") and completing the issue upon PR merge. `task_board_github_close_issue` was later added and is bounded by exactly that judgement — it is refused unless the card's pull request is MERGED — so the original concern is preserved rather than traded away, and the rationale above remains the reason for the guard rather than the reason the tool is absent.

A per-repository workspace pin in the GitHub configuration was considered as the way to route an issue to its checkout. It was not chosen: it is explicit and exact, but it needs a configuration edit per repository and silently rots when a user adds a checkout without touching the settings. Directory-name inference covers the common case with no configuration at all, and because every miss falls back to the previous behavior rather than to a wrong pin, adding the explicit mapping later is strictly additive.

Fuzzy or "closest match" workspace selection was considered and rejected. Matching a repository to the workspace whose name is most similar would pin `dsh-web` issues into a `dsh-web-old` checkout in exactly the multi-project setup this rule exists for, and a similarity score is not a fact the board can put in a report. Equality on a normalized name can be explained to the user; a score cannot.

Keeping the boolean re-entry guard and only adding a timeout was considered and rejected. The timeout is necessary but not sufficient: the guard is the thing that turns one bad pass into a permanent outage, and any future await inside a pass re-arms the same failure. The guard now carries the instant it opened, so a pass that outlives one poll interval is treated as wedged and taken over rather than waited on. The two guards are deliberately redundant — the AbortSignal releases the socket, the race guarantees the await returns, and the timestamp guarantees that even an await nobody bounded cannot stop the next poll.

Exposing sync health only in the host log was considered and rejected. A log line is read after the fact, by whoever happens to be looking, and this failure presented as a board that was simply empty. Health therefore rides the provider summary and the settings card: the operator sees "stopped" where they configure the integration, which is the moment they can act on it.

Keeping the issue body as the execution prompt was the original behavior and is replaced. The body tells the agent what someone wants, but not which repository conventions apply, how to report back, when the work counts as done, or that the text is untrusted; every run had to rediscover the extension's own write-back tools and the merged-PR guard, and a notice-only issue armed a goal the agent then pushed to manufacture changes for. The template carries those facts deterministically and keeps the body verbatim, so nothing the issue says is lost.

Letting a model write the whole execution prompt was considered and rejected. A rewrite launders injected text into authoritative-sounding instructions and erases the boundary the provenance wrap exists to keep; the workflow rules (branch, write-back, no closing before merge) are hard requirements a generator drops or paraphrases sooner or later; the goal acceptance judge reads the same prompt, so model-invented completion criteria would let one model grade against its own yardstick; and a deterministic fallback is needed anyway for a deployment without a model. The model therefore writes one bounded, labeled section and never replaces the verbatim body.

Generating the analysis automatically during synchronization was considered and rejected. A poll runs every five minutes by default and an issue edit would re-spend quota each time, outputs vary between calls, and nobody reviews a prompt that changed in the background. Generating it at execution time instead was rejected because the operator could not see what the agent actually received. The analysis is an explicit, per-card action whose result is cached against the issue content and shown before the card runs.

Tracking hand edits with a boolean flag instead of a prompt fingerprint was considered and rejected. The board's detail form edits the prompt through the board's own update action, which no provider event reports, so a flag would never be set; comparing the current prompt to the fingerprint of the generated one detects an edit from any surface (form, agent tool, ledger import) without a contract change.

Making the execution prompt a runtime section the board asks the provider for at launch (a new contract capability) was considered and deferred. It would let a template change reach un-run cards and fetch recent comments at execution time, but it needs a contract version bump, a board-side wrap and truncation rule, and an Agent Note on the contract; storing the composed prompt on the card keeps the contract unchanged and lets the operator read the exact text before running.

Making the client read the credential store itself was considered and rejected. The store is async and `getToken()` is synchronous on the request path, so "the client resolves its own credential" means either an async client (a rewrite of every call site) or a cached value that is exactly the thing that was wrong. The owner already resolves the credential for the status and connection-test surfaces; giving the pass the same seam keeps one resolution point and one wording.

Bundling `undici` to get a `ProxyAgent` dispatcher was considered and rejected. The client exchanges JSON only — status, headers and a small body, never a stream — so a `CONNECT` tunnel (and an absolute-form request for an `http://` base URL) is the whole transport it needs, while `undici` would add an HTTP stack to a host half that ships as a single bundle and would still be unusable in a deployment that does not resolve the package. Relying on `NODE_USE_ENV_PROXY` alone was rejected for a different reason: it is read at process start, so a running Host cannot adopt it without a restart and the plugin cannot set it for the process it lives in. A single retry was chosen over an unbounded backoff because a pass makes many sequential requests and a wedged connection must not multiply the whole pass's cost; one fresh connection covers the failure actually observed, where a socket died while the Host was idle and the next request inherited it.

`auto` reading the operating system proxy, instead of the environment variables alone, was a reported failure rather than a preference: the machine had a system proxy configured (the Windows registry's `ProxyServer`, `127.0.0.1:7890`) and no `HTTPS_PROXY` anywhere, so every GitHub call went direct and failed at the transport while a freshly spawned CLI worked. Reading the environment only is the wrong default for a desktop application, where a proxy is normally configured once in the OS and inherited by nothing.

Caching the detection for 30 seconds rather than re-probing per request was chosen because the probe is a synchronous child process: a pass issues a hundred or more sequential requests, so an uncached probe would spawn a process per request and block the event loop while doing it. Thirty seconds is long enough that a pass costs at most one probe and short enough that a user who turns the system proxy on does not have to restart the Host. A failed probe is cached the same way as an absent one, because the failure this must not produce is a request path that learns about a missing `reg` command.

Supporting only `http` and `https` proxies, rather than adding SOCKS, was chosen because the transport is a `CONNECT` tunnel and an absolute-form request over `node:http`, and a SOCKS proxy needs a different handshake that would mean writing (or bundling) a SOCKS client. A SOCKS-only configuration therefore resolves to "no proxy" with a reason naming the scheme, which is honest, instead of a connection attempt that fails as an opaque transport error.

## Consequences

- Teams can manage issue backlogs on GitHub while delegating implementation directly to DSH agents.
- Task Board cards retain full backward compatibility with non-GitHub tasks without requiring ledger schema migrations.
- GitHub API outages degrade gracefully to cached state and explicit retry indicators without interrupting active agent runs.
- Token management remains server-side, requiring deployment configuration in environment variables or profile patches rather than browser inputs.
- A silent poll is now a shipped defect rather than an operator's intuition problem. The report that prompted this change — a configured, credentialed, enabled integration that had synced nothing for over an hour while every status field read healthy — is only diagnosable because `lastSyncAt` exists. `lastSyncAt` is written only by a pass that reached a repository WITHOUT errors, so it is a fact about contact with GitHub rather than a heartbeat that keeps ticking while nothing works.
- A card's prompt is now several times longer than the issue body it came from, and its wording is owned by `src/core/prompt.ts`; a template change reaches cards on their next sync only while their prompt is still the generated one, and never reaches a card that has executed.
- The AI analysis spends the deployment's own model quota, once per explicit request; a deployment without a model service keeps the templated prompt and refuses the request with a reason. The model call itself is exercised against an injected stand-in for the `llm` service in `tests/issue-analysis.spec.ts`, not against a live model.
- The re-entry guard now permits a second pass to start while a first is still running. That is intentional (a wedged pass must not be able to stop the next poll) and it is bounded by the fact that every request is itself bounded, so overlapping passes are short-lived rather than accumulating.
- GitHub traffic follows the machine's proxy configuration — environment variables, the operating system's own proxy, or a URL pinned in the settings card — and the settings card shows the proxy a request would actually dial, because "auto found the system proxy" is otherwise invisible. The system proxy is read and parsed from the OS, not detected by connecting to it: a proxy that is enabled but dead is reported as the proxy in use, and the transport failure that follows is what names it.
- A transport failure reports its endpoint and cause instead of `fetch failed`. The retry is one attempt on a fresh connection after 250 ms, and it is granted only to idempotent methods; a timeout, an API refusal, an aborted request and every `POST` are never repeated, so a pass can at most double the transport cost of an idempotent request that failed at the socket level while a write is never silently duplicated. Coverage of the `CONNECT` branch reaches the tunnel request (authority and refusal) but not a completed TLS handshake, because the tests speak plain HTTP through a local proxy rather than standing up a certificate authority.
- Every GitHub tool result is lossless JSON. The host runtime snapshots a successful value before the model ever sees it and rejects a member whose value is undefined, while JSON.stringify merely drops such a member silently, so a projection checked only against JSON.stringify looks healthy while the tool itself is unusable. Absent optional members are therefore left out of the object by conditional spread, the idiom normalizeGitHubMetadata already used; githubTaskSummary delegates its remote half to githubIssueSummary, and the pull request metadata both PR tools return omits an absent draft, headBranch, baseBranch and mergedAt the same way. tests/tool-output-json.spec.ts asserts the rule for every tool, and it is why task_board_github_list and task_board_github_refresh had been failing outright on every call.
