# Agent Note: 梁神模式可追加调度者规则集

Status: implemented

在 persona 内容上延续 [V4.1 Flash 原生重建](2026-09-16-liangshen-v41-flash-native-rebuild.md)，在工作纪律上延续[有界检查与收敛](2026-09-18-liangshen-bounded-inspection-convergence.md)：两篇的决定都保持有效，追加块与它们组合而不是取代任何一方。

## Problem

梁神 persona 刻意极简：一行身份，加上几条固定工作纪律。这个形态对「自己干活的会话」是划算的，对一个职责是驱动其他会话的会话则是错的形态。调度者必须先判定任务多大再动手，先判定同伴是 teammate 还是 subagent 再派发，交出带边界与验收标准的任务书，拿证据核对回报而不是听自我陈述，并且清楚自己的授权到哪里为止。这些都无法从一份从不提派发的纪律里推出来，任其临场发挥的会话每次都会发明一套不同的流程。

那套流程已经存在、经过评审并被写下来，就在订阅仓数据面的独立 dispatch 预设里：`[Role Identification]` 段（告诉子代理哪些规则不落到它头上）、`[Coordinator Identity]` 段、R0 到 R8 含 R-W，以及结尾的反模式清单。在本地重推一份更短的版本，等于为同一件事再造第二套会分叉的流程。

照搬来的这套规则是单向的，而单向正是它在真实会话里没站住的部分。它的反模式只罚「问得太少」——需求没问清就规划或动手；没有任何一条罚「问得太多」。于是调度者握着一张无上限的访谈许可：没有提问预算，没有给不想做访谈的用户的出口，没有「新证据如何并入而不重开已敲定决策」的规则，没有说明「理解一致」到底要用户确认什么、确认完了落在哪里，没有要求推荐必须带上理由，也没有给 R0 已经许诺给 L1 的那一两个问题任何形式。每一条缺失的规则，都是会话把用户的注意力花掉、而不是花自己注意力的方式。

## Decision

梁神 Config 新增布尔字段 `dispatcher`（schema 默认 `true`，与其余塑造预设的字段一样 `volatile()`），经 `applyPresetOverrides` 把 `dispatcher` 键写进所声明预设的 `minimal-prompt` 行——与 `presentation` 写入 `tool-catalog` 的方式完全同构。开启时 `minimal-prompt.mjs` 在工作目录行之后把调度规则块追加到 persona 段；关闭时回到仅含 persona 与工作纪律的形态，逐字节与该开关存在之前一致。

出厂默认开启：全新安装得到的就是本模式的调度能力，而不是一个需要自行发现并打开的隐藏项；设置界面上的开关是把会话退回 persona-only 面的手段。插件自身的兜底默认值与出厂行一致，因此「行上丢了该键」与「激活时未提供配置」解析出同一个值。

- 规则文本放在新的纯文本模块 `presets/liangshen/dispatcher-rules.mjs` 中，导出 `DISPATCHER_RULES`。它从 `[Role Identification]` 段到结尾反模式清单承载上游文本：`[Role Identification]` 段、`[Coordinator Identity]` 段、R0、R0.5、R-G、R1 到 R5、R6、R-W、R7、R8，以及二十条反模式。（2026-10-18 重新抽取；就地折入的更正记录在[维护笔记](../../architecture/2026-10-18-liangshen-dispatcher-rules-maintained-in-place.zh.md)。）相对本决定最初携带的那一块，文本还带来了身份段下的 `[Execution Pipeline]` 行、R-W 回合边界段，以及执行这三条的反模式第 13 到 16 条。开启该开关的会话跑的就是这份上游参考块，而不是它的本地摘要；块里没有 R-T：本模式只派发子代理，遇到 Agent Teams 类工具面时直接拒绝而不是降级进去，R0.5 就是停下来并把退出选项交给用户的那一处。
- 此后对规则的改动一律追加，绝不折进原文。**就「更正」而言此条已被取代**（2026-10-18）：新增内容仍进附录，但上游谱系已经改正过的句子就地重写——追加一条更正会让模型对同一个决策握着两条规则，而更严的那种解读会不经核对地胜出。见[维护笔记](../../architecture/2026-10-18-liangshen-dispatcher-rules-maintained-in-place.zh.md)。`DISPATCHER_RULES` 承载上游文本，`DISPATCHER_RULES_APPENDIX` 承载本地新增；`DISPATCHER_RULES_WITH_APPENDIX` 把两者拼起来，也是提示词实际追加的东西。附录是英文，装着本地新增的访谈条目 G7 到 G14 与两条本地违规项，并加上 G15——上游没有任何对应的一条规则，它让任务看板停在做跟踪的表面、而不是派发路径。附录开头声明它是本地补充、与 G1 到 G6 冲突时以它为准，同一事实因此仍然只有一个家。`withDispatcherRules` 分别检查两半：已经带着参考文本的 persona 仍会补上附录，两半都不会被追加两次。
- 附录新增的内容：G7 给提问定预算——一轮最多 4 个问题、全程最多 3 轮、按影响面排序，且两种答案都不会改变实现路径、验收标准或成本的问题不许问；G8 给出假设出口（逐条列出将据以执行的假设，绝不静默跳过）；G9 只把新证据并入受影响的分支；G10 指出可被确认的对象——四行以内的访谈纪要，其中已敲定的决策与不可变约束登记为事实——并把「都行」读作委托，已敲定的决策不二次追问；G11 要求推荐带上理由与「什么情况下该被推翻」，并把观察与归因分开；G12 记录塌缩工具面下的提问路径与工具不可用时的降级；G13 把 G3 的最小形式给到 L1；G14 把只读查证型派发从 R5 的前置条件里豁免出来——R5 本来也只把该条件限定在实现型；另有 G15 一条——这里唯一没有上游对应的规则——写明看板面的后果：看板卡片不替代 R5 派发，而任务清单本身落在 `todo_write`，由参考文本自己的 R-W 段钉住。
- 归属（OWNERSHIP）。文本来自 `@eddyskywalker/dsh-chatgpt-subscription`（github.com/Aa728848/dsh-chatgpt-subscription）的 `dispatch` 预设，那是一个从 npm 发布的第三方包，在本机与本仓都没有可写的 checkout。这个块起初就是该上游 0.24.6 的文本——它的 persona 前缀，原文英文——自 2026-10-18 重新抽取起改为在本仓维护：`DISPATCHER_RULES_PROVENANCE` 记下出处、承继版本、重抽日期与每一条就地折入的更正，`tools/check-dispatcher-rules.mjs` 则对已安装的上游副本报告漂移。与上游对齐不是本仓持有的保证：规则集归本仓所有、在本仓演进，上游文本被采用一次就整块替换一次，而所有本地新增都放在它旁边的附录里。
- 上游文本整块照进，没有任何本地改写的句子。它的模型路由段按作用描述运行时路由守卫——DSH 自身「子代理」设置里启用的子代理模型授权守卫，默认启用——不点名任何仓库、也不点名任何配置键。唯一的删除是上游用来开头的那行模板。
- `[Role Identification]` 段之上的身份行（`You are powered by {{model}}. Your working directory is {{cwd}}.`）不予携带。它的占位符属于那个预设自己的渲染器；梁神不绑定这些变量，而在文本由 harness 插值的段里留下 `{{...}}` 会让每次请求都抛错。梁神本来就自己追加工作目录行。
- `minimal-prompt.mjs` 引入该常量，并在 `withWorkspaceLine` 中追加，因此顺序由构造决定：persona、它的纪律、工作目录行、然后是追加的规则。两者之间用两行分隔标题（`## Dispatcher rules (a mode-level append)`）隔开，标题点明该块的含义并声明上面的纪律仍然有效，于是这些规则读起来是一段被宣告的追加，而不是又一条 persona 条目。追加是幂等的：已经带有该块的段不再重复追加。
- `dispatcher` 与 `presentation` 正交。该开关只改提示词；工具面由 `presentation` 决定。不因此改动任何工具、任何行、任何仓库插件。
- 出厂 `agent.cordis.yml` 的 `minimal-prompt` 行带 `dispatcher: true`，该行注释写明了语义。键是显式存在而非缺失，这样 overlay 写入的是该行本就声明的键——与 `guard`、`tool-catalog` 两行的出厂形态一致。

## Testing

- `packages/dsh-liangshen/tests/minimal-prompt.test.ts` 固定：关闭态逐字节一致（persona 段等于 persona 加工作目录行、段列表不变、组装出的段里不出现任何调度文案）；开启态（追加的文本恰为分隔标题加 `DISPATCHER_RULES_WITH_APPENDIX`、persona 纪律仍在其之前、段列表不变）；规则覆盖完整（`[Role Identification]`、R0 到 R8 含 R-W、反模式清单齐备）；文本中不含订阅仓名称、不含未绑定的 `{{...}}` 占位符；经 harness 渲染器渲染；无 cwd 的会话；幂等性；追加块从不落进 `workspace-instructions` 段。
- `packages/dsh-liangshen/src/composition.test.ts` 固定：出厂行（shipped `agent.cordis.yml` 中确实带 `dispatcher: true`）；未设置 `dispatcher` 时不写任何键；提交 `true` 时写入该键且该行其余键不动；`tool-catalog` 与 `guard` 两行不移动。
- `packages/dsh-liangshen/src/index.test.ts` 固定 schema 默认值与 volatile 引用，以及 `presentation` / `dispatcher` 的每种组合彼此独立解析。
- `packages/dsh-liangshen/tests/preset-composition.test.ts` 在既有配置键之外固定出厂行的 `dispatcher: true`。
- `packages/dsh-liangshen/tests/minimal-prompt.test.ts` 另固定附录边界：参考常量仍以上游最后一条反模式结尾、且不含 `G7`；附录不含任何参考段的标题；拼接常量恰为参考块加附录；每条新增内容恰好出现一次且位于最后一条反模式之后；已经带着参考块的 persona 只会补上附录一次。那条本地看板规则同样被固定：它落在附录里，而不是参考常量里。三处精确文本断言拼的是 `DISPATCHER_RULES_WITH_APPENDIX`。
- 提问路径是实测而非假设。在 `run_code` 程序内通过 `tools.ask_user_question` 派发的提问正常渲染出卡片并回收了答案，这正是 G12 让模型在塌缩工具面下依赖的路径。分页限制不可能扣下这个工具：分页只匹配 `mcp__*` 名称，而 `ptc` 与 `both` 的差别在于模型能直接调用什么，不在于程序能触达什么。

## Alternatives considered

- **只携带精简版调度规则。** 否决。梁神的极简 persona 哲学与约九十行的追加确实存在张力，短版本在上下文预算上是更便宜的答案。它在另一个轴上输了：这些规则不是写作风格指南，而是一套相互咬合的流程。R2 的路由判定是 R5 任务书所依赖的前提，R6 的两次重派上限才是 R8 兜底有界的原因，反模式清单则是整套东西可执行而非仅供参考的原因。裁剪意味着挑选放弃哪些保证，而裁出来的集合既不是评审过的那套、也不是自洽的短版本——它是没人评审过的第三套流程，恰恰是本决定要避免的分叉。调度模式还有一个自我指涉的风险：一个自己发明派发流程的调度者，正是规则所描述的那种失败。完整规则集因此全量携带，代价付在它该付的地方——该开关是运维者可以关掉的一个键，而退回 persona-only 的会话与开关存在之前逐字节一致。
- **就地改写 G1 到 G6，而不是追加缺失的规则。** 否决。那些句子是另一位评审者签过字的产物，改掉它们会让本记录的「逐字照搬」主张、模块的出处注释、以及评审者手上的文本同时描述一个已经不存在的东西，也没有任何标记指出被评审的部分到哪结束。追加则让参考文本保持可读、仍是它本来的样子；而两个家唯一会引出的问题——以哪段为准——由一行优先级声明解决。
- **手工维持与第三方预设的逐字节同步，或把新增内容贡献回上游。** 作为对本仓的约束否决。上游从 npm 发布、本机没有 checkout，而且它自己已经越过这个块；对齐无法维护，还会把梁神的访谈纪律钉在一份它控制不了的日程上。附录陈述的是本仓为之背书的内容；同时跑那个预设的部署会看到同一套流程的两个世代——这是一个看得见的差异，而不是无声的差异。
- **在梁神之外另设一个 `dispatcher` agent preset。** 否决。本模式是一套纪律，不是一个工具面：第二个 preset 会为了一个布尔值的差异而复制组合、guard、分页与设置卡。开关保持一份组合、一个设置面，运维者按会话切换一个字段即可。
- **把规则并进 `agent.cordis.yml` 的 persona `prefix`。** 否决。prefix 是组合读取器解析的块标量；九十行的追加会让出厂 persona 与追加规则在维护者唯一用来查看「本模式说了什么」的文件里无法区分，而且不会给运维者留下开关。开关还保证了关闭态逐字节一致，改 prefix 做不到这一点。
- **把规则改写成英文以匹配预设其余文字。** 否决。参考文本是被评审的产物；翻译等于重开已经定稿的措辞，而周边 persona 本来就按设计混用语言。
- **绑定 `{{model}}` 与 `{{cwd}}` 以便顺带携带身份行。** 否决。`minimal-prompt` 不拥有组装的变量表，而 `{{cwd}}` 会与插件已从会话头追加的工作目录行重复——同一事实出现在两处，任一侧改动就会漂移。

## Consequences

- 开启该开关创建的会话是调度会话：它的交付物是计划、任务书、审查结论与交付说明，派发规则从第一次请求起生效。关闭该开关的会话不受影响。
- 追加块随 persona 段传递，因此是稳定前缀上的提示词文本。开启开关会在会话创建时一次性改变该前缀，此后前缀缓存照常复用；会话中途切换会重新声明预设，下一个会话组装出新的提示词。
- 调度规则假定会话可能并不具备的能力（没有子代理工具、没有模型选择开关）。R2 正是为识别这些情况而写，也是规则自带可用性探测、而不是依赖部署来保证的原因。本模式此前还带一道针对 teammate 类工具面的 R0.5 兼容性闸门；该闸门在 2026-11-13 的再同步中移除，因为能呈现这类工具面的那代 harness 已不存在，而随之保留的任务板契约如今是常驻的 [Agent Teams Board] 段。
- 梁神自身不带子代理模型授权守卫；希望强制 R2【可用时】分支的部署需在本包之外提供。没有它时，会话观测到的是【不可用时】分支。
- 该开关与 `presentation` 正交，因此两者可自由组合；设置界面把它们呈现为彼此独立的字段。
- 这个块与它所来自的第三方 `dispatch` 预设是同一份文本的两份拷贝，而那个预设确实装在部分机器的梁神旁边。两者只在上游不动时才一致：上游那份预设此后每次修订都被本块跟踪，本地新增则是本仓自己持有的部分；读这个块的会话先看到上游文本，再看到一段声明自己优先的补充。从不读附录的部署跑的仍是上游规则本身。
- G7 的预算只是提示词层面的上限，不是机制：运行时没有任何东西在数提问次数，所以这个数字成立的前提是模型遵守它。而能显示它是否遵守的度量——每任务的提问次数与干预次数——`tools/benchmark-live-run.mjs` 的 `summarizeSession` 已经在产出，只是 `tools/tasks/liangshen-v41-flash.json` 里没有任何任务走访谈，于是这些新增内容目前不由任何场景钉住。补一个需求模糊的任务与一个需求明确的对照任务，是让这条预算可被证伪的下一步。
- 那条本地看板规则堵的是一条路径，不是加一项能力：一个拿看板卡片代替 R5 派发的调度者，是用一条关于派发的记录替换了派发本身。它与访谈补充一样是提示词层面的——运行时没有任何东西在路由一次派发——因此它成立的前提仍是模型遵守它，且它只管运行本规则块的会话。
