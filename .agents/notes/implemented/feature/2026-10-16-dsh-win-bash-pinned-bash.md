# Agent Note: dsh-win-bash — a pinned private bash as a Windows plugin

Status: implemented

English | [中文](2026-10-16-dsh-win-bash-pinned-bash.zh.md)

## Problem

DeepSeek models are post-trained primarily against a bash tool surface; a Windows session that only has pwsh sees the model push bash syntax into PowerShell, producing error loops that burn tokens and attention (dsh-ops' self-reported benchmark points the same way; our own benchmark has not measured this dimension yet). The liangshen preset once shipped its own Git Bash (custom-bash.mjs), retired in [liangshen shell and paging](2026-09-17-liangshen-shell-and-paging-ptc-surface.md) for being stateless, unconfined, and bash in name only — but that decision also left a "no real bash on Windows" gap.

## Decision

The gap is filled by an **independent plugin package**, not the preset: `packages/dsh-win-bash` (npm `@linxin666/dsh-win-bash`) registers the `win_bash` tool on win32 x64 hosts — one persistent private bash process per session, state kept across calls. Liangshen's "a preset ships no shell implementation" principle stands unreversed: the two compose and never wire into each other.

- Pinned payload: Git for Windows v2.56.0.windows.2 ships in the package as a curated extraction drawn from **two assets of that one release** — MinGit `MinGit-2.56.0.2-64-bit.zip` supplies everything except `usr/bin/sleep.exe` and `usr/bin/seq.exe`, which MinGit does not ship at all and which come from the same release's full `Git-2.56.0.2-64-bit.tar.bz2` (91 files, 16.09 MiB, 22 license texts and PROVENANCE.md). `checksums.sha256` records every file's SHA256 and the **whole payload is verified before mount** — a mismatch refuses the mount; the shell resolves only by absolute path, never PATH, and the tree it runs is a verified copy published under the DSH home outside the package so a running shell cannot lock the package directory ([payload cache](2026-11-01-win-bash-payload-cache-outside-package.md)). The OpenSSH/Heimdal/OpenSSL family is excluded after PE-import analysis proved nothing kept references it.
- The tool is named `win_bash`, not `bash`: a same-named tool would silently replace or be replaced by the host's. Row id `dsh-win-bash`, row name exactly the package name, `disabled: !!js process.platform !== 'win32'` on POSIX.
- Framing: a nonce-marked quoted heredoc sourced via `.` — a brace group aborts on a syntax error and would swallow the end marker, wedging the shell forever; a heredoc parses as one unit, so an unterminated quote is reported and the next call succeeds on the same process (measured). stdout comes from the parsed frame, never the raw accumulator, so framing never reaches the model.
- Permissions: the policy resolves through the `sandboxPolicy` service **for the calling session** — a session's own `sandbox/mode` outranks the deployment default, so a session the user restricted cannot reach this shell through the default. **This tool serves `danger-full-access` only, and it declares that rather than implementing confinement**: every other mode is refused with `SANDBOX_UNSUPPORTED` before any process is spawned or any job registered, on the foreground and background paths alike (`tests/sandbox-mode.spec.ts`). The reason is measured, not assumed: under the real ACL restricted-token runner the pinned MSYS payload cannot start at all — `bash.exe`, `sh.exe`, `dash.exe` and `echo.exe` all die before main with `NtCreateDirectoryObject(\BaseNamedObjects\msys-2.0S5-<hash>): 0xC0000022` (exit 3221225794 / 0xC0000142), and system Git for Windows fails the same way (`couldn't create signal pipe, Win32 error 5`), so it is an MSYS/Cygwin runtime requirement rather than an artifact of this package's extraction; `cmd.exe`, `node.exe` and `powershell.exe` run confined on that same runner. Confinement therefore cannot produce a working shell here, and a shell whose every command dies before main would still be reported as running inside a boundary that never held a command — refusing is the honest answer. The earlier confined-spawn path and its two specs (`confinement.spec.ts`, `confinement-live.spec.ts`) were removed with it: they certified that the `confine()` argv was the one spawned, which is no longer a reachable state.
- Recovery is visible: an exited, timed-out or aborted shell is destroyed and the next call states that state was lost; shells are released on agent disposal and plugin unload.
- The rendered view carries no terminal escapes. The streams stay honest bytes — the pipe model is why this tool exists — but a coloured stream is unreadable as text: on Windows the colour libraries a build tool uses decide on `platform === 'win32'` rather than on whether a terminal is attached, so `TERM=dumb` (which the shell environment already sets) turns nothing off and a piped `vitest` or `pnpm` run still emits SGR. `src/tool.ts`'s `renderResult` therefore strips CSI and OSC sequences and keeps only the final frame of a line a progress renderer repainted in place (a bare CR repaints; a CRLF line ending is preserved as written). Truncation notices are appended after stripping, so the tool's own text is never touched. `tests/escapes.spec.ts` pins colour, OSC payloads, repaint collapse, CRLF preservation, and the no-escape identity case.

## Alternatives considered

- Putting bash back into the liangshen preset. Rejected: the 2026-09-17 "a preset ships no shell" principle still holds, and an independent package keeps the binary-distribution surface off both host and preset.
- Probing the system Git Bash on PATH. Rejected: version and bytes are uncontrollable, which is exactly the shape pinning exists to exclude (dsh-ops likewise lists system fallback as a security downgrade).
- Spawning a fresh process per command (the retired custom-bash.mjs shape). Rejected: a stateless shell was one of the original reasons for retirement.

## Consequences

- v1 ships Windows x64 only; ARM64 and other platforms refuse the mount with an honest warning.
- Wired into the dsh-web-all aggregate family (aggregate row `web-ui-win-bash`, family subpath `@linxin666/dsh-web-all/win-bash`, locked by an explicit `familyIds` mapping), so it installs with the family by default; the root patch stays untouched. A packaging-time script that re-downloads the pinned asset and diffs it against checksums remains a follow-up.
- **Availability follows the platform and the payload only**: once the shipped payload verifies, `win_bash` registers on a supported Windows x64 host whether or not the LiangShen preset is enabled. The LiangShen declaration gate and its `syncWithLiangShen` switch are gone ([retire-message-edit-and-win-bash-gate](../simplification/2026-11-14-retire-message-edit-and-win-bash-gate.md)); registration happens synchronously in apply, and a registration error is logged instead of escaping as a rejection. See [packages/dsh-win-bash/AGENTS.md](../../../packages/dsh-win-bash/AGENTS.md).
- The host schedules tools without `isConcurrencySafe` as exclusive (fail-closed), so one persistent shell never faces concurrent frames.
- **Shell ladder (Windows only)**: win_bash is the PREFERRED shell, never the only one, so the host pwsh is withdrawn only from sessions win_bash can actually serve — the withdrawal follows serviceability, not mount state, and a session in a mode win_bash refuses KEEPS its pwsh (otherwise the session would have neither shell, which is the capability loss this ladder exists to prevent). The withdrawal itself is `agent.ctx.tools.restrict` (src/pwsh-replacement.ts), deliberately visibility-only with no execution denial: a deliberate pwsh call still runs, which is the ladder's lower rung (win_bash first; pwsh carries Windows-native work and the fallback after win_bash failures; this package ships no PowerShell payload, that rung stays the host's). Every model-visible refusal and failure names that fallback too (src/shell.ts `NATIVE_FALLBACK_HINT`), so a model switches shells instead of retrying one that will not come back. `replacePwsh: false` keeps both shells listed. Restrictions are per-agent, lifted on agent disposal and plugin unload; a host pwsh row that mounts later is hidden through `tools/change` (restrict throws on unknown names, so absence is not a verdict); the lifts slot is pre-claimed to stop `tools/change` self-recursion. POSIX is a total no-op (the platform gate is the module's first line, before any read, listener, or restrict). The win_bash description's first sentence — inside the catalog truncation window — carries the "prefer over pwsh" guidance, while the mechanism fact sits beyond the window.

## Testing

- 114 package tests (framing protocol, registry recovery, payload verification, config, mount gating, vendored-bash live runs, truncation visibility, background jobs, and the sandbox-mode declaration); the four real defects found during acceptance (shared cursor across streams, frame re-parse, stdout read from the raw accumulator, unlatched begin marker) each carry a regression test, and so do the two later findings (the policy read that dropped the calling session, and the pwsh withdrawal that ignored the session mode).
- Independent reruns: `pnpm --filter @linxin666/dsh-win-bash build/test/typecheck` all green; `verify-docs`, `emoji-audit`, `test-standards`, `aggregate --check`, `sync-shared --check`, `runtime-deps-check`, `family-dsh-engines` pass; all 91 payload checksums verified and the vendored bash reports 5.3.15(2)-release.
