# Agent Note: 手机在连接时自选配对来源，且只广告可达的局域网字面量

Status: implemented

## Problem

一条配对链接只能命名一个基址，而桌面面板把这件事变成了抛给用户的问题：每个可构造的局域网字面量一行单选，加上公网（隧道/中继）基址一行。用户答不了这道题。桌面端无从知道即将扫码的手机是否与本机同网，而恰恰是问题最难的地方列表最长——一台多网卡主机（Wi-Fi 加有线再加一条 VPN）会给出三到四行，从本机视角看全都同样可信。

这些行背后的推导也过于宽松：每个非内部 IPv4 接口地址都会被广告，包括 fake-IP 代理采到的 TUN 网关（Clash/Surge/Mihomo 发放 `198.18.0.0/15` 地址，运行它们的 macOS 主机会报出 `198.18.0.1`）。物理网络里的手机路由不到该地址，于是"能用"的那一行正是必然让手机配对页打不开的那一行——却被和其他候选一样列出，等用户自己发现并避开。

## Decision

- **二维码链接固定指向公网基址。** 只要配置了 `publicBaseUrl`，`POST /api/pair/issue` 就用它构造 URL，无论存在多少局域网字面量：它是唯一随处可拨的基址，链接因此不再取决于扫码手机的网络。按请求传入的 `address` 载荷仍可为脚本调用方指定某个局域网字面量，下面的手动覆盖也能把基址钉在局域网。
- **由设备门控的落地页在连接时决定。** `/pair-app` 是本插件自己的页面，早在官方应用壳启动之前就已渲染，因此它带第二段内联脚本（`src/lan-source.ts`）：对每个广告的局域网源，向新增的 `/pair-ping` 信标各发一次 no-cors GET，总预算 800 ms。第一个应答的候选成为手机的源：落地页导航到 `<局域网源>/pair-app?grant=<新的一次性授权>`，UI 从局域网源启动。该决定连同它所依据的候选集写入 `sessionStorage`；候选集不变则不再探测，变了则重探。
- **探测不可能阻塞配对。** 它是在一张已经交付、已经可用的页面上即发即忘：没有候选应答、超时、存储不可用、乃至没有 `fetch`，都只是让公网页原地不动。只有下面的 `auto` 才会带上跳转。
- **跳转失败会回落。** 决定写着 `lan`，而当前页面**不在**任何局域网候选上，且发生在两分钟之内，读作"这次切换没生效"——手机重扫了二维码——于是落定为 `public`，而不是再次跳进同一个洞。更晚的再次访问会重新探测。
- **跳转所用的局域网凭据是一枚新的一次性授权，而不是令牌。** 授权表活在进程里而非某个源上，因此为公网落地页签发的授权可被局域网接口兑换，跳转重新配对的正是**同一个**设备会话，不会多出一台设备。它只出现在设备已经通过验证的那次落地页响应体里。
- **只广告可达的字面量。** `src/lan.ts`（`lanIPv4Addresses` / `lanIPv4Candidates`）按接口名丢弃隧道与 VPN 适配器（`utun*`、`tun*`、`tap*`、`ppp*`、`ipsec*`、`wg*`、`wireguard*`、`tailscale*`、`nordlynx*`、`proton*`、`openvpn*`、`zt*`）、容器与虚拟机网桥（`docker*`、`veth*`、`virbr*`、`vmnet*`、`vboxnet*`、`vEthernet*`、`br-*`），以及所有对端路由不到的地址：`0.0.0.0/8`、`127.0.0.0/8`、`100.64.0.0/10`（CGNAT，Tailscale 所在段）、`169.254.0.0/16`、`198.18.0.0/15` fake-IP 段、组播与保留段。`bridge0`/`br0` 被特意保留：真实的桥接局域网（macOS 互联网共享）正是手机能拨到的地址。同一份过滤后的列表同时供给二维码基址、落地页候选、栅栏的可信字面量与姿态探测，因此广告集与接受集不可能分叉。规则是否定清单而非 RFC1918 白名单：只有一条可路由字面量的独立主机仍保有可构造的基址。
- **`pairingSource` 是手动覆盖。** 仅补丁可见的配置字段（默认 `auto` | `public` | `lan`），每请求重读：`auto` 让二维码指向公网基址、落地页可以跳转；`public` 钉住公网基址且不派发探测；`lan` 直接用第一个局域网字面量作为二维码基址。设置卡片没有它的控件，因此卡片保存无法清空它。
- **面板陈述事实而非发问。** 单选组、其处理器、issue 响应中的 `lanAddresses` 一半，以及 `address.label` / `address.public` / `address.lan` / `address.hint` 四个键全部删除；面板只显示一行，说明当前链接走的是哪个源。

## How the probe gets past the mixed-content fence

https 页面通常不得 fetch `http://` 子资源，而每个局域网候选都是这种形状。以自签 https 源（公网 DNS 名、私有 IP 字面量、回环三种各一次）对 Chrome 实测，访问 `http://192.168.31.220/…`：请求被投递，控制台只报警告，图片变体更是明确**未被**升级——"This request was not upgraded to HTTPS because its URL's host is an IP address"。IP 字面量主机因此同时处于拦截与升级之外，这正是探测所依赖的形状。`fetch(..., { mode: 'no-cors' })` 形式会以不透明响应 resolve，可达性本身就是全部信号，不需要读取响应体。

## Testing

- `tests/lan.spec.ts`：以 Clash TUN 形状（`utun4` 的 `198.18.0.1` 与真实网卡并列）为锚，覆盖隧道/虚拟机接口名、每个被拒网段及其两侧、畸形字面量、接口顺序，以及只有可路由字面量的主机。
- `tests/lan-source.spec.ts`：把生成脚本跑在假 window 上——先应答者胜、授权编码、绝不二次导航、预算到期后落定 `public`、已在局域网源上的短路、同候选集跳过、候选集变化重探、刚失败跳转的回落、过期决定重探，以及不可读/被拒的存储。
- `tests/routes.spec.ts`：存在两个局域网字面量时二维码仍指向公网基址、落地页带上其余候选与一枚新授权、在局域网源上或任一覆盖下不带跳转、`public` 而公网基址未配置时以 `lan-required` 拒绝，以及 `/pair-ping` 对自家 authority（含探测产生的 cross-site 标记形状）答 204、对外来 Host 答 403。
- `tests/remote-entry.spec.tsx`：面板陈述来源，且不渲染任何单选行。

## Alternatives considered

- **把选择器收进折叠区保留。** 否决：这道题在桌面端答不了，而它造成的失败（手机停在一张永远加载不出的页面）不是用户能从那张提供选择的面板上诊断出来的。
- **让服务端按手机地址猜。** 隧道边缘会转发客户端地址，因此"同一 NAT"确实可推。否决：它分不清"同一 NAT"与"同一局域网"，猜错就会把手机导航到一个它到不了的地址且没有回头路——正是选择器造成的死胡同，只是现在自动发生。
- **严格的 RFC1918/ULA 白名单。** 否决：那会让只有一条可路由字面量的主机（VPS、独立服务器）完全没有可构造的基址，把原本可用的二维码变成 `lan-required` 横幅。否定清单丢掉了被举报的那一类噪声，却没有这个回归。IPv6 ULA 候选留在范围外：采样从来只做 IPv4，而广告一个带方括号的字面量会牵动每一处 URL 构造，只为没有受影响部署报过的场景。
- **只按接口名过滤，或只按地址段过滤。** 两者都必需且各自都不充分：WireGuard 的 `10.x` 通过所有网段规则，而一个改到 `198.18/15` 之外的 fake-IP 网关会通过所有名称规则。
- **不先探测就直接导航到某个局域网候选。** 否决：失败的导航在浏览器里没有返回路径，手机只会停在一张错误页上，而配对好的页面只在一次后退之外。
- **从 service worker 或隐藏 iframe 探测。** 否决：service worker 只存在于安全的公网源上（纯 HTTP 局域网源上从不会有），而 iframe 探测属于可拦截的混合内容——恰恰是过不了那道栅栏的那一种形式。
- **复用配对令牌进入局域网源。** 否决：令牌已在 `/pair-accept` 消费过，再消费一次会给同一台手机多配一个设备会话。绑定到既有设备的新授权才是精确的。
- **保留面板的 `lanAddresses` 响应字段。** 否决：它存在的意义是让选择器省掉一次往返；选择器一去，就没有任何东西读它。

## Consequences

- 同一网络的手机用一次额外导航（公网落地页 → 局域网落地页）换来一条不再走隧道的链接；局域网页面打开期间完全不依赖公网。
- 该特性依赖一项实测到的浏览器行为而非规范保证：若未来浏览器开始拦截或升级 IP 字面量主机上的 `http://` 子资源，每次探测都会失败，手机留在公网源——退化为今天的默认值，而不会坏掉。手动覆盖在这种情况下仍保住局域网路径。
- 跳转若发现那枚一次性授权已经不在，会落在双语的重新配对页上。重扫二维码即可恢复，而正是那条决定记录让恢复落在 `public` 而不是同一个失败的跳转上。
- 广告候选集如今是本机接口的**有意子集**：局域网地址落在被拒网段或接口名上的非常规部署会失去自动局域网路径，需要 `pairingSource: 'lan'`（它只把过滤后留下的第一个局域网基址指定为二维码基址——过滤后为空的机器仍需以别的方式让地址可达）。
- `198.18.0.1` 再也无法出现在二维码链接、落地页候选列表或栅栏的可信字面量里。
