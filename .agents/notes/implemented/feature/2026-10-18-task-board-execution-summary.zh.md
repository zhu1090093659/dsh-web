# Agent Note: Task board execution summaries

Status: implemented

## Problem

任务看板的每次执行只记录一个判决，别的一概不留：`result`、失败文本 `error`，以及级联记账。于是跑成功的卡片不留下任何产出的痕迹，父卡检查子卡时只能看到"成功了"，看不到交付了什么。读者剩下的选择只有猜，或者重做一遍。

另一个显而易见的做法——让跑完的子卡改写自己的 `description`——在设计上就是堵死的：卡片内容是计划，`canEditTaskContent`（`core/use-cases/task-update.ts`）在出现第一条执行记录时冻结标题、描述与 Prompt。这条冻结的意义是让"当初给 agent 的 Prompt"始终可审计；为了承载产出而重新打开它，等于让计划在执行之后仍可变。

## Decision

执行记录新增可选字段 `summary`：该次运行最后一条 assistant 消息的文本，外加它取自哪条会话事件（`seq`）（`core/tasks.ts` 的 `ExecutionSummary`，上限 `EXECUTION_SUMMARY_LIMIT` = 4000 字符）。

文本在结算时取，取自巡检已经读过的那批事件：`HostExecutionRunner.inspect` 从会话历史判定结果，同一窗口里的收尾文本随判决对象（`ExecutionInspection.summary`）一并返回 `TaskBoardHostService.settleAndNotify`，再由它交给 `HostTaskLedger.settle` 落到记录上。抽取本身（`core/execution-summary.ts`）是纯函数：只吃事件与执行的起始时刻。

实现遵守的规则：

- **窗口。** 只认 `startedAt` 及之后的事件。复用会话里带着之前几次执行的历史，它们的收尾话语不是本次的产出。
- **最后一条"有正文"的消息。** 末尾一条只含工具调用或推理的消息没有可记的东西，所以读者往回走到最后一条带文本块的消息。刻意排除推理与工具流量：一条以工具调用或思考块开头的摘要会把结论埋掉。
- **截断。** 超过上限时保留尾部，并把被丢掉的长度以 `[truncated N chars]` 前缀写明。收尾段落承载结论；需要全文的读者顺着 `summary.seq` 去会话历史里找。
- **缺失而不是空串。** 没有 assistant 正文、会话不可读、或会话还没建立就启动失败，字段整体缺席。结算路径上没有任何东西依赖摘要，所以结算不会因它失败。
- **失败也留文本。** `error` 保持原有含义；失败的运行把收尾文本记在它旁边，而不是替换它。
- **级联。** 级联父卡把自己的回合摘要连同自身结果（`ownResult`）一起记下；之后把卡片收口的折叠没有自己的会话，因此保留已经记下的内容不动。

该字段是加法式的可选字段，双向兼容。老文档没有 `summary`，`parseLedger` 也会修复读到的任何形状：不可用的值只丢自己，不牵连这次执行或整行任务。`isTaskRecordShape` 不变，所以老版本 Host 读新文档同样不受影响；不涉及账本 schema 升版，因为不需要迁移。

看板两侧读同一份快照：`TaskBoardHostService.snapshot()` 原样返回账本的任务行，所以该字段无需改桥就能到达手机与桌面，不认识这个键的客户端会忽略它。

Agent 工具面（`src/host/agent-tools.ts` 的 `executionView`）刻意不投影摘要：`task_board_get` 一次列出同一任务最多十条执行记录，十条 4000 字符的转录碎片会把模型的上下文淹掉。记录是事实源；把它投影进工具结果是一个独立决定，有自己的预算问题。

## Alternatives considered

**让跑完的卡片改写自己的 description 来承载交付物。** 否决：这正是 `canEditTaskContent` 的设计冻结；打开它会让计划——也就是当初用来 Prompt agent 的那段文字——在执行后仍可变，而可审计正是这条冻结存在的理由。

**存整段转录而不是收尾消息。** 否决：账本是决策记录，不是会话镜像。它会让每次执行的账本字节成倍增长，重复会话存储已经拥有的历史，并把远超"这次运行交付了什么"的信息塞给每个读者。

**超长消息保留头部而不是尾部。** 否决：assistant 的收尾段落陈述结论（交付了什么、什么失败了），开头段落通常只是铺垫。看板历史上的验收证据当时同样从尾部截断，理由一致。

**读不到时写入空字符串。** 否决：那会让"什么都没产出"与"看板读不到会话"无法区分，而这恰恰是父卡判断一次成功是否可信时需要的区别。

**每次级联折叠而不是每次执行记一条摘要。** 否决：折叠没有可读的会话，而折叠出来的文本是对没有任何单个会话做过的工作的合成断言。

## Consequences

结算后的执行记录现在仅凭看板快照就能回答"它交付了什么"，父卡因此可以直接读子卡的结果，而不必重做。代价是每条执行记录最多多出 4000 字符，并受既有的每任务保留 20 条执行的限制约束。

摘要在任何方向上都是信息性的：它不改变判决、不参与列移动的门禁，而它的缺席对没有正文的运行、对读不到会话的读者所结算的执行、以及对本次改动之前写下的每一条记录而言都是常态。

验证：`tests/execution-summary.spec.ts` 固定了抽取、执行窗口、截断、修复、持久化、两条结算路径与快照；`tests/host-runner.spec.ts` 固定了 runner 返回的判决携带收尾文本。包级门禁是 `pnpm --filter @linxin666/dsh-client-ui-task-board test`，加上仓库的 `pnpm test`、`pnpm typecheck` 与 `pnpm build`。

这些界面的字号尺度、结果槽位与折叠行为由[卡片界面呈现契约](2026-10-20-task-board-card-surface-contract.md)所有。
