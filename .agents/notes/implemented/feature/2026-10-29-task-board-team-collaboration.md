# Agent Note: Team collaboration extension for the task board

Status: implemented

## Problem

The DSH task board is a single-machine, single-writer Host ledger without the concept of humans or persons. In remote-bridge ([remote bridge protocol v1](../architecture/2026-10-16-remote-bridge-protocol-v1.md)), each paired device corresponds to a single public key record, and all calls are emitted under the identity of the same owner peer. The task board only tracks `initiatedBy` on execution records, with no concept of an assignee or owner. In small teams of 2 to 5 people, each member runs their own DSH and Agents, but there is no shared collaboration surface where human teams and Agent teams can assign tasks to one another, ask for help, and review work. The design reference is Linear.

## Decision

Team collaboration provides a shared external collaboration surface across multiple Hosts, comprising a cloud hub, a Host plugin, a mobile client, and task board contract extensions:

1. **Topology and deployment**: Multiple Hosts connect to a cloud hub `team-hub`. `team-hub` is one Go service with one SQLite file, listening on loopback behind a TLS-terminating reverse proxy and kept alive by systemd; it holds no Cloudflare dependency. Each team WebSocket push stream and its serialized writes are carried by one in-process channel, and the replay buffer lives in memory, so a restart makes clients resync. The tests run the real binary against a temporary SQLite file and a real HTTP listener on an ephemeral loopback port.
2. **Protocol and contract samples**: The communication protocol specification is fixed in `team-hub/PROTOCOL.md` (version 1.0.0). Host-side request and response samples live under `team-hub/contract/`, and the plugin fake hub and its tests read those same files, so a change on either side that is not reflected there fails a test. In the plugin test suite, hub-side interface samples (such as `hub.bootstrap`) are listed separately, and the Host never calls them at runtime.
3. **Bootstrap endpoint**: A `POST /api/v1/bootstrap` endpoint is available exclusively when the `teams` table is empty. The endpoint compares the `X-Bootstrap-Token` header against the Worker secret `BOOTSTRAP_TOKEN` to provision the initial team and administrator by email on a blank hub; upon successful team creation, the endpoint becomes naturally disabled (answering 409).
4. **Authority and task board extension**: `team-hub` is authoritative over collaboration fields (issues, assignees, collaboration status including `in_review`, comments, activity stream, pending questions); the Host executing the card is authoritative over execution (sessions, execution progress, and execution verdict; automated goal acceptance was removed in [2026-11-11](../simplification/2026-11-11-remove-task-board-goal-run-and-acceptance.md)). The extension plugin `@linxin666/dsh-task-board-team` (`packages/dsh-task-board-team`) connects as an external provider under the [task board extension contract](../architecture/2026-09-30-task-board-extension-contract.md), leaving core board columns and ledger structures unchanged. Local cards mirror hub issues via opaque `integrations` payloads and write back execution settlements to the hub. The task board extension contract (`TASK_BOARD_API_VERSION = 1`) provides two optional capabilities: `followUp` (queuing follow-up messages into a card's current or recent session) and `rework` (re-running an executed card within the same session).
5. **Identity and credential custody**: Human members authenticate via GitHub OAuth (Web and iOS), and administrators invite members by GitHub username. Each Host registers as an execution node using a Host Token minted by an administrator. The Host Token is stored under the configuration reference named by `hostTokenRef` (default `DSH_TEAM_HUB_TOKEN`). The current deployment environment serves no credential service (the profile does not mount a `@deepseek-ai/dsh-credentials` provider), so "Paste Host Token" in plugin settings is read-only, and the token can only come from the environment variable named by `hostTokenRef`.
6. **Assignees and claim gate**: Assignees can be humans or Agents. Each Agent member (sourced from `dsh-agents` member definitions) binds to a specific human member's Host, which claims and executes tasks under lease. When the Host is offline, cards on the hub remain in "waiting for execution node" and never migrate to other Hosts. The Host applies an upfront claim gate: when no available run workspace exists, the Host refuses to claim issues and reports a single visible problem; the effective workspace resolves in order from configured `workspaceId` to agent-bound `team.workspaceId` to empty. A mirror card without a workspace cannot start execution, which would leave the hub issue running indefinitely.
7. **Help-seeking routing and permission fencing**: Decision questions from `ask_user_question` and "stuck / requires input" signals are routed via the hub to the card's human assignee or reviewer; tool permission approvals remain strictly with the owner of the executing Host. When answered across multiple surfaces, the first response wins. The Host joins the in-process approval waterfall, claiming only "questions" from sessions associated with team cards while never claiming tool permission approvals.
8. **Human review and rework loop**: Once the card's own execution verdict settles as succeeded, hub status transitions to `in_review`; only when the reviewer approves does it enter Done. Upon rejection, review comments serve as rework instructions, re-running the task in the same session via `rework` (`reuseSession`). Local board columns maintain their closed set, with `in_review` existing solely on the hub.
9. **Comments and interaction tools**: Comments that `@` an Agent are delivered into its execution session as follow-up messages via `followUp`; Agents post comments via a new tool `team_comment` registered through the extension contract. All activities are recorded in the hub activity stream.
10. **Mobile entrance via Whale iOS**: The Whale App (the Remote project) serves as the primary entrance for human members, providing inbox, assignment, comments, review, and question answering. It connects directly to `team-hub` (HTTPS + WebSocket with GitHub login), with push notifications dispatched by the hub itself to APNs. The direct channel connecting to the user Host via Tailscale and bridge remains in place for inspecting sessions and approving tool permissions.
11. **Scope boundary and non-goals**: Planning layers including Projects, Cycles, Triage, and estimation remain excluded from Phase 1 to preserve a clean operational boundary.

## Alternatives considered

**Share a single Host**: Rejected because team members need to run Agents on their own machines using their respective repositories, local configurations, and API keys. A shared single host cannot accommodate distinct local developer environments.

**Replicate the full ledger across every Host via CRDTs**: Rejected because it requires altering the task board ledger data structures, writing complex conflict resolution merge logic, and breaking the single-writer invariant that guarantees local deterministic consistency.

**Pooled online Host task claiming**: Rejected because execution environments vary widely across machines (dependencies, tooling, working directories), and API expense attribution becomes ambiguous when arbitrary nodes pick up tasks.

**Allow teammates to approve tool permissions**: Rejected because tool execution runs directly on the local machine with its sandbox and host access; allowing remote team members to approve tool permissions violates the security boundary of local host execution.

**Custom identity with invite codes and device keys**: Rejected because building proprietary auth forces implementing bespoke account recovery, device revocation, and multi-device identity synchronization from scratch, adding maintenance burden with no security advantage over GitHub OAuth.

**Self-hostable Node.js service**: Rejected because maintaining both a Node.js server stack and a serverless edge deployment doubles the runtime surface and operational maintenance overhead; standardizing on Cloudflare Worker, D1, and Durable Objects keeps the operational footprint unified.

**Skip the `in_review` human review stage (or historically, trade human review off against the former automated acceptance gate)**: Rejected at design time because human review owns the collaborative sign-off into Done after an execution succeeds (the board's separate automated acceptance gate was later removed in [2026-11-11](../simplification/2026-11-11-remove-task-board-goal-run-and-acceptance.md), so a succeeded Host execution verdict now enters `in_review` directly).

**Comments circulated solely among humans**: Rejected because it eliminates the collaboration interface between humans and Agents; delivering `@` comments into agent sessions and letting agents reply via comments are essential for human-agent team interaction.

## Consequences

- End-to-end collaboration delivery: Supports card creation by human members, assignment to remote Agents, lease-backed claiming by Hosts, automated execution and verdict write-back of local mirror cards, progression to `in_review`, and manual rework or approval into Done, with all lifecycle events, questions, and comments recorded in the hub activity stream.
- Permission and security boundary isolation: Tool permission approvals remain strictly on the local executing Host and are never transmitted across machines or through the hub to remote members; remote reviewers cannot approve local tool operations.
- Claim gate guarantees execution reachability: The Host refuses to claim issues when no effective workspace is available and reports a clear diagnostic problem, preventing mirror cards from stalling and leaving hub issues stuck in `running`.
- Credential isolation and ambient fallback: The Host Token is never exposed in board snapshots or summaries; in deployments lacking a `@deepseek-ai/dsh-credentials` provider, the settings interface remains read-only and credentials rely entirely on environment variable injection.
- Fixed network and deployment boundaries: Service ingress is confined to the `workers.dev` domain to avoid conflict with the `dsh-market.com` wildcard route; local curl inspection requires an explicit proxy, whereas the Host's Node runtime reaches the endpoint directly.
- Bounded context and payload overhead: The `team_comment` tool uses a compact schema, appending follow-up messages into active sessions only upon `@` comments or decision questions; each mirror card adds an opaque `integrations` payload bounded at 64 KiB.
- Offline resilience: When a Host disconnects, its cards on the hub remain in "waiting for execution node" without migrating across nodes, awaiting reconnection of the original Host.
