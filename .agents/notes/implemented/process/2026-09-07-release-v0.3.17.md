# Agent Note: v0.3.17 release run

Status: implemented

## Problem

No decision record existed for the v0.3.17 release itself: it is the first release whose desktop-release workflow executed its new Windows lanes for real, and the run surfaced failures that needed coordinated repairs across two parallel agent sessions sharing one checkout.

## Decision

- Target defaulted to the next patch after v0.3.16 (npm latest 0.3.16 verified from the registry); the local gate suite and the auto-upgrade compatibility audit of v0.3.16..dev found no persisted-identifier or wire-protocol change — the aggregate tombstone subpath exports are themselves the deterministic migration shim for stale profile rows (#1381).
- Pre-release reconciliation: main carried one unpushed note commit (e9ffd799) whose patch already existed on dev as 5f64f101 (identical patch-id); resolved on the integration branch — main merged into dev, then main fast-forwarded back to dev.
- Release commit 46f1616f (chore(release): bump to 0.3.17), tag v0.3.17 cut from main; release.yml green in 5m35s: 19 family packages published at 0.3.17, the legacy aggregate left at its final 0.3.6 with deprecation metadata (window closed), mount smoke and headless render passed, and the GitHub Release was created from the committed bilingual notes (Chinese default view, English folded view, zero user-mention tokens).
- The desktop release failed on its first two real Windows-lane executions; three defects, three commits:
  - Git-bash GNU tar rejects drive-letter paths and cannot read zip: Windows-safe bsdtar extraction (36de9e36, [tar extraction fix](../bug-fix/2026-09-07-desktop-tar-windows-bsdtar.md)).
  - spawnSync cannot execute the pnpm.cmd shim without a shell (404f0c4a, [pnpm spawn shell fix](../bug-fix/2026-09-07-desktop-pnpm-spawn-windows-shell.md)) — landed by a parallel session repairing the same release; both sessions committed disjoint file sets through precise-path adds and neither clobbered the other.
  - setup-node v5's default package-manager cache demands pnpm in the Node-builtins-only windows CI job (e4b0b21a, recorded in [the Windows CI lanes note](../testing/2026-09-06-windows-ci-lanes-for-desktop.md)).
- The installers were rebuilt without re-cutting the tag: desktop-release.yml dispatched for the existing tag v0.3.17 from ref main (run 34077860441), which carried both desktop fixes.

## Alternatives considered

- Re-cutting the release as v0.3.18 to ship the desktop fixes: rejected — npm versions are immutable and the npm family was already published and correct; desktop assets are rebuildable per existing tag by dispatch, so only the desktop lane needed repairs.
- Attaching installers without a real Windows boot: rejected — that evidence is the point of the new gate.

## Consequences

- Both Windows lanes now hold real execution evidence at release time; the same failure classes cannot silently return without a red gate.
- Parallel-session coordination on the shared checkout held under the precise-path discipline: disjoint files, no blanket staging, no force pushes; the only cost was one redundant local edit attempt against a file the other session had just rewritten.
- Future workflow lanes should execute once on their target platform (push or dispatch) before the release window that first depends on them — the tag-time gate caught these defects by design, but the release then waits on repairs.
