# Agent Note: v0.3.18 release run

Status: implemented

## Problem

No decision record existed for the v0.3.18 release itself: it is the first release that ships a brand-new family package through the aggregate, and the run surfaced two operational facts that were not written down anywhere — npm propagation lag long enough to break a consumer install right after the tag, and a release gate that silently absorbs a missing publication instead of failing.

## Decision

- Target defaulted to the next patch after v0.3.17 (npm latest 0.3.17 verified from the registry); the family grew from 19 to 20 packages because `packages/dsh-model-capabilities` joined the aggregate, and `node scripts/verify-version.mjs 0.3.18` reports all 20 matching the tag.
- The v0.3.17..dev auto-upgrade compatibility audit found no persisted-identifier, profile-format, wire-protocol, or migration-surface change: `shared/host/legacy-migration.ts`, the doctor and plugin-manager profile writers, settings namespace ids, API paths, localStorage keys, and request headers are untouched. The release is backward compatible with no migration.
  - The new plugin reaches existing profiles through the aggregate's `dsh.bundle.patch`, which the host reads from the installed package at boot, not through a profile rewrite: the `web-ui-model-capabilities` row and the `./model-capabilities` subpath export ship in the same version, the row id stays inside the aggregate's `web-ui-*` namespace, and the host half dedups through mount-once.
  - Two deliberate behavior changes carry no persisted state: `ssh_cluster` requires aliases, environment, or tags and returns 400 otherwise (#1417), and the pet display-size bound widens from 512 to 1024 with existing values still valid.
- Release commit 2d59d099 (chore(release): bump to 0.3.18) landed on dev, fast-forwarded into main, and tag v0.3.18 was cut from main.
- The release build also refreshed `packages/dsh-web-all/lib/client.js`, which had drifted from its child sources: the committed aggregate bundle still lacked the task-board `reuseSession` UI and the skill-explorer filter-class rename from the range. The rebuild, `market:build`, and the committed `market/dist` ride in the release commit.
- The committed bilingual notes at `docs/release-notes/v0.3.18.md` were used verbatim by the pipeline (the GitHub Release body differs only by GitHub's trailing newline), with a zero user-mention count.
- Post-publish recovery was not needed: every one of the 20 packages reached npm at 0.3.18, but `@linxin666/dsh-client-ui-web-ui-settings@0.3.18` was unreadable for about ten minutes after the pipeline reported it published. The version document appeared at 13:57 and the tarball at 14:02, so the first isolated upgrade attempt failed with `ERR_PNPM_FETCH_404` on that tarball and succeeded on retry.
- The release gate that should have caught a real missing publication did not exist: `scripts/e2e-mount-rewrite` auto mode rewrites any family dependency it cannot find on the registry to a workspace tarball, so the mount smoke passes even when the registry lacks a version the aggregate depends on. The new `scripts/verify-registry.mjs` closes it: after the publish step the pipeline asserts every non-private family package version resolves from the registry, retrying the sweep on a bounded budget so propagation lag passes and a lost publish fails.

## Alternatives considered

- Re-running the tag push to republish: rejected — npm versions are immutable, so a second run cannot publish 0.3.18 again and would only add noise; the registry converged on its own.
- Publishing the lagging package manually: rejected as unnecessary once the version document and tarball both resolved; a manual publish would also have raced the pipeline's own artifact.
- Making the mount smoke fail on any unpublished family dependency: rejected — it runs inside the same lag window and would turn every release red for a self-healing propagation delay; the registry assertion waits out the lag with the same evidence.
- Folding the gate fix into the release commit: rejected — v0.3.18 was already tagged and published; the gate ships as a follow-up commit on dev and main.

## Consequences

- Existing profiles gain the new capability on upgrade with no profile edit; the upgrade is a plain package update whose only observable delta is one extra `web-ui-model-capabilities` row (verified 19 to 20 rows in `--dump-config`).
- A publish that never reaches the registry now fails the release run before the mount smoke and the GitHub Release, instead of shipping a tag whose aggregate cannot install.
- The gate costs one registry sweep per release and up to the retry budget (about ten minutes) only when a version is missing, which is exactly the propagation window observed here.

## Testing

- Local gates on dev before and after the bump: sync-shared:check, typecheck, test, test:scripts, docs:check, i18n:check, aggregate:check, runtime-deps:check, market:check, skin-center:check, community:check — all green.
- release.yml run 34234368345: green (publish job plus the mount-smoke and GitHub Release job); 20 family packages published at 0.3.18, the legacy aggregate left at its final 0.3.6 with deprecation metadata.
- Registry assertion after propagation: all 20 `@linxin666/*@0.3.18` version documents return 200, and `npm view` dist-tags latest is 0.3.18 for dsh-web-all, dsh-client-ui-skin-center, dsh-client-ui-model-capabilities, and dsh-client-ui-web-ui-settings.
- Isolated DSH_HOME upgrade (/tmp/dsh-web-upgrade-0.3.18, official CLI, the real ~/.dsh untouched): the profile installed `@linxin666/dsh-web-all@0.3.17`, then `dsh plugin --profile web add @linxin666/dsh-web-all@0.3.18` upgraded it in place; `dsh --profile web --dump-config` shows the bundle list unchanged and the row count 19 to 20 with `web-ui-model-capabilities` pointing at `@linxin666/dsh-web-all/model-capabilities`; `dsh web` boots with no errors, the token URL redirects to a 200 index, and the served module list contains `@linxin666/dsh-web-all/client.js`.
- Full-suite runs: `pnpm test` passed before and after the bump and again on a clean re-run; one follow-up run failed only on `packages/dsh-remote-web-ui/tests/loopback-proxy.spec.ts` (stops the inner request when the outer client aborts mid-body), which passes 6/6 in isolation and has no source change in this range — a load-sensitive flake under the parallel suite, not a release regression.
- desktop-release.yml run 34234368305: green (Windows payload boot smoke plus packaging); the v0.3.18 Release carries mac-arm64 and mac-x64 dmg/zip plus win-x64 exe/zip installers.
- New gate tests: `node --test scripts/verify-registry.test.mjs` passes 5 cases (URL encoding, miss ordering, network and HTTP misses, retry-until-resolved, budget exhaustion).
