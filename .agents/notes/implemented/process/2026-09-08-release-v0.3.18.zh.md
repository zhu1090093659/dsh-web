# Agent Note: v0.3.18 发布运行记录

Status: implemented

## Problem

v0.3.18 这次发布本身没有决策记录：它是第一个把全新家族包经聚合包发布的版本，而这次运行暴露了两件此前没有落到文档里的事实——npm 传播延迟长到足以让 tag 推送后的真实安装失败，以及一条发布门禁会静默吞掉缺失的发布而不是报错。

## Decision

- 目标版本默认取 v0.3.17 的下一个补丁号（已从 registry 验证 npm latest 为 0.3.17）；家族从 19 个包增加到 20 个，因为 `packages/dsh-model-capabilities` 加入了聚合包，`node scripts/verify-version.mjs 0.3.18` 报告 20 个包全部与 tag 一致。
- v0.3.17..dev 的自动升级兼容性审计未发现持久化标识符、profile 格式、线协议或迁移面变更：`shared/host/legacy-migration.ts`、doctor 与 plugin-manager 的 profile 写入器、设置命名空间 id、API 路径、localStorage 键与请求头均未改动。该版本向后兼容，无需迁移。
  - 新插件经聚合包的 `dsh.bundle.patch` 到达既有 profile——host 在启动时从已安装的包里读取该文件，而不是改写 profile：`web-ui-model-capabilities` 行与 `./model-capabilities` 子路径导出在同一版本内发布，行 id 留在聚合包的 `web-ui-*` 命名空间内，host 半区由 mount-once 去重。
  - 两处有意的行为变更不涉及持久化状态：`ssh_cluster` 必须给出 aliases、environment 或 tags，否则返回 400（#1417）；宠物显示尺寸上限由 512 放宽到 1024，既有取值仍然有效。
- 发布提交 2d59d099（chore(release): bump to 0.3.18）落在 dev 上，快进合入 main，tag v0.3.18 从 main 打出。
- 发布构建同时刷新了 `packages/dsh-web-all/lib/client.js`：已提交的聚合客户端 bundle 相对子包源码已经漂移，缺少本区间内 task-board 的 `reuseSession` 界面与 skill-explorer 的筛选类名重命名。重建产物、`market:build` 与 `market/dist` 一并进入发布提交。
- 管线逐字采用了入库的双语 notes `docs/release-notes/v0.3.18.md`（GitHub Release 正文只差 GitHub 追加的一个换行），user-mention 计数为 0。
- 发布后无需补救：20 个包全部以 0.3.18 到达 npm，但 `@linxin666/dsh-client-ui-web-ui-settings@0.3.18` 在管线报告发布成功后约十分钟内不可读。版本文档在 13:57 出现，tarball 在 14:02 出现；第一次隔离升级因此在该 tarball 上以 `ERR_PNPM_FETCH_404` 失败，重试即成功。
- 本应抓住真实发布缺失的那条门禁此前并不存在：`scripts/e2e-mount-rewrite` 的 auto 模式会把 registry 上找不到的家族依赖改写为 workspace tarball，于是聚合包依赖的某个版本即使缺失，挂载冒烟照样通过。新增的 `scripts/verify-registry.mjs` 补上这一环：发布步骤之后，管线断言每个非 private 家族包的该版本都能从 registry 解析，以有界重试预算轮询整个集合，使传播延迟可通过、真正丢失的发布失败。

## Alternatives considered

- 重推 tag 再发布一次：否决——npm 版本号不可复用，第二次运行无法再发布 0.3.18，只会增加噪音；registry 自身已经收敛。
- 手动补发滞后的包：否决——版本文档与 tarball 随后都解析成功，手动发布没有必要，而且会与管线自己的产物竞争。
- 让挂载冒烟在任何家族依赖未发布时失败：否决——它运行在同一段延迟窗口内，会把每次发布都因自愈型的传播延迟而变红；registry 断言用同样的证据等过了这段延迟。
- 把门禁修复并入发布提交：否决——v0.3.18 已经打好 tag 并发布完成；门禁作为后续提交分别进入 dev 与 main。

## Consequences

- 既有 profile 升级即获得新能力，无需改 profile；升级就是一次普通包更新，唯一可观察的差异是多出 `web-ui-model-capabilities` 一行（`--dump-config` 实测 19 到 20 行）。
- 永远到不了 registry 的发布现在会在挂载冒烟与 GitHub Release 之前让发布运行失败，而不是发出一个聚合包装不上的 tag。
- 该门禁每次发布只多一次 registry 扫描；只有版本缺失时才会花到重试预算（约十分钟），而这正是本次观测到的传播窗口。

## Testing

- 本地门禁在 bump 前后各跑一遍：sync-shared:check、typecheck、test、test:scripts、docs:check、i18n:check、aggregate:check、runtime-deps:check、market:check、skin-center:check、community:check 全绿。
- release.yml run 34234368345：全绿（发布 job 与挂载冒烟 + GitHub Release job）；20 个家族包以 0.3.18 发布，legacy 聚合包保持终版 0.3.6 并带弃用元数据。
- 传播完成后的 registry 断言：20 个 `@linxin666/*@0.3.18` 版本文档全部返回 200，`npm view` 的 dist-tags latest 在 dsh-web-all、dsh-client-ui-skin-center、dsh-client-ui-model-capabilities、dsh-client-ui-web-ui-settings 上均为 0.3.18。
- 隔离 DSH_HOME 升级（/tmp/dsh-web-upgrade-0.3.18，官方 CLI，真实 ~/.dsh 未被触碰）：profile 先安装 `@linxin666/dsh-web-all@0.3.17`，再用 `dsh plugin --profile web add @linxin666/dsh-web-all@0.3.18` 就地升级；`dsh --profile web --dump-config` 显示 bundle 列表不变、行数由 19 变 20，`web-ui-model-capabilities` 指向 `@linxin666/dsh-web-all/model-capabilities`；`dsh web` 启动无报错，token URL 重定向后首页返回 200，服务的模块列表包含 `@linxin666/dsh-web-all/client.js`。
- 全套运行：`pnpm test` 在 bump 前后各通过一次，干净重跑也通过；有一次后续运行仅 `packages/dsh-remote-web-ui/tests/loopback-proxy.spec.ts`（外层客户端在响应体中途断开时停止内层请求）失败，该用例单独运行 6/6 通过、本区间内无源码改动——并行跑全套时受负载影响的抖动，不是本次发布的回归。
- desktop-release.yml run 34234368305：全绿（Windows 载荷启动冒烟与打包）；v0.3.18 Release 附带 mac-arm64、mac-x64 的 dmg/zip 与 win-x64 的 exe/zip 安装包。
- 新门禁测试：`node --test scripts/verify-registry.test.mjs` 5 个用例通过（URL 编码、缺失顺序、网络与 HTTP 缺失、重试至全部解析、预算耗尽）。
