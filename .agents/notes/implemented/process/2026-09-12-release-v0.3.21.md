# Agent Note: v0.3.21 release run

Status: implemented

## Problem

The v0.3.20 release record covered a host-contract change with a small source delta. v0.3.21 is the opposite shape: 108 commits and 1674 changed files across plugins, skins, the market site and the shared client runtime, and it is the first release whose commit must also carry refreshed committed-lib fingerprints. The mandatory automatic-upgrade audit therefore had to classify a wide delta, and the release procedure itself needed steps the existing record did not name.

## Decision

- Target defaulted to the next patch after v0.3.20 (registry `latest` verified 0.3.20); `node scripts/verify-version.mjs 0.3.21` reports all 21 family packages and the root aggregate pin matching v0.3.21.
- The v0.3.20..dev compatibility audit found no persisted-identifier, profile-format, wire-protocol, or migration-surface break. Frozen and verified unchanged: `packages/dsh-web-all/cordis.patch.yml` (every `web-ui-*` row id, the self row, `config.plugin`, the disabled-by-default rows), the aggregate `exports` map and the browser loader id, every package `name`, every `dsh.engines.dsh` (`>=0.1.5-rc.1`, unchanged and not above the host the pipeline mounts), `shared/host/legacy-migration.ts`, `scripts/publish-legacy-aggregate.mjs`, and the Doctor migration code. Aggregate membership is unchanged: `aggregate.yml` differs only in a comment, and `aggregate:check` reports 20 rows / 19 deps / 17 client children at both revisions.
- The changes are additive and backward compatible: `dsh-better-sidebar` moves to 0.19.0 with an identical bundle patch, `exports`, `dsh.client.inject`, dependencies and `files` (only version, peer ranges and copy differ); `POST /api/pet/set-skin` is new; the persisted pet `skins` map and `incomeCarryMs` / `restoreCarryMs` fields and the usage `spendWatch` field are new and absent-tolerant; the market Worker widens its `kind` enum with `preset`, which needs no D1 migration because `kind` is an unconstrained TEXT column; and dsh-liangshen gains an additive `./client` export and `dsh.client` block (its new `@deepseek-ai/*` entries are devDependencies, not peer dependencies).
- Two non-blocking degradations for narrow cohorts are published in the release notes rather than omitted: the reviewed-hook re-pin refuses the executable hooks facet of a provenance-less Workshop install of `xp` or `maid-atelier` until it is reinstalled (the skin still renders), and the LiangShen preset rewrite overwrites and prunes `~/.dsh/.agent-presets/liangshen`, so sessions created by earlier revisions whose durable history already holds the retired message kind stay unopenable.
- The root alias pin is part of the release contract: `scripts/verify-version.mjs` fails the tag pipeline unless root `package.json`'s `@linxin666/dsh-web-all` dependency equals the tag exactly, and the `pnpm-lock.yaml` importer specifier moves with it. The release skill's bump block names only `packages/**`, so this run bumped the root pin and the lockfile specifier explicitly.
- The version bump rewrites three committed bundles (`dsh-market`, `dsh-web-all` and `skins/skin-center` `lib/client.js`), so the release commit carries them together with `scripts/lib-artifact-fingerprints.json` refreshed by `pnpm libs:write`; the [committed lib artifact gate](2026-09-12-committed-lib-artifact-gate.md) makes that mandatory from this release on.
- The legacy dual-publish window stays hard-closed (`LEGACY_DUAL_PUBLISH_WINDOW_OPEN = false`): `@linxin666/dsh-web-ui-all` stays frozen at its final 0.3.6 with the migration deprecation message, and the pipeline's legacy step is a no-op.
- Desktop packaging resolves the preinstalled profile seed from the registry at build time; the committed seed stays at 0.3.19 as the disabled-lane fallback.
- The bilingual notes are corrected by hand rather than shipped from the draft: the generator drops subjects that start with a byte-order mark or lack a conventional-commit prefix, which silently lost the Blueprint skin and the dsh-backup community-index registration from this release's draft.
- The bump commit `chore(release): bump to 0.3.21` carries the 21 manifests, the root pin, the lockfile specifier, the three regenerated bundles, the refreshed fingerprints and `docs/release-notes/v0.3.21.md`; it is committed on dev, fast-forwarded into main, and the tag is cut from main.

## Alternatives considered

- Shipping the generated notes draft verbatim: rejected - it omits the two commits above, so the release page would have understated the release.
- Bumping only `packages/**` as the release skill's command block shows: rejected - the root pin and the lockfile specifier would stay at 0.3.20 and `verify-version.mjs` would abort the pipeline before anything reaches npm.
- Treating the reviewed-hook re-pin as a release blocker: rejected - it is the designed behaviour of the reviewed identity, whose recovery path is deliberately pinned to the current release; the skin keeps rendering, and the affected population is provenance-less installs of the two skins this release changes anyway.
- Bumping the committed desktop seed to 0.3.21: rejected - the packaging path resolves the tag version from the registry, and the committed value is the documented fallback for a disabled publish lane, so it must keep naming a version that exists.
- Verifying only the fresh install: rejected - the isolated in-place upgrade from a published 0.3.20 profile is the path existing users take.

## Consequences

- Upgrading from v0.3.20 needs no migration. The plugin manager's update path is the only path that performs this version upgrade, because Doctor's pre-start migration is a no-op for a profile already on the current package name.
- A provenance-less Workshop install of `xp` or `maid-atelier` loses the executable hooks facet until it is reinstalled from the Workshop; the release notes state the recovery.
- Sessions created by earlier LiangShen revisions that already contain the retired message kind stay unopenable; this release stops producing new ones.
- Every later release must bump the root pin and the lockfile specifier and refresh the lib fingerprints alongside the family versions.

## Testing

- Local gates on the bumped tree: sync-shared:check, typecheck, test, test:scripts, aggregate:check, runtime-deps:check, market:check, skin-center:check, libs:check, i18n:check, docs:check - all pass.
- Mount smoke `bash scripts/e2e-mount.sh`: the freshly packed 0.3.21 aggregate mounts into a scratch profile under the real 0.1.5-rc.1 CLI, `dsh web` boots, and the Playwright headless render passes 1/1 with better-sidebar mounted and the excluded archive-manager absent.
- Isolated in-place upgrade (scratch DSH_HOME under /tmp, the real home untouched): the profile installed `@linxin666/dsh-web-all@0.3.20` from the registry, then upgraded with the locally packed 0.3.21 aggregate whose unpublished family dependencies were rewritten to workspace tarballs. `dsh --profile web --dump-config` is byte-for-byte identical before and after - 173 rows each, 173 unique ids, zero duplicates, zero rows added or removed - and the profile bundles list is unchanged, so the upgrade introduces no double mount, duplicate row or lost configuration.
- The upgraded profile boots and serves: an unauthenticated root is refused, the tokenized launch URL answers 303 and then 200 with a cookie jar, and the served index references both `@linxin666/dsh-web-all/client.js` and `dsh-better-sidebar/client.js`.
- Not covered locally: Windows and Linux runtime verification (the tag pipeline runs the mount smoke on ubuntu-latest and boots the Windows desktop payload), failure injection and retry of the upgrade path, and a live LLM tool call.
