# Agent Note: v0.3.22 release run

Status: implemented

## Problem

The v0.3.21 record established the standing release rules: the root alias pin and the lockfile specifier move with the tag, the version-embedding bundles are regenerated in the same commit, and the automatic-upgrade compatibility audit is a hard gate. v0.3.22 is the first release to run under those rules on an ordinary plugin-and-skin delta (39 commits, 212 changed files), so this note records what the audit froze and which artifacts the bump actually moves.

## Decision

- Target defaulted to the next patch after v0.3.21 (registry `latest` verified 0.3.21); `node scripts/verify-version.mjs 0.3.22` reports all 21 family packages and the root aggregate pin matching v0.3.22.
- The v0.3.21..dev compatibility audit found no persisted-identifier, profile-format, wire-protocol, or migration-surface break. Frozen and verified unchanged: `packages/dsh-web-all/cordis.patch.yml` (every row id and the self row), aggregate membership (20 rows / 19 dependencies / 17 client children at both revisions), the aggregate `exports` map and browser loader id, every package `name`, every `dsh.engines.dsh` floor (`>=0.1.5-rc.1`, unchanged and not above the `0.1.5-rc.1` host the pipeline mounts), `shared/host/legacy-migration.ts`, `scripts/publish-legacy-aggregate.mjs`, and the Doctor migration code.
- The changes are additive and backward compatible. `dsh-task-board` gains an optional `tags` field on the persisted task record: the store repairs it field by field on read (`normalizeTags`), the import path validates it strictly (`isTaskTagList`), and an older client still reads and writes the row. The Skin Center gains an optional `bubbleBlur` field in its background configuration (default 10px). Neither change renames an existing key or alters the persisted shape of any other field.
- One non-blocking degradation is published in the release notes rather than omitted: the Miku skin redesign changes the skin manifest, so the reviewed hook identity re-pins (its `manifestSha256` moves while `hooksSha256` is unchanged) and an earlier install loses the executable hooks facet until it is reinstalled from the Workshop; the skin keeps rendering.
- A version-only bump moves exactly three committed bundles (`dsh-market`, `dsh-web-all` and `skins/skin-center` `lib/client.js`) and leaves `scripts/lib-artifact-fingerprints.json` untouched: the artifact guard fingerprints source inputs and the bump changes no source, so `pnpm libs:check` passes on the bumped tree. The release commit carries the 21 manifests, the root pin, the lockfile specifier, those three bundles and `docs/release-notes/v0.3.22.md`; it is committed on `main`, tagged from there, and merged back into `dev`.
- The legacy dual-publish window stays hard-closed (`LEGACY_DUAL_PUBLISH_WINDOW_OPEN = false`): `@linxin666/dsh-web-ui-all` stays frozen at its final 0.3.6 with the migration deprecation message, and the pipeline's legacy step is a no-op.
- Desktop packaging resolves the preinstalled profile seed from the registry at tag time, so the committed seed is not bumped.
- The tag was already pushed when this record was written, so the record rides the following `dev` commit rather than the tagged commit; the published release is unaffected.

## Alternatives considered

- Bumping only `packages/**` as the release skill's command block shows: rejected - the root pin and the lockfile specifier would stay at 0.3.21 and `verify-version.mjs` would abort the pipeline before anything reaches npm.
- Re-running `pnpm market:build` and committing `market/dist`: rejected - the market inputs are the community index, the skin catalog and the presets, none of which carries a family package version; the rebuild produced no diff and `market:check` stayed green on the committed dist.
- Treating the Miku reviewed-hook re-pin as a release blocker: rejected - it is the designed behaviour of the reviewed identity, the skin keeps rendering, and the recovery (reinstall from the Workshop) is stated in the release notes.
- Force-moving the pushed tag to include this record: rejected - the tag is published and npm forbids reusing a version, so rewriting it would re-run the publish lane against an occupied version.
- Replacing the merge back into `dev` with a rebase: rejected - the tag's commit must stay an ancestor of the integration branch, and `origin/dev` already carried concurrent work.

## Consequences

- Upgrading from v0.3.21 needs no migration: neither automatic path has anything to change, so the plugin-manager update and Doctor's pre-start migration land on the same package set.
- A provenance-less or earlier Workshop install of the Miku skin loses the executable hooks facet until it is reinstalled from the Workshop; the release notes state the recovery.
- Every later release must keep the root pin, the lockfile specifier and the version-embedding bundles in the same commit; the source fingerprints change only when source changes.
- `dev` receives concurrent work from other sessions, so post-release integration is a merge rather than a fast-forward whenever `origin/dev` has moved on.

## Testing

- Local gates on the bumped tree before the tag: `pnpm sync-shared:check`, `pnpm typecheck`, `pnpm test`, `pnpm test:scripts`, `pnpm aggregate:check`, `pnpm runtime-deps:check`, `pnpm market:check`, `pnpm skin-center:check`, `pnpm skin-hooks:check`, `pnpm community:check`, `pnpm docs:check`, `pnpm i18n:check` and `pnpm libs:check` all pass.
- Tag pipeline run 34762329210 succeeded in 11m15s; both jobs completed, including `Verify package versions match the tag`, `Publish packages to npm`, `Verify published versions on the registry`, the mount smoke and `Create GitHub Release`.
- Registry verification after the run: all 21 family packages resolve at 0.3.22; `@linxin666/dsh-web-ui-all` stays at 0.3.6 with its deprecation message; the GitHub Release body carries the committed bilingual notes with zero rendered `user-mention`.
- Merging the five concurrent `origin/dev` commits into the release commit re-ran the full gate suite on the merged tree, and rebuilding the aggregate from the merged sources was byte-identical to git's auto-merged bundle.
- Not covered locally: Windows and Linux runtime verification (the tag pipeline runs its mount smoke on ubuntu-latest), failure injection and retry of the upgrade path, and a live LLM tool call.
