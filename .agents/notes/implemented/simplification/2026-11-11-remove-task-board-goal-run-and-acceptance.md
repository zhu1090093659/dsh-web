# Agent Note: Remove task-board /goal runs and goal acceptance

Status: implemented

Supersedes [Task runs start with dsh's built-in /goal](../feature/2026-09-27-task-board-goal-run.md) and [Task-board goal acceptance](../feature/2026-09-30-task-board-goal-acceptance.md), and narrows the built-in topic list of [Task-board settings open as collapsed topic cards](../feature/2026-10-01-task-board-settings-disclosure-cards.md). Both superseded feature notes stay in the active tree as historical records because on-disk v7 ledgers and legacy profile patches retain load-time compatibility handling rather than a destructive migration; neither note is authority for current behavior.

## Problem

`packages/dsh-task-board` carried two coupled subsystems around multi-round autonomous execution: a two-level native `/goal` opt-in (`goalRunEnabled` on the settings card and `TaskRecord.goalRun` on each card, both off by default) and an end-to-end judge acceptance subsystem (`goalVerification`, `goalVerificationModel`, `goalVerificationReasoningEffort`, `goalVerificationCallTimeoutSeconds`, and `goalVerificationBudgetSeconds` settings; `TaskRecord.skipVerification`; `ExecutionRecord.verification` contracts, attempts, applicability, and post-pass detail cleanup; the `tools/pre-execute` gate on `update_goal(action: complete)`; a six-call LLM judge runner with workspace diff evidence rendering; the `reset-verification` action on `task_board_manage`; `VerificationReport` in the execution log; and the Task acceptance section on the settings card).

Together they accounted for the largest configuration, protocol, ledger, and UI surface in the package while sitting inert for every default card run. Multi-step board work is already handled inside one root turn through parent-card subtask orchestration under the `liangshen` dispatcher preset, whereas `/goal` continuation coupled board settlement to `session/projections` phase reads, burned up to twelve extra LLM judge requests per execution cycle, and introduced anomaly/invalid hold states that required manual `reset-verification` intervention.

## Decision

- **Plain single-turn execution only.** Every manual, scheduled, and reworked board run executes as one ordinary turn: `HostExecutionRunner` applies the pinned workspace, agent preset, `/permission`, and model/reasoning effort, queues the composed task prompt, never dispatches `/goal` through `commands`, never reads `session/projections` to inspect goal phase, and settles strictly from that turn's `turn/end` result.
- **Full removal of the `/goal` switches and the acceptance subsystem.** `goalRunEnabled` and all five `goalVerification*` keys leave the plugin configuration schema and the settings card. `TaskRecord.goalRun`, `TaskRecord.skipVerification`, and `ExecutionRecord.verification` (`ExecutionVerification`, frozen contracts, attempt records, applicability tags, and detail cleanup) leave task and execution records, wire protocol actions, `task_board_create` / `task_board_update` inputs, the `NewTaskModal` and `TaskDetail` checkboxes, and `ExecutionLog`. The `tools/pre-execute` `update_goal` gate, judge runner, workspace diff evidence renderer, `VerificationReport` component, and `task_board_manage(action: 'reset-verification')` are deleted. The host model-catalog helper and HTTP route drop their acceptance wrapper (`modelCatalogOptions()` and `GET /api/task-board/model-catalog`).
- **Non-failing legacy ledger and config compatibility.** The authoritative ledger `$DSH_HOME/task-board/ledger-v2.json` remains at `schemaVersion: 7` with no schema bump. Existing task rows carrying `goalRun` or `skipVerification` and existing execution rows carrying `verification` (from historical schema v5) load without error: normalization ignores and drops those retired fields in memory, never rejects a row because of them, and never writes them back, preserving every card and historical execution record. Non-strict plugin config loading likewise ignores leftover `goalRunEnabled` and `goalVerification*` keys in older profile patches.
- **Remote surface alignment.** `packages/dsh-task-board-remote` removes `goalRunEnabled` from `board.options` `meta` (`META_KEYS`) and serves `{ catalog, meta: { sessionDefaultPermission?, cardDefaults?, maxSubtaskDepth? } }` over `modelCatalogOptions()`.
- **Unchanged board contracts.** Session reuse (`reuseSession`), fail-closed pins, handover bundles and the human permission confirmation gate, 5-field cron and one-shot schedules with run budgets, subtask lineage and `liangshen` parent-card dispatch, card attachments, daily token spend cap (`spendBudgetTokens`), and external provider extensions (`dsh-task-board-github`, `dsh-task-board-team`) keep their existing behavior and copy.

## Alternatives considered

- **Keep `/goal` runs and remove only the judge acceptance gate.** Rejected: without a completion gate, `/goal` continuation relies on unverified self-reported `update_goal(action: complete)` calls or burns continuation rounds up to the harness limit — the exact failure mode that forced the acceptance gate to be built — while subtask trees under `liangshen` already cover multi-step execution inside one turn.
- **Keep the retired config keys, checkboxes, and tool parameters as no-op tombstones.** Rejected: leaving inert controls in the settings card, task dialogs, and model-facing tool schemas misleads operators and agents into configuring behavior the runner no longer performs; silent load-time stripping already protects existing data.
- **Bump the ledger schema to v8 or reject rows containing retired fields.** Rejected: ignoring optional legacy properties requires no structural migration; bumping `schemaVersion` forces unnecessary rewrite churn across upgrades, and rejecting legacy rows would break existing user boards.
- **Consolidate and delete the 2026-09-27 and 2026-09-30 feature notes.** Rejected under `.agents/notes/implemented/AGENTS.md`: a feature-addition note may be consolidated and deleted only when the feature is absent from durable formats, migration, and compatibility behavior as well as production code and current docs; because schema v5 remains part of the v2-to-v7 migration chain and the loader retains explicit compatibility stripping for persisted `goalRun`, `skipVerification`, and `verification` fields, both notes remain cross-linked as historical records.

## Consequences

- Every card execution settles on its turn's `turn/end` verdict and incurs zero judge LLM calls; workflows that need multi-step decomposition use subtasks under `liangshen` or native `/goal` inside an interactive chat session.
- The settings card's built-in disclosure list shrinks to two topics (Basics and New-card defaults, with the Runtime behavior and Task acceptance sections removed) ahead of provider extension sections, and the task detail's Run Mode fold (`detail.settings.run`, unified from the former Advanced settings title to match the create dialog) holds session reuse alone.
- Upgrading an existing `$DSH_HOME` succeeds in place without data loss; retired `goalRun`, `skipVerification`, and `verification` fields are silently omitted the next time the ledger writes.
- Callers invoking `task_board_manage` with `reset-verification` receive a standard invalid-action refusal, and paired remote clients reading `board.options` receive `{ catalog, meta }` without acceptance contracts or `goalRunEnabled`.
