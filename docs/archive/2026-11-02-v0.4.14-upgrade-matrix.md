测试桩替代（唯一的披露替换）：发布前 npm 官方源 `https://registry.npmjs.org/@linxin666%2Fdsh-web-all/latest` 仍返回 0.4.13，故网关仅将文档化的测试缝隙 `fetchManifest` 指向本地 fixture 注册表（`127.0.0.1:48811`），其余 `updateHandler` -> `CliGateway.update` -> `dsh plugin add` -> `verifyBoot` -> `pruneOrphanOverrides` -> `writePatchAtomic` 全流程均为发布生产路径。

### 5.2 首轮执行发现：FAIL（已退役行未清理）

首轮升级执行后，整体升级链路顺利通过，`package.json`、bundles 以及插件数据均更新到 0.4.14，但孤儿覆盖行未被清理：

```
$ ... dsh --profile upgradeB --dump-config
dsh: [.../cordis.patch.yml] patch: entry "web-ui-update" not found
```

现象：每次 profile 启动时控制台均出现一条 `patch: entry "web-ui-update" not found` 警告；检查 `cordis.patch.yml` 发现指向已退役行 `web-ui-update` 的 `disabled: true` 覆盖依然存留，未发生清理且未生成备份。

根因排查：
1. `CliGateway.pruneOrphanOverrides` 内部依赖 `liveOverrideIds` 判定哪些覆盖行依然有效。
2. 修复前的 `liveOverrideIds` 实现遍历 `manifest.bundles`，要求每个包的 `package.json` 都能在当前 profile 目录下被解析（`join(profileDir, 'node_modules', ...name.split('/'), 'package.json')`）。
3. 官方 CLI 创建的 profile 天然在 `dsh.profile.bundles` 中包含未安装的官方 bundle（`@deepseek-ai/dsh-base` 与 `@deepseek-ai/dsh-web-app`）；这两者由宿主运行时从宿主自身安装树加载，profile 内并无实体目录。
4. 导致 `readFile` 发生 ENOENT 抛错，`liveOverrideIds` 返回 `undefined`，最终 `pruneOrphanOverrides` 命中安全防御直接 `return []`，跳过了对孤儿覆盖行的裁剪。

### 5.3 根因排查、归因前置检查与补测对照

代码修复方案（[代码核验] `packages/dsh-plugin-manager/src/host/gateway.ts`）：
- 新增 `hostBundleDir(binary, name)`：以 CLI 可执行入口路径出发，通过 `realpathSync` 解析符号链接真实路径后，沿祖先目录（上限 16 层）深度优先探测 `node_modules` 与 `lib/node_modules` 下的安装包目录；若 `binary === null` 则返回 undefined。
- 重构 `bundleLayerDir`：优先查找 profile 本地 `node_modules`；若不存在且该 bundle 名属于 profile 的 `dependencies`，判定为 profile 自身依赖尚在替换中，返回 undefined 维持安全防御；若不属于 profile `dependencies`（即官方预置 bundle），则回退调用 `hostBundleDir` 从宿主运行树解析。

归因前置检查（[本机核验]）：
- 检查本机宿主运行树：`/usr/local/lib/nodejs/node-v24.21.0-linux-x64/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/` 下真实存在 `dsh-base` 与 `dsh-web-app`。

- 第三次调用更新接口：立即返回 HTTP 409（already at 0.4.14），`cordis.patch.yml` 与 `package.json` 哈希逐字节一致，再次验证了失败恢复后的幂等性。

### 6.3 C3 安装成功但预检失败（预检失败阻断、再次点击重装重试与幂等收敛）

注入手法：执行方通过 PATH shim 拦截 `dsh` 命令，强行令 `--dump-config` 预检步骤返回退出码 1（`dsh: injected preflight failure`），模拟依赖安装完成但宿主配置校验崩溃的异常场景。

行为机制变更与代码决策（fix ②，[代码核验] `packages/dsh-plugin-manager/src/host/routes.ts` 与 `gateway.ts`）：
- 原行为问题：对于「依赖名未发生变化」（即版本就地升级）的包，若启动预检失败，网关策略将任务标记为 error 且不盲目触发回滚卸载，以避免引入锁文件或依赖损坏风险。但此时 profile 已就位新版本，导致用户在前端再次点击更新时，`routes.ts` 判定 `row.version === latest` 直接返回 HTTP 409（`already at <version>`），使更新陷入死路，必须手工介入修复。
- 修复后机制：`routes.ts` 的 HTTP 409 仅在「真的已是最新」时生效；若该插件最近一次已结算的 update 任务为 `phase === 'error'` 且 `targetVersion` 等于当前已装版本（新增 `CliGateway.lastUpdateFailed(id, version)` 判定），再次点击更新将不再是 409 死路，而是走一次**真正的重装**（重跑完整安装与 `--dump-config` 启动预检）。若无失败记录或重装已成功结算，则恢复 409 拦截。

修复后复跑实测数据（[执行方报告]）：
- **点击 1（注入预检失败）**：发起更新触发 `job-1`，预检因注入报错 `dsh: injected preflight failure`，任务结算为 `phase: error`。现场核验：profile 已处于 0.4.14 新版本，`cordis.patch.yml` 未做孤儿清理且逐字节未动，磁盘无任何 `.bak`、`.tmp` 残留。
- **点击 2（解除注入并发起重试）**：再次发起更新请求，接口返回 **HTTP 200** 并启动 `job-2`（成功突破原本 409 的死路）；任务顺利完成并结算为 `phase: done`。CLI 调用统计：`install` 累计 2 次、`dump` 累计 2 次（严格遵循每次点击至多触发一次安装与预检的预算约束）。
- **点击 3（重复更新验证幂等性）**：再次发起更新请求，此时最近一次任务 `job-2` 为成功态，`lastUpdateFailed` 返回 false，接口正确返回 HTTP 409（`already at 0.4.14`），`install` 计数不再增加，完全符合幂等契约。
- **补通孤儿清理实测**：在另一轮把宿主 bundle 探测（`hostBundleDir`）补回后，重试路径把孤儿清理也一起跑通：`cordis.patch.yml` 由 203 字节缩减至 134 字节，备份文件大小为 203 字节且逐字节全同，`dsh --profile upgradeC --dump-config` 退出码 0，总行数 1289 行，stderr 0 行。

注入手法：执行方构造双重异常场景——同时注入「迁移预检失败（`verifyBoot` 返回退出码 1）」与「回滚过程中 `dsh plugin remove` 移除新包失败（模拟退出码非 0）」。
