> **If 0.4.17 was installed by hand on rc.1, `dsh web` still starts but the whole dsh-web plugin set does not load**: the official boot gate skips bundles that do not satisfy the floor, one bundle at a time, and `stderr` carries a single line, `dsh: skipping profile bundle "@linxin666/dsh-web-all": <reason>` (the format is `<binName>: skipping profile bundle <JSON package name>: <reason>`). Nothing is thrown, no data is deleted, and the remaining bundles boot normally. **Raise the host to `0.2.2-rc.2` and restart to recover; the profile needs no edit**. Two stopgaps exist: grant the exact-version exemption with `dsh plugin --profile <profile> allow-version <package>@<version> --dsh-version 0.2.2-rc.1 --accept-risk`, which applies only to that package and that DSH version, or remove the package and roll back to `0.4.16`.
> **For hosts already on `0.2.2-rc.2`, this release is a fix**: rc.2 removed the `@deepseek-ai/dsh-subagent/internal` subpath export, and 0.4.16's `dsh-agents` imported it statically at module top level, so the aggregate's `web-ui-agents` row threw `ERR_PACKAGE_PATH_NOT_EXPORTED: './internal'` at import time and was recorded as a degraded row at `stage: import` - that row's UI and tools were missing while the other rows kept working. This release probes `Symbol.for('dsh.subagent.deliverPrompt')` first and falls back to `subagents.sendMessage(caller, target.id, content, { signal })`, so one artifact loads and works on both host generations.
> **Browser view: pages idle for three days close themselves**: `TabRecord.lastActiveAt` is stamped when a target is adopted and refreshed only by a `browser_*` call that resolves to that page; `BrowserViewService.sweepIdle` runs every ten minutes (an `unref`'d timer, cleared on dispose) and closes pages past the window through the existing `closeTab` path - the session binding pointing at it is dropped, a panel pinned to it falls back to the remaining tabs, and panel state is broadcast; nothing is scanned and no browser is launched when none is running. The window is the new `idleCloseDays` setting: default 3 days, minimum 0, **0 disables the capability**, read on every sweep, so an edit takes effect on the next sweep without remounting the plugin or reconnecting the browser. **Adopted real-browser pages are never candidates**: only tabs the plugin created (`origin: 'created'`) qualify, and watching a page in the panel, selecting its chip or projecting its frames does not count as activity. The idle clock lives in memory only, so **a host restart restarts every page's window**.
> **LiangShen pages plugin tool families by default**: the shipped `pagedToolPatterns` grows from the MCP bridge alone to `['mcp__*', 'browser_*', 'task_board_*', 'team_*', 'squad*', 'ui_*', 'ssh_*']`, while host builtins (shell, the file system, `glob`/`grep`, background jobs, `skill`, `ask_user_question`, `todo_write`, `web_search`, subagent delegation, plan, goal, `fact_register`, `tool_activate` and the MCP resource readers) stay resident. A withheld family is announced as one namespace summary in the catalog and **needs `tool_activate({ namespace })` before its first call**: `mcp__*` takes the first `__` segment of the tool name (`mcp__codegraph__codegraph_explore` becomes `codegraph`) while the others derive a literal-prefix family (`task_board_*` to `task_board`, `squad*` to `squad`), and a bare `*` is refused. **At most three activated namespaces are held at once**, and activating a fourth returns the least recently used one to its summary; under `ptc` those summaries are genuinely unreachable - absent from the request's `tools:sdk` section and not callable inside a `run_code` program. The settings card exposes the list as the on-demand tool family field, and **writing it empty removes the grouping and returns every tool to the resident face** (all three rows that page from that one pattern list are rewritten together). Measured on one session, the system prompt dropped from 104,949 to 58,961 characters and the `tools:sdk` section from 73,675 to 27,666.
> **The task board loses the `/goal` run option and goal acceptance**: `goalRunEnabled` and `TaskRecord.goalRun`, the `/goal` dispatch, the `session/projections` goal-phase settlement, the five `goalVerification*` keys, `TaskRecord.skipVerification`, the `ExecutionRecord.verification` contract, the `update_goal(action: complete)` gate on `tools/pre-execute`, the judge-model runner and `task_board_manage(action: 'reset-verification')` are all removed; manual runs, scheduled triggers and `rework` now run as an ordinary single turn and settle from that turn's `turn/end` result, with no extra judge-model calls. **Existing cards and execution history stay intact**: the authoritative ledger `$DSH_HOME/task-board/ledger-v2.json` keeps `schemaVersion: 7`, leftover `goalRun`, `skipVerification` and `verification` fields on old rows are dropped at load rather than rejecting the row, and **they are never written back**; non-strict plugin config loading likewise ignores leftover keys in old profile patches. Passing `reset-verification` to `task_board_manage` is now refused as an unknown action.
> **Plugins page batch update: one request runs the whole batch, and a refused row does not stop the others**: updates now go through the official `updateBundle(name, version, { requestId })` primitive (the manager verifies the target, removes the installed version, installs with the selection it found and restores on failure), so a batch is this host running that one primitive over its rows in order and the browser sends one request and polls one job. Each row carries its own result (`phase`, `targetVersion`, `landed`, `error`, `restartRequired`), the request resolves every id by the single route's own rules before touching anything, and **a refusal becomes that row's error instead of failing the batch**; a batch is capped at 50 rows, duplicate ids resolve once, and the batch always settles after the last row answers. A package that landed but cannot be loaded in this process is a restart row rather than an error, named on both surfaces - **a restart of DSH may still be needed before the new version loads**.
> **A fresh install that reports `ERR_PNPM_IGNORED_BUILDS` needs the builds approved and the command re-run**: on a profile that has never approved build scripts, pnpm ends with `[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: cloudflared@..., cpu-features@..., ssh2@...` plus `Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.`, `dsh plugin add` exits **1**, and the package is not added to `dsh.profile.bundles` - installed but not in effect. Run `pnpm approve-builds` for those three dependencies and re-run the same `dsh plugin add`.

### Upgrade Notes

- **The host floor moves from `>=0.2.2-rc.1` to `>=0.2.2-rc.2`**: this release raises `dsh.engines.dsh` and the `@deepseek-ai/dsh` peer floor, so a host on `0.2.2-rc.1` no longer qualifies. The host goes first, and npm's `latest` is still `0.2.2-rc.1`: install it from the `next` tag (`npm i -g @deepseek-ai/dsh@next`) and verify with `dsh --version`.
- **The refusal on an rc.1 host is protective by design**: HTTP 412 plus `requires DSH >=0.2.2-rc.2 (current DSH 0.2.2-rc.1); upgrade DSH before updating`, raised before any write, leaving no half-installed state. Seeing it means the host has not been upgraded yet, and nothing about the plugin needs investigating.
