# Team Hub Protocol Specification v1

Status: draft contract for M1 (team-hub), M2 (dsh-task-board-team), and M3 (Whale iOS App).

## 1. Overview and Division of Authority

The team collaboration system connects multiple DeepSeek Harness (DSH) Host nodes, native iOS mobile clients (Whale App), and Web GUI instances through a centralized Cloudflare Worker hub named `team-hub`. The protocol establishes a strict division of authority between collaboration management and task execution.

| Domain | Authority | Responsibilities |
| --- | --- | --- |
| Collaboration Domain | `team-hub` Worker | Issue tracking, assignment, collaboration lifecycle status, human review gates, comment threads, user decision questions, activity stream, and push notifications. |
| Execution Domain | Local DSH Host | Execution sessions, local workspace filesystem, sandbox policy enforcement, tool execution, model routing, and execution outcome verdicts. |

### Invariant: Division of Authority
`team-hub` is authoritative over collaboration fields (issues, assignees, collaboration status including `in_review`, comments, activity stream, pending questions). The Host executing the card is authoritative over execution (sessions, local workspace execution, execution outcome verdicts, process execution sandbox). Neither domain may override or bypass the authority of the other.

### Protocol Version and Version Negotiation
The protocol version string follows Semantic Versioning (`MAJOR.MINOR.PATCH`). The current protocol version defined by this document is `1.0.0`. All HTTP REST requests MUST include the header `X-Team-Hub-Protocol-Version: 1.0.0`, with the exception of `GET /auth/github/authorize` and `GET /auth/github/callback` which are initiated via browser navigation and external OAuth redirect and cannot carry custom request headers. All WebSocket connection handshakes MUST supply `protocol_version=1.0.0` as a query parameter or include the `X-Team-Hub-Protocol-Version` header.

| Condition | Server Response | Behavior |
| --- | --- | --- |
| Major version matches, minor/patch equal or lower | `200 OK` / WebSocket accepted | Full compatibility; server serves the requested protocol. |
| Major version matches, minor higher on client | `200 OK` / WebSocket accepted | Backward-compatible; server ignores unrecognized additive fields. |
| Major version differs or version header missing | `400 Bad Request` (`UNSUPPORTED_PROTOCOL_VERSION`) | Connection rejected; client must update or negotiate compatible version. |

## 2. Identity and Authentication

The system identifies three classes of actors: human team members, execution nodes (Hosts), and autonomous Agents bound to Hosts.

### Human Authentication via GitHub OAuth
Human team members authenticate exclusively through GitHub OAuth. No custom password or credentials database is maintained on the Hub. Both `GET /auth/github/authorize` and `GET /auth/github/callback` are browser-navigated endpoints and are exempt from the `X-Team-Hub-Protocol-Version` header check.

| Platform | OAuth Flow | Mechanics |
| --- | --- | --- |
| Web GUI | Authorization Code Flow | Browser navigates to `GET /auth/github/authorize`. Hub binds `state` to a short-lived `HttpOnly` cookie `th_oauth_state`. GitHub redirects to `GET /auth/github/callback`, where `state` is verified against `th_oauth_state`. Hub sets `th_session` cookie and `th_refresh` cookie (`HttpOnly`, `Secure`, `SameSite=Lax`) and issues session tokens. |
| iOS Whale App | Authorization Code with PKCE (RFC 7636) | App initiates `ASWebAuthenticationSession` with SHA-256 `code_challenge`. Callback scheme is `whale://auth/callback`. App exchanges `code` + `code_verifier` via `POST /auth/token`. Hub verifies `code_verifier` against the stored `code_challenge` using SHA-256 (`S256`). |

#### Authorization Parameters (`GET /auth/github/authorize`)
Clients initiate OAuth by directing user-agents to `GET /auth/github/authorize`. The request MUST supply the following query parameters:

| Query Parameter | Type | Required | Constraints and Validation Rules |
| --- | --- | --- | --- |
| `client` | String | Yes | Client platform: MUST be either `web` or `ios`. |
| `redirect_uri` | String | Yes | Callback URL. When `client=ios`, MUST be exactly `whale://auth/callback`. When `client=web`, MUST be same-origin with the Hub's own `/auth/github/callback`. |
| `state` | String | Yes | Cryptographic state parameter generated by the client to mitigate CSRF attacks. MUST be at least 32 bytes and base64url encoded. |
| `code_challenge` | String | For `ios` | RFC 7636 SHA-256 code challenge. Required when `client=ios`. |
| `code_challenge_method` | String | For `ios` | PKCE challenge method. Required when `client=ios` and MUST be exactly `S256`. |

If any parameter is missing, invalid, or fails these validation constraints, the Hub returns HTTP `400 Bad Request` with error code `VALIDATION_FAILED`.

In the Web flow, the Hub binds the generated `state` parameter to a short-lived `HttpOnly` cookie named `th_oauth_state` at authorization time and compares it against the callback parameter at `GET /auth/github/callback`. For `client=ios`, `POST /auth/token` MUST supply `code_verifier`, which the Hub independently verifies against the stored `code_challenge` using SHA-256 (`S256`).

### Hub Session Tokens
Upon successful GitHub authentication, the Hub issues a dual-token pair. Both the initial token exchange response (`POST /auth/token`) and the token refresh response (`POST /auth/refresh`) include the authenticated `member` object alongside the token credentials:

```json
{
  "access_token": "th_usr_...",
  "refresh_token": "th_ref_...",
  "token_type": "Bearer",
  "expires_in": 7200,
  "member": {
    "id": "mem_01j7b5w8m4f9q2e3r6t1y8u4i6",
    "team_id": "team_01j7b5w8m4f9q2e3r6t1y8u4i5",
    "github_user_id": 1234567,
    "github_username": "octocat",
    "mention_handle": "octocat",
    "display_name": "Mona Lisa Octocat",
    "avatar_url": "https://avatars.githubusercontent.com/u/1234567",
    "account_user_id": "acct_01j7b5w8m4f9q2e3r6t1y8u4id",
    "role": "member",
    "status": "active",
    "created_at": 1700000000000,
    "updated_at": 1700000000000
  }
}
```

`account_user_id` is the Whale account subject bound to this membership, and `null` while the member is unlinked; it is read-only and never takes part in an authorization decision. The field is a backward-compatible addition - a client that predates it ignores it - and it is the only account-service attribute exposed here: no email, no account display name, no token.

A member invited by email is created already bound, because `account_user_id` is what sign-in matches. `github_user_id` and `github_username` are legacy identity columns: they are `NOT NULL` and unique per team, so an email-invited row carries a reserved placeholder instead of a GitHub identity - a negative `github_user_id` (real GitHub ids are positive) and a `github_username` prefixed `account:` (a colon is not legal in a GitHub login). Neither value identifies a GitHub account, and a client must not resolve or display them as one.

`mention_handle` is the name a comment can `@` (section 7), and the only field mention resolution reads: lowercase `[a-z0-9_-]`, unique within its team, matched case-insensitively. A GitHub identity member takes its login. An email-invited member takes the local part of its address with every run of any other character folded into one `-` and both ends trimmed - `mei.lin@example.com` is mentioned as `mei-lin`, because the dot a mention cannot carry and the full stop that ends a sentence are the same character - and `member` when nothing survives; a name its team already answers to counts up `-2`, `-3`. `display_name` stays free text and takes no part in resolution, and two members may share it. The `account:` placeholder above stays a placeholder - a mention can never carry a colon, and a client that wants to show a name to type reads `mention_handle` instead.

The `expires_in` field returned by `POST /auth/token` and `POST /auth/refresh` represents the access token lifetime in seconds (`7200`, corresponding to 2 hours), following OAuth 2.0 convention (RFC 6749). Clients MUST process and calculate expiration in seconds.

In Web environments, the `th_refresh` cookie is set during web callback (`GET /auth/github/callback`) and token refresh (`POST /auth/refresh`) with `HttpOnly; Secure; SameSite=Lax`. The `th_session` cookie is also set and remains valid for Web authentication.

| Token Type | Storage | Lifetime | Usage |
| --- | --- | --- | --- |
| Access Token | In-memory / Secure storage | 7200 s (2 hours) | Bearer token in `Authorization: Bearer <token>` for all REST and WebSocket calls. Returned as `expires_in: 7200` (in seconds) per OAuth convention; clients must calculate expiry in seconds. |
| Refresh Token | D1 / Secure Keychain / `th_refresh` cookie | 2,592,000 s (30 days) | Submitted to `POST /auth/refresh` (or sent via `th_refresh` cookie) to obtain a new token pair with automatic refresh token rotation. |

Calling `POST /auth/revoke` invalidates the submitted refresh token and terminates the associated session immediately.

### Host Token
Execution nodes (Hosts) authenticate using a dedicated Host Token minted by a team administrator.

| Property | Specification |
| --- | --- |
| Format | `th_host_<64_hex_characters>` (high-entropy cryptographically secure random string). |
| Storage | Plaintext token is returned exactly once at issuance. D1 stores SHA-256 hash (`token_hash`). |
| Scope | Restricted strictly to Host execution endpoints: host registration, heartbeats, task claiming, lease renewal, question submission, settlement write-back, and agent comments. |
| Restrictions | A Host Token cannot access administrative endpoints, invite members, modify team settings, create issues, or approve human reviews. |
| Revocation | Team administrators can revoke any Host Token immediately via `POST /api/v1/teams/:teamId/hosts/:hostId/revoke-token`. Revoked tokens return `401 Unauthorized`. In agent listings, agents bound to a revoked Host report `host_status: 'offline'`. |

### Member Invitation and Management
Team administrators invite members by email address. The Hub resolves the address through the account service, so the membership is created already bound to the account the invitee signs in with.

**Backward incompatible change.** The invite used to take `github_username` and let the invitee enter through GitHub OAuth. GitHub login is now closed on the Hub (`github_login=false`), so that shape could never work: the row was created `invited` and unbound, the invitee's first sign-in could not find a member bound to their account and answered `409 NOT_LINKED`, and the binding route requires an existing membership. `github_username` is therefore no longer accepted - a request that sends it instead of `email` is refused with `400 VALIDATION_FAILED` - and there is no compatibility mode. Clients MUST send `email`.

| Step | Actor | Action | Result |
| --- | --- | --- | --- |
| 1 | Admin | Calls `POST /api/v1/teams/:teamId/members/invite` with `email` and `role`. The Hub resolves the address with `POST {ACCOUNT_SERVICE_BASE}/v1/admin/users/lookup`, carrying `x-admin-token: {ACCOUNT_ADMIN_TOKEN}` and body `{ email }`. | Member record created `active`, bound to the resolved account user id, named after the address's local part, with the requested `role`. An address the account service does not know answers `404 USER_NOT_FOUND` and writes no row; an account that is already a member of a team on this Hub answers `409 ALREADY_MEMBER`. |
| 2 | Invitee | Signs in with an account assertion (`POST /auth/account`). | The Hub matches `members.account_user_id` and opens a session immediately; the invite needs no second step. |
| 3 | Admin | Calls `DELETE /api/v1/teams/:teamId/members/:memberId` to remove a member. | Member status set to `suspended`; active sessions revoked immediately. |

### Hub Bootstrap (`POST /api/v1/bootstrap`)
A freshly deployed Hub has no team, and a Hub with no team has no administrator who could invite anyone. This one call creates the first team and its first administrator. It is closed unless the process holds `BOOTSTRAP_TOKEN` (sent as the `X-Bootstrap-Token` header), and it succeeds only once.

The first administrator is named by an email address, exactly as an invited member is. The Hub resolves the address with `POST {ACCOUNT_SERVICE_BASE}/v1/admin/users/lookup`, carrying `x-admin-token: {ACCOUNT_ADMIN_TOKEN}` and body `{ email }`, and writes the admin row bound to the resolved account user id, `active`, named after the address's local part. The account that signs in with an assertion is therefore the administrator from its first attempt. The row carries the same reserved placeholder GitHub identity an email-invited row carries (see above), derived from the account user id, so one account's placeholder is identical in every team it joins.

**Backward incompatible change.** The bootstrap request used to name a GitHub login (`github_username`): the Hub fetched that profile and created an admin row with no `account_user_id`. Sign-in matches nothing but `account_user_id`, so that administrator answered `409 NOT_LINKED` to every assertion, and the first person of a new deployment could not enter at all. The request therefore takes `email` instead - a request that still sends `github_username` is refused with `400 VALIDATION_FAILED`, and there is no compatibility mode. Resolving an address needs the account-service admin API, so bootstrap now depends on `ACCOUNT_SERVICE_BASE` and `ACCOUNT_ADMIN_TOKEN` the way the invite does: a Hub without them answers `503 NOT_CONFIGURED` here too.

Request:
```json
{
  "team_name": "Team Example",
  "team_slug": "team-example",
  "email": "admin@example.com"
}
```

Response (`201 Created`):
```json
{
  "team": { "id": "team_01j7b5w8m4f9q2e3r6t1y8u4i5", "name": "Team Example", "slug": "team-example" },
  "member": {
    "id": "mem_01j7b5w8m4f9q2e3r6t1y8u4i6",
    "github_username": "account:acct_01j7b5w8m4f9q2e3r6t1y8u4id",
    "mention_handle": "admin",
    "account_user_id": "acct_01j7b5w8m4f9q2e3r6t1y8u4id",
    "role": "admin"
  }
}
```

| Condition | Response | Behavior |
| --- | --- | --- |
| The Hub already has a team | `409 CONFLICT` | `details.team_id` names the team that exists. Decided before the address is resolved, so a Hub that has bootstrapped refuses the call whatever its account service looks like. |
| The address has no account | `404 USER_NOT_FOUND` | Nothing is written. The remedy is to sign in to the Whale app with Apple once, then repeat the call. |
| The account service is unreachable, or answers something the Hub does not accept | `502 ACCOUNT_UNAVAILABLE` | The upstream body is never forwarded. |
| `ACCOUNT_SERVICE_BASE` or `ACCOUNT_ADMIN_TOKEN` is missing | `503 NOT_CONFIGURED` | The message names the missing setting. |

## 3. D1 Database Schema

Data persistence uses Cloudflare D1 (SQLite-compatible relational database). All timestamps are stored as UTC milliseconds (`INTEGER NOT NULL`). All identifiers use typed prefix strings (`<prefix>_<id>`).

| Entity | ID Prefix | Example |
| --- | --- | --- |
| Team | `team_` | `team_01j7b5w8m4f9q2e3r6t1y8u4i5` |
| Member | `mem_` | `mem_01j7b5w8m4f9q2e3r6t1y8u4i6` |
| Host | `host_` | `host_01j7b5w8m4f9q2e3r6t1y8u4i7` |
| Agent | `agent_` | `agent_01j7b5w8m4f9q2e3r6t1y8u4i8` |
| Issue | `issue_` | `issue_01j7b5w8m4f9q2e3r6t1y8u4i9` |

| Activity | `act_` | `act_01j7b5w8m4f9q2e3r6t1y8u4ib` |
| Question | `ques_` | `ques_01j7b5w8m4f9q2e3r6t1y8u4ic` |
| Push Token | `ptok_` | `ptok_01j7b5w8m4f9q2e3r6t1y8u4id` |

## 4. Issue State Machine

The issue state machine coordinates human assignments, Host node execution leases, and human reviews.

### Invariant: Offline Execution Node Does Not Migrate
When a Host node is offline, any issue assigned to an Agent bound to that Host remains in `waiting_host` status and NEVER migrates to another Host. Task execution environments are bound to the specific developer machine, local repository state, and local credentials of the agent owner; tasks cannot be claimed by arbitrary nodes.

### State Transition Matrix

| From | To | Trigger | Actor | Preconditions | Activity Logged |
| --- | --- | --- | --- | --- | --- |
| `todo` | `assigned` | Assign task | Human | Target member or agent specified. | `issue.assigned` |
| `assigned` | `waiting_host` | Host offline check | Hub system | `assignee_type='agent'`; agent bound host status is `offline`. | `issue.waiting_host` |
| `assigned` | `running` | Claim lease | Bound Host | `assignee_type='agent'`; Host online; holds valid Host Token; claims active lease. | `issue.claimed` |
| `waiting_host` | `running` | Claim lease | Bound Host | `assignee_type='agent'`; Host returns online; claims active lease for its agent. | `issue.claimed` |
| `running` | `waiting_host` | Lease expired / Host offline | Hub system | `assignee_type='agent'`; lease timeout (60 s) expired without renewal or host missed 3 heartbeats. | `issue.host_offline` |
| `running` | `in_review` | Settle success | Executing Host | `assignee_type='agent'`; execution finished and its own turn verdict succeeded locally. | `issue.settled_in_review` |
| `running` | `failed` | Settle failure | Executing Host | `assignee_type='agent'`; execution failed or unrecoverable error encountered. | `issue.failed` |
| `assigned` | `in_review` | Submit for review | Human | `assignee_type='member'`; `reviewer_member_id` is set; human assignee finishes work and requests review. Permitted only for assignee or admin. | `issue.submitted_for_review` |
| `assigned` | `done` | Complete task directly | Human | `assignee_type='member'`; no `reviewer_member_id` set; human assignee marks task complete. Permitted only for assignee or admin. | `issue.completed` |
| `in_review` | `done` | Approve review | Human | Human reviewer accepts the work. | `issue.approved` |
| `in_review` | `assigned` | Reject review (rework) | Human | Reviewer provides rework instructions; `rework_instructions` stored on issue. Non-null `rework_instructions` with `status='assigned'` signals pending rework. | `issue.rework_requested` |
| `failed` | `assigned` | Retry execution | Human | Issue in `failed` status; human triggers retry; clears failure error, `execution_attempt_id`, `lease_token`, `lease_expires_at`, and `executing_host_id`. | `issue.retried` |
| Any active state | `canceled` | Cancel task | Human | User cancels issue before completion. | `issue.canceled` |

Human-driven lifecycle transitions (`submit-for-review` -> `in_review`, `complete task directly` -> `done`, `retry execution` -> `assigned`, and `cancel task` -> `canceled`) are performed via `PATCH /api/v1/teams/:teamId/issues/:issueId` with `{ status }` in the request body, and are validated strictly against the matrix preconditions. Transitions `submit-for-review` (`assigned` -> `in_review`) and direct task completion (`assigned` -> `done`) are strictly restricted to the assignee themselves (`assignee_id = current_member_id` when `assignee_type='member'`) or a team administrator; calls by any other member return HTTP `403 Forbidden` (`FORBIDDEN`). Disallowed transitions return HTTP `422 Unprocessable Entity` (`INVALID_STATE_TRANSITION`). Retrying a failed issue (`failed` -> `assigned`) clears `execution_attempt_id`, `lease_token`, `lease_expires_at`, and `executing_host_id` alongside `failure_error`.

#### Claim Preconditions and Atomicity
Claiming an issue transitions it to `running` and MUST be executed via a single conditional `UPDATE`:
- `WHERE status IN ('assigned', 'waiting_host') AND bound host matches`, OR
- in reconnect scenarios: `WHERE status = 'running' AND execution_attempt_id = :attempt_id AND lease_token = :lease_token`.

Issues in `failed` and `todo` statuses CANNOT be claimed; any claim attempt on `failed` or `todo` returns HTTP `422 Unprocessable Entity` (`INVALID_STATE_TRANSITION`).

#### Reliable Delivery of Rework
When an issue's `rework_instructions` is non-null and `status = 'assigned'`, it indicates a pending rework execution. Whether the Host receives the card via the `issue.rework` WebSocket event or via a sweep, it MUST first claim the card successfully before invoking `rework(instructions)` on the existing mirrored card in the local task board. At any point in time, each issue permits at most one in-flight claim request (single-flight concurrency control). Once rework execution begins, the Hub clears `rework_instructions` upon settlement (`settle`).

## 5. Host Execution Protocol

The DSH Host plugin `@linxin666/dsh-task-board-team` coordinates local card execution with the Hub.

### Registration and Heartbeat
1. At Host startup, the plugin reads configured Hub URL and Host Token.
2. Host calls `POST /api/v1/teams/:teamId/hosts/register` with request body strictly using snake_case:
   ```json
   {
     "hostname": "string",
     "client_version": "string",
     "agents": [
       {
         "name": "string",
         "preset_id": "string",
         "model": "string",
         "reasoning_effort": "string"
       }
     ]
   }
   ```
   `preset_id` MUST be non-empty. Any member without a preset is skipped by the Host, not reported to the Hub, and flagged with a visible local warning on the Host (executing tasks with default presets is disallowed).
3. Hub marks the host `online`, updates agent records, and returns:
   ```json
   {
     "host_id": "string",
     "status": "online",
     "agents": [
       {
         "id": "string",
         "name": "string"
       }
     ],
     "conflicts": [
       {
         "name": "string",
         "reason": "string"
       }
     ]
   }
   ```
   The Host uses `agents: [{ id, name }]` to map local agent member names to the Hub's registered `agent_id`. When an agent name is already owned by another Host on the team, the Hub skips that agent definition, registers the remaining agents normally, and keeps the Host `online`. Skipped definitions are returned in `conflicts` with `reason` fixed to `"agent name already belongs to another host"`.
4. Host sends periodic heartbeats via `POST /api/v1/teams/:teamId/hosts/:hostId/heartbeat` every 15,000 ms.
5. If Hub receives no heartbeat for 45,000 ms (3 consecutive misses), Hub marks host `offline` and marks running tasks `waiting_host`.

### Claiming Agent Cards and Lease Management
1. Host queries `GET /api/v1/teams/:teamId/issues?assignee_host_id=:hostId&status=assigned,waiting_host`. The endpoint supports `assignee_host_id` and comma-separated `status` filters. When authenticated via Host Token, the returned issues are strictly scoped to cards assigned to agents bound to that Host.
2. Host issues an atomic claim call: `POST /api/v1/teams/:teamId/issues/:issueId/claim`.
   - Claiming MUST be executed via a single conditional `UPDATE`:
     `WHERE status IN ('assigned', 'waiting_host') AND bound host matches`, OR in reconnect scenarios `WHERE status = 'running' AND execution_attempt_id = :attempt_id AND lease_token = :lease_token`.
   - Issues in `failed` and `todo` statuses CANNOT be claimed; any claim attempt on `failed` or `todo` returns HTTP `422 Unprocessable Entity` (`INVALID_STATE_TRANSITION`).
   - Claim requests for the same issue are strictly single-flight (at most one in-flight claim at any time).
3. `execution_attempt_id` is generated by the Hub: for any fresh claim (`status IN ('assigned', 'waiting_host')`), the Hub generates a new `execution_attempt_id` (and a unique UUIDv4 `lease_token`), sets `lease_expires_at = now + 60000` ms, transitions status to `running`, and returns the lease. An `execution_attempt_id` submitted by the Host is only honoured during reconnection when `status = 'running'` and both `execution_attempt_id` and `lease_token` match.
4. While execution is active, Host renews the lease every 20,000 ms via `POST /api/v1/teams/:teamId/issues/:issueId/renew-lease`, passing `lease_token`.
5. Hub extends `lease_expires_at` by 60,000 ms upon each successful renewal.

### Reliable Delivery of Rework
When an issue's `rework_instructions` is non-null and `status = 'assigned'`, it represents a pending rework execution. Whether received via the `issue.rework` WebSocket event or via a sweep, the bound Host MUST first claim the card successfully before calling `rework(instructions)` on the existing mirrored card in the local task board. Claims on the issue remain single-flight. Once rework execution starts, the Hub clears `rework_instructions` when the Host calls `settle`.

### Reconnect Idempotency and Duplicate Execution Prevention
If network connectivity drops temporarily or the Host process restarts:
1. The issue transitions to `waiting_host` upon lease expiry, but is NEVER reassigned to another node (Invariant: Offline Execution Node Does Not Migrate).
2. Upon reconnecting, Host calls `POST /api/v1/teams/:teamId/issues/:issueId/claim` providing its previous `execution_attempt_id` and `lease_token`.
3. Hub verifies reconnect conditions: the attempt submitted by the Host is only reused when `status = 'running'` and both `execution_attempt_id` and `lease_token` match the active lease. When matched, the Hub re-establishes the active lease and returns the existing state without creating duplicate execution sessions.
4. If local execution already finished before reconnection, Host immediately submits `POST /api/v1/teams/:teamId/issues/:issueId/settle` with the existing `execution_attempt_id`.

### Settlement Write-Back
When local execution completes:
1. Success path: The Host settles the execution as succeeded from its turn verdict. Host calls `POST /api/v1/teams/:teamId/issues/:issueId/settle` with `outcome: "succeeded"`, optional `execution_attempt_id`, `summary`, and optional `verification_evidence`. Hub transitions status to `in_review` and clears `rework_instructions`.
2. Failure path: The Host settles the execution as failed (or canceled). Host calls settle endpoint with `outcome: "failed"`, optional `execution_attempt_id`, and failure text. Hub transitions status to `failed` and clears `rework_instructions`.

Late settlement and lease expiration: The `settle` endpoint accepts an optional `execution_attempt_id`. Whenever `settle` supplies an `execution_attempt_id`, if it does not equal the issue's current `execution_attempt_id`, the Hub rejects the call with HTTP `412 Precondition Failed` (`LEASE_EXPIRED`). If the active lease has expired, late settlement write-back is permitted only when the supplied `execution_attempt_id` matches the issue's current `execution_attempt_id`.

### Manual Retry
When a human retries a failed issue (`failed` -> `assigned`), the Hub clears `execution_attempt_id`, `lease_token`, `lease_expires_at`, and `executing_host_id`. This returns the issue to a clean slate, ensuring subsequent claims generate fresh execution attempts and preventing stale attempts from settling.

## 6. Help-seeking and Questions

When an agent needs human guidance or user confirmation during execution, it routes the question to the Hub.

### Workflow
1. Host intercepts an agent's question event (such as `ask_user_question` or stuck input signal) in-process from the execution session.
2. Host sends `POST /api/v1/teams/:teamId/issues/:issueId/questions` with the question text, options, and multi-select flag.
3. Hub saves the question with status `pending`, emits WebSocket event `question.created`, and sends APNs push notifications to the issue reviewer, plus the human assignee (if `assignee_type='member'`). By the default reviewer rule (Section 13), every agent-executed issue always has an active human reviewer (defaulting to the issue creator).
4. An authorized team member responds via Whale iOS App or Web GUI by calling `POST /api/v1/teams/:teamId/questions/:questionId/answer` with request body `{ selected: string[], custom?: string }`. Both `selected` and `custom` MUST NOT be simultaneously empty; if both are omitted or empty, the request is rejected with `400 Bad Request` (`VALIDATION_FAILED`).
5. Resolution rule: First response wins.
- The first answer sets status to `answered`, recording `first_responder_member_id` and timestamp. - Any competing responses submitted after the first receive `409 Conflict` (`QUESTION_ALREADY_ANSWERED`).
6. Hub broadcasts WebSocket event `question.answered` containing the selected answer.
7. Host receives the WebSocket event, identifies the waiting agent session, injects the user answer, and resumes agent execution.

### Question Termination Lifecycle
A question terminates in one of three ways: answered, expired, or withdrawn.
1. Answered: A human responds first, transitioning the question to `answered` and broadcasting `question.answered` (Step 5 above).
2. Expired: If a pending question reaches its 24-hour TTL (86,400,000 ms) without an answer, the Hub marks question status `expired`, records `question.expired` activity, and broadcasts WebSocket event `question.expired` with `{ question_id, issue_id }`. The executing Host receives the event and resolves the waiting session question as unanswered / timed out, allowing the agent to proceed with default assumptions or pause.
3. Withdrawn: If the agent cancels or aborts execution locally before an answer arrives, the Host calls `POST /api/v1/teams/:teamId/questions/:questionId/withdraw`. Only the Host that submitted the question (`host_id`) or a team administrator may withdraw the question. Calls by another Host return `403 Forbidden` (`HOST_MISMATCH`), and calls by non-admin members return `403 Forbidden` (`FORBIDDEN`). The Hub verifies the question is pending, marks status `dismissed`, records `question.withdrawn` activity, and broadcasts WebSocket event `question.withdrawn` with `{ question_id, issue_id }` so mobile and web clients dismiss the prompt.

### Question Queries
Team members can query questions across the team via:
`GET /api/v1/teams/:teamId/questions?status=&issue_id=`

Query Parameters:
- `status`: Optional filter by question status (`pending`, `answered`, `dismissed`, `expired`).
- `issue_id`: Optional filter by associated issue ID.

Response (`200 OK`):
```json
{
  "questions": [
    {
      "id": "ques_01j7b5w8m4f9q2e3r6t1y8u4ic",
      "issue_id": "issue_01j7b5w8m4f9q2e3r6t1y8u4i9",
      "text": "Should we proceed with migration plan A or B?",
      "options": [
        {
          "label": "Plan A",
          "description": "Proceed with immediate database migration"
        },
        {
          "label": "Plan B",
          "description": "Stage migration behind feature flag"
        }
      ],
      "multi_select": false,
      "status": "pending",
      "answer": null,
      "first_responder_member_id": null,
      "created_at": 1700000000000,
      "answered_at": null
    }
  ]
}
```
Only members and administrators can query questions. Host Tokens cannot call this endpoint.

## 7. Comments and Mentions

The comment stream supports collaboration between human members and autonomous agents.

### Mention Syntax and Resolution
Comments are formatted in Markdown. Mentions are parsed using the regular expression `/(?:^|\s)@([a-zA-Z0-9_-]+)/`. A handle carries no dot, so the full stop that closes a sentence is not read as part of the one above.

| Target Type | Identifier | Delivery Mechanism |
| --- | --- | --- |
| Human Member | `mention_handle`; `github_username` is accepted as well, and a match on either one resolves the member. Both fold case, and a handle wins when the two disagree. | Hub emits WebSocket event `comment.created` and APNs notification with category `mentioned`. |
| Agent | Agent name | Hub resolves the agent's bound Host, emits WebSocket event `comment.mentioned` to that Host. |

A handle no member and no agent answers to is not a mention: the comment is stored and no `comment_mentions` row is written for it.

When a comment is written (via `POST /api/v1/teams/:teamId/issues/:issueId/comments`), the Hub parses `@` mentions in the same D1 batch transaction as the comment creation, resolving targets and writing records into `comment_mentions`:
- For mentioned human members: `target_type = 'member'`, `target_member_id = member.id`, `read_at = NULL`.
- For mentioned agents: `target_type = 'agent'`, `target_agent_id = agent.id`, `read_at = NULL`.

### Delivering `@Agent` Comments to Session
When an agent is mentioned in a comment:
1. Hub pushes WebSocket event `comment.mentioned` to the Host owning the agent.
2. Host receives the event and invokes the DSH task board extension capability `followUp` (M0).
3. The comment text is injected as a new user message into the card's active or most recent execution session.

### Agent Comment Submission
Agents post comments to the Hub using the registered tool `team_comment`:
1. Agent invokes tool: `team_comment({ issue_id: "issue_...", text: "..." })`.
2. Host receives tool call and sends `POST /api/v1/teams/:teamId/issues/:issueId/comments` with Host Token.
3. Payload specifies `author_type: "agent"` and `author_agent_id`.
4. Hub stores comment, records `comment.created` activity, and broadcasts to team members.

### Inbox
The Hub provides an aggregated inbox endpoint for team members:
`GET /api/v1/teams/:teamId/inbox`

Auth: Member session token (Admin or Member). Host Tokens cannot call this endpoint.

Response (`200 OK`):
```json
{
  "assigned": [],
  "review": [],
  "questions": [],
  "mentions": []
}
```

The four lists in the inbox response are filtered by the following rules:
1. `assigned` (`Issue[]`): Issues where the assignee is the calling member (`assignee_type = 'member'` and `assignee_id` matches the calling member's ID) and the issue status is neither `done` nor `canceled`.
2. `review` (`Issue[]`): Issues where `status = 'in_review'` and `reviewer_member_id` matches the calling member's ID.
3. `questions` (`Question[]`): Questions where `status = 'pending'`, and the calling member is an intended recipient as defined in Section 6 (the issue reviewer, or the human assignee when `assignee_type = 'member'`).
4. `mentions` (`[{ comment: Comment, issue_id: string }]`): Unread comment mentions targeting the calling member (`comment_mentions` where `target_type = 'member'`, `target_member_id` matches the calling member's ID, and `read_at IS NULL`).

#### Marking Mentions as Read
To dismiss an unread mention from the inbox:
`POST /api/v1/teams/:teamId/inbox/mentions/:commentId/read`

Auth: Member session token (Admin or Member). Host Tokens cannot call this endpoint.
Request Body: None.
Response Body (`200 OK`):
```json
{
  "ok": true
}
```
This updates `comment_mentions.read_at` to the current UTC timestamp for the record matching `(comment_id = :commentId, target_member_id = current_member.id)`.

## 8. Human Review

The Host's execution verdict records whether the agent turn completed without runtime failure; human review verifies whether the delivered work satisfies the requirement.

### In-Review Lifecycle
When the Host settles the execution as succeeded from its turn verdict, the issue transitions to `in_review` on the Hub. The card remains in the Host ledger's Done column locally while awaiting human review on the Hub.

### Approval
1. Reviewer inspects execution output, diffs, and verification summary.
2. Reviewer or team administrator calls `POST /api/v1/teams/:teamId/issues/:issueId/review/approve`. Only the designated `reviewer_member_id` or an admin may approve; calls by other members return `403 Forbidden` (`FORBIDDEN`).
3. Hub transitions issue status to `done` and records `issue.approved` activity.

### Rejection and Rework
1. Reviewer or team administrator calls `POST /api/v1/teams/:teamId/issues/:issueId/review/reject` with `instructions`. Only the designated `reviewer_member_id` or an admin may reject and request rework; calls by other members return `403 Forbidden` (`FORBIDDEN`).
2. Hub stores rework instructions on the issue (`rework_instructions = instructions`), clears any active lease, transitions issue status to `assigned` (or `waiting_host` if the bound Host is offline), and records `issue.rework_requested` activity. An issue with non-null `rework_instructions` and `status = 'assigned'` represents a pending rework.
3. Hub delivers WebSocket event `issue.rework` with rework instructions to the bound Host as a notification signal to claim the card.
4. Bound Host receives the card via `issue.rework` or sweep and calls `POST /api/v1/teams/:teamId/issues/:issueId/claim` (a fresh claim where the Hub generates a new `execution_attempt_id`). The claim is atomic and executed via a single conditional `UPDATE` (`WHERE status IN ('assigned', 'waiting_host')` matching the bound host); issues in `failed` or `todo` cannot be claimed (HTTP `422` `INVALID_STATE_TRANSITION`). The claim is strictly single-flight (at most one in-flight claim per issue).
5. Only after the claim succeeds does the Host invoke the DSH task board extension capability `rework` (M0) to re-run the task in the same session (`reuseSession`) feeding rework instructions into the session context. If the claim fails, the Host aborts execution and records a local error without starting the rework session.
6. Once rework execution begins, the Hub clears `rework_instructions` upon settlement (`settle`).

### Durable Object WebSocket Protocol
Each team is backed by one Durable Object (`TeamChannelDO`). Clients connect to: `wss://<hub-domain>/api/v1/teams/:teamId/ws?since_seq=<seq>`.

#### WebSocket Authentication and Version Negotiation
- **Authentication**: Host and iOS clients authenticate exclusively using the `Authorization: Bearer <token>` HTTP request header during the WebSocket upgrade handshake. The Hub NO LONGER accepts `?token=` query parameters (tokens must not appear in the URL). In Web scenarios, the `th_session` cookie remains valid for WebSocket upgrade authentication.
- **Protocol Version Negotiation**: Version negotiation is uniform across all clients. The client MUST supply the protocol version through either:
  1. The `protocol_version=1.0.0` query parameter (e.g. `wss://<hub-domain>/api/v1/teams/:teamId/ws?protocol_version=1.0.0&since_seq=<seq>`), OR
  2. The `X-Team-Hub-Protocol-Version: 1.0.0` HTTP request header during handshake.
  Connections omitting both or specifying an incompatible protocol version are rejected during handshake with HTTP `400 Bad Request` (`UNSUPPORTED_PROTOCOL_VERSION`).

| Frame | Direction | Schema | Purpose |
| --- | --- | --- | --- |
| `ping` | Client -> DO | `{ "t": "ping", "ts": <number> }` | Connection keepalive probe. |
| `pong` | DO -> Client | `{ "t": "pong", "ts": <number> }` | Response to ping probe. |
| `resume` | Client -> DO | `{ "t": "resume", "since_seq": <number> }` | Requests replaying missed events from `since_seq`. |
| `event` | DO -> Client | `{ "t": "event", "seq": <number>, "event": "<name>", "payload": {...}, "ts": <number> }` | Broadcasts real-time team mutations. |
| `resync_required` | DO -> Client | `{ "t": "resync_required", "reason": "<reason>", "latest_seq": <number> }` | Sent when `since_seq` is too old; client must re-fetch full state via REST. |

#### WebSocket Close Codes
When a WebSocket connection violates transmission rate limits or payload constraints, the Durable Object terminates the connection immediately using standard WebSocket close codes:
- `1008` (Policy Violation): Rate limit exceeded (`RATE_LIMITED`).
- `1009` (Message Too Big): Inbound message exceeds frame size limit (`PAYLOAD_TOO_LARGE`).

| Event Name | Recipient | Payload Shape |
| --- | --- | --- |

| `issue.updated` | All connected | `{ issue: Issue, changed_fields: string[] }` |

| `issue.claimed` | All connected | `{ issue_id: string, executing_host_id: string }` |

### Monotonic Event Sequence and Resumption Rules
1. `seq` is a strictly monotonically increasing 64-bit integer maintained by the team's Durable Object.
2. The Durable Object holds a ring buffer of the last 1,000 events or events from the last 3,600,000 ms (1 hour).
3. Upon reconnecting, client provides `since_seq` in query parameter or `resume` frame.
4. If `since_seq` is within the buffer window, the Durable Object immediately streams all missed events in monotonic order before streaming live events.
5. If `since_seq` is absent, 0, or older than the buffer boundary, the Durable Object emits `resync_required`. The client MUST clear its local delta cache and re-fetch the complete team snapshot via REST API.

### Token Registration and Secret Custody
1. Client registers device token upon login via `POST /api/v1/push-tokens`.
2. Stale or invalid tokens returning HTTP `410 Unregistered` from APNs are automatically purged from D1.
3. Client unregisters device token upon logout via `DELETE /api/v1/push-tokens/:token`.
4. APNs `.p8` private key and credentials are encrypted as Cloudflare Worker secrets:
- `APNS_KEY_ID`: 10-character Apple Developer Key ID. - `APNS_TEAM_ID`: 10-character Apple Developer Team ID. - `APNS_BUNDLE_ID`: Mobile application bundle identifier. - `APNS_PRIVATE_KEY_P8`: PEM-encoded EC private key.
5. The Worker signs ES256 authentication tokens on demand with a 3,000,000 ms (50 minutes) cache.

### Rate Limiting

| Target | Window | Maximum Requests |
| --- | --- | --- |
| Authentication routes (`/auth/*`) | 60,000 ms (1 minute) | 20 requests per client IP |

### Audit Logging
All state-modifying actions on issues record an immutable record in the `activity` table. Activity stream entries are append-only. No API endpoint exists to update or delete activity records. Because `activity.issue_id` is a required foreign key (`NOT NULL REFERENCES issues(id)`), team-level operations (such as member invitations and member removals) do not record activity entries; all issue-scoped actions are recorded.

Members can query the paginated activity stream for an issue via `GET /api/v1/teams/:teamId/issues/:issueId/activity?before=<activity_id>&limit=<1..100>` (default limit 50), which returns `{ activity: Activity[], next_cursor: string | null }`. Host Tokens cannot call this endpoint.

## 12. Non-Goals for Phase 1

To preserve delivery velocity for M1 through M4, the following capabilities are explicitly excluded from Phase 1:
1. Planning hierarchy layers: Projects, Milestones, Cycles, Epics, and Roadmaps.
2. Automated issue triage, sentiment scoring, and automated routing rule engines.
3. Story point estimation, developer velocity calculations, and burndown analytics.
4. Multi-team billing, payment plans, and subscription tier metering (Phase 1 schema is multi-tenant capable, deployed for a single team).
5. Custom role definitions and fine-grained ACLs beyond `admin` and `member`.
6. Outbound webhook integrations to third-party issue trackers (e.g. Linear, Jira) or chat systems (e.g. Slack, Discord).

## 13. Open Defaults

The following defaults are defined by this specification for operational parameters not fixed by the proposal note.

| Parameter | Value | Rationale |
| --- | --- | --- |
| Lease duration | 60,000 ms (60 seconds) | Provides sufficient buffer for network latency and edge Worker cold starts during execution, while bounding recovery time if an agent host terminates abnormally. |
| Heartbeat interval | 15,000 ms (15 seconds) | Balances real-time liveness detection against Cloudflare Worker D1 and invocation cost. |
| Host offline detection threshold | 45,000 ms (45 seconds) | Corresponds to exactly 3 missed heartbeat intervals, preventing false positives caused by transient network jitter. |
| Lease renewal cadence | 20,000 ms (20 seconds) | Guarantees that at least two lease renewal attempts occur before a 60,000 ms lease expires. |
| Session access token TTL | 7200 s (2 hours) | Industry-standard duration for mobile and web session tokens, limiting the exposure window of compromised bearer tokens. Returned as `expires_in: 7200` (in seconds) per OAuth convention; clients must calculate expiry in seconds. |
| Session refresh token TTL | 2,592,000,000 ms (30 days) | Provides seamless mobile login persistence without requiring daily re-authentication on iOS. |
| Host Token TTL | Indefinite until revoked | Execution Hosts run as background daemon services and must not fail intermittently due to calendar-based credential expiration. |
| Question expiration TTL | 86,400,000 ms (24 hours) | Gives team members a full business day to answer agent queries before the question automatically expires. |
| Durable Object event replay buffer | 1,000 events or 3,600,000 ms (1 hour) | Accommodates typical mobile tunnel reconnection gaps while preventing unbounded memory consumption in Durable Objects. |
| APNs JWT signing token cache TTL | 3,000,000 ms (50 minutes) | Apple permits JWT tokens up to 60 minutes; a 50-minute cache maximizes reuse while eliminating expiration edge cases. |
| Execution summary character limit | 4,000 characters | Directly mirrors DSH task board `EXECUTION_SUMMARY_LIMIT` (`packages/dsh-task-board/src/core/tasks.ts`), preventing ledger truncation drift. |
| Issue description byte limit | 65,536 bytes (64 KiB) | Directly mirrors the DSH task board opaque `integrations` payload cap (64 KiB) defined in the extension contract. |
| Comment text byte limit | 32,768 bytes (32 KiB) | Permits detailed markdown explanations, logs, and code snippets while guarding against database bloat. |
| Member API rate limit | 120 requests per minute | Accommodates rapid navigation in Web and iOS clients without triggering false rate limit rejections. |
| Host API rate limit | 120 requests per minute | Accommodates heartbeats, lease renewals, coalesced sweeps, and question/settlement traffic while bounding abuse. Host coalesces event-triggered sweeps to at most once per 5 seconds. |
| Auth route rate limit | 20 requests per minute per IP | Protects edge Worker authentication endpoints against brute-force attacks and abuse. |
| Default reviewer for Agent issues | creator_member_id | When an issue is assigned to an Agent (`assignee_type='agent'`) and no explicit `reviewer_member_id` is provided, the issue creator automatically defaults to the reviewer. This guarantees that every agent-executed card has a designated human reviewer for questions, push notifications, and the `in_review` approval gate. |
